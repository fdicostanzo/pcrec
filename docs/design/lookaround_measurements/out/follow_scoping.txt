F3 -- CAN A LOOKBEHIND BODY EVEN HAVE A PRUNE SITE? (measured, and the
==============================================================================
     answer refuted this lane's first simplification)

The tempting derivation: §2.5 ships only FIXED-width lookbehind
branches, a fixed-width body has no quantifier to prune, so the hazard
cannot arise behind. **THAT IS FALSE**, and one row below is why: an
EXACT COUNT `a{3}` is fixed-width by §2.5's rule AND is lowered as an
`A_REP` that takes a cursor rung with an MRL clamp. A design that had
shipped the derivation would have left the lookbehind unscoped on
exactly the bodies §2.5 admits.

A capture wrapper is needed to force the VM at all (a capture-free
pattern compiles to the DFA, which has no prune sites); it is stated
rather than hidden, because a sweep without it measures nothing.

body, wrapped + followed   engine       | prune sites
------------------------------------------------------------------------------
a{3}                       vm           | alone=['1'] followed=['3']   <- EXACT COUNT -- FIXED per §2.5, and it PRUNES
ab                         vm           | alone=[] followed=[]   <- a literal run -- fixed, no rung
(a)(b)                     vm           | alone=[] followed=[]   <- two captures -- fixed, no rung
a|bc                       vm           | alone=[] followed=[]   <- two fixed branches -- no rung
a{2,3}                     vm           | alone=['1'] followed=['3']   <- bounded variable -- REFUSED by §2.5
a+                         vm           | alone=['1'] followed=['3']   <- unbounded -- REFUSED by §2.5
a(?=b+c)                   dfa          | alone=[] followed=[]   <- FIXED width 1, but it CONTAINS a lookahead whose body is unbounded

READ THIS AS: a lookbehind body that §2.5 ADMITS can still carry a
prune site whose literal moves with the follow, so the lookbehind
needs its own ruling and cannot inherit the lookahead's by
derivation. R33 C1-1 said exactly this and it is now measured.

THE ARITHMETIC, per direction (ARGUED, with the cells that would break it):
  LOOKAHEAD:  the body's bytes and the follow's bytes are THE SAME
              BYTES (both start at the entry position p), so
              `cursor + bodyremaining + fmin` double-counts and the
              bound is UNSOUND. Under the NEGATIVE polarity an unsound
              prune makes the body fail, which makes the assertion
              SUCCEED -- a FALSE MATCH, not a missed one.
  LOOKBEHIND: the body ENDS at p, so a cursor inside it satisfies
              `cursor + bodyremaining == p` and the test becomes
              `p + fmin <= ceiling` -- EXACTLY the follow's real
              requirement, hence SOUND in both polarities.
  BUT the last row of the table above is the reason the RULE is still
  uniform: a lookbehind body may CONTAIN a lookahead, and that inner
  lookahead's scoping requirement is unconditional. Scoping at
  `vm_look` for every direction and polarity is one rule at one site;
  the cost is the lookbehind's lost (sound) prune, and the table above
  prices it -- `a{3}` behind a 3-byte follow keeps bound 1 instead of 3.

F5 -- `\K`'s REFUSAL SCOPE (R33 C1-7): the NEGATIVE controls
==============================================================================
§2.7 says the hook rejects an A_KRESET 'while parsing a lookaround
body'. That sentence has two readings and only one matches PCRE2. The
REFUSED set must be recursive through nested groups AND nested
lookarounds; the COMPILING set is what a too-broad check would break.

REFUSED (err 199 expected):
    (?=(a\K))x           -> err 199
    (?=a(?:\K))x         -> err 199
    (?=(?:(?=\K)))x      -> err 199
    (?*a\K)x             -> err 199
    (?<*\Ka)x            -> err 199
    (*pla:a\K)x          -> err 199
    (*nlb:\Ka)x          -> err 199
    (?<=\Ka)x            -> err 199
    (?=a\K)x             -> err 199
    (?!a\K)x             -> err 199
    (?<!\Ka)x            -> err 199
COMPILES (a too-broad check would break these):
    (?=a)\Kb             -> ok
    a(?=b)\Kc            -> ok
    (?<=a)\Kb            -> ok
    a\Kb                 -> ok
