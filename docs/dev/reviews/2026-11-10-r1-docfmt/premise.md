### PREMISE-5 — G4 (top priority) has no check in any unit; the unit order lands both big transforms before anything verifies a cite resolves
CONFIRMED (by reading the unit table). Severity: design (goal-order). Effort: small (a tree-wide cite resolver as a doc_lint rule, built in T2, run before and after unit 1). Blast: G4, §2.4 C7/C8, §5 units T2/1/2/3.
The rules that touch cites: C7 resolves only ids cited IN AN INDEX LINE; C8 bans `file.md:line` cites. Nothing resolves the tree's cites into the details: measured in the build tree, 4,814 `Dn` tokens in src/tests/scripts/lib/cli (36,416 tree-wide), 2,714 `Dn add./addendum k` cites (127 distinct Dn/k pairs), 216 unnumbered "Dn addendum" cites, 54 ordinal ("D45 third addendum", "D47 SECOND ADDENDUM"), 1,090 dotted `Dn.k` ruling cites, 25,990 `Kn` tokens. G4's measurable form ("every ... cite resolves after migration") therefore has no instrument, while G2 (lower priority) gets an acceptance test (D47) and G3 (lowest) gets the first two units. The renumbering rule (unnumbered addenda take the lowest free number) is exactly where `Dn add. k` cites can silently re-point (see PREMISE-6), so the G4 check is needed by unit 1, not after.
Also on order vs G5 > G1: unit 1 lands the decisions index with PROVISIONAL statements = the old titles (state `?`), which the doc itself says "state the first ruling, not the current one"; until 1.S8 finishes (8 batches, 2-3 at a time, across the freeze) the index the manager "acts on" (§6) says other than its details, i.e. G5 is knowingly broken to deliver G1/G2 sooner, and §6's manager rule says nothing about `?` lines. Either the order needs a stated exception or `?` lines must be "do not act; read `entry`".
