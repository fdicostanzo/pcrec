### COST-2 (size/design, CONFIRMED) — a one-third-cost partial already exists: the heading grep

The incremental buy of 1.S1-S8 (8 OPUS writer + 8 OPUS critic batches, ~16 opus lanes, 24 entries x ~4 KB read twice each) is the CURRENT-ruling sentence (+~8 KB) over titles the doc itself says "state the first ruling, not the current one". Statements are the only unit whose value cannot be had mechanically; they are 16 of the ~28 lane-units. Costlier must prove more: nothing in the doc shows titles-only fails for recall (no trial).

### COST-4 (maintenance/overlap, CONFIRMED) — landing collision load, measured
git log --since=2026-10-27 6638e3679 -- FILE (commit counts): plan.md 178 (12.7/day), decisions.md 41 (2.9/day), known_issues.md 19, plan_completed.md 7; 202 distinct commits touch decisions.md or plan.md, of 1740 total in the window (11.6%). The doc's "re-run converter on HEAD" mitigation (§5/§6) holds for the transform, but unit 2 (plan) rewrites the file every lane edits at nearly 13 commits/day, and every open lane branch carrying a plan.md hunk (status lines, STATE flips) then conflicts structurally, not textually: the hunk's target moves to plan_details.md and `now`. §5 says "mixed-file input means in-flight branches need only a re-run" - true for NEW old-form rows, not for edits to an existing row on a branch. Cost unstated: a quiet point for plan must be arranged (all lanes merged), unlike decisions. Also all lane briefs/skills that say "update plan.md STATE" change meaning (the manager skill's grep STATE:started keeps working only because index keeps STATE: tokens - good). Recommend: unit 2 gated on a measured need and a declared quiet point; decisions first has the lowest collision.

### COST-6 (size, SUSPECTED) — always-on load is priced low and the cap is soft with a 1-2 month runway
Doc §3: two indexes add ~80 KB to a ~85 KB always-on manager load (almost doubles it), and its own growth figure (+8 KB/month for decisions) reaches the soft cap in 1-2 months, after which the gestalt line fires every heartbeat; so the steady state is 'permanently over cap' unless supersessions shrink. The doc measures tokens by 4 B/token estimate only. Nothing says WHICH sessions load both indexes: lanes do not (good); the manager does, and its reset rule is 35% context. Confirm: measure real token count of the two index files against the manager's context at wake. If the plan index (40 KB, 339 rows of which 296 not-started and the doc moves their triggers OUT) is mostly not-started rows that the manager never reads at wake (it greps STATE:started), the plan index may be held out of always-on and loaded via `entry --work -k` only; that halves the cost with no format change.

### COST-7 (family, CONFIRMED) — sibling family: MEMORY.md index + per-fact files; also scripts/NOTES.md and plan_row_bodies
The nearest sibling is MEMORY.md (index line -> per-fact file) which the doc itself names 'the model'; second, docs/design/plan_row_bodies/ (22 files, PL15 pointer) which the doc ABSORBS rather than reuses; third, docs/dev/history/ + plan_completed.md (archive tier: row leaves the live file verbatim). Differences that justify a new member: (1) MEMORY.md/plan_row_bodies are one-file-per-entry, here one details file (the doc argues this, §2); (2) entries carry addenda; (3) a linter with a bijection check. Not a sibling: wake.md/owner.md (rewritten whole), gestalt (a consumer here), CLAUDE.md/NOTES.md split (same instinct: orientation vs history, 12 KB cap) - the CLAUDE.md/NOTES.md split is also the closest precedent for the soft-cap + 'move the rest to NOTES' discipline. The doc should state the family: 'index tier + details tier with an archive tier', of which MEMORY.md, CLAUDE.md/NOTES.md, plan.md/plan_completed.md and plan_row_bodies are four already-existing, differently-spelled instances (four spellings is the forest-for-the-trees trigger, ~3 members per memory pcrec-forest-for-trees). Unification is therefore a legitimate benefit only if the new profile table is also the home for plan_row_bodies and plan_completed (the doc does fold the former, only partially the latter, and not MEMORY.md or CLAUDE.md caps, which have their own checkers check_claudemd_size.sh / memory conventions): say so, or name why they stay out.

### COST-8 (design, general form + unlocks with triggers)
GENERAL FORM: a declared 'tiered-document' profile table (file, id grammar, states, tier boundaries, per-tier caps, level-1 fields) read by ONE accessor and ONE linter, where a tier is index | details | archive. Today's four instances (MEMORY.md/memory files, CLAUDE.md/NOTES.md with check_claudemd_size.sh, plan.md/plan_completed.md/plan_row_bodies, and this) become rows. The doc builds ~this already for decisions/plan/known/upstream; the general form simply adds rows rather than a sixth parser.
UNLOCKS, each with a trigger (do not build ahead, D77): (1) CLAUDE.md/NOTES.md cap check folded in - trigger: a third size-checker script appears or check_claudemd_size.sh needs a second rule; (2) MEMORY.md (23.5 KB, loaded by every lane) over-cap warning via the same --over-cap - trigger: MEMORY.md passes its own cap or a lane brief reports it truncated; (3) kit ledgers via a 'kit' row - trigger: the kit answers K feedback with adoption; (4) cross-file `--work` ('what is open anywhere': plan not-started + K OPEN + U OPEN + R open) - trigger: the manager's wake read needs more than two entry --work calls; (5) a wake-time 'ruling touched since' view (state change by date) - trigger: a session acts on a superseded ruling (measure first; cf. COST-1). Not unlocked: anything for dev_journal/ideas (append-only), correctly excluded.

### COST-9 (cost, SUSPECTED) — unit 3/4 and K are cheap only if the profile is truly data
Unit 3: 139 K entries -> 6 opus batches x2 (writer+critic) = 12 more opus lanes for known_issues; unit 4: 25 U -> ~2. Per-K value is the 'symptom in one line to prevent re-filing' claim (§4) - unmeasured (count of duplicate K filings). known_issues is cited by K-number from ~70 tests, never parsed; 71 of 139 are FIXED, so the live recall population is 42 OPEN + 3 ACCEPTED; indexing only OPEN ones (leaving FIXED as ≤80-char lines, the doc's rule for retired entries) cuts statements from 139 to ~45 -> ~2 batches. The doc applies 'superseded shrink to 80 chars' to decisions but not to FIXED/CLOSED known issues; it should (cost -60% of unit 3's opus work, no loss of recall for open work).
