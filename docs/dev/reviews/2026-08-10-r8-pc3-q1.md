# R8 — PC-3 and Q1: the first external check, and how much of "external" survived contact

Checkpoint review (D6) of the second step in docs/plan.md's AGREED ORDER, over
the working tree at `effdad5` + the PC-3/Q1 change. Four critics, four lenses,
each working in its own copy of the tree and required to append findings to a
scratchpad file as it confirmed them.

Baseline before the work, green in place: 876 corpus / 73 CLI / 261 reject /
127 registry + 2 SR-4 doc checks / 29 codegen / 7 trie-identity, verify_rxt
844/844, fuzz seed 1 zero divergences, bench zero budget failures.

**The one-line summary: the instrument shipped with the exact defect it was
built to detect — a control sharing a source with the thing it controls — three
separate times, and the panel measured all three.**

---

## What was built

**Q1 — the `(*` doorway reads the NAME.** Two `VerbName` tables in
`src/parse/registry.c` (31 upper + 19 lower), chosen by the CASE of the first
name byte exactly as libpcre2 chooses between its own two, with per-name form
bits recording which spellings libpcre2 accepts. Four possible answers replace
one. Decision recorded as D25.

**PC-3 — `tests/registry/pcre2_check.c`.** Every registry row against libpcre2:
an `RS_MODULE` row's construct must COMPILE there, an `RS_REJECTED` row's must
be rejected with a matching error identity, and — the part that scales — a
differential over ~75,000 generated verb names in 13 forms, about 824,000
probes in 2.3 seconds. Candidate names are generated from libpcre2's own shared
object rather than from pcrec's table. Skips loudly, and exits 0, without
libpcre2 installed.

**Shared ABI header** `tests/fuzz/pcre2_abi.h`, extracted from
`pcre2_oracle.c` rather than copied into a second consumer.

PC-3 found one thing before any critic ran: the verb row's probe was `(*...)`,
which libpcre2 rejects — the row named a construct PCRE2 does not have, and no
check reading only pcrec's files could ever have seen it.

---

## The panel's findings, and what they cost

### The three the instrument deserved (C1)

**C1-F4 — the "external" pool could contribute nothing, and everything still
passed.** `pool_from_library()` returning success with zero names left 84% of
the probes running (they come from mutations seeded by pcrec's OWN table), all
four liveness assertions green, the "every verb name was reached" guard green —
and **deleting the real `(*SKIP)` row became completely invisible.** The
liveness checks asserted the pool was non-empty. The property that matters is
that it is EXTERNAL, and only provenance can assert that.
*Fixed:* every name is tagged with the source that first produced it, every
name pcrec claims must be produced by libpcre2's binary INDEPENDENTLY, and the
library's contribution has a floor. The critic's own sabotage now yields 51
failures.

**C1-F3 — the fabrication check was defeated by a comment.** A wrapper must
contain the row's `syntax`; `(?#\3)` contains it and compiles, so a fabricated
row could be rescued by one line — and the failure message tells the reader to
write a wrapper.
*Fixed:* the syntax must be LOAD-BEARING where it sits. Substitute it out for
`\Y` (always error 103) and the wrapper must stop compiling.

**C1-F5 — `check_rows` never ran pcrec.** It asked libpcre2 whether a construct
exists and never asked pcrec what it does with it, so a row that had started
MISCOMPILING passed. *Fixed:* both halves, both directions. Validated with a
real `\K` miscompile in `esc_char_value` — 1 failure.

**C1-F2 — `required_answer()` made this file the authority on a question
libpcre2 was never asked.** It required the literal string
`"(*...) requires module 'verbs'"` for every accepted name, certifying
`(*atomic:a)`, `(*script_run:a)` and `(*UTF)` as module `verbs` when in PCRE2's
taxonomy they are atomic groups, script runs and option settings. And it
ratcheted the wrong way: the day SR-6 routes them correctly, the conformance
test FAILS and someone loosens it to accept a more correct compiler.
*Fixed:* two strengths of obligation. Where libpcre2 supplies an identity
(errors 160/195/166/109/148) pcrec must reproduce it exactly; where libpcre2
supplies only a verdict, the requirement is the diagnostic's SHAPE — a rejection
naming some module. All 20 sabotages still caught after the relaxation.

**C1-F1 — the default bucket's comment named 114/115/204 and missed its
dominant member.** 231 of 326 probes are error 122. *Fixed:* the file no longer
states the contents, it prints them, per code, with libpcre2's own message.

### The two real pcrec bugs (C2)

**C2-3 — `VF_EQNUM` had no MAGNITUDE rule.** The differential wrote exactly two
`=` bodies, `=1` and `=x`, so the `=` axis was one digit wide.
`(*LIMIT_MATCH=4294967290)` is libpcre2 error 160 and pcrec said "requires
module 'verbs'". The boundary is 4294967290, not 4294967296, because PCRE2
refuses *while accumulating*, one digit early; and it is a magnitude rule, not a
length one — `=00000000000000000001` compiles.
*Fixed in `ext.c`, reproducing both properties.* And then the sabotage battery
said **0 failures** for reverting it: the fix was in and nothing generated a
probe that could see it. Two forms added; now 4.

**C2-4 — a verb NAME over 128 bytes is a different complaint.** libpcre2 gives
error 148 "subpattern name is too long", from both tables, in every form, and
the pool's 64-byte cap sat below it. The cap's comment — "64 is above every name
PCRE2 has (the longest is 30 bytes)" — was true and the inference was wrong: the
longest real name bounds where a MATCH occurs, not where the REJECTION changes
shape. *Fixed:* pcrec implements the limit, the cap is 256, and a fourth
candidate source generates the boundary lengths on purpose, because nothing
inside libpcre2 is a 129-byte run of one letter.

**C2-1 / C2-2 — measured, and NOT defects.** `(*FAIL)*` is libpcre2 error 109
while pcrec says "requires module 'verbs'"; `(*UTF)a(*UTF)` is error 160 about
the second option while pcrec answers about the first. Both are pcrec reporting
the LEFTMOST construct it cannot handle and stopping, which is its rule at every
doorway and always has been: `\d{3,1}` is "requires module 'classes'" here and
"numbers out of order" in PCRE2, and nobody has ever called that a bug. The
finding that survives is about the CHECK, not the compiler: `required_answer` is
only valid for patterns whose only error is at the verb doorway. That
precondition is now written down beside `FORMS`, and both shapes are pinned in
`tests/reject/` so that changing the rule has to be deliberate.

### The silent narrowing (found during the work, before the panel)

The generic 255-byte doorway sweep asks "did the parser say *requires module*".
Before Q1 all 255 bytes after `(*` said exactly that. Q1 made most of them say
"not recognized" — correctly — and the sweep went from **255 bytes asserted to
ONE** while still printing `PASS: sweep ... all 255 bytes agree`. Replaced by
`sweep_verb()`, which asserts every byte reaches the doorway, that its answer is
one the registry can account for, and that the two name tables are selected by
case — with liveness counters, because one-answer-for-everything is exactly what
the old sweep had been reduced to.

### What the claim actually covers (C4)

**C4-1 — 65 of the 67 rows are verified by ONE BIT.** The `RS_MODULE` arm is
`if (rc == 0) ok()`. `RegRow` has 12 fields; PC-3 reads five, and `msg` only on
the two `RS_REJECTED` rows. **Seven columns — `feature`, `module`, `flavours`,
`engines`, `diag`, `flags`, `note` — are read by no external check at all.**
`module` is admittedly pcrec's taxonomy; `note` is a factual claim about PCRE2
and is not.

**C4-2 — `\v`, the row this entire registry exists for, is not verified.** Its
probe is `\v`, and libpcre2 compiles `\v` under either semantics. The critic
rewrote the row's note to the pre-PC-1 WRONG semantics and PC-3 stayed at 74/0.
Only a MATCH differential could distinguish them, and PC-3 calls none of the
match API it links. **This is a compile-verdict differential and nothing more.**
Not fixed, and the reason is worth stating rather than apologising for: pcrec
has no semantics for any registry row today — every one is rejected — so there
is nothing on pcrec's side to differ. It becomes buildable and necessary the day
module `classes` lands, and it is now a plan step (PC-4).

**C4-4 — the wrapper probes do not verify the row's INDEX.** Replacing all 18
digit-family wrappers with the same nine-group prefix changed nothing: 74/0.
`(a)(a)(a)\3` proves `\3` needs at least three groups, never that it is three.
Nine near-identical wrappers assert one fact. Recorded, not fixed.

**C4-8 — a LIVE WRONG-MODULE BUG, and it is the `\v` shape exactly.** `(?*...)`
is PCRE2's NON-ATOMIC POSITIVE LOOKAHEAD — the `(?` spelling of `(*napla:...)`
— and pcrec had no row for it, so the `(?` catch-all answered "requires module
'modifiers'". The module name is the one fact that diagnostic exists to carry.
Proven behaviourally rather than by reading a name, on subject "abab":
`(?*(a|ab))\1$` matches [2,4), `(?=(a|ab))\1$` does not, and
`(*napla:(a|ab))\1$` matches [2,4). **Three homes and one disagreeing**: Q1's
own verb table already knew `napla`, and docs/pcre2_compliance.md has named
`(?*...)` as non-atomic lookaround since the 2026-08-09 survey. Only the
registry did not.
*Fixed:* a `GROUP('*', "(?*a)", lookaround, ...)` row, plus a hand-written
tests/reject/ row, because the iterated probe reads the module from the row the
parser renders from and structurally cannot see a wrong name.

I then swept the whole doorway rather than fixing the one instance: of the 21
byte-values libpcre2 accepts after `(?`, `*` was the ONLY one pcrec routed to
the wrong module. `(?<*...)` — the lookbehind of the same family — needs no row,
because it enters through `<`, which already names lookaround.

**C4-9 — PC-3's own spec text promised something not built.** docs/plan.md's
PC-3 entry ends "this is the natural home for the finding that pcrec accepts
`[:alpha:]` (K3) — found by hand, and findable mechanically". It was not built:
there is no class-bracket differential, and `[:alpha:]` still emits C.
*Disposition: sequencing, not omission, and it was already written down.*
docs/wake.md §6 says the class-bracket sweep "is right but will FAIL until K3 is
fixed — so add it WITH FIX-2". Adding a differential today that goes red on a
known, pinned, deferred bug would be a ratchet, and this project has a ratchet
already (tests/known_fail/). The plan entry for FIX-2 now carries it as an
acceptance criterion rather than leaving it in PC-3's prose.

**C4-10 — the exact-count tripwires instruct you how to disarm them.** A critic
added `GROUP('^', "(?^)", assertions, ...)` — a real PCRE2 construct with a
WRONG module — and three exact-count guards fired, each printing its own remedy.
Following all three verbatim (67→68, 66→67, `--write`) produced a green
`make test` with zero FAIL lines and a PASSING PC-3. This is the residual SR-4
explicitly deferred to PC-3, and **PC-3 does not close it**: libpcre2 can say a
construct exists, and cannot say pcrec should call its module `lookaround`
rather than `assertions`. Noted, with the mechanism written into
tests/registry/CLAUDE.md beside the count itself: these guards make a change
visible in the diff, they do not make a wrong one fail.

*(I hit all three of those tripwires myself adding the C4-8 row, which is the
honest illustration: the legitimate path and the attack are the same path.)*

**C4-7, and it is the headline.** T-12 promised the wall comes down "for the two
NAME-keyed doorways". **One was built.** Measured:

| doorway | registry rows | PC-3 probes | over-promises |
|---|---|---|---|
| `(*` verbs | 1 | ~824,000 | **0** (this change) |
| `(?` | 24 | 21 | **217 of 255 bytes** |
| `[` in a class | 3 | 3 | **12517 of 12531 names** |
| `\` | 39 | 39 | 0 — the control |

217 byte-values after `(?` are told a pcrec module will implement a construct
libpcre2 says does not exist (error 111), and pcrec answers "requires module
'classes'" for all 12531 candidate POSIX class names where libpcre2 recognises
14. That is *character for character* the `(*NOTAVERB)` over-promise D25 was
built to end, at doorways 217x and 900x wider than the one that got fixed. The
escape doorway is clean, which proves the asymmetry is not inherent — it is
specific to the two catch-all rows.

**C3-F1 — the hand-written safety net is smaller than its comment claimed.**
With PC-3 skipped, deleting `F`, `NO_JIT` or `scs` fails `tests/reject/`;
deleting `LIMIT_HEAP` or `naplb` failed **nothing**. *Fixed by narrowing the
claim and pinning one name per FORM GROUP*, with the honest statement that the
other 26 names are covered by PC-3 alone.

**C3 CLEARED.** The oracle refactor onto `pcre2_abi.h` is behaviourally
identical over 4010 invocations (rc and stdout, zero divergences); `fuzz.py`
still uses the oracle and reports zero divergences; nothing outside the `(*`
doorway changed behaviour.

## Sabotage battery

20 edits to `src/parse/{ext,registry,parse}.c` and
`tests/registry/pcre2_check.c`, each reverted after measuring, each caught. The
exact edits and failure counts are in `tests/registry/CLAUDE.md`. Two are worth
naming here: reverting the doorway to its pre-Q1 behaviour is 21 failures, and
neutering the external pool is 51 — neither was detectable by anything in this
repo before this change.

**And the battery lied once, in the way this project keeps re-learning.** The
first `\K`-miscompile sabotage reported 0 failures and would have read as "the
guard is missing": it inserted `return;` into a function declared `noreturn`, so
the sabotage never happened. The rule that caught it is the one already written
down — *prove your instrument is live before trusting a negative result* —
applied one level further down, to the sabotage itself.

## Reflection

Three of this file's four headline claims did not survive measurement, and all
three failed the same way: **a control that shares a source with the thing it
controls.** The wrapper was authored by the same person as the row. The mutation
pool was seeded from the table it audits. The required answer was pcrec's own
catch-all. `tests/registry/CLAUDE.md` has written that hazard down since R4, the
new file's header is unusually candid about it in the abstract, and it
reproduced the hazard three times in the concrete on the first attempt.

The generalisable habit is narrower than "watch for circularity", because that
is too abstract to act on. It is: **for every input your check consumes, name
the file it came from, and if that file is one you also wrote, say so in the
output.** Provenance printed at runtime is what turned C1-F4 from an argument
into a failing assertion — and the fix is three lines and one array.

The second habit: **a fix without a probe that exercises it is unguarded.** The
magnitude rule was correct, committed, and worth nothing until two forms were
added; the battery is the only reason anyone knows. Adding the guard is not the
last step of a fix, it is the step that tells you whether you made one.

And the third, which C4 earned: **fixing the narrowest instance of a defect and
describing it as the class is the most expensive mistake available here.** Q1
closed the over-promise at the doorway with one row and left it at the doorways
with 24 rows and 3 rows, which are 217x and 900x wider, while the commit message
would happily have said "the over-promise is closed".
