# SEAM2 findings

## Findings

### SEAM2-1 CONFIRMED (design; text) -- target identity gets a second home beside measure_store's `class`; `ms` per target has no named mechanism
§2 row `ms`: "the measurement set for THIS target (D188 per variant)"; §5: "pcrec owns the target table (tag, family, features, attribute string, probe string)". Nothing names how a target row reaches ITS set.
The tree already has a target-identity key: measure_store/index.tsv `class` column ("x86_64-avx2/zen4"; docs/spec/measures.md [5¶6], measure_store/CLAUDE.md:57 "the ISA level and tuning class it was measured for"), DEFAULTS maps class -> set (`idk` = "a compile that declares no class"), and [MEASURE-SET]'s FORMAL LIBRARY (b) (plan.md row [MEASURE-SET] @5b43f8e9a) plans "closest-match selection ... as DECLARED FALLBACK ROWS (microarch -> ISA level -> arch family -> generic)". So "family", "ISA level" (= features) and "generic" are ALREADY the key of a planned pcrec table, spelled differently (`x86_64-avx2` vs §2's `x86-64` + token list), and M2 (same row) turns `idk` into "an ISA envelope".
Disagreement possible: a compile with target list {v3} and `--measures=zen4-grid1` (class x86_64-avx2/zen4) is fine; with an aarch64 target and the same --measures nothing refuses. With list {generic, v3} and no --measures, which set does each art get (idk default for both? the generic envelope for generic?) is unstated.
Fix: the target table row carries (or IS) the measure class; DEFAULTS/fallback rows key on the target tag; a set whose class's family/features disagree with the art's target is refused (or declared fallback). This also gives `tag` its reader (SEAM2-3). Severity design; effort small at design time; blast radius: D188 per-variant pricing, [MEASURE-SET] M2 + fallback rows.

### SEAM2-2 CONFIRMED (design; sibling of a family) -- the variant is ALREADY ruled a compound part chosen by the compound controller; the note builds a parallel "pcrec dispatcher"
plan.md@5b43f8e9a row [MEMFN-RTDISPATCH]: "SHAPE RULED (D155 add. 5): each ISA level a target-attributed part chosen by the compound controller; one-shot search checks per call, the iterator keeps the choice in its state". The note §0 quotes D155 add. 5 only for "never an artifact static", and §3/§5/§10 name the selector as "pcrec's dispatchers" (`rx_search` becomes a dispatcher over `rx_v3_search`), never the compound controller (docs/design/compound_entries.md, D163). A variant here is a WHOLE matcher with its own entries, which is exactly a compound part (an independently callable matcher with its own entry, picked per call by a controller whose state lives in the caller's iterator, D165).
Consequence: two choice mechanisms over "which complete matcher runs this call" (compound parts by subject/shape facts; variants by CPU facts), with two stamp spellings and two test shapes (§7 invents per-variant `.rxt` runs + one dispatcher cell). Fix: state a variant as one more compound part, the CPU probe as one more controller predicate (a controller row column `needs` = features), and the per-variant entries as the parts' entries; then §7's "dispatcher cell" is the controller's existing test. If the note's position is that variants are NOT compound parts (e.g. because compound parts share one target), it must say so and amend D155 add. 5's ruled shape. Severity design; effort a § rewrite; blast radius D155/D163/D165, [MEMFN-RTDISPATCH].

### SEAM2-3 CONFIRMED (answer: SIGILL class; design) -- features, attribute string and probe string are three homes for one fact; the note names no deriver and no check, and the probe must cover the ATTRIBUTE, not the features
§5: "pcrec owns the target table (tag, family, features, attribute string, probe string)". §2: features = "the instruction-set facts the target guarantees". Nothing says which column is primary or who checks they agree.
Repro (scratch seam2/p1.c, gcc 15.2 -O2): pcrec-side SCALAR code (a shift, a ctz) inside `#pragma GCC target("arch=x86-64-v3")` compiles to `shlx` (BMI2) and `tzcnt` (BMI1) -- instructions no kit level `needs`. Since a variant is the WHOLE matcher (§3), the variant's code requires everything the ATTRIBUTE enables, not what `features` lists. A row whose probe is derived from features (e.g. `__builtin_cpu_supports("avx2")` for features `...,avx2`) admits a CPU/VM that masks BMI2 and the variant SIGILLs. Conversely features > attribute (features lists avx2, attribute arch=x86-64-v2) is caught only as a gcc "target specific option mismatch" compile error, after the kit planned for it.
Also the macro sets differ per -march (gcc -dM -E: SSE2/SSSE3/SSE4_2/AVX2/BMI2/POPCNT count 1 / 4 / 6 at x86-64 / v2 / v3), so features is checkable against `gcc -march=<attr> -dM -E`.
Fix: ONE primary column (the attribute / ISA level name), features and probe DERIVED from it by a declared rule (x86: the psABI level lists; probe = `__builtin_cpu_supports("<level>")` or the conjunction of every feature the attribute enables), plus a table check: for each row, the attribute's predefined macros ⊇ features and the probe ⊇ the attribute. Severity answer (wrong-CPU crash, no wrong match); effort small; blast radius every non-generic variant.

### SEAM2-4 CONFIRMED (speed + design) -- `-fmemfn-simd`, `-fno-memfn-simd`, the target list and MF_P_PORTABLE_ONLY are four homes for "may the kit use SIMD"; the note maps only one of them, and the default list silently drops today's live SSE2 rung
§2: "`-fno-memfn-simd` stays as pcrec's deny and maps to the generic target"; §5/§6: default list = `generic` alone, features empty, "no level is admitted". Unstated: what `-fmemfn-simd` means with the default list (inert? the build target per [XARCH-DEV] RULED "Build time: pcrec emits the build target's variant"?), and what `-fno-memfn-simd` does with an explicit list `{generic,x86-64-v3}` (refuse? drop v3? keep v3 but portable-only inside it, which is a variant with an attribute and no SIMD kit text?).
Repro (build tree build/pcrec, `-fmemfn-simd -p rx --pattern '(?i)cat'`, gcc -O2 default -march): the w16 arm (`#if ... defined(__SSE2__)`, b.c:89/167) is LIVE (14 xmm instructions in objdump; x86-64 psABI guarantees SSE2, gcc defines __SSE2__ by default). Under the note's default `{generic}` that rung is no longer admitted, so every default `-fmemfn-simd` artifact on x86-64 loses its SSE2 path. §6 says these artifacts "DO move: their #if arms go away" but not that they get SLOWER; and `generic` (any family, portable C) is conflated with the x86-64 baseline target (family x86-64, features sse2, no attribute needed), which is a different row.
Also the bit is not "one fact replaced": MF_P_PORTABLE_ONLY is a K96 row-contract class (fields.def:137 MF_CLASS(PORTABLE), gate.c:438-451, vrun.c:498 `[FLD_policy] = CM(NONE)|CM(SIZE)` "never PORTABLE"), so retiring it re-derives every row's FLD_policy contract and the PORTABLE decline class from features.
Fix: one first-match table from (flag, list) to the per-art feature set, e.g. no list + -fno-memfn-simd -> {generic}; no list + -fmemfn-simd -> {build target}; list + -fno-memfn-simd -> refuse or {generic}; and add an `x86-64` (v1) row distinct from `generic`. Severity speed (SIMD-on default) + design; effort small; blast radius the axis, axes_dump.c:858-870 wording, the PORTABLE class.

### SEAM2-5 CONFIRMED (design; answer-risk on a mixed token) -- `target.family` has no reader in the stated admission rule, and levels.def's `family` column has no reader today; feature tokens are not family-unique
§2: "a level is admitted iff `needs` is a subset of `target.features`". `target.family` (§2 row 2) is sent but this rule never reads it. levels.def:12/41/44 carries `family` ("x86-64"), but its only reader is levels.c:14-15's struct copy (grep of memfn/ src/ tests/ for `->family` on a level: 0 hits; simd_floor_check.py reads column [1], the guard). Feature-token names collide across families (x86 `aes`, `sha`, `crc32`/sse4.2; aarch64 `aes`, `sha2`, `crc`), so a subset test over tokens alone can admit an x86 level for an aarch64 target as soon as both spell a token the same way.
Fix: the admission rule is `level.family == target.family && needs ⊆ features` (the two family columns become one fact read in one place), or tokens are family-qualified (`x86-64:avx2`) and `target.family` is dropped as derivable. Either way one of the two family slots goes. Severity design (latent answer risk: wrong-ISA text is a compile error under the attribute, so this surfaces as a refused build, not a wrong match); effort trivial; blast radius levels.def, §2.

### SEAM2-6 CONFIRMED (doc/design) -- `tag` vs `vtag`: the stem source is not a column of the named table, and the tag crossing to the kit duplicates `prefix`
§3: "A non-default variant's stem is `<prefix>_<vtag>` (e.g. `rx_v3`), where `vtag` comes from pcrec's target table"; §5 lists that table's columns as "(tag, family, features, attribute string, probe string)" -- no `vtag`. Either vtag IS tag (then say so; the stamp `<PREFIX>_TARGETS "generic"` (§6) and §4's `RX_V3_MEMFN_FORMS` also read it, so tag is NOT "for traces and refusals only" as §2 says -- it reaches emitted names and an abi-stamped line), or vtag is a sixth column. On the kit side, `target.tag` is redundant: the art's `prefix` already carries `rx_v3`, and the kit's only stated use (traces/refusals) can print the prefix. A slot the kit must not branch on (D157) is cheapest absent.
Fix: name tag the stem token and the stamp's list token in §5 (its readers: stem, TARGETS stamp, per-variant stamp line names, rx_info at Q2, measure class at SEAM2-1); drop `target.tag` from the pcrec->kit row (prefix serves traces). Also the default variant's tag `generic` yields stem `rx` (special-cased) while non-default yields `rx_<tag>`: state the rule as "the FIRST list member keeps the bare stem", or the default list `{x86-64-v3}` has no bare-stem variant. Severity doc; effort trivial.

### SEAM2-7 CONFIRMED (answer: link error, G3; doc) -- "the default variant keeps the stem `rx`" collides with "the public entries become pcrec's dispatchers" in any multi-variant list that contains the default target
§3:94-99: "The default variant keeps today's stem (`rx`) ... With several variants, the public entries (`rx_search`, ...) become pcrec's dispatchers, and each variant keeps its own entry (`rx_v3_search`)." With list {generic, x86-64-v3} (the ruled "generic + 1-2 SIMD" shape), the generic variant at stem `rx` defines `rx_search` and so does the dispatcher: a duplicate symbol, exactly what G3 measures against. The note's own sentence only holds for the single-member list.
Fix: the bare stem belongs to the dispatcher (or to the lone variant when the list has one member); in a multi-member list EVERY variant, generic included, gets `<prefix>_<tag>`. Consequence to state: the generic variant's internal names (`rx_w8`, `rx_mf<h>`) differ between the one-member and the multi-member artifact, so "the generic variant's bytes = today's" holds only for the one-member list (G2 is stated for that case, so G2 survives). Severity answer (build fails) at design; effort trivial; blast radius §3, §7 (harness calls `rx_<vtag>_search`: for generic that name must exist).

### SEAM2-8 CONFIRMED (design) -- the kit's in-flight form-hash entry table (span_cards' timing source, D188 pricing) keys forms by the POLICY WORD, a slot §2 retires; it has no target slot

Severity design; effort small; blast radius span_cards §3.2 entry table, D188 per-variant pricing.

### SEAM2-13 (GENERAL FORM + UNLOCKS) -- "a variant per target" is one instance of "an artifact = a controller over complete matchers, each planned for its own declared FACT VECTOR"
The general form: an artifact holds parts P_i, each a whole matcher planned and priced under a declared fact vector F_i (target features + measure set today); a controller picks a part per call (or per iterator) from run-time predicates over facts it can observe. The compound controller (D163, compound_entries.md rev 4) is already this with subject-shape facts; D155 add. 5 already says an ISA level is "one more part the controller selects among" (SEAM2-2). Variants add the CPU-feature predicate; nothing else is new. Unlocks, each with its trigger (D77):
- U1 shared parts across variants (dedupe identical const tables / identical variant text, §8's "byte-identical .text" count): trigger = §8's measurement shows >X% artifacts with identical variants or table bytes > text.
- U2 per-variant compound layout (a variant may itself be compound, or a part may exist only in some variants): trigger = a pattern whose compound split is priced differently on two targets.
- U3 measure-set fallback rows keyed by target tag ([MEASURE-SET] (b), SEAM2-1): trigger = the second committed set of another class (the M1-made set [XARCH-DEV] names first).
- U4 target rows for non-ISA run-time facts (e.g. "fast unaligned", "ERMS rep movsb", page size for over-read) as features with a probe: trigger = a kit form whose admission needs a fact the -march level does not imply.
- U5 other emitters (another language back end, D188/2026-11-04 addendum): a target row then also names the emitter; trigger = the first non-C back end.
- U6 build-target-only mode (no dispatcher, the ONE variant for the declared build target, [XARCH-DEV] "Build time: pcrec emits the build target's variant"): already the one-member list; trigger none, state it as the degenerate case.
