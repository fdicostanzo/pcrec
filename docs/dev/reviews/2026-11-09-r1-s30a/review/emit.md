# emit findings

## Findings

### EMIT-1 (SUSPECTED, latent; design/answer-shape; effort small; blast radius: every window site and every pre-check part once any ST-many exists)
The window family's ST-many ("?stream") refusal is raised BEFORE Table E walks: `wf_plan_site` (memfn/src/window.c, the `if (fx->brow && !strcmp(fx->brow, WF_STREAM_REFUSAL))` block right after the quiet `wf_find_decide`, ~:2195) returns -1 before `kit_walk(&wf_etable, ...)`. Table E's ORDER puts the legacy rows E-func/E-stmt FIRST ("every site the legacy translation serves keeps today's bytes", window.c THE ORDER comment) and their holds (`e_legacy_holds`) do not read `fx`; E-find (`e_find_holds` = fx->holds) is third, and E-find can also be denied (`window-search`). So the day a search gains two streams on E-find, a site whose Table E answer is E-func or E-stmt (legacy) -- or whose E-find is denied, so the floor would serve it -- is REFUSED instead of keeping its legacy/floor text; and `wf_parts_prepare` (which REQUIRES the legacy row for every pre-check part) fails every part whose stop decides that pick. plan_frame.md §2.4 [rev2.2 R3] asks for the refusal "in wf_find_decide ... and refuses the define": the define E-find renders, not the site. Expected: raise the refusal only when Table E answers E_FIND (i.e. after kit_walk, at `r == E_FIND`, or make e_find_holds hold on the refusal and refuse there). Unreachable in 3.0a (no search has two streams; every 3.0a probe below is unchanged), so no byte moves today; sabotage row (R) (S2993, PAIR given two streams) would show it: with that plant, sites Table E serves by E-func/E-stmt would also be refused, which the (R) assertion (every B-pair site refused) does not distinguish. Confirm: apply S2993's plant and compile a window site whose Table E row is E-func with a PAIR stop (G2's func frame): refused at SUBJECT, where the design's order would keep its legacy bytes.

### EMIT-2 (SUSPECTED, latent; maintenance; effort small; blast radius: the first E-find search row given a predicate)
The search renderer table's predicate context is NOT one type per row: `ren_key.holds(const void *x)` on an E-find row receives a `wf_bx *` from `wf_find_decide` (`ren_find(REN_ROWS(ren_search), E_FIND, ..., &bx)`, window.c ~:2135) but an `mf_site *` from `wf_renders` (`ren_find(REN_ROWS(ren_search), f, REN_PICK(pick), s)`, ~:2090), the function T-FIND's gate (`fd_holds`) calls for E-find too; E-stmt rows read `mf_site *` (stmt_end0/1_holds). Today every E-find search row has `holds` NULL, so no byte moves (all probes below hold). But the table's comment invites "its predicate over the selection's context"; the first E-find search row written with a wf_bx-reading predicate (B-fn's `b_fn_holds` is the model in the sibling fused table) is silently fed an `mf_site *` at the gate: a wrong read, not a compile error, so the gate and the composition can DISAGREE, which §2.4 says the one-function design forbids ("read by T-FIND's gate and by the composition, so the two cannot disagree"). Fix: pass one context type to every ren_find on a table (e.g. a small struct holding the site and, where known, the plan), or _Static_assert/comment that E-find search rows take no predicate. Confirm: add `b_fn_holds` as an E-find search row's predicate and trace wf_renders' x.

### EMIT-3 (ANSWER to the standing "sibling of a family" question; design; no defect)
The four renderer tables (skeleton, search, stream, check) plus the fused rows already share one key struct and one accessor (`ren_key`, `ren_find`): that family is unified. The one third-member candidate: `ren_skel` and `ren_check` are both keyed by frame ALONE with exactly one row per composing frame (E-find, E-generic; ren_check adds E-stmt's empty C-caller), beside Table E (`wf_etable`), which is also one row per frame and already names each frame's arm (wf_find_arm / wf_floor_arm). Three per-frame row sets (Table E's row, its skeleton, its check) are one table's columns in all but spelling. Recommendation: not now (the design ruled the split explicitly, §2.6.0 [rev2 F3]); trigger: a second check spelling on one frame (vrun's mask-trimmed compare, which the ren_check comment already names) makes ren_check keyed by more than the frame, and then it is no longer a sibling; if instead a third composing frame arrives with one skeleton and one check, fold skeleton+check into Table E's row. `wf_support` vs the search renderer table: both list the built picks (an unbuilt pick has no row in either), a fact stated twice; held apart legitimately (support is frame-independent, search rows are per frame), and rows_check §S pins support against the ruling text.
