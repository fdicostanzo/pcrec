### HOUSE-1 (SUSPECTED, magic codes) wf_renders's 0/1/2 and the "?stream" row sentinel
- window.c:2088 wf_renders returns 0 / 1 / 2 (kit.h:545-548 documents "2 where Table S answers ST-many"); finder.c:688 tests `== 2`, finder.c:510 reads it as a boolean (2 is truthy). It re-encodes table_s's own enum (window.c:2060 ST_ONE=0, ST_NONE=1, ST_MANY=2) into a different numbering (ST_ONE->1, ST_NONE->0, ST_MANY->2), so the declared row enum already exists and is not what crosses the seam. A row-table's index is the shared abstraction: export an enum (e.g. wf_render_t {WF_NOT, WF_RENDERS, WF_STREAM_MANY}) or the Table S row.
- The same fact travels a second way as a magic STRING in the `row` out-param: kit.h:554 WF_STREAM_REFUSAL "?stream", tested by strcmp at window.c:2195 and compose.c:1076 (and written finder.c:689), the "?need" idiom extended. Three readers of one sentinel; a typo'd or new consumer silently takes the "no row" path.
- wf_renders is also evaluated twice for one decision (finder.c:510 inside fd_holds per row, finder.c:688 again for the terminal pick): the second call re-derives what the walk already knew.
- Severity: maintenance. Effort: small (enum + one typedef). Blast radius: finder.c, window.c, compose.c, kit.h; zero emitted bytes.

### HOUSE-3 (SUSPECTED, side effect in a predicate, carried) b_fn_holds writes while the new accessor makes the write order-dependent
- window.c:1847-1859 b_fn_holds (the fused row's `holds`) calls translate(b->d, b->w, 0, b->fn) (window.c:1852) which rewrites the wf_legacy at b->fn; its result is then consumed later through fx->fn (window.c:2132, 2145-2149: allocated only `if pick==FF_PAIR`). Pre-existing in BASE (b_fn_holds at base :1773), but 3.0a moves it from Table B's private walk into the shared `ren_find(..., holds)` accessor (window.c:1800) whose contract (1795-1798) says only "predicate holds over x". Any future second row using REN_PICK(FF_PAIR) with a predicate, or a reordering of ren_fused/ren_search, silently changes who sees the translated site. Plan the translation as an explicit step in wf_find_decide (`translate` then `fused = ren_find(...)` with a pure predicate over the translated plan), or state in ren_find's header that holds may fill the context.
- Also: `ren_key.keys` is one uint32 holding three different vocabularies in one field: REN_FRAME = 1u (window.c:1792), REN_PICK(f)=1u<<f (so REN_FRAME == REN_PICK(FF_UNSTATED)), and WF_ST_* (1u<<0 == RESTART == REN_FRAME). The tables are separate so nothing collides today, but ren_find (void* rows, size, key) cannot catch passing a pick where a stream is wanted; typed per-table finders (or three key typedefs) would. wf_renders asks `REN_PICK(pick)` for pick FF_UNSTATED => bit 0 => would match any REN_FRAME row.
- Severity: maintenance/design. Effort: small.
