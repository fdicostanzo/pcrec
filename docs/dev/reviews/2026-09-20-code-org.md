# Code-organization candidates from Frank's tour — a separate list

Opened 2026-09-20 (seventy-second session) beside the tour list
(`2026-09-20-frank-tour.md`). The tour list holds READABILITY tidy-ups whose
proof is a byte sweep. THIS list holds CODE-ORGANIZATION changes — a structure
that would replace a convention, a parallel mechanism, or a comment-held
invariant. Each item is a question, and **"not worth it" is an acceptable
answer**: an item is dispositioned BUILT / NOT WORTH IT / DEFERRED with the
measurement or argument that decided it (D77: build under a named need).

## [ORG-1] src/gen/emit_vm.c — the repeat rung ladder is decided three times

**Observation (manager, walking vm_count_slots with Frank):** `vm_cost_rep`
(2029), `vm_count_slots_rep` (2691) and the emitter's `vm_rep` each re-decide
CURSOR → REVDET → COUNTER → GENERAL by calling the same predicates
(`vm_cursor_fits`, `vm_revdet_fits`, `vm_counter_fits`) in the same order, with
`under_atomic` threaded into each. The invariant that they agree is held by
the banner "slot counting (must mirror the emitter's own rung decisions)" and
by mech rows, not by the code. A divergence sizes the slot array for a rung
other than the one emitted.

**Candidate:** one `vm_rung_of(Vm *v, const Ast *a, bool under_atomic)`
returning an enum (`VM_RUNG_CURSOR/REVDET/COUNTER/GENERAL`), consumed by all
three walks; each walk's ladder becomes a `switch` on the enum. Sub-question:
memoize the decision on the node (or a side table keyed by node) — today
`vm_cursor_fits` fills two scratch buffers (the stride sequence table and the
capture offsets) to answer yes/no in the pre-passes, then recomputes them at
emission.

**Why it might NOT be worth it:** the three ladders are short and the
predicates are already shared — the duplication is the ORDER and the
threading, ~15 lines total; mech rows S-series already witness the mirror;
a memo on the node is a new field for a compile-time-only fact. The measured
need would be a divergence that actually shipped (none recorded) or a fourth
walk arriving (a listing-only pass, say). Tier if built: opus, with
[TOUR-2]'s lane.

**Disposition:** OPEN.

## [ORG-2] tree-wide — should switch arms become per-case functions, as a rule?

**Observation (Frank):** the same comment as [ORG-1] applies to switches in
general — turning individual `case` pieces into functions ([TOUR-2] step 2 is
the vm_cost instance; wave 2 already did it to vm_emit's ten arms).

**Measured at 16343fce (a code-line census of every `switch` under src/ and
cli/, comment lines excluded, case labels at the switch's own indent or one
level in):** 87 switches. Longest arm ≥20 code lines: **3**. ≥40: **0**.
The three: `src/parse/parse.c:693` (the `'x'` escape arm, 39 code lines),
`src/parse/rxt_source.c:1269` (`RXT_C_EXACTLY_ONE_OF`, 25 lines of a 44-line
constraint switch), `src/gen/emit_vm.c:2301` (vm_cost's `A_CAT`, 21 lines —
[TOUR-2] takes it to ~4 with `cost_add`). Everything else is ≤16 code lines
per arm; the long SPANS (possessify.c:891 at 183 lines, revdet.c:101 at 128,
dfa.c:690 at 125, emit_vm.c:2861 at 124) are long because of their COMMENTS,
not their code — the census says the tree's switch arms are already lean.

**Leaning: NOT WORTH IT as a tree-wide pass.** A rule "every arm is a
function" would manufacture ~80 one-to-ten-line functions for no reader
gain. Worth it where an arm carries BOTH code and a correctness argument
(the [TOUR-2] reasoning — the argument becomes the function's header) or
exceeds ~20 code lines: today that is parse.c:693 and rxt_source.c:1269,
two candidates for the tour list if Frank reaches those files, and vm_cost,
already listed. The census script is a scratchpad one-off; if the rule is
wanted as a standing floor, `tools/review/function_census.py` is where a
`longest_switch_arm` column would live (D77: not before a second reader).

**Disposition:** OPEN — leaning NOT WORTH IT tree-wide; three named arms
individually.

## [ORG-5] src/parse/parse.c — pcrec_is_bare_anchor is a KIND property in switch clothing

**Observation (Frank, reading parse.c):** "pcrec_is_bare_anchor() screams OO
design" — a switch over the AST kind whose arms all `return` a constant; the
function's own comment says it is "a property of a KIND, not a per-NODE
flag". OO puts it on the node class as a virtual; C puts it in a per-kind
property table (one row per kind, the measured PCRE2 cells beside each row);
the exhaustive no-default switch is the C idiom for the pure-virtual guarantee.

**Measured at 3611f1dc:** 46 switches over an AST kind tag in the tree; **1**
is a pure kind→constant table (this one); 45 are structural walks (cost,
nullability, minw, lowering, emission — pass-shaped, per §2 of the
experiments file). A kind-property table would have one column today.

**Leaning: NOT WORTH IT until a second pure kind property exists** — that is
the trigger (D77: name the measurement). Disposition: OPEN.
