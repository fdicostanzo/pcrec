## Findings

### COST-1 (CONFIRMED, design/doc) Stage 2 adds a stamp the LOCATE slot cannot write: `RX_VM_START_SCAN` belongs to the NEXT slot, and `RX_DFA_SCAN` on a VM artifact means "the hybrid's DFA"
- Subject: "What moves on regeneration" (Mechanism, standing question 3): "the stamps `RX_DFA_SCAN "landmark-walk"` and `RX_VM_START_SCAN`".
- Evidence: src/gen/emit_dfa.c:12157-12171 `cand_list_stamp`: `CAND_SLOT_LOCATE -> "RX_DFA_SCAN"` on every route; `CAND_SLOT_NEXT -> rt == VM ? "RX_VM_START_SCAN" : "RX_DFA_PREFILTER"`. `landmark-walk` is a LOCATE row; `RX_VM_START_SCAN` is the NEXT slot's VM stamp, whose spec (match_api.md 6.3.7 p12) is a two-value set `"first-class"`/`"none"` meaning "where a VM attempt can start". A LOCATE row has no business writing it, and the design itself says `first-class` goes OFF the path when the row is selected (so the stamp would read `"none"`, which the spec defines as "every position is attempted": false).
- Equally, `composite` carries `.scan` only for DFA/ATTEMPT (emit_dfa.c ~10226); a LOCATE row on `CR_VM` has no LOCATE stamp to write, and match_api.md 6.3.4 p-hybrid example (line ~2108) defines `RX_DFA_SCAN` on a VM artifact as "this DFA" (the hybrid's). Reusing it for a VM-route landmark walk would make one macro mean two things.
- For stage 1 the DFA stamp is consistent: today the LOCATE row sets `RX_DFA_SCAN` (values `unanchored`, `rev-end`, `attempt`, `empty`; `cover` is set in code but is not yet in the spec value-set either). `RX_DFA_START` is the RECOVER slot's stamp and is NOT what a LOCATE row sets; the premise-test table's `RX_DFA_START "reverse-pass"` is correct as a RECOVER reading.
- Severity: design (stage 2 stamp is unspecified; the named stamp is the wrong slot's). Effort: a naming ruling before stage 2 (a new VM-route LOCATE stamp, e.g. a new macro, plus its value-set row). Blast radius: stage 2 only, but it reopens the `rx_info.scan` mirror (match_api.md line 1662 enumerates `"unanchored"/"rev-end"/"attempt"/"empty"/"compound"`).

### COST-3 (CONFIRMED, answer-free but costly) Flag-bit arithmetic: "about 8 remain" is 7, and the design takes the budget to 6 with `cover`'s candidate bit still owed
- lib/pcrec.h: `PCREC_BIT(0..54)`, bit 55 is the kit's (`-fno-kit-size-drop`, comment line 1196), `PCREC_BIT(56)` is `PCREC_NO_REV_END_ONEWALK`; bit 45 is retired to the kit (registry test comment). So 57 bits are allocated and bits 57..63 (7) are free.
- plan.md [IFACE-PUSH] already records a pending candidate for bit 57 (`PCREC_NO_WINDOW_REPORT`, the cover locator's deny). So landmark-walk is the 2nd claim on the last 7: after both, 5 remain against the HARD trigger of <= 4 (Frank, 2026-10-10). One more mechanism with a deny bit opens the interface push. That is a real cost, not a reason to decline, but the design should say "the push opens at the next bit" rather than "about 8".
- The deny is not optional here: every row in `cand_rows[]` that is choosable carries one and the registry pins 3 checks per bit; the ladder rung reuses the same flag, so no second bit (good).

### COST-6 (CONFIRMED, maintenance) Stage 1 builds VM-side and scan-edge scope that stage 1 does not use
- Item 6: "The ladder rung ... (DFA and VM; deny: the row's own flag)": stage 1 is DFA-only, so the VM half of the rung is dead code until stage 2. fit_rungs rows have an `.applies` per engine; a rung that cannot apply is untestable (no witness can reach it), which is exactly the "witness that stopped reaching its site" the check-design lessons name. Ship the DFA rung in stage 1, the VM position (the labelled UNMEASURED "before 1") with stage 2.
- Item 3: "`pcrec_scanedge_dfa` over it. p48's priced SCAN_SITE_ROWS sits INSIDE here ... row 4 (split-exit, the one-state relaxation priced by k* ~ 2.3 B), held for P1": the report's own numbers say the edge adds 2.4% on 5b (79.7M vs 77.8M) and the hand class-context edge on the VM walk is "negligible". Stage 1 couples the first build of the landmark walk to an UNBUILT p48 row held for it. Build cost (an edge-table row, a bounded-head entry rule, the `RX_DFA_SCAN_EDGE` stamp reading for W) for 2.4% is hard to defend under "costlier must prove more"; the walk without an edge already gives x68.8. Suggest the edge be an explicit follow-up with its own card, not part of stage 1.
- Item 6 also rests on the ladder text in limits.md 8.4 p2a (rung 3 applies only where dropping leaves a strict subset of machines); the design's argument that W "needs A" makes rung order (W before 3) correct, but the cost is a new `needs` edge (W -> A) in the path closure, a new machine bit `W` (the `CAND_M*` set: MR/MF/MATT/MVM/A...), and a new `FitAct`. That is the real size of "a ladder rung": 4-5 code sites plus 6 spec/test sites (COST-2).
