## Findings

### SIMULATE-1: `anchor.whole` fires on anchors that MEAN something (any anchor in a filter role's own text, not only edge anchors); the hand expansion of `padded(/^5/)` is told its `^` "adds nothing"
- CONFIRMED. Severity: design (a diagnostic whose text is false; G0 look-alike between a macro and its expansion). Effort: small (one reach sentence + table row). Blast radius: §11 THE WARNING `anchor.whole` (rev 14 copy lines 2422-2426, text 2444-2448), §7.1 (2014-2016), L17's spelled body, L69.
- The text: it FIRES on `^`, `$`, `\A`, `\z`, `\Z` "written in the OWN rx text of an rx that stands in a FILTER ROLE" (no position restriction), and the text says the anchor "always holds and adds nothing". Its own oracle criterion (table (C), line 2427) is narrower: "with and without its EDGE anchor give the same answer". An anchor that is not at the edge of the role's text is meaningful, and the warning lies.
- Repro: `cd $R/simulate; timeout 120 python3 -I sim.py` (rule implemented from the text: filter role = PCRE2 ANCHORED|ENDANCHORED on the stretch, holes spliced `(?:...)`; libpcre2-8 10.46 and Python `re`, 0 disagreements). Rows S1-S1e of `sim.out`:
  - `/\d+/ & /0*^5/` on `x005`: 3-4; without `^`: 1-4. This is the TEXT `padded(/^5/)` expands to (L13: "the anchor is MEANINGFUL"); written by hand it is in the own text of an `&` side, so it warns "adds nothing", while `padded(/^5/)` (identical answers, 3-4) is silent.
  - `/[\w ]+/ & /.*^err.*/` on `x err`: 2-5; without `^`: 0-5. L17 itself cites `/.*^err.*/` as the meaning of `contains(/^err/)`; written as a filter it warns.
  - `/[\w\n]+/ & /(?ms).*^foo.*/` ("some line starts with foo") on `xfoo`: 1-4; without: 0-4. The table says `(?m)` anchors fire "with or without `(?m)`".
  - `/\w+/ & /a?^b/` on `ab`: 1-2 vs 0-2; `/\w+/ & /foo$(?s:.*)/` on `foobar`: 0-3 vs 0-6.
- Expected: the warning fires only where the anchor provably always holds, i.e. it can be reached only at the stretch's start (every path to `^`/`\A` from the role's start consumes nothing; `$`/`\z`/`\Z` the mirror; `(?m)` the same at the edge only): a static property, the same one the table's witness column already uses. Then the hand expansion and the macro agree in the warning too.

### SIMULATE-2: the warning's definition gives TWO answers for an anchor in a hole inside a filter role (`padded(/^5/)`, `contains(/^err/)`, a hand-written `x & /0*${/^5/}/`)
- CONFIRMED (text reading). Severity: design (L13 / E-CTX-5 / L17's "no warning" rests on one of the two readings). Effort: one sentence. Blast radius: §11 lines 2422-2426, §7.1 2014-2016, §0.3 "scoped match" (555).
- The sentence: fires on an anchor "written in the OWN rx text of an rx that stands in a FILTER ROLE once macros are expanded, i.e. an anchor whose innermost scoped match is that filter role's stretch". The two halves are not equivalent. A hole opens no scoped match (§0.3, §11 line 2299 "A HOLE NEVER OPENS ONE"), so the `^` of `/^5/` in `x & padded(/^5/)` = `x & /0*(?:^5)/` HAS the `&` side's stretch as its innermost scoped match: by the "i.e." half it FIRES; by the "own rx text" half (the `^` is in the argument's text, which stands in a hole) it does not. The §11 table resolves only the macro-parameter case ("a parameter the body splices into a HOLE: no") and the final-pattern hole; a hole WRITTEN by the author inside a filter role (`x & /0*${/^5/}/`, `(x: /.*${/^err/}.*/)`) has no row. After expansion all three spellings (macro, written hole, inline `/0*^5/`) are one text, so "decided by the role after expansion" cannot tell them apart either: the distinction the table draws is the literal/hole boundary, which the text never names as the criterion.
- Expected: one criterion, stated once. Either the boundary ("the anchor's own literal or hole argument is itself the filter role"; delete the "i.e.") or the meaning test of SIMULATE-1 (which gives `padded(/^5/)` silence for the right reason and makes the three spellings agree).

### SIMULATE-3: `anchored(...)` is exempted from the warning by WHO WROTE the anchor, so a user macro with `anchored`'s own body warns where the library one does not
- CONFIRMED (text reading + oracle). Severity: design (against the 20:45 ruling "padded is a simple macro so the warning shouldn't key off of the name", CF:1104-1105, and the record's "a user macro with the same body behaves the same", CF:1110). Effort: small. Blast radius: §11 table row `anchored(...)` (line 2437), L69 (395), §7.1.
- The text: after expansion `x & anchored(r)` is `x & /\A(?:r)\z/`; its `\A`/`\z` are written in the OWN rx text of the body, and the body stands in a filter role, so the general definition (lines 2422-2426) says FIRES. The table says no: "the author writes no anchor ... which is the macro's purpose". That is authorship (library vs program text), i.e. keyed off the macro, not the role. A user `my_anchored(S) := /\A(?:${S})\z/` (the same body) has no such exemption in the text: by the definition it warns at every filter-role use; by "a user macro with the same body behaves the same" it does not. Two answers.
- What the anchor does there: nothing. `sim.out` S3: `/\w+/ & anchored(/foo/)` on `xfoo` 1-4 = `/\w+/ & /foo/` 1-4 (L69: "identity in filter position"). So the exemption keeps silent exactly where the anchors add nothing, which is the case the warning exists for.
- Expected: one rule that does not name `anchored`. Options for the owner/lane: (a) anchors in ANY macro body (library or user) never warn, only anchors in text the caller wrote (including a parameter's text): states the authorship rule openly and keeps L69's silence; or (b) `x & anchored(r)` warns (identity in a filter role, "write `r`"), which is also the role rule applied literally. Either way L69's "not on `anchored(r)`" must cite the rule, not the macro.

### SIMULATE-4: "a parameter the body splices into a HOLE: no warning, the anchor MEANS something" is false for `startsWith`, `endsWith`, `anchored` and `padded(/5$/)`: the warning is silent where the anchor adds nothing
- CONFIRMED. Severity: doc (the silence is RULED: CF:1110-1111 "a parameter the body splices into a hole is NOT in a filter role and draws no warning there"; the stated REASON is wrong). Effort: reword two sentences. Blast radius: §11 table row (line 2436), §2.7 lines 1105-1106 ("No warning fires there (the anchor is meaningful, plain PCRE)"), §0.1 L13's "MEANINGFUL" clause is right for `padded(/^5/)` only.
- Repro (`sim.out` S2; libpcre2 + Python `re`): `/\w+/ & startsWith(/^foo/)` vs `startsWith(/foo/)` on `xfoobar`: both 1-7; `endsWith(/bar$/)` vs `endsWith(/bar/)` on `foobarx`: both 0-6; `anchored(/^foo$/)` vs `anchored(/foo/)` on `xfoo`: both 1-4; `padded(/5$/)` vs `padded(/5/)` on `x0057`: both 1-4. The hole sits at the body's edge, so the anchor always holds there.
- Expected: state the silence as the ruling (the role decides, a hole is no role) and say plainly it also covers anchors that add nothing (`startsWith(/^foo/)`); if a "redundant anchor" lint is ever wanted it is a separate, later item (beside §13 O66's never-match warning), not this warning. The table's witness column header ("where it does not [fire], they differ") is then false for this row and needs the same correction.
