# CRITIC fidelity: memfn-bsu6 (r80)

## Findings


### FIDELITY-1: the re-time's "fresh pool" repeats first-pass layouts by the harness's OWN layout measure (and an A/A pool can equal H64's)
CONFIRMED. Severity: verdict (a layout-driven reading is re-timed partly on the layouts that produced it, so "repeated" is weaker evidence than c6_rule.md RE-TIME states). Effort: small. Blast radius: every re-timed cell (C6 and C6c).
- c6_rule.md RE-TIME: "on a FRESH POOL (cards.py's re-time salt: four new layouts per text, never the first pass's)". `arm_pool` (cards.py:301) enforces "new" only as distinct (prelude bytes, flags) pairs. But `pool_proof`/`pool_refusal` (cards.py:936/955) define a built LAYOUT as (each hot loop's 64-B phase, 32-B phase, relative layout), and that descriptor depends only on (prelude mod 64, alignment variant). `pool_variants` stratifies every pool over the four 16-B classes mod 64 with the class->alignment pairing fixed by the per-pool draw r = hd[0] % 4 (even variants classes r, r+1; odd r+2, r+3). So two pools of one text share 4 layouts when their r is equal (p = 1/4), 2 when r differs by 1 (p = 1/2), 0 only when r differs by 2: in expectation 2 of the re-time's 4 "new" layouts ARE first-pass layouts, and in one text in four all four are.
- Repro (no compile, no clock): one-pattern DRY `kit/cards.sh fidelity time .../fidelity/scratch/orig --cards C6 --dry --patterns c6_dig32`, then `fidelity/scratch/tools/lay.py` (imports the SUBJECT cards.py, calls pool_proof on the cached exes with compiles guarded off). Observed at c6_dig32/on: V first-pass vs re-time pools share 2 of 4 (p64,p32,rel) layouts (rt0 v2 == rt1 v0, rt0 v3 == rt1 v1); H64 0 of 4; H64.b 2 of 4. Also H64.b's first-pass pool has EXACTLY H64's four layouts (same descriptors, preludes differ only in multiples of 64): at this text the A/A arm compares one layout set with itself, below what the A/A is there to read (r79 F2: "V vs H64 compares two pools, so the A/A arm compares two pools too").
- Fix shape: draw the re-time pool's r as (first pass r + 2) mod 4 (four new (class, alignment) pairs, i.e. four new layouts by pool_proof's own descriptor), and have `time`'s proof check first-vs-re-time disjointness of the BUILT descriptors, not of the parameters; for the A/A, either do the same or state in c6_rule.md that "own pool" means an independent draw (which is then identical one text in four). If the absolute prelude above 64 B is meant to count (4 KiB aliasing, uop-cache sets), say so and put that bit in the descriptor: today the proof and the "new" test disagree on what a layout is.
- file:line cards.py:281-322 (pool_salt, pool_variants, arm_pool), 936-998 (pool_proof, pool_refusal), 1819 (_time's proof: proves each pool alone, never first-vs-re-time).

### FIDELITY-2: a planted "re-time reuses the first-pass pool" fault passes DRY, the record and c6selftest unnoticed
CONFIRMED (the sub-part plant). Severity: verdict (the timer can time a different pool than the one it proved and the rule names, and no check in the subject would say so). Effort: small. Blast radius: the re-time pass; by the same mechanism any arm->exe mis-wiring in time_cells.
- Plant (a COPY, `fidelity/scratch/mut/cards.py`, one edit): cards.py:1855, the re-time call's `retime=1` -> `retime=0` (the re-time launches now run the FIRST pass's exes; `_time` step 3 still builds and proves the re-time pools, which then go unused).
- Command: `CARDS=.../fidelity/scratch/mut/cards.py kit/cards.sh fidelity time .../fidelity/scratch/mutrun --cards C6 --dry --patterns c6_dig32` vs the subject's own run (`.../orig`). Observed: rc 0 both; identical verdict and REPORTED lines (stdout differs only in the run id and one synthetic void count, 8 vs 9, a jitter of DryProbe's launch counter); the record's `retime` rows are shape-identical (9 rows, `variants` indices only). `c6selftest` on the mutant: 52 rows, 0 failed. Expected: a red somewhere (the record or DRY naming the pool each launch ran).
- Why: `DryProbe.measure` (cards.py:1532) checks only `os.path.exists(exe)`, then keys its synthetic reading on (pass, cell label) — never on the exe it was handed; and `row_line`'s `variants` field records a pool INDEX 0..3 with no pool identity (the same indices name the first-pass and re-time pools). So neither DRY nor the record binds a reading to the exe that produced it. By the same reasoning (inference, not planted: one plant per lens) a swap of two arms' argv in `time_cells`, or a re-time pool drawn under the wrong salt, reads clean too.
- Fix shape: record the exe's identity per launch (the cache name's variant key `vk`, or the exe basename) in the row instead of / beside the index; have DRY assert each handed exe is a member of the pool `pool_proof` proved for that (pattern, arm, layer, retime) and that a re-time exe is never a first-pass exe; c6decide can then refuse a re-time row whose exes intersect the first pass's (a record-level check of RE-TIME's "never the first pass's").

### FIDELITY-3: the record keys the rule's inputs but not the timer: no cards.py / tree hash, no exe manifest (710 recorded both)
CONFIRMED (by reading; the ref record's header is the evidence). Severity: verdict-attribution / maintenance (two records with byte-equal `#c6` headers can come from different timers; a re-decided record cannot say which DRIVER, pool scheme or layer table produced it). Effort: small (one field). Blast radius: every C6/C6c record, the per-box CANDIDATE bookkeeping that compares records across boxes (D144 add. 4).
- What the header binds (c6_header, cards.py:1345; kit/ref `results_c6_7b3cb55c2d7922f5.tsv` line 1): rule, rule710, form, binary (build/pcrec), cc.<layer> (`$cc --version` only), widths (the C6_WIDTH/C6_SITE constants), run. What decides the timed number but is in NONE of them: the DRIVER text (the 50 ms calibrated timing loop, the eviction sweep: cards.py:584), the LAYER table's levels and the alignment rows (`cc.on` and `cc.off-os` carry the SAME hash in the ref record, e0f6792d053025c2: -O2 vs -Os is not keyed), PHASE_ORDER/PRELUDE_STEPS/POOL_SALT/RETIME_SALT, the QC constants. All live in cards.py, which the record never hashes.
- 710's harness wrote meta.json {"tree": git_head(), "rule_sha", "src_hash" (the correctness marker), "variants", ...} and copied the exe manifest into the run dir (confirm.py ~1190-1200; rule_710.md RECORD: "measure copies them, the marker and the exe manifest into the run directory"). c6_rule.md RECORD "applies (adapted: the header above, no depth profile or walk identity)" — the adaptation names what it drops (profile, walk identity) but the drop of the manifest and the tree/harness identity is not named. So this argues against the adaptation's completeness, not against a ruled field list.
- Also: `form` is mf_form_hash read from `arm_fixtures` linked against build/libpcrec.a (c6_form_hash, cards.py:1723), while `binary` hashes build/pcrec; nothing ties the two (a partial rebuild of one keeps both fields "valid"). Cheap fix: add `harness=<sha-256 of cards.py, 16 hex>` (or the tree commit + dirty flag) to C6_HEADER_KEYS, and per launch the exe identity (FIDELITY-2's fix) — together they are 710's manifest.

### FIDELITY-4: a wrong answer AT a timed launch is recorded as a void (-> INCONCLUSIVE-NOISE), never as the gate failure the rule makes red
CONFIRMED by reading (not planted: one plant per lens). Severity: answer (low probability: the same exe passed its untimed gate on the same subject moments before, so this fires only on a nondeterministic answer, e.g. an uninitialised read, which is exactly a red). Effort: trivial. Blast radius: C6/C6c timed launches; the same shape is pre-existing in C1-C5's `run` path.
- Path: the DRIVER re-checks count and sum before every timed loop (cards.py:650-652, returns 1 "GATE FAIL"), `_exec` raises GateFail (cards.py:1022), `RealProbe.measure` -> `QuietControl.launch` do not catch it, and `time_cells` catches it with `except Exception` (GateFail is a RuntimeError) and writes `row_line(c, "void", note=...)` (cards.py:1184-1185). c6_read collects `gatefail` only from rows whose STATUS is gatefail (cards.py:1651, 1661), so the record reads a void arm -> both comparisons INCONCLUSIVE-NOISE, rc 0 or 4, never rc 1 ("a gate failed: the run is red whatever it reads", cmd_c6decide's own contract).
- Fix: `except GateFail as e: out[c] = row_line(c, "gatefail", note=...)` beside the generic void in the launch loop (prepare_cell's path already does this, cards.py:1168-1169).

### FIDELITY-5: a compile burst sits between the job's quiet wait and the QUIET SAMPLE (710 built in a separate command)
SUSPECTED (what would confirm it: a quiet_sample_c6_*.tsv of a real run whose first sample seconds read higher sibling busy, or first-cell readings drifting against later rounds; DRY cannot show it). Severity: design (the control's thresholds are taken on a box the run itself just loaded). Effort: small. Blast radius: the quiet sample's thresholds and the first cells.
- rule_710.md CPU-QUIET CONTROL: "QUIET SAMPLE, in the job after the quiet wait and before the first timed cell, from nothing of the run's own data ... with nothing of ours running". 710's `measure` started with `quiet_sample` on prebuilt exes (confirm.py ~1188-1204: build/check were their own commands, the manifest pre-made). `_time` runs, inside the job and after any queue quiet wait: the C6 text check, the reach builds and passes, then step 3's full pool build (every first-pass AND re-time pool, 84 pools / 336 exes in the ref DRY, JOBS-parallel gcc), the form-hash link, the calibration cell's 4 gate execs, and only then the 60 s sample (cards.py:1786-1829). The clause's letter holds (nothing of ours runs during the sample), its intent (a settled box after the wait) is not argued anywhere; thermal/frequency recovery after an all-core burst is exactly what a 60 s sibling-busy sample does not see.
- Fix shape: either a `time --prepare` step (or `dry`) that builds/proves every pool before the job's window and `time` refuses to compile (it already says "no compile inside the timing"), or a stated settle wait after step 3. Note for the rule lens (not pursued here): 710 also refused to START when now + estimate passed the window's end (rc 77); `_time` has no such check, and its deadline is caller-supplied only (710's: min(STOP_AT, start + cap - 600)).

### FIDELITY-6 (standing question: SIBLING OF A FAMILY): the CPU-quiet control is now the fifth copy of one instrument, and cards.py itself times two ways
CONFIRMED (inventory by grep). Severity: design / maintenance. Effort: medium to unify, small to name. Blast radius: every pcrec-side timing harness.
- The family: (1) cards.py `QuietControl`/`RealProbe`/`smt_sibling`/`read_stat`/`busy_between` (cards.py:1375-1515, this subject); (2) its source, 710's confirm.py `quiet_sample`/`timed_pass_a`/`void_reason` (untracked scratch; the port is a near-verbatim copy, same function names and constants); (3) docs/design/findall_iter/twin/parity.sh `sibling_of` (sysfs sibling); (4) docs/design/memfn/probes/rq4/rq4.py (sysfs thread_siblings_list); (5) pcrec-bench's pcrecbench/quiet.py (the bench's measured quiet gate: load, mpstat occupancy with the SMT sibling, a per-group /proc/stat timeline: provenance only, never a per-launch void). Same facts (pin, sibling, /proc/stat busy deltas), different rules.
- Inside cards.py: C1-C5's `run`/`c3` call `time_cells` with the default `timed_launch` and NO quiet control, no void log, no `#c6`-style header, while C6/C6c use the control through the `launch=` hook. Two timing disciplines in one file; a C1-C5 re-run tonight would be judged without the control the same file applies to C6.
- Recommendation: keep ONE in-tree instrument (the cards.py port is the natural home: it is tracked, has a probe seam and a DRY twin) and make it time_cells' default launch for every card; record the bench's quiet.py as the box-level sibling it is (pre-flight + provenance, a different question), not to be merged across repos (the MANDATE keeps dependencies on the bench side).

### FIDELITY-7 (standing question: GENERAL FORM + UNLOCKS)
NOTE (proposal, not a defect). The general form here is a TIMED-LAUNCH LEDGER: every launch is one row (pass, cell, exe identity = the variant key, attempt, sibling busy, nivcsw, seconds, ns/B, valid/void) appended as it happens, with a header that hashes the harness (cards.py), the binary, the compilers and the rule; the per-arm rows, the voids file and the quiet sample become VIEWS of that ledger, and c6decide reads the ledger alone.
- Unlocks: (a) FIDELITY-1/2 become record-level checks (re-time exes disjoint from first-pass exes, each exe a member of its proved pool); (b) the void share by direction that 710 printed, and any later re-reading of the control's thresholds (CPU7_MAX, NIVCSW_MAX are UNMEASURED-derived per night) can be recomputed from the record instead of re-timed; (c) a cap kill leaves a readable partial ledger (710's REPLOG did this; time_cells flushes only per cell group); (d) C1-C5 and C6 share one recorder (FIDELITY-6).
- Trigger: the first time a C6/C6c record must be re-read under a changed control threshold, or the first real run whose re-time reads differ from the first pass's and the question "did the re-time run fresh exes?" is asked of a record. Until then, FIDELITY-2's per-launch exe field is the 90 % piece.
