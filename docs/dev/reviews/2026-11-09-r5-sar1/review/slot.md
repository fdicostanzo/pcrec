## Findings

### SLOT-1 — CONFIRMED — the power's piece width is a second, UNSATURATED computation of the repeat's width; it overflows (signed UB) and lists a negative width
- severity: answer-adjacent (compiler UB; listing value wrong) / maintenance. effort small. blast radius: `req_pieces` only (inert today, facts.h:485 "no reader"), and every later reader of the description (R2's altnf, the kit's pieces) inherits it.
- site: src/facts/desc.c `pcrec_pd_pow`, the shortcut `g->w += (long long)(k - i) * d.g[0].w;` (and the pre-existing unsaturated `l->w + r->w` in `pd_cat_group`, which before R1 was bounded by the pattern's length because no repeat had a description).
- The run side computes the same quantity (the exact repeat's width) by `rr_rep_w` = `pcrec_sat_mul(..., PCREC_W_UNBOUNDED)`; the description computes it by raw multiply-add. Same fact, two spellings, and they disagree past 2^63.
- repro: `S/build/pcrec --features all --engine=vm --emit-facts --pattern '(?:(?:(?:(?:ab){65535}){65535}){65535}){65535}|yz'` -> `req_pieces derived -2251748274601982:[97][98]...|2:[121][122]` (true width 2*65535^4 = 3.69e19, over LLONG_MAX). With `(?:q|rs)` appended instead of `|yz`: two groups at widths -2251748274601981 / -2251748274601980. Three levels (`...){65535}|yz`) list `562924184010750@...` correctly. (`--engine=vm` because the default compile stops at the NFA limit first; the walk is reached on the VM path.)
- expected: a group whose width saturates is dropped (or the description declines `over-bound`), never a negative width. Which side is right: the code's run side (saturating, design §3.1 point 3 "maxw ALWAYS the exact rr_rep_w"); the description should use the same saturating width, ideally the same helper (`pcrec_sat_mul`/`pcrec_sat_add`), and treat `PCREC_W_UNBOUNDED` as a wall.

### SLOT-2 — CONFIRMED — `rr_pow_count`'s width-0 sentence and `pcrec_pd_pow`'s "never by k" are false on the restored-EMPTY path; the same body lists two different runs by copy count
- severity: doc / maintenance (harness-only path; no shipped answer moves). effort small. site: src/facts/req.c `rr_pow_count` comment ("every count gives it the same value, so it takes 1") + `rr_rep_exact` (`o.all = o.all && c == m`); src/facts/desc.c `pcrec_pd_pow` header ("bounded by the two bounds, never by k").
- With EMPTY restored, a width-0 `all` body (e.g. `c{0}`, which row 2 makes the unit) reaches row 2 with sat = 1, so c = 1 < m forces `all` false: the value DOES depend on the count. repro (S/build/pcrec-harness --features all --emit-facts --harness=restore=empty): `ab(?:c{0}){1}de` -> req_whole_run 61626465 (abde); `ab(?:c{0}){3}de` -> 6465 (de). The true X^3 of the unit is the unit (`all`), so {3} is looser than {1} for the same body. Sound, but the comment's claim is false and a lever-on run of R1 is not count-invariant on a width-0 body.
- Same path in desc: a width-0 single-group description (the unit) makes `pcrec_pd_cat` return early every copy and the shortcut never fires (n = w = 0), so `pcrec_pd_pow` runs k iterations (65535 max; cheap, but the header's "never by k" is untrue).
- fix: sat for `maxw == 0` should be "no copy changes anything" in both directions — either return c = m for a width-0 body (count-free since rr_cat with the unit is identity), or drop the `c == m` clause when `b->maxw == 0`; in pd_pow return `d` at once when `d` is one width-0 group. Or correct both comments. Which side is right: design §6 T2 row 1 (width-0 bodies are `all`); the code's row-2 handling of them under the lever contradicts it.

### SLOT-3 — CONFIRMED (by reading + probes) — design §3.2 says the description's power is "`pcrec_pd_cat` applied c times"; the code (rightly) applies it m times with the description's OWN saturation. The two saturations are different facts, not one fact computed twice
- severity: doc (design text) — the code side is right. effort small. site: design §3.2 bullet 2 (frozen 90ab55fd3) vs src/facts/req.c `rb_rep_exact_into` (`pcrec_pd_pow(..., b->desc, m)`) and src/facts/desc.c `pcrec_pd_pow`.
- `rr_pow_count`'s c is the RUN's content fixpoint (32 stored cube positions; a non-`all` body stops at 2). The description must carry X^m's EXACT group widths (m·w per group), so c copies would be wrong (`(?:a|bc){3}` has c = 2: two copies would list widths 2..4 where the repeat has 3..6, as `(?:a|bc){3}` lists today). pd_pow stops on its own bound (single group full at `max_pos` or truncated -> width added in closed form; ≥2 groups -> `PD_OVER` within `max_groups` copies). Probed: pd_pow's output equals the literally unrolled body on 5 pairs (`(?:a[bc]){20}|q` vs 20 written-out copies: `40@8`; `{16}` -> `32`; `(?:a[bc]d){3}`, `{11}` -> `33@1`; 40-byte body ×2 -> `80@48`; `(?:(?:a|bc){2}){2}`).
- A second, smaller text error in the same family: design §3.1 point 3 and the `rr_pow_count` header list `trunc` among the fields that cannot change past sat. When `c·w == 32` exactly and c < m (e.g. `(?:abcdefghijklmnop){3}`, `(?:ab){17}`), X^c's head has `trunc` false while X^m's would be true. Harmless: `trunc` is read only in `rr_cat`'s `all` (req.c:470), and T2 has already forced `all` false, which no later combinator can restore. The sentence should say "no field a later step reads".
- fix: design §3.2 -> "`pcrec_pd_cat` applied m times, stopping at the description's own bounds (a different bound from the run's c: the description keeps exact widths)"; a one-line note in both function headers that the two counts are deliberately different, so a later "unify the saturation" edit does not merge them.

### SLOT-4 — CONFIRMED (by reading) — SIBLING OF A FAMILY: `rb_rep_copies_into` is `rb_cat_into` re-spelt field by field; T2's rows are effects where the design's T2 column is a VALUE
- severity: maintenance (simplification). effort small. blast radius: req.c only, answer-neutral. site: src/facts/req.c `rb_rep_copies_into` (new), req.c:635, against `rb_cat_into` (:532) and `rb_rep_unit_into` (:753).
- `rb_rep_copies_into` does `set := union(S, acc.set, rep.maxw); runs := rr_cat(rep, acc.runs); desc := pd_cat(desc, acc.desc)`. That is exactly `rb_cat_into(w, acc, &v)` for `v = {S, *rep, desc}` (`rb_cat_into` unions at `r->runs.maxw`, which is `rep->maxw`). `rb_rep_unit_into` (E1, same table) already does it the house way: build the value in the slot `t[1]`, then `rb_cat_into`. So the family "acc := V · acc" now has five spellings — `rb_cat_into`, `rb_gap_into`, `rb_rep_into` (BEST), `rb_rep_unit_into` (via cat), `rb_rep_copies_into` (inline re-spelling) — differing only in how V is built.
- general form: each T2 row BUILDS its value V into `t[1]` (unit: the body or the unit; exact: X^c + pd_pow; split: the two decompositions; best; gap) and the A_REP arm ends with ONE `rb_cat_into(w, acc, &t[1])`. That is the design's T2 shape (the column is "consumed value", not an effect), the switch's five `case`s become value builders, and the gap's `break` + post-switch tail disappears. Trigger: now (it is a rewrite of code this unit added), or at E2/L1, which add guard fields that every one of the five spellings would otherwise have to carry by hand (the inline spelling is where a guard would be forgotten).
- the table itself (`rb_rep_rows`) is a proper first-match table (predicate, row, arm), not an if-chain; rows 4-5 (BEST, GAP, arm 0) are reachable only under a restored REP, which the comment says. Held.

### SLOT-5 — SUSPECTED (design) — GENERAL FORM + UNLOCKS: R1's two closed-form saturations approximate ONE rule, "the power of a value is CAT iterated to its content fixpoint, width exact"
- severity: design. effort medium. blast radius: req.c's power + desc.c's pd_pow; later R2 (altnf's head) and L1 (guards).
- What R1 approximates: X^m computed by iterating the CAT step until one more copy changes no field a later step reads, then adding the remaining width exactly (`rr_rep_w`, saturating). R1 spells that fixpoint TWICE in closed form, each a hand proof: `rr_pow_count` (non-`all` -> 2, `all` -> ceil(32/w)) and pd_pow's shortcut (single group full or truncated). Both proofs hold today (SLOT-3's probes; 138+69 restore cases), but each new field breaks its formula: design §3.1 point 3 already concedes a guarded body is "looser" at the formula's sat, and SLOT-2 shows the formula is wrong at width 0 under the lever.
- The general form: `pow(V, m)` = iterate `V_{i+1} = CAT(V, V_i)` while `i < m` and `V_{i+1}` differs from `V_i` in content (bytes/masks/all/guards; groups' positions) — offsets excluded, since offsets come from the prefix — then set the width to the exact `rr_rep_w(m, w)` (and each description group's width to its exact, saturating value, which also closes SLOT-1). One loop, no count formula, no per-field proof; termination is bounded by the storage bounds as now.
- Unlocks, each with its trigger:
  1. Guarded bodies at their exact (not looser) value — trigger: L1's census showing a guarded repeat body (§3.1 point 3's own trigger).
  2. R2's adjacency head (`PdHead`'s REP wall, altnf.c) gets the same power without a third closed-form rule — trigger: R2's census firing.
  3. A description for `X{m,n}`, m < n: `pd_alt` over `pow(d, j)`, j = m..n, which the group bound caps (`PD_OVER` past 10 widths) — `(?:ab){1,3}` would list 3 groups instead of `not-fixed-width`. Trigger: the first READER of `req_pieces` (none today, facts.h:485 "inert").
  4. The VM half (§3.8) reads the same power — trigger: that CHOICE row.
- What would confirm it is worth building: a fixpoint version answer-identical to R1 on the witness corpus (it should be, by SLOT-3's probes) plus the guarded census from (1).
