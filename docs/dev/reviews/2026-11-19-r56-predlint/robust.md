ROBUST-2 CONFIRMED wrong-verdict (ratchet), effort S, blast: the L10 "only shrinks" guarantee. --write-ratchet runs lint but ignores its result and the exit code:
 (a) failing tree: `--write-ratchet` on a tree with an L4 failure prints "wrote ... core=1, lib=1, parked=1", rc 0, no failure shown.
 (b) EMPTY / broken base file ratchets DOWN: base predicates.md emptied (L11 "no pieces" fails) -> `--write-ratchet` rewrites core 1 -> 0, rc 0. The count of '?' pieces is 0 only because the parse found nothing; the ratchet is now tightened on garbage (and a legitimately-restored file with 1 '?' then FAILS L10). Likewise a piece whose heading is malformed is not counted as '?'.
 (c) malformed ratchet is treated as absent rows (see ROBUST-3), so --write-ratchet starts from old={} and writes the CURRENT count as the new limit: a ratchet the lint silently skipped can be re-based UP by the writer. Repro: ratchet "core 1" (spaces) with 3 '?' pieces: lint passes, --write-ratchet writes core=3.
 (d) missing root: `--root /nonexist --write-ratchet` CREATES /nonexist/docs/dev/pred/doc_ratchet.tsv (0 bytes, os.makedirs) and prints "wrote ...: " rc 0. Repro created w/nonexist/docs/dev/pred/doc_ratchet.tsv in my lens dir.
Expected: write only when lint has no failures (or refuse and say why), never create a root, never write when pairs is empty. pred_doc_lint.py:442-455.

ROBUST-3 CONFIRMED silent-pass, effort S, blast: L10. read_ratchet silently drops any line that is not exactly `word<TAB>digits`. Each of these exits 0 with the line ignored and L10 count dropping:
 non-numeric (`core\tx`), space-separated (`core 1`), 3 columns, empty file, negative (`core\t-1`), CRLF is OK (isdigit after strip), a DIRECTORY at the path (reported as "absent"). Unknown words (`bogus 3`) ignored. Duplicate rows: last wins, so `core 0` then `core 99` silently LOOSENS the ratchet to 99 (rc 0). An empty/garbled ratchet file therefore disables L10 entirely with "L10=0" in the counts line as the only trace. Expected: every non-blank line must parse and name a known word, no duplicates, else a loud L10 failure. pred_doc_lint.py:433-439.

ROBUST-4 CONFIRMED traceback, effort S, blast: every mode but --selftest. Repro: append printf '\xff\xfe' to predicates.md; run lint, --show x, --list: all traceback rc=1. Also --show/--list over a root with a bad file in a pair that the key does not live in crash (every file is parsed). read_lines at :79-81. Expected: catch UnicodeDecodeError/OSError in read_lines, print "L?? file: not valid UTF-8" and fail (rc 1) or rc 2 for I/O. Same for OSError (unreadable file, dir at the path of a base file is skipped by isfile - fine).

ROBUST-5 CONFIRMED wrong-verdict (false positive), effort S, blast: any base/details file containing a fenced code block, which the format's own heading/fence logic tries to support (fence exemption exists for headings and L6).
 (a) base: `needs:`/`by:`/`was:` lines and the "statement" scan (parse_base :129-140) do not honour fences. A fenced example under a piece containing `needs: nothing/here` yields `L5 predicates.md:18: needs: nothing/here names no piece` (repro: append ```/### Fake .../needs: nothing/here/``` after the last piece; rc 1). A fenced line can also become the piece's statement (L7) when it is the first line.
 (b) details: the field-continuation branch `elif field and ln.strip()` (:174-175) appends fence lines and fenced text to the preceding field; a fence after a `slugs:` field gives `L9 ...details.md:23: slug '```' is not lower-case kebab` plus 5 more failures (rc 1, 6 failures from one fenced block).
 (c) fence matching: infence toggles on ANY ``` or ~~~ line (FENCE_RE) so ~~~ opened and ``` "closed" mis-pair; no closing-must-match-opener, no indentation limit. Repro: "~~~\n### x\n```\n### y [core/z/z] ruled 2026-01-01" makes y a real piece (L3 failure) though inside the ~~~ fence.
 (d) unterminated fence: a lone ``` mid-file hides everything after it from heading parsing. It fails here only indirectly (L3/L5 mismatch with details), with messages that never mention a fence ("details entry core/holes/class has no base piece"). A pair where both files hide the same tail would pass. Expected: end-of-file inside a fence is its own failure. pred_doc_lint.py:57, 90-99, 129-140, 150-175, 243-249.

ROBUST-11 CONFIRMED maintenance/design (FAMILY question), effort M. This lint is the sibling of a family and a second parser is being grown beside the first:
 - scripts/entry + doc_profiles.py parse the tracker base+details pair (profile table, `form: pair`, pair_index/pair_entries/pair_text, levels 0/1/2, exit 0/1/2, "never a second parser" for plan_lint's grammar at entry:19-20). pred_doc_lint has its own piece parser (parse_base/parse_details, :84-180), its own reader with the same level semantics and same exit codes (`--show KEY -l 0|1|2`, `--list [STATUS]`, :506-528), its own tmpdir snippet, its own selftest harness (compare entry's selftest at :842 and plan_lint's).
 - doc_format.md (the spec, line ~83) already says the reader IS entry: "the files registered as a profile of scripts/entry (`entry core/holes/class`: level 0 the heading and statement, 1 the piece, 2 the details entry; `entry <slug>`...)". The subject instead ships `--show/--list`, so the spec and the script disagree on where the reader lives, and one of them will have to move.
 - Differences that make a plain reuse impossible today: the predicate pairs use `### name [tag] status date` headings and `## tag — name` entries, not `- ID slug state — stmt` index lines; ids are slash tags not `[A-Z]+[0-9]+`; three file pairs not one.
 GENERAL FORM: a shared "tagged-piece document" model: parse(base, details) -> pieces {id/tag, name, status, date, statement, fields, body-lines, details-lines} with the fence/BOM/CRLF/UTF-8 handling done ONCE, selected by a profile row (heading regex, id regex, field names), exposed to three clients: the structure lint, the levelled reader (entry), the over-cap census (`entry --over-cap`). doc_profiles.py already has `form` in {single, pair, archive, list, dormant}; the predicate docs would be a `form="pieces"` row.
 UNLOCKS: (1) the reader is not written twice and `entry --lint-scripts`/`--over-cap`/`-g` search work on the predicate docs for free; (2) one place fixes ROBUST-4/5 (fences, UTF-8) for every tracker file; (3) a heading-form profile also fits scripts/INDEX.md-style and plan row bodies.
 TRIGGER that justifies building it (D77: name the measurement): the second lint or reader needing the same pieces (e.g. wiring pred docs into `entry -g`, as the spec already promises), or the first divergence bug between the two parsers (ROBUST-5(a) is already one: entry's `pair_entries` cuts at `## ` with no fence handling at all, pred_doc_lint's parse_details honours fences in headings only). Until that trigger: a one-way dependency is cheap (pred_doc_lint imports nothing from entry today; a reader-only profile in doc_profiles would drop --show/--list, ~60 lines) and removes the spec/script mismatch. Not recommended before the pilot migration (spec step 1) shows the shape stable.
