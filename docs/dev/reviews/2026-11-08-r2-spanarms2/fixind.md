### FIXIND-1 (CONFIRMED as a contract break; doc/design; effort small; blast: stamps, spec, one structural check) -- a guard-narrowed EXACT run member is not a `req_set` member, and three sites say it always is. F1/F2/F21.
CAT-R/CAT-L (§5.2) narrow a CONSUMED cube position to an exact byte; §1's non-goal keeps the SET guard-free. `pcrec_req_pick` (`src/facts/req.c:866-876`) returns `run->bytes[idx]` whenever `mask[idx] == 0xFF`, so after L1 `RX_REQ_BYTE` can name a byte that is not in `req_set`. Three readers state the opposite: `match_api.md` §6.3.7¶5 ("every value is a member of the necessary set"), `pcrec_req_pick`'s own comment ("every value here stays a member of `req_set`"), and `tests/codegen/reqcube_check.py:256-262` check 4 (RX_REQ_BYTE not in req_set -> FAIL, "S452's shape"). Its population is 12 fixed witnesses with no lookaround, so it does not fire. The invariant is what it encodes.
Repro (rule applied to today's facts): `x(?=q)[pq]` today gives `req_set 120`, run none. CAT-R narrows `[pq]` to `q`, and the run is the spelled `xq`, whose facts are `req_run 7871@1`, `req_byte 113`. So L1 gives RX_REQ_BYTE "113" with req_set {120}. The answer is sound at reach 0, because `q` is consumed. At L2/L3 the scan member can be a GUARD byte: `bar(?=baz)` gives `z`, and `(?<=\x00\x01)...` gives a byte before the attempt start. Then ¶4's "a byte every match must contain" is false too.
The design leaves unstated what the SET does with a consumed position a guard narrowed (take it, since it is consumed and in the match, or not), and §5.4 has no row for `req_byte` as a run-member reader. A4 says "the SET takes no guard byte", but `req_byte` is not only the set's. L1's gate lists only facts_listing hunks. The ¶5 hunk, the req.c comment and reqcube check 4's rule are owed at L1, not at L2's A7 hunk.
Fix: an A-row for `req_byte`/RX_REQ_BYTE (¶4/¶5/¶7, `pcrec_req_pick`, reqcube check 4). Either the set takes a narrowed consumed exact byte (the cheapest, and it restores ¶5 at L1), or ¶5 is reworded in L1's gate. At L2/L3 also say whether a guard byte may become RX_REQ_BYTE at all.

### FIXIND-2 (CONFIRMED; design + witness reach; effort small-medium; blast: L1's whole mover population of one-character lookarounds, and six of rev 1's new witnesses) -- a one-character positive lookaround is NOT an `A_LOOK`. It is an `A_CTX` node, which T3/E-4 sends to the plain width-0 unit, so the ITEM row never fires for it. F1, F2 (b)(c)(d), F5.
`pcrec_look_t3` (`src/parse/ctxnode.c:117-140`, row `ctx-node`, deny `PCREC_NO_CTX_NODE` bit 35) turns `(?=C)`/`(?<=C)` into `pcrec_ast_ctx(..., CTXFN_NEXT/CTXFN_PREV)` whenever the body's language is a set of single one-byte characters. The comment at `internal.h:3986` says the same: "a one-character lookbehind becomes an A_CTX node". Rev 1 names `A_CTX` only as `\b`/`\B`/`^`/`$` in E-4 (§4.1 row E-4). T3 is "first match on the kind row's TEXT ZERO and the node kind (A_EMPTY first; A_LOOK positive before negative)", and T4 ITEM is "positive lookaround". So under the natural reading, `CTXFN_NEXT/PREV` contexts get the E-4 unit and carry no guard.
Measured at the build tree (`--emit-facts`, `kinds`): `a(?=b)[bc]` gives kinds `none` (`-fno-ctx-node` gives `lookaround`), and so do `(?<=a)b`, `xy[ac](?:(?<=a)b|c)` and `(?:ab(?=a)){2}` (kinds `collapsible_rep`). The inner `(?<=x)`/`(?=c)` of W-N1/W-N2 and the `(?<=c)` of W-S1 are single-character bodies with no assertion, so they are ctx nodes too.
Consequences: (i) W-L5 (F1's own witness), W-A1 (F2 b), W-RG, W-N1, W-N2 (F2 d) and W-S1's second guard (F2 c) have no ITEM to plant against. Their sabotages cannot fire under default flags, which is a [MECH-REACH] failure for the very witnesses F1/F2 added. They reach only under `-fno-ctx-node`. (ii) The §5.6 movers `a(?=b)[bc]` -> `ab`, `xy[ac](?:(?<=a)b|c)` (its ALT-drop claim), `[ac][ac]c(?<=ac)(?<=c)d` -> `[ac]acd` and `ab[xy](?=(?<=x)y)[xy]` -> `abxy` do not happen as written. (iii) The run would differ between default and `-fno-ctx-node`, a deny that today moves no run. That is not an answer risk, but test-axes' run/stamp identity across that deny should be checked.
Note also: span_facts ALREADY reads these contexts at d >= 0 (`a(?=b)[bc]` span `2:97,98`, `(?<=a)b` span `1:98`). That bears on §5.3's "no producer" (see FIXIND-6).
Fix: T1/T3 name `A_CTX` with a positive context function (`CTXFN_NEXT`/`CTXFN_PREV`) as an ITEM producer: a one-position `rg`/`lg`, the context set as a cube when it fits `pos_set`, else no guard. Or the witnesses switch to two-character bodies AND the census counts ctx-node lookarounds as a separate population. The first is the general form (one item for every positive context, whichever lowering made it).

### FIXIND-4 (text gap; one misreading deletes a match, oracle repro; design/doc; effort small; blast: ITEM, CAT-EDGE, TOP storage) -- the guards' STORAGE is unsized, and which END a truncated guard keeps is unstated. F1/F2 (new fields `lg`/`rg`).
§2 defines `lg` as "run positions at offsets [-t, 0)" and `rg` as "[0, h)". It does not say where they are stored (an `RbRun` of `PCREC_MAX_REQ_RUN_SCAN` = 32 positions, `facts_derive.h:104-105`, or something else), what `trunc` means on a guard, or which end survives a truncation. Guards GROW by concatenation in two rows. ITEM: a lookbehind's `lg` = the body's own `lg` followed by its tail, and a lookahead's `rg` = the head followed by the body's own `rg`. CAT-EDGE: `o.lg` = `l.lg` met with `r.lg`'s shifted leftover. So two 32-position pieces can exceed the bound, and the existing helpers disagree on the end they keep: `rn_app` keeps the FIRST 32 (head form, `req.c:337-348`), `rn_pre` keeps the LAST 32 (tail form, `:354-366`). Only "keep the positions nearest the cursor" (rn_pre for `lg`, rn_app for `rg`) keeps the offsets `[-t, 0)` true. Keeping the first 32 of `lg` shifts every kept position by the dropped count.
Witness (hand-applied, oracle-checked): `(?i:a){40}(?<=(?<=A{20})a{20})y` on `x` + `A`x20 + `a`x20 + `y` gives M 1 42 (libpcre2 10.46). The body `(?<=A{20})a{20}` is `all` (20 <= 32 copies, T2 row 2), so ITEM `lg` = `A`x20 `a`x20, 40 positions. Kept nearest the cursor: `A`x12 `a`x20 at [-32, 0). CAT-L meets them against the cube tail of `(?i:a){40}`, giving the run `A`x12 `a`x20 followed by `y`, which is present. Kept first-32 (the `rn_app` reading of "followed by", the helper ITEM's lookahead half must use): `A`x20 `a`x12 placed at [-32, 0) claims `A` at -20..-13, where the subject has `a`. That run is absent: a pre-check NOMATCH where (1,42) is expected. The run is 264 bits, far over the floor, and the cube positions are not k-set singletons, so not dominated.
Also unstated: (i) `trunc` on a guard. TOP's `lg ++ head` via `rn_app` inherits `a.trunc`, which is harmless only because `best` never reads `all`; say so. (ii) TOP's BACK `t` is the STORED `lg.n`, not the body's width. (iii) The REP saturation (§3.1 point 3) counts content fields: do guards count? A body with a guard is still non-`all`-saturating at 2 copies, but an `all` body with `rg` (`(?:ab(?=a)){20}`) saturates at ceil(32/2) by head bytes while its `rg` keeps changing nothing. State it.
Fix: one sentence in §2: guards are `RbRun`s at the run's bound, kept at the END NEAREST the value's edge (tail form for `lg`, head form for `rg`), `trunc` unread. Plus the witness above (or a shorter twin) as a sabotage row.

### FIXIND-5 (answer risk at L3, from the text's own soundness claim; CONFIRMED by tracing the build tree's emitters + oracle; severity answer; effort small text / medium code; blast: every L3 handoff artifact, DFA and VM) -- §5.4 A3's "the move at k <= 0 emits pos = landmark_position, which is sound and loose at a negative K ... a precision change, not a soundness one" is false. Under BACK the landmark lies BEFORE the attempt, so moving the start TO it can start the body below `search_from` and report a match before the start offset. F8 (the census fix), F9.
Trace at `f07aaef69`. ENTRY: `emit_req_handoff_rest` (`emit_dfa.c:1167-1197`) only ever subtracts. With `k <= 0` and no rounding (byte), the whole `if (k > 0 || round.len > 0)` block is skipped, so `handoff_position` stays the kit's hit `c`. Its comment's invariant "`c >= posvar` always ... cannot underflow" (`:1158-1160`) is exactly what L3's `omin = -t` breaks: the kit then returns hits in `[posvar - t, posvar)`. Under utf8 the block is emitted, and `handoff_position - posvar` is a size_t that wraps. RE-ENTRY: `emit_req_landmark_move` (`:7795-7813`) re-asks only `if (landmark_position < pos)` and, at `k <= 0`, sets `pos = landmark_position`. Both read "landmark >= attempt start", and under BACK that becomes "landmark = attempt start - t".
Witness (rule applied; oracle 10.46): `(?<=ab)ab[a-z]*q`. Today the run is `ab`, `dominated`. Its spelled twin `abab[a-z]*q` is `emitted` with `RX_REQ_HANDOFF "0"` (measured), so L3's run `abab` at `omin = maxoff = -2` takes the handoff route. Subject `abababq` from start 3: expected M 4 7 (from 2 it is M 2 7). The scan floor is max(0, 3-2) = 1, and the leftmost `abab` at or after 1 is at 2, so c = 2. A build that makes K signed (A3's stated work) and keeps the move ("sound and loose") starts the body at 2 and reports (2,7) where (4,7) is expected. The tight move `c + t` = 4 is the ONLY sound one. The required form is `max(posvar, c - K)` with K signed, i.e. `c + t` clamped at `posvar`. At re-entry, the re-ask condition becomes `landmark_position + t < pos`.
Fix: A3's cell says "BACK NO, and the move is a SOUNDNESS change: `pos = max(pos, landmark - K)` with signed K, the compare done without size_t wrap". Add `emit_req_handoff_rest` + `emit_req_landmark_move` by name to L3's changed sites (A2's "re-entry floor" names the floor but not the move). Add W-L10 = the witness above, which is red under the rule A3 currently states.

## PROBED-AND-HELD

Read at the build tree `f07aaef69` (worktrees/crit-spanarms2). Oracle libpcre2-8 10.46 via p2probe: 14 subject runs. pcrec compiles: about 25 `--emit-facts` single-pattern listings.

- **`all` implies an exact, fully stored width** (it is what CAT-EDGE's shift needs).
