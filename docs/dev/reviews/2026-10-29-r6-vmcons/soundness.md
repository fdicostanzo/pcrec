## Findings

**Common root of SOUNDNESS-1, -2, -3, -5 (and -7).** The design moves the analyses from the prototypes' TEXT readers onto the EVENT stream, and Stage -1 extends the stream with the statement shapes F1 found (slot reads, conditional `goto <p>_L`, cuts, locals, site kinds, BREF, CLASSB, callouts, checkpoints, work). The base's matcher text has at least four more shapes with an effect on some column and no event: guarded blocks `if (c) { ... }` (S-1), a conditional `goto <p>_fail` that the stream records as an unconditional FAIL (S-2), cursor assignments `scan_position = ...` other than a consume's own advance (S-3), and the cursor-span consume itself (S-5). The completeness check counts five text shapes, none of which is any of these, so it stays green; the F12 checker implements the same table, so it agrees with the build. The prototypes' 0-difference identity runs (Measurements) read the TEXT and so are not evidence for the event-based build. The general fix is one check, not four rows: every statement the emitter prints inside a matcher function (every `;`-terminated statement and every `{`-block opener at body depth, outside `#define`s) is either a typed event or on a short declared list of no-effect forms, counted per artifact over the corpus.

### SOUNDNESS-1 — CONFIRMED, answer, DOC: guarded statement blocks (`if (c) { <P>_SET...; }`, `if (c) { <P>_PUSH }`) are invisible control flow; the SET row's "kill s" turns a MAY-write into a MUST-kill, and V3 (DEAD) then deletes a live capture write

- Rule applied: statement-kind table row `SET s <- e` (successors `next`, writes s, copies "kill s"), verdict V3 in round A1; Stage -1's event list and completeness check (§ The analysis input).
- The base emits SETs (and PUSHes) INSIDE raw `if (...) { ... }` blocks: emit_vm.c:5044 and :5195 (span cursor rung: groups published only `if (span_cursor >= slot_values[low] + stride)`), :5854 (revdet low-water `if (iteration == rmin)`), :5934/:5941 (revdet retreat/extend PUSH), :5953 (revdet group publish `if (group_seen[j])`). None of these `if (` openers is a goto, so Stage -1's VE_BRANCH ("every conditional `goto <p>_L`") does not record them, and the completeness check (counts `slot_values[`, `goto <p>_L`, `_PUSH(`, `_CUT(`, `resume_depth =`, `return`) does not count `if (...) {` blocks, so it stays green. The listing today already shows these as unconditional `set` rows (`--emit-ir`, L8/L13 below).
- Witness: `^(?:(?:(a)b)*c){2}$`, `--features all --engine=vm` (the default route is also vm: `RX_ENGINE "vm"` without the flag). Two mandatory copies of the outer body, each with a cursor-rung `(?:(a)b)*` that publishes group 1 conditionally (L8 and L13). Rule as written: after L8's two SETs every path (L7 c, L5, L11 SET slot5, span, L13 BRANCH/PUSH L14 whose live-in reaches L13 again) reaches L13's SETs of slots 2,3 = kill, before any read (ACCEPT); so slots 2,3 are dead after L8's SETs, V3 DELETE both.
- Twin: `w/s1t.c` (diff `w/s1t.diff`: L8's two RX_SET lines removed, the empty `if` left). Built with `bld.sh` (drv.c driver, rx_search, every span).
- Observed (base `w/s1b` / twin `w/s1tw` / libpcre2 `p2`):
  - `abcc`: base 1:0,1 / twin 1:-1,-1 / libpcre2 1:0,1
  - `ababcc`: base 1:2,3 / twin 1:-1,-1 / libpcre2 1:2,3
  - `abcabc`, `cc`: all agree.
- Why: the second copy's inner loop runs zero times, its `if` is false, and group 1 keeps copy 1's value (the emitter's own comment at :5189 states this is the intended semantics). The analysis modelled the guarded write as a must-write.
- Same defect in the other columns: COPY's "gen s==t" from a guarded SET is a must-fact on one path only (V4 unsound by the same token); V5's liveness inherits the wrong kill. A guarded PUSH is only over-approximated (MAYFRAMES, FIRST+ fork), which is safe.
- Would the stated gates catch it? Stage 2d's corpus gate needs a cell with a guarded write followed on every path by a second guarded write of the same slot; a crude scan of the 6,245 corpus patterns found no `{n>=2}` copy of a capture-carrying `*` loop, and the design's W-cells have none. Likely NOT caught before landing.
- Fix shape: a VE_GUARD/VE_ENDGUARD pair (or route every guarded block through a BRANCH around it) recorded by the primitive that prints `if (...) {`, and the completeness check counts `if (` block openers inside matcher functions; until then a guarded SET has copies "none" and no kill (a may-write: kills nothing, gens nothing).
- Severity answer; DOC (Stage -1 table + SET row); effort S (one primitive + one check line); blast radius: every artifact with a cursor rung carrying captures or a revdet loop with rmin>0 / groups (the bench's cscan/JSON members carry revdet loops).
- Design rows: § The analysis input (Stage -1 table, completeness check); § The verdict table, SET row, V3/V4/V5.


### SOUNDNESS-2 — CONFIRMED, answer, DOC: the caller-variable compare `${v}` has no row; its events are LABEL/WORK/FAIL/GOTO, so every column reads it as a dead end — V3 deletes captures before it and D drops its arm

The listing shows exactly that (`L3 label / note / fail / goto L6`). The conditional fail is recorded as an UNCONDITIONAL FAIL, so the stream successor of the variable's label is a dead end and the GOTO after it is unreachable. The completeness check stays green: the one `goto <p>_L` is a GOTO event; `goto <p>_fail` is not counted. The design adds VE_BREF for the identical shape in `vm_bref` but not for `vm_var` (module `vars`, [VAR] M10).
- Witness A (slot flow, V3): `^(a)${v}c`, `--features vars` (default engine vm), v="b". Rule as written: after L5's SET of slot 3 (and L2's of slot 2) the only path is L3 -> WORK -> FAIL (no successor): both writes DEAD. Twin `w/v1t.c` (diff `w/v1t.diff`: both RX_SET lines removed). Driver `drvv.c` (rx_search with one rx_var "v" from env V).
  - `abc`: base 1:0,1 / twin 1:-1,-1 / libpcre2 (quotemeta splice `^(a)(?:b)c`) 1:0,1.
- Witness B (D, row D2): `^(?:${v}x|by)z`, v="a" and v="b". FIRST+(arm 1) = {} (its path ends at FAIL, E false), FIRST+(arm 2) = {b}; D2 admits (every byte drops arm 1) and emits `switch: 'b' -> arm 2, default fail`. Twin `w/v2t.c` (diff `w/v2t.diff`).

- Would the stated gates catch it? The D form, probably: `tests/vars/basic.rxt:62` `^(${a}|${b})$` (both arms F = {}) on `cat`/`dog` would go red at stage 2b (VM route by default: checked). The V3 form needs a capture before a variable: no such cell in `tests/vars/` by grep.

### SOUNDNESS-3 — CONFIRMED, answer, DOC: raw cursor moves (`scan_position = ...`) are NOTE events, so FIRST+ reads a consume after a lookbehind back-step or a lookaround cursor restore as a consume AT the dispatch byte; D2 then drops a matching arm. The CLASSB row's premise ("lookbehind consumes backward") is not the base's shape

- Rule applied: FIRST+ column (CLASS/LIT "F ∪= the byte class; stop"; NOTE has no row and is decoration; CUT OPAQUE; PUSH fork), D2. Stage -1's table: "VE_CLASSB | the backward consuming test (lookbehind)".
- Base: a lookbehind is NOT a backward consume. `vm_lookbehind` (emit_vm.c ~7140-7225) emits `scan_position = <p>_back_step(subject, n, scan_position, k);` (recorded as VE_NOTE "the ENCODING SEAM's back-step") and then the branch's bytes as ordinary FORWARD VE_CLASS/LIT consumes, then the end-check and the CUT. The only "consumed BACKWARD" VE_CLASS producer (:5531) is the revdet walk. A positive lookaround's success restores `scan_position = (size_t)slot_values[POS]` (:7488), also a NOTE; for an ATOMIC lookahead a CUT precedes it (OPAQUE, safe), but for a lookbehind the forward consume comes BEFORE the CUT, and for a non-atomic lookahead (`(*napla:...)`) there is no CUT at all. Stage -1 lists no event for a cursor assignment, and the completeness check does not count `scan_position =`.
- Witness A (lookbehind): `^x(?:a|(?<=x|yz))w`, default flags (engine vm). Rule as written at the alternation (L3): arm 1 F = {a}; arm 2: SET, SET, BRANCH (fork), PUSH (fork), NOTEs (the back-step), CLASS 'x' -> F ∪= {x} stop; the L12 fork reaches CLASS 'y'. F(arm 2) = {x, y}, E false. D2 admits (byte 'w' drops both). Twin `w/lb2t.c` (diff `w/lb2t.diff`: the push replaced by `switch: 'a' -> arm 1, 'x','y' -> arm 2, default fail`).
  - `xw`: base match 0,2 / twin NOMATCH / libpcre2 match 0,2. (`xaw`, `xxw`, `yzw` agree.)
- Witness B (non-atomic lookahead): `^(*napla:x(?:a|))xb`, default flags. Arm 2 (empty) reaches L4 `scan_position = slot[LOOK_POS0]` (NOTE), then CLASS 'x': F(arm 2) = {x} although that 'x' is read at the lookahead's ENTRY, one byte back. Twin `w/nat.c` (diff `w/nat.diff`).
  - `xb`: base match 0,2 / twin NOMATCH / libpcre2 match 0,2.
- Would the stated gates catch it? Probably: `tests/lookaround/lookbehind.rxt:212` `(?<=a)b|(?<=bc)d` on `bcd` (expects 2,3; under the rule F(arm 2) = {b}, the byte is `d`) would go red at stage 2b (that artifact takes the VM route by default: checked). The design's proof claim is still wrong; the corpus is the backstop.
- Why the design's argument misses it: FIRST+ is position-blind (it assumes the cursor stands still until the first consume); any statement that moves the cursor without consuming breaks that, and the base has three (lookbehind back-step, lookaround cursor restore, revdet lazy commit `scan_position = slot[low]` :5873, the last one safe only because its forward scan starts at the arm's own position). The design's W11/W17 cells are lookahead/callout shapes and never put a lookbehind or a napla in a dispatched arm's continuation.
- Fix shape: a cursor-assignment event (VE_SEEK) recorded by the primitive that prints `scan_position = <expr>` (other than `++`/`+= took` inside a consume), FIRST+ row OPAQUE for it, and the completeness check counts `scan_position =` sites against it. Correct the CLASSB row's description (lookbehind = back-step + forward consumes).
- Severity answer; DOC (Stage -1 table, FIRST+ column); effort S; blast radius every VM artifact with a positive lookbehind of width >= 2 (one-character lookbehinds, including alternatives of single characters such as `(?<=x|y)`, are emitted as an ASSERT on `subject[scan_position-1]` and are safe: probed) or a non-atomic lookahead, reachable from an alternation arm before that arm's first own consume.
- Design rows: § The analysis input (VE_CLASSB row); § The verdict table, FIRST+ column (CLASSB, CUT, NOTE absent), D2; § Soundness at the seams ("D's commit opacity, lookarounds ... AD's arguments unchanged").

### SOUNDNESS-4 — SUSPECTED (design, latent answer), SEAM: "keyed by the ordinal of the site's event in the walk that decided it" does not identify a site in the NEXT walk once that walk's event sequence differs; the only keying check is the all-KEEP table, which cannot see it

- Rule applied: § Pipeline and stages, "Verdicts are keyed by site id: the ordinal of the site's event in the walk that decided it. Walks run the same deterministic AST walk, so ids match. D's new chain labels are allocated after every walk-1 label, so walk-1 ids stay stable." and "A codegen check pins the keying: a walk taking an all-KEEP verdict table must emit byte-identical C and events to its input walk."
- The applying walk does NOT emit the deciding walk's event sequence:
  - walk 2 vs walk 1: D's first dispatched site replaces its push chain with SWITCH + CASE events and per-class chains (new LABEL/PUSH/GOTO events; `[abd]x|[acd]y|[bcd]z` has 5 push sites against 2). Every event after that site has a walk-2 ordinal different from its walk-1 ordinal, so D's verdict for a SECOND site (keyed by its walk-1 ordinal) lands on whatever event walk 2 emits at that ordinal (possibly a new chain push), or on nothing;
  - walk 3 vs walk 2: a DELETEd SET emits nothing (V3/V4 "emitted: nothing"); unless a deleted site still advances the counter, every later verdict is applied one site off. The design does not say which.
  - "Chain labels are allocated after every walk-1 label" stabilises LABEL ids, not event ordinals; the two are different numbering spaces.
- Concrete shape (no build exists to run): any matcher with two D2 sites in sequence, e.g. `^(?:a+x|a+y|b+z)(\w)(?:c+x|c+y|d+z)$` (the arms are not finite literals, so no island), or any matcher with two slot-flow DELETE sites in stream order (W1's own program has DEAD candidates at slots 4..6 and 2,3). A one-site shift deletes a LIVE write (a SOUNDNESS-1-class answer change) or dispatches with another site's FIRST+ classes (a SOUNDNESS-3-class answer change).
- Why the stated check misses it: an all-KEEP table changes no event sequence, so ordinals coincide by construction; the bug class only exists for non-empty tables. The F12 checker would catch the RESULT (a deletion it cannot re-derive), but the design names the keying check as the pin.
- Fix shape: key every verdict by a walk-invariant id (the AST node plus the primitive's role enum and an occurrence counter local to that node, recorded on the event), and pin it with a non-trivial table: for each site k of the corpus' first N artifacts, a one-verdict table {k: DELETE} must change exactly site k's line(s) in the emitted C (diff confined to that site).
- Severity answer (latent: depends on the implementation choice the text leaves open, and the text's stated reason is wrong); SEAM (walk 1 -> 2 -> 3 composition); effort S in the design text, M in the check; blast radius every artifact with >= 2 sites of either kind.
- Design rows: § Pipeline and stages ("Verdicts are keyed by site id", "A codegen check pins the keying"); Build plan stage 2a gate.

### SOUNDNESS-5 — CONFIRMED under the literal Stage -1 reading, answer, DOC: the "span (cursor rung)" row has no producer; EVERY cursor span (greedy, lazy, possessified) consumes in raw text that records no event, so FIRST+ sees only the continuation's byte and D2 drops an arm that starts with a span

- Rule applied: statement-kind row "span (cursor rung) | F ∪= class, continue as zero iterations; stop if the reach test demands one"; Stage -1's event table (which adds no span event: the VEKind list has none, and RUNG is the rung-kind record with no class); D2.

The class test is a conditional `goto <p>_fail` or a `while` condition, so neither VE_BRANCH nor the completeness check sees it.

A builder following Stage -1 literally gets the twins above. The corpus gate (stage 2b) would very likely catch the greedy form (`(?:\w+x|...)`-like arms are common), much less likely the lazy form (a crude scan of the 6,245 corpus patterns found no non-nullable lazy-span-led arm).
- Fix shape: Stage -1 row "VE_SPAN a=class id, b=min, recorded at the rung's entry label for every cursor-rung form (greedy, lazy, possessified)", and the completeness check counts span blocks / class tests on `span_cursor` against it.

- Design rows: § The analysis input (Stage -1 table: no span event); § The verdict table, span row; D2.
