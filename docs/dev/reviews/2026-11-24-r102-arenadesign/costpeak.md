# Findings: lens costpeak (r102 arenadesign)

## Findings

### COSTPEAK-1 CONFIRMED (memory/design; effort: one gate sentence; blast: G2a's gate at F4, R2) G2a "arena high-water IDENTICAL" is false at F4 by design, and the design's own rule would then forbid keeping F4
- Today a part's `MEMFN_FORMS` string is copied INTO THE OUTER ARENA: compound.c:182 `w->facts[i].into = &w->cx->arena;`, compile.c:3735 `pf->memfn_forms = pcrec_sb_fragf(pf->into, "%s", cx.job->memfn_forms);` (an arena StrBuf, grow-by-copy in the arena). F4 (design "Clients" table) replaces this with "a heap copy" stored in a hold. So on every compound pattern whose part has kit forms, the outer arena's bytes DROP by the fragf's arena bytes and the heap rises by strlen+1. G2a (§Goals: "attempt-arena high-water bytes IDENTICAL on the corpus (records are heap; nothing new is allocated from any Ctx arena)") cannot hold at F4, and §Goals G2 says "A favourable move cannot arise ... if one appears it is reported, not kept" -- read literally, F4 is "not kept".
- Second unstated move: `pcrec_arena_hold` (API) is "a BASE entry"; today's record is an arena AOwn (arena.c:42-44, `pcrec_arena_alloc(a, sizeof(AOwn))`, 16 B). The design says records are heap (D-1 "Records live on the heap") but `Arena.owned` stays `AOwn *`; it does not say where `pcrec_arena_hold`'s record comes from. If heap (consistent with "records are heap"), arena bytes move by -16 B per part at R2; if arena, F4's SECOND hold per part (c_src's own hold compound.c:183 stays, plus the new `memfn_forms` hold) adds +16 B per part to the arena.
- Fix: state G2a as "identical at R1, T1, F1-F3, F5; at R2/F4 the move is exactly the named bytes (sign and size per part, PCREC_COMP_MAXPARTS = 2, internal.h:9132)", and say where the hold record lives. Also: no arena high-water counter exists in the tree (`git grep -n -i -E 'high.?water|arena_bytes|arena_used' -- src cli tests scripts tools` finds only stack/trail high-water), so G2a's check needs a scratch counter that no unit names; C0(b) should say it is a scratch build.

### COSTPEAK-2 CONFIRMED (memory/design; effort: one flag + one sentence; blast: every G2b read, F1/F3 gates) massif's DEFAULT peak is only 1%-accurate, so a +1% band is at the instrument's noise; and the band is ~30x the predicted rise
- valgrind massif records a new peak only when the heap exceeds the previous one by `--peak-inaccuracy` (default 1.0%). The design (Standing question 1, G2b) calls massif "deterministic" and gates at "+1% or +4 KB, whichever is larger", but names no flag: with the default, base and build can each report a "peak" up to 1% below the true one, so a real +1% rise can read as 0 and a 0 rise as +-1%. Repro: one run here used `--peak-inaccuracy=0.0` on `[a-z]+@[a-z0-9.-]+\.(com|org|net|edu)(x|y){1,200}[^\n]{3,40}z` (peak 7,593,920 B total, snapshot 70); the gate must pin that flag (and `--heap-admin`, default 8 B/block, since the build adds blocks).
- Sizing: on that peak +1% = 75,939 B, against a predicted rise of at most 10 records x 224 B = 2,240 B (COSTPEAK held counts below). So the gate admits ~34x the design's own prediction, i.e. it cannot see e.g. one stray 64 KB child block (COSTPEAK-3) on any pattern whose peak is above 6.4 MB. R-3's refused rise was +7-12%; the band is safely below that, but it is not a check of the claim. Fix: with `--peak-inaccuracy=0.0`, gate on the PREDICTED delta: peak(build) - peak(base) <= (max live records on the peak's arenas) x record chunk + admin, which is exact and deterministic for a given glibc; keep +1% only as the R-3 backstop.
- Same blindness for fragmentation: massif counts requested bytes, not heap pages. The `spare` list (API: "released records, reused", freed only in `pcrec_arena_free`) pins small chunks malloc'd immediately BEFORE each table (design's "order inside every registering call": record first) in the brk heap for the rest of the attempt; glibc's dynamic mmap threshold rises after the first large free, so later tables come from brk too. A pinned 224 B chunk between freed tables can block coalescing/trim. Not visible to massif; the design makes RSS "secondary" (Standing q1). SUSPECTED, small: confirm by `--pages-as-heap=yes` or malloc_info arena size base vs build on the R-3 families; cheap alternative design: release records with their scope at the outermost close (depth 0) instead of keeping a spare list (cost ~10 mallocs per scope set, below noise per COSTPEAK held cost counts).

### COSTPEAK-3 SUSPECTED (memory/doc; effort: one sentence; blast: S10-S12 STRBUF, S14 ARENA) the registering order's step (3) reads as EAGER resource creation for STRBUF and ARENA, which today is lazy
- §API "THE ORDER INSIDE EVERY REGISTERING CALL": "(3) make the resource (malloc / the StrBuf's first growth / the child's first block ...)". Today a StrBuf's storage and an Arena's first block are made by the first append/alloc (sb.c:52-66 `sb_grow`; arena.c:17-19 `pcrec_arena_alloc`, ABLOCK_MIN 64 KB arena.c:6). Built literally, `pcrec_scope_arena` mallocs a 64 KB block at birth: on clskit's empty path (clskit.c:1127 `if (k->nsec <= 0) { emit_empty(c, fn); return; }`) that block is NEW, and a STRBUF gets a 256 B buffer that its first real append then reallocs (sb.c:53). The rise is small and rare (no `nsec = 0` writer found by `grep -n -E 'nsec *= *0|->nsec = ' src/gen/clskit.c`), but G2b as written (COSTPEAK-2) would not see 64 KB on a large pattern. Confirm: the build's `pcrec_scope_arena`. Fix: say STRBUF and ARENA entries are zero-initialised in the record and grow on first use (already safe: the storage lives inside the record, so there is no "birth before owner" window; only HEAP needs steps 1-4).

### COSTPEAK-4 CONFIRMED (doc/design; effort: one table cell; blast: D-1's (A)-vs-(B) row S13, no decision change) D-1 says `keyseen` is a per-refinement-pass table; it is allocated once per call, before the refinement loop
- D-1 table row S13, column (A): "plus a nested scope per refinement pass for `keyseen`, else its per-pass table is retained n times". Code: minimize.c:132 `int *keyseen = malloc(...)` and minimize.c:148 `free(keyseen)` are inside the one-shot initial-partition block; the refinement loop is minimize.c:151-194 and allocates nothing (its only buffers `htab`, `keys`, `sig`, `part`, `newpart` are made once at minimize.c:83-89 and reused per pass). Under (A) keyseen would be retained ONCE (n ints, 4n B) for the call, beside `keys` (n x siglen ints, minimize.c:89), i.e. at most 1/(siglen) of the call's own peak, never "n times". The row overstates (A)'s cost; (B) still wins on S4/S10/S12, so D-1's choice stands, but the count should be corrected (it is the kind of cost claim R-3's gate reads). Measured: `pcrec_minimize_dfa` calls = 2 per compile on both probes (callgrind, below), so scopes per minimize = 1, not per pass.

### COSTPEAK-5 CONFIRMED (speed/design; effort: one gate sentence; blast: G5 at F1 and F4) G5's corpus-summed +1% cannot see the mechanism's cost going wrong: predicted cost is ~0.05%, and the sum is dominated by a few heavy compiles
- Measured (callgrind, review tree): pattern `[a-z]+@[a-z0-9.-]+\.(com|org|net|edu)(x|y){1,200}[^\n]{3,40}z` = 1,113,108,821 Ir, `pcrec_arena_alloc` 116,415 calls (9.78M Ir incl), `sb_grow` 5,172 calls, `pcrec_minimize_dfa` 2, `pcrec_scanedge_dfa` 2, malloc 232; pattern `a(b|c)+d` = 60,002,692 Ir, `pcrec_arena_alloc` 5,977, `sb_grow` 1,813, minimize 2, scanedge 2, malloc 80. The lent check (load `a->cx`, NULL test, load `lent`, branch: ~4 Ir) costs ~0.5M Ir = 0.04% on the big pattern and ~31k Ir = 0.05% on the small one; scope bookkeeping (~40 entries/attempt: minimize 7+7 live, scanedge 10+10, render_buf 2, splice_mark ~4, target_headers 1, clskit k) is a few thousand Ir. So G5's estimate ("well under +1%") HOLDS, by ~20x.
- But the CHECK, "instruction count ... of compiling the corpus within +1%" summed over the corpus, is weighted by the heavy compiles (here one pattern is 18x a small one), so a fixed per-scope or per-compile regression (e.g. records malloc'd per entry instead of reused, or the release walk made O(entries^2)) is diluted below 1% on the sum while being several % on small patterns. Fix: gate per pattern (max or 95th-percentile ratio over the corpus, deterministic under callgrind) at a bound tied to the estimate (e.g. +0.3%), or report the two numbers above (arena-alloc calls and entries per attempt) as the cost model and check them.
- Not superlinear in any user-controlled size: scopes per attempt are O(1) + one per class kit (emit_dfa.c:13225 loop over `f->nscan`, emit_vm.c:13313/13344), each O(1) + its entries; minimize/scanedge one scope per DFA build (compile.c:404/441/461/3214/3217/3249/3251/3282; minimize via dfamemo.c:156 only on a memo miss); `pcrec_scope_free(keyseen)` hits the TOP entry (keyseen is registered after minimize.c:83-89's five, freed at :148 before :198-199), so O(1). Retries multiply all of this by <= the retry count, linearly. Place the sb_grow lent check after the capacity early return (sb.c:52) so it runs per growth, not per append (sb_grow is called on every append: 5,172 calls vs 51 reallocs on the big probe); the design does not say where.

## PROBED-AND-HELD

- Struct sizes at F (gcc, `sizeof` on internal.h, lens dir sz.c): StrBuf 192 B, Arena 24 B (design adds top/spare/depth/child: ~48-56 B), ABlock 24, AOwn 16. A uniform record (union of StrBuf/Arena/void*, + next + kind) is ~208 B -> a 224 B glibc chunk. The design's "about 200 bytes" HOLDS.
- Max live entries per client, from code: minimize max 7 live (part,newpart,sig,htab,keys minimize.c:83-89 + keyseen :132, freed :148, then seq,ns :198-199; 8 tables total); scanedge 10 live (indeg..stg,drop :581-586, exitv,remap,found :617-619, ns :762, all freed :787/:796); STRBUF clients 1 each (memfn_stamps.c:250 `tail`, :362 `nb`; part_layout.c:600 `o`); clskit 1 ARENA (clskit.c:1126). No two scopes nest on one arena: minimize/scanedge run in the DFA phase, clskit inside emitters that open no other scope, the three STRBUF clients are post-emission and call none of the others. So the attempt arena's spare list peaks at 10 records = 2,240 B: the design's "about 10, under 4 KB" HOLDS. Largest/most nested case reached: a compound shell (PCREC_COMP_MAXPARTS 2, internal.h:9132) with a part compile running while the outer's spare holds <=10 records and the inner's own registry holds <=10: <=20 records ~4.5 KB, slightly over the literal "under 4 KB" but inside G2b's +1% on any compound peak above 450 KB.
- Where the global peak sits (massif --peak-inaccuracy=0.0, one run, the big probe): snapshot 70, 7,593,920 B, inside `pcrec_build_dfa` intern (dfa.c:1591/1611/1620/1629) on compile.c:3214's FIRST build, before any scope client has run in that attempt, so the spare list is empty at that peak (delta 0 there). Peaks that fall after a minimize/scanedge carry the <=2,240 B.
- Storage timing unchanged for every client: S10 `nb` adopts at the instant today's transplant frees `c->p` (memfn_stamps.c:370-373) and both copies coexist for the same span as today; S12 `o` likewise (part_layout.c:643-648); S11 `tail` freed at close where :257 frees it; keyseen's `pcrec_scope_free` frees at :148's point. The spare list adds no storage time to any TABLE, only to records.
- clskit child arena: same ABLOCK_MIN (arena.c:6, 64 KB) block sizing, same retention (freed at the function's close, where clskit.c:1134 frees today); only the record (~224 B) is new. Holds, modulo COSTPEAK-3's eager-block reading.
- Arena-allocation lent check cost: ~4 Ir x 116,415 calls on the big probe = 0.04%; G5's estimate holds (COSTPEAK-5 is about the check, not the cost).
- Runs used: 5 of 60 (1 perf stat on a refused pattern, 2 callgrind, 1 massif, 1 plain compile).
