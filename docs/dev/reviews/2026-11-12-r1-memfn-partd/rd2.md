# rd2 findings: partd

## Findings

### RD2-1 CONFIRMED (code read) — "run_len 1 kept as a RUN term" is unreachable: translate's grouping rule is not in D2's list
- Severity: answer-adjacent (compile REFUSAL, G1) / design text. Effort: S (one more listed site + one plant/witness). Blast radius: every stage-3 run whose findable member stretch is a lone CUBE between wide positions.
- part_d.md §2.1 bullet 3 and §5.1 D2 ("`run_len` 1 kept as a RUN term", "so that a lone cube scan keeps `fn-pair`"). At 35bee4da9 `translate` makes a RUN term only when `grouped = j - i >= 2` (memfn/src/window.c:1522); a one-position pterm group is ALWAYS an `MF_T_SET` term. So a lone cube scan (e.g. a run `\d[aA]\d`, scan `{41,61}`) becomes a 2-member SET scan term, which `ofs_fn_applies` refuses (ofsskip.c:128 `sc->kind == MF_T_SET && set_count(sc->set) != 1`), so no legacy row serves the part and `wf_parts_prepare` refuses at window.c:2597 ("a pre-check part's plan renders through no legacy row"). The design's new `run_part` clause ("a RUN term or a one-member SET") agrees with the intent, but nothing in D2's content list or §3.1's table changes `translate`'s `grouped` rule (nor names `c_run`'s pterm-of-one inside a pinned R as the trigger). Expected: D2 lists `translate` (window.c:1505-1522): inside a pinned R, the member's findable stretch is a RUN term at ANY length >= 1. Also add a G2 floor/witness "lone cube scan between wide positions" (none of §5.2's layouts names it: "a wide position next to the scan" with a cube scan is the case) so the gap reds.

### RD2-2 CONFIRMED (code read) — the deny as written MOVES today's bytes on P3 (WINDOW) runs longer than 8
- Severity: answer-identity of the alpha OFF arm (G3 for the deny arm; `test-axes` answer-identity holds, bytes do not). Effort: S (text fix). Blast radius: every derived run part on the OPTIONAL route (P3, `fd_run_modes[]` finder.c:747) whose run is longer than `MF_PRES_WINDOW` (8, kit.h:330).
- part_d.md §5.1 D2: "denied, the WHOLE and WINDOW stretch is the member's findable stretch (a `run_modes[]` stretch like `stretch_exact`) ... the part is today's one RUN term". Today `run_modes[]` (presence.c:221-225) gives KIT_RUN_WINDOW on n > 8 the `stretch_window` extent (ver_len = 8, the least-mass 8-window holding the scan). On today's corpus every position is findable, so "the member's findable stretch" is the WHOLE run (n > 8 positions): the denied arm states a longer `ver_len`, derives a longer part and renders a different RUN term than today. Only WHOLE (and WINDOW on n <= 8) is reproduced.
- Fix: state the deny as "the MODE's stretch, clipped to the member's maximal findable stretch" (WINDOW: the least window among windows holding the scan that lie inside the findable stretch, or stretch_window then intersected; either reproduces today because today the clip is the identity). Say which, since the clip changes P3's least-window choice on wide runs.

### RD2-3 CONFIRMED (code read, INFERRED for stage-3 input) — under the deny, a run whose findable stretch is ONE position still refuses the compile
- Severity: answer (compile refusal on the deny arm, i.e. `test-axes`/G2's deny pass reds on the design's own witnesses). Effort: S-M (a stated rule for the case + witness). Blast radius: every wide run whose scan has wide neighbours on both sides, e.g. `\d{3}a\d{3}`, `[a-z]x[a-z]`, a UTF-8 lead between continuation sets.
- Question (b): "keep the compile from refusing on wide runs". With the deny, ver extent = the member's findable stretch = 1 position. `derive_run_part` accepts `ver_len` 1 (window.c:2546), the derived span has len 1, so `run_shaped` is 0 (window.c:277) and even with the kit's R flag `run_member` gives `run_len` 1 and `c_pin` returns early on `d->run_len < 2` (window.c:1040): no pin, `c_stop` drops the stop, and `translate` emits ONE SET term that is the scan. `ofs_fn_applies` then returns `runs <= 1 && checked > 0` = 0 (ofsskip.c:138: the scanned one-member SET is `scan_only`, nothing is checked), so no legacy row serves and `wf_parts_prepare` refuses at window.c:2597. For a lone CUBE scan it already fails at ofsskip.c:128 (RD2-1). The non-deny arm does not hit this (its extent keeps the wide positions, so `checked` > 0).
- Fix: the design must state what a 1-position findable stretch does under the deny: the stated decline (§2.4 item 2's row, "no findable position" widened to "no findable stretch of >= 2" ON THE DENY ARM ONLY), or a scan-only part admitted by `ofs_fn_applies` (`checked > 0` relaxed for a derived part: the scan proves its one position). Either is a listed site; neither is in D2. Add the layout "findable stretch of length 1" to §5.2 with a deny-arm refusal floor of 0 so it reds.

### RD2-6 CONFIRMED (code read) — plant (p6) can go green: no G2 floor guarantees a wide R position LIGHTER than the scan
- Severity: check design (K35 / MECH-REACH: a plant whose witness population nobody counts). Effort: S (one floor). Blast radius: the D2 mech row for (p6) and S3012's re-aim.

### RD2-7 CONFIRMED (code read) — "R by the kit's flag": its carrier and its one writer are unnamed
- Severity: design text (build-readiness). Effort: S. Blast radius: D2's lane.
- §2.1 bullet 2 / D2: "a kit-internal flag on the derived statement, not a seam field".
