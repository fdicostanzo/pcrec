## Findings

### D3G-1: the set-pin plants test `set_why`, not its wiring. Unwiring the set check keeps 40/40 plants green while a swap passes. MEDIUM, FIX BEFORE LAND (small)
S3232 and S3233 call `set_why(fl, pinned, hit_)` directly. main() adds the set verdict on a separate line
(`why += [w for w in set_why(fl, pinned_sets[cell], hit) ...]`, d3_floor.py:297), and no plant reaches that line. This is
the learnings §3 shape: the control shares the function but not the site.

Sabotage repro: copy d3_floor.py and replace line 297 with `pass`. Run it on the swapped sweeps:
```
D3-FLOOR byte/c-vm compiles=5031 failed=485 records=1055 census=174 floor=174 band=0 pin=117 ok
D3-FLOOR cells=4 failed_cells=0 failed_plants=0      rc=0, 40 plants ok
```
The swap goes green and so does every plant (sab.out).

Proposed fix: create one per-cell function, e.g. `cell_why(cell, fl, recs, pin, pinned)` = verdict + set_why. Both main()
and the plants call it. S3232 plants the swap in the RECORDS, as bin/mut.py does (swap the pat_hex of a hit record and a
non-hit record), so the counts stay equal and only the set catches it. The S3228-S3231 plants already go through
`verdict()`, the same function main uses.

### D3G-2: REPIN pins an empty or truncated census without complaint (rc 0). MEDIUM, FIX BEFORE LAND (small)
Repro: run `d3_floor.py --repin --census COPY` with utf8/c-vm's sweep empty and byte/c-vm's cut to its first 100 lines
(empty.out):
```
D3-REPIN-ROW byte/c-vm census_floor=11 compiles=89 failed=11 records=18 (d3_floor.tsv: set these, bands 0)
D3-REPIN-ROW utf8/c-vm census_floor=0 compiles=0 failed=0 records=0 (d3_floor.tsv: set these, bands 0)
rc=0; the census file now has 0 utf8/c-vm rows; 410 "-" lines printed
```
The plain gate's `census_floor >= DIFFER pin` check would catch these two cases after a hand copy (0 < 181, 11 < 117). A
partial truncation that stays above the pin would pass (byte/c-vm keeps passing anywhere from 117 to 173). The wrapper
only stops a collect.py that exits non-zero. A missing cell crashes with a KeyError traceback before the file is written,
which is safe but ugly.

Proposed fix: before writing, refuse (exit 1, write nothing) when any cell is missing, has 0 compiles, has a census below
its live DIFFER pin, or has compiles below the old d3_floor.tsv value. A deliberate shrink passes with an explicit
override (e.g. `D3FLOOR_REPIN_SHRINK=1`). Add one plant row for this (an empty sweep under --repin is refused).

### D3G-3: REPIN does not write d3_floor.tsv. LOW-MEDIUM, FIX WITH D3G-2 (or rule as accepted)
The brief's Q2 expects both files to be rewritten consistently. Today the census is written and the floor numbers are
printed for a hand copy. The consistency check makes a half re-pin red, so nothing goes wrong silently, but two files
encode one measurement and a human carries the second. Proposed: --repin also rewrites the four data rows of
d3_floor.tsv (census_floor/compiles/failed/records, bands kept at 0, provenance = the note) and keeps the comment block.

### D3G-4: REPIN leaks its whole scratch dir (~130 MB per run). LOW, FIX WITH
run_d3floor.sh runs the REPIN with `exec`, which replaces the shell, so the `trap 'rm -rf "$WORK"' EXIT` never fires. My
REPIN run left `$PCREC_TMPDIR/scratch/d3floor.zAmqzZ` (130M; the traced build + 4 sweeps, no floor.out). I removed it.
Fix: run python without `exec`, then `exit $?`.

### D3G-5: the provenance note names HEAD even when the tree is dirty. LOW, NOTE
The default note is `$(git rev-parse --short HEAD) tree, $(date)`. My re-pin measured an uncommitted corpus file and
recorded "6af642db1 tree, 2026-11-15". The real re-pin flow always runs on an uncommitted change. Suggest appending
`+dirty` when `git status --porcelain` is non-empty, or requiring D3FLOOR_NOTE.

### D3G-6: the remedy text points at the wrong file and repeats itself. LOW, NOTE
- A set-only red (the swap) says `census changed: re-pin tests/memfn/d3_floor.tsv`, but nothing in d3_floor.tsv needs to
  change. The file that moves is d3_census.tsv, and the remedy is the `D3FLOOR_REPIN=1 bash tests/memfn/run_d3floor.sh`
  command. Neither is named in any red line.
- A +1 red prints "re-pin tests/memfn/d3_floor.tsv" three or four times.
- Proposed: emit REPIN once per cell as `census changed: re-pin with D3FLOOR_REPIN=1 bash tests/memfn/run_d3floor.sh
  (rewrites d3_census.tsv; d3_floor.tsv rows printed)`.
- Doc nit: d3_floor.py's S3233 comment says "a pure gain names the gained one", but only the pure-loss plant exists. The
  module docstring's SELF-TEST paragraph still lists only S3228-S3231.
