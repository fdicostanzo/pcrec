# SEAM findings

## Findings

### SEAM-1 (CONFIRMED, design; effort S; blast: the one seam entry + 2 pcrec readers): the target crosses as an ADDRESS, and identity is by address, not by token
- Sites: memfn/src/compose.c:946-958 `mf_art_target` refuses `!mf_target_c_of(t)`; memfn/src/targets.c:197-209 `mf_target_c_of`/`mf_family_c_of` match `t == &target_table[i]` (address); memfn/include/memfn.h:1765 `mf_target.family` is a POINTER pcrec dereferences (src/gen/memfn_targets.c:140,160 `t->family->name`, `mf_family_c_of(t->family)`); src/gen/memfn_targets.c:104 the one-family rule compares `a->family != b->family` (pointer).
- Against: manifesto principle 9 ("no pointers ... cross"), and target_seam_units.md §3 "it asks the kit each member's family token and COMPARES TOKENS" (ruled), D146 add. 1 "passes it [the token] across the seam".
- Observed: S2998 (tests/mech/sabotages/S2998_art_target_accepts_copy.sh) and g2_simd_gen.c's case make it a CHECKED CONTRACT that a value copy of a row (same name, same facts, another address) is refused. A seam read back from text yields exactly such a copy (or a name), so the round trip fails by construction; the seam's real fact is the canonical NAME, which the stamp `<PREFIX>_TARGETS` already writes and the kit already re-parses in its own formhash entry table (memfn/src/formhash.c:415 `mf_art_target(art, mf_target_parse(e->target, ...))`: the kit itself crosses its seam as text, then converts).
- Answers today: none move (rows are static, one process). The cost is the next reader: a serialized plan, a second emitter, or U4's per-part target list would each carry the name and have to know to re-parse; the address rule makes "a row with the same name" a different target.
- Fix form (small): key identity by canonical name (mf_target_c_of/mf_art_target look the row up by `t->name`, or `mf_art_target` takes the token text and parses it, refusing an unknown one with the parse text); pcrec compares family NAMES at :104; S2998 re-aimed to "a row the table does not hold by name". Pointers stay as in-process handles, never as identity.

### SEAM-2 (CONFIRMED, maintenance/design; effort S; blast: memfn.h entry signature + kit.h switch): two seam slots survive the joint merge with no reader
- (a) `mf_art_begin(..., uint32_t policy, ...)`: memfn.h:1334-1339 "The art-level `policy` is stored and read by nothing"; compose.c:927 stores it, kit.h:279 "stored, read by nothing"; pcrec passes a literal 0 (src/gen/memfn_sites.c:199). The sheet item 1 kept it ONLY because "mf_art_begin's signature cannot change on the kit's branch without breaking today's pcrec build"; the joint U2+U3 merge (one abi event) removed that obstacle and the slot stayed. A slot that crosses the seam with a value nobody reads is exactly what a text round trip would have to carry and a second reader would have to guess the meaning of (D-row "no silent defaults": pcrec now sends a presumed 0).
- (b) `MF_TARGET_REQUIRED` (kit.h:713-722) is now 1 under `#ifndef`, so its 0 position (an unstated art silently renders the portable text; bit 0 classes OTHER) is reachable only by a `-DMF_TARGET_REQUIRED=0` rebuild, which no build or test does (git grep: only `=1` overrides, tests/memfn/run_finder.sh:217, now redundant). It was a staging switch for the two-branch period (sheet item 11); after the flip it is a dormant lever that re-opens the silent-default path the flip closed, and its tests compile a second kit copy for nothing.
- Fix form: drop the art-level `policy` parameter (one more abi-neutral kit signature change, pcrec's one caller) or name it reserved and refuse nonzero; make the two refusals in compose.c:1085-1092 unconditional, delete the macro and run_finder.sh's second kit build.

### SEAM-3 (CONFIRMED, doc; effort XS; blast: comments in 6 files): the seam's own contract text still describes the switch at 0
- memfn/include/memfn.h:1823-1826 (the PUBLIC contract of mf_art_target): "An art whose target is never stated renders no SIMD level ... the portable target's text". At SUBJECT (MF_TARGET_REQUIRED 1) such an art is REFUSED at its first define (compose.c:1085). memfn.h:1826-1828 lists "a call after the art's first define" as a refusal; the code (compose.c:951-955) and sheet rev 1.1 item 1 refuse only a FIRST statement after a define (restating the same row after a define is accepted).
- memfn/src/kit.h:713-719 "0 until the U2+U3 joint merge ... At 0 ..." over `#define MF_TARGET_REQUIRED 1`; tests/memfn/policy_check.c:6 "kit.h guards the default 0", :8 "At the branch default the refusal is not reached"; tests/memfn/run_finder.sh:210 "kit.h's default is 0"; S3000:7 "the branch default 0 never reaches the refusal". All false at SUBJECT.
- Consequence: a second emitter / reader written from memfn.h would build an "unstated = portable" path that the kit refuses. Fix: rewrite the six comments to the as-built rule (or delete them with SEAM-2(b)).

### SEAM-4 (CONFIRMED, doc + design consequence; effort XS doc / K2 for the behaviour; blast: every `-fmemfn-simd` artifact with MEMFN_FORMS "none"): "none" no longer means "same as SIMD-off", and such an artifact is now family-locked
- Repro (2 compiles): `build/pcrec -p rx -fmemfn-simd -o out.c --pattern 'ab+c'`, BASE vs SUBJECT. Both read `RX_MEMFN_FORMS "none"`. SUBJECT also carries `RX_TARGETS "amd64:x86-64"`, the family guard (`#if !(defined(__x86_64__) && !defined(__ILP32__))` / `#error`) and the sse2 region pragmas (lines 17-29, 418-420). `clang --target=aarch64-linux-gnu -ffreestanding -fsyntax-only out.c`: SUBJECT stops at `out.c:19:2: error: "this file was generated for another CPU family..."`; BASE gets past the file's own text (it fails only on this box's missing aarch64 libc header). So an artifact with no target-dependent form is no longer portable at `-fmemfn-simd`; BASE's was (MEMFN_FORMS "none" = byte-identical to SIMD-off).
- Contract still says otherwise: docs/spec/match_api.md §6.3.10¶4 "`MEMFN_FORMS` is "none" iff the artifact is byte-identical (stamp lines aside) to its own `-fno-memfn-simd` compile" (guard/region are not stamp lines), and tuning.md §2.43¶4's last sentences "`"none"` iff the artifact is identical to its SIMD-off compile". ¶4's first sentence was amended ("its target's own text aside"), the iff was not; §6.3.10¶4 tells consumers to bucket on "none".
- Ruled? The guard+region on every `-fmemfn-simd` artifact is target_seam_units.md §2 U3's bytes column, and eliding them where nothing depends on the target is K2's `target_dependent` fact (§2, after U3). So the behaviour is the ruled interim; the finding is (i) the two iff sentences (fix: "none iff no kit form depends on the target; at a SIMD target the artifact still carries the guard and region, until K2"), and (ii) for the manager: the interim costs portability on the common case (most patterns reach no SIMD row), a regression against BASE that no spec line names. pcrec already knows the fact K2 would state for the single-art case (its own guarded-byte count of kit blocks is 0, MEMFN_FORMS "none"), but the guard is written in the prologue; K2's per-art fact is the right home (no special case).

### SEAM-5 (CONFIRMED by reading, maintenance; effort XS; blast: mf_sink contract): the target-dependent BRACKET carries an unread kit index and is a second, silent SIMD gate
- `mf_sink.simd_open(void *u, int level)` (memfn.h:879-901): `level` is "the kit's levels.def index, opaque to the host"; pcrec drops it (src/gen/memfn_sites.c:375-378 `(void)level`). An integer index into a kit-private table is not a fact a text reader could use (the level's TOKEN, `mf_level.stamp`/`token`, would be); it is an unread slot (principle 9's "assumptions about the other side").
- memfn.h:887-888 "NULL = not offered: the kit then renders no guarded text at all". In the art path this is a SECOND gate on SIMD beside the stated target (ofsskip.c:648-649 passes `o->simd_open && o->simd_close` into the row's input): an art that states `x86-64-v3` through a sink without brackets silently renders the portable text, the exact silent-default shape MF_TARGET_REQUIRED was flipped to refuse for an unstated target. And the kernel path contradicts the sentence: vany.c:158,174,191 render each level's block and selector call whether or not the brackets exist (only the bracket calls are conditional), so `mf_kernel_find_any` with a bracket-less sink emits UNguarded target-dependent text.
- Fix form: make the bracket mandatory where a stated target admits a level (refuse at define, as for an unstated target), or document it as a capability fact; pass the level's token (or nothing) instead of the index; make vany's kernel decline or refuse without brackets, matching the header.

### SEAM-6 (CONFIRMED, design; effort S; blast: levels.def + memfn.h mf_level, kit-internal readers): the facts/C-spelling split (D146 add. 1) was applied to targets and families but not to their sibling, the LEVELS table
- memfn/include/memfn.h:1701-1713 `mf_level` (public, enumerated by `mf_levels`) mixes facts (`family`, `needs`, `vw`, `forbid`, `stamp`) with a C spelling (`header`, "the compiler header its text includes": `emmintrin.h`/`immintrin.h`, levels.def). D146 add. 1: "Facts and C spellings are separate structs (mf_target/mf_family vs mf_target_c/mf_family_c), so another emitter's spellings sit beside the C ones"; the manifesto's 2026-11-07 note names the target seam as the example. The level is the third member of the same table family (family -> target -> level, joined by admission) and the only one where a Rust emitter's spelling (`core::arch::x86_64`) has no place to sit.
- Same family, two key representations: `mf_level.family` is the family TOKEN string ("amd64", compared by strcmp, levels.c:55) while `mf_target.family` is a POINTER (SEAM-1). check_targets.sh:50/317 holds the strings to the table, so no answer moves; it is the round-trip shape: the level table is already text-keyed, the target table is not.
- Fix form: `mf_level_c` (header) beside `mf_level`, reached by a `mf_level_c_of` like the other two; or move `header` into the vany/ofsskip C renderers' own table. Not pcrec-facing (pcrec never reads mf_level), so no abi event.

## STANDING

**Sibling of a family.** Yes. The target seam is the third member of "a kit table whose rows cross to pcrec": (1) the `--memfn=` row names (registry §6¶8a, `opts` string), (2) the measurement set's per-machine header (`isa`/machine free text, measures_table.inc), (3) this target table (families, targets) with its sibling (3b) the levels table. Each keys its rows differently: names as text (1), free text nobody parses (2), row ADDRESSES (3, SEAM-1), family as a string token (3b, SEAM-6). They should be ONE shape: a kit-owned table of canonical TOKENS, each with a facts record and per-emitter spelling records, reached by name; the address is an in-process handle only. Proposed unification at this third member: "kit vocabulary rows" (token, facts, spellings), with one lookup-by-name rule and one listing entry.

**General form + unlocks.** The general form of U2+U3: a compile states a set of FACT TOKENS on the art (today one target), the kit derives admissions from table facts, and returns placement TEXT the host positions by structure (guard: file, region: part). Unlocks, each with its trigger:
1. Multi-target artifacts (U4): the art's target becomes a per-part token; requires SEAM-1's name identity so a part list is text. Trigger: U4's go (after K2).
2. Guard/region elision (K2's `target_dependent` fact): restores portability for the MEMFN_FORMS "none" majority (SEAM-4). Trigger: K2, or the first user report of a family-locked artifact with no SIMD form.
3. Pricing per target (D188 "read per variant's target"): the measurement set's `isa` header should name the kit's TARGET TOKEN, so a price row joins to the art's stated target. Trigger: kit pricing opens (deferred, pcrec-pilot-is-pricing-baseline).
4. A second emitter (Rust): add `mf_target_rs`/`mf_family_rs`/`mf_level_rs` beside the C structs; needs SEAM-6 first. Trigger: the plan/emit split's first non-C back end, or a serialized plan record (principle 9 test made real).
5. Cross-compile one artifact per family (D188 add. 2's workaround): already reachable (`=arm64`); a CLI loop over `--list-cpu-targets` families is the user's build recipe. Trigger: first user distributing generated C for two families.
