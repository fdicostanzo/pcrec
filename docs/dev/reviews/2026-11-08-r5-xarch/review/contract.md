## Findings

### CONTRACT-1: "MEMFN_FORMS none iff identical to the SIMD-off compile" is false at every SIMD target (three unrevised sentences)
CONFIRMED. severity: doc (contract statement a consumer is told to bucket on). effort: small (3 sentences). blast: every `-fmemfn-simd[=LIST]` artifact whose MEMFN_FORMS is "none".
Repro: `build/pcrec -p rx -o d0/out.c --pattern abc` vs `build/pcrec -p rx -fmemfn-simd -o d1/out.c --pattern abc`: d1 reads `RX_MEMFN_FORMS "none"` yet differs from d0 by the family GUARD (`#if !(defined(__x86_64__) ...) #error ... #endif`, 3 lines), the REGION open (`#pragma GCC push_options`/`target("sse2")` ... 6 lines) and close (5 lines), besides the stamp lines TARGETS and SIMD_GUARDED_BYTES. Same at `=armv8-a` (FORMS "none", guarded 0xa5).
Still-unrevised text: match_api.md §6.3.10¶4 ("`"none"` iff the artifact is byte-identical (stamp lines aside) to its own `-fno-memfn-simd` compile"; guard and region are not stamp lines); §6.3.10¶7 ("its movers half holds an `-fmemfn-simd` compile byte-identical to the default exactly where its `MEMFN_FORMS` reads `"none"`"); tuning.md §2.43¶4 last sentences ("**The stamp** is `<PREFIX>_MEMFN_FORMS`, `"none"` iff the artifact is identical to its SIMD-off compile"), which now contradicts ¶4's own revised first sentence ("its target's own text aside"). Expected: each carries the same "its target's text aside (TARGETS, guard, region, guarded count)" carve-out, or ¶4 restates the iff over the SAME target. Whether C11's movers half (the check ¶7 names) was revised to tolerate the target text is the checks lens's question; the sentence describing it was not.

### CONTRACT-2: §6.3.10¶9 "at `-fmemfn-simd[=LIST]` every artifact carries a nonzero count" is false for `=generic`
CONFIRMED. severity: doc (self-contradiction inside ¶9). effort: one clause. blast: any LIST resolving to the portable target.
Repro: `build/pcrec -p rx -fmemfn-simd=generic -o o/out.c --pattern '(?i)hello'` (also `=Generic`, `=generic,generic`): `RX_TARGETS "none:generic"`, `RX_SIMD_GUARDED_BYTES 0x0000000000000000ULL`, and the file is byte-identical (`cmp`) to the default compile. That is RIGHT by cli.md §1.24¶3 ("the portable target only when SIMD is off or the list says so") and by ¶9's own first clause ("zero on every artifact for the portable target, which is every artifact compiled at the default"), but ¶9 then says "at `-fmemfn-simd[=LIST]` every artifact carries a nonzero count, the guard and region at least". Expected wording: "at every SIMD target (a target with a family)". The ¶9 "which is every artifact compiled at the default" also undercounts the portable population (it is also every `=generic` list).

### CONTRACT-3: armv8-a carries a GUARD but no REGION; §6.3.10 para 15 (lane/u3tgt)/¶9 and tuning §2.43¶3a say every family target has both
CONFIRMED. severity: doc. effort: one sentence ("a target whose features are its family's baseline has an empty region"). blast: the one arm64 target today; every future no-needs target.
Repro: `build/pcrec -p rx -fmemfn-simd=armv8-a --emit-main -o arm/out.c --pattern '(?i)hello'`: `RX_TARGETS "arm64:armv8-a"`, guard `#if !(defined(__aarch64__)) #error ... #endif` ahead of `#include "out.h"`, and ZERO `#pragma` lines in the file; `RX_SIMD_GUARDED_BYTES 0xa5` = 165 = exactly the 3 guard lines (`sed -n 18,20p | wc -c`). Kit source: memfn/src/targets.def:94 armv8-a is `MF_NO_NEEDS` ("NEON is the baseline"), so its region text is empty.  para 15 (lane/u3tgt) says "For a target with a family, the artifact carries two pieces ... the family's GUARD ... and the target's REGION, opened before ... closed after `rx_info`", and "The portable target has neither (its texts are empty)" (implying only the portable target's texts are empty); ¶9 "the guard and region at least". Behaviour is fine (nothing to enable); the text over-promises a region. The x86 count checks out: 209 (guard) + 172 (open) + 88 (close) = 469 = 0x1d5 on `abc` at `-fmemfn-simd`.

### CONTRACT-4: an unknown-token refusal is cut at 256 bytes, so "the kit's text unchanged" (cli.md §1.24¶2, match_api §8.2¶7d) fails on a long token, and its headroom shrinks as the kit's table grows
CONFIRMED (secondary subject: P1, bfecd6143; unchanged by U3). severity: doc/maintenance (diagnostic only; refusal and exit code hold). effort: small (size the joined buffer, or emit the two kit texts separately). blast: refusal text only.
Repro: `build/pcrec -p rx -fmemfn-simd=$(printf 'z%.0s' $(seq 1 120)) -o o/out.c --pattern a` prints 263 bytes ending mid-token: `...; unknown CPU family 'zzzz...zzz` (no closing quote, no `(known: amd64 arm64)`). Cause: src/gen/memfn_targets.c `add_list` appends `"; %s"` (the family refusal) into the same `err` (n = 256 at the CLI, `pcrec_error.msg[256]` at the API), truncating silently. With a SHORT token today's message is ~150 bytes; each target or family the kit adds lengthens both "known:" lists (cli.md §2.16 promises a kit-added token needs no change to pcrec), so the cut moves toward ordinary tokens. Also note the shown text is TWO kit refusals joined by pcrec's `; `, which is defensible but is not "the kit's refusal text" in the singular the spec states.

### CONTRACT-5: limits.md §8.3 (the guarded-bytes section match_api ¶9 and tuning ¶3a cite) was not revised and now states the retired model; §8.3¶3 is falsified by the build
CONFIRMED. severity: doc (contract; a spec reader is told the opposite of the artifact). effort: small (3 paragraphs; owed in the same change, D80). blast: every `-fmemfn-simd[=LIST]` artifact.
limits.md is not in the SUBJECT's spec hunks (`git diff BASE SUBJECT -- docs/spec/` touches cli, match_api, tuning only). Its text at SUBJECT:
- §8.3¶3 "At `-fmemfn-simd` it is nonzero exactly where a SIMD row rendered: the `vrun` rows". Repro: `build/pcrec -p rx -fmemfn-simd -o d1/out.c --pattern abc` reads `RX_MEMFN_FORMS "none"` and `RX_SIMD_GUARDED_BYTES 0x00000000000001d5ULL` (469 = guard 209 + region open 172 + close 88); likewise `(?i)hello` at `-fmemfn-simd --memfn=no-vrun-w16` (FORMS "none", 0x1d5) and every `=armv8-a` compile (FORMS "none", 0xa5). match_api §6.3.10¶9 (revised) says the opposite ("every artifact carries a nonzero count, the guard and region at least") and cites this very paragraph for the per-row bounds; ¶3's bounds list has no guard/region bound, which ¶9's check sentence now adds ("plus, for a SIMD target, the guard and region's own bound").
- §8.3¶1 "whole guarded blocks (`#if <level>` ... `#endif`)": the levels carry no `#if` now (tuning §2.43¶3a "The text carries no CPU `#if`"; the v3 artifact's only `#if`s are the guard, the two region `#if defined(__clang__)` and `__has_attribute`).
- §8.3¶2 "At `-march=L` the guarded text is compiled" and "reads `0` on an artifact with no guarded block": the region compiles it at every `-march` (verified: the v3 artifact builds and answers under plain gcc/clang, `-mno-sse2`, `-mgeneral-regs-only`).
Expected: §8.3 restated in the target model (bytes depending on the target; zero exactly at the portable target; guard+region bound beside the per-row bounds).

### CONTRACT-6: `<PREFIX>_SIMD_GUARDED_BYTES` no longer describes what it counts (D174): it is nonzero on artifacts holding no SIMD code and no level guard
CONFIRMED (observable); disposition is a ruling. severity: design/doc (a caller-facing name). effort: none now (a rename rides [IFACE-PUSH]) or one sentence in §6.3.10¶8 acknowledging the name is historical. blast: the stamp's readers.
Repro: `build/pcrec -p rx -fmemfn-simd=armv8-a -o arm/out.c --pattern '(?i)hello'` reads `RX_MEMFN_FORMS "none"`, no SIMD helper, no vector intrinsic, no level `#if` anywhere, yet `RX_SIMD_GUARDED_BYTES 0xa5` (the family `#error` guard alone); `abc` at `-fmemfn-simd` reads 0x1d5 (guard + a `#pragma GCC target` region) with no SIMD text. §6.3.10¶8 was revised to "how many bytes of the artifact depend on its CPU target", which is the right meaning, but the name still says "SIMD-guarded" (the retired `#if <level>` model, limits §8.3¶1). Per memory/D174 ("caller-facing names say what the caller sees"; not retroactive) this is a NEW meaning given to an existing name in this change, so it is in scope; the cheap fix is to list it for [IFACE-PUSH] (e.g. a `_TARGET_BYTES` spelling) rather than rename now.
