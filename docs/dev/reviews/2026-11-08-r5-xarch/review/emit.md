# EMIT findings

## Findings

### EMIT-1 CONFIRMED (doc) match_api §6.3.10¶4 and ¶7 still state "FORMS none iff byte-identical", false at every -fmemfn-simd artifact
- Repro: `build/pcrec -p rx -fmemfn-simd -o s/out.c --pattern 'abc'` reads `RX_MEMFN_FORMS "none"`, yet differs from its `-fno-memfn-simd`/default compile by the TARGETS line, the 3-line family guard, the 6-line region open, the 5-line region close and `RX_SIMD_GUARDED_BYTES 0x...1d5` (21 diff lines; same for `a(b|c)+d`, `^\s+|\s+$`, `x.*yz`, and at `=x86-64-v3`).
- Expected per ¶4: "`MEMFN_FORMS` is `"none"` iff the artifact is byte-identical (stamp lines aside) to its own `-fno-memfn-simd` compile"; ¶7: "its movers half holds an `-fmemfn-simd` compile byte-identical to the default exactly where its `MEMFN_FORMS` reads `"none"`". The guard and region are not stamp lines. The check itself (tests/memfn/libc_census.py via target_text.py) and tuning.md §2.43¶4 already say "its target's own text aside"; the spec's ¶4/¶7 did not get that hunk (D80: the spec is the contract, a consumer bucketing on "none" to mean "identical to SIMD-off" is now wrong).
- Fix: add "and the target's own text ( para 14 (lane/u3tgt)- para 15 (lane/u3tgt))" to ¶4's "stamp lines aside" and ¶7's movers sentence.  tuning.md §2.43¶4 last-but-one sentence ("`"none"` iff the artifact is identical to its SIMD-off compile") carries the same stale claim right after the corrected one. Effort: two clauses. Blast: doc only.

### EMIT-2 CONFIRMED (doc/design) A `MEMFN_FORMS "none"` artifact at `=x86-64-v3` now compiles to AVX (VEX) code: "none" no longer means "SIMD-off/portable", and `SIMD_GUARDED_BYTES` ("bytes that depend on its CPU target") understates what the region makes target-dependent
- Repro: `build/pcrec -p rx -fmemfn-simd=x86-64-v3 -o s/out.c --pattern 'abc'` (FORMS "none"); `gcc -O2 -c s/out.c; objdump -d | grep -E '\bv[a-z0-9]+\b'` -> `vpxor %xmm0..`, `vmovdqa %xmm0..` in the matcher (gcc 2, clang 2; `a(b|c)+d` gcc 6/clang 26; `^\s+|\s+$` gcc 26/clang 12; `x.*yz` 2/2 VEX/BMI insns). BASE's same compile: 0. Such an object faults (SIGILL) on a pre-AVX host although every stamp but TARGETS reads as "no SIMD".
- Expected/contract: match_api §6.3.10¶4 tells consumers to "bucket on none / not-none", and ¶4/tuning §2.43¶4 equate "none" with identity to the SIMD-off compile; ¶8 defines GUARDED_BYTES as "how many bytes of the artifact depend on its CPU target". Since U3 the region ( para 15 (lane/u3tgt)) puts the WHOLE part (engine body included, not only the kit's helpers) under the target's features, so the honest portability reader is `<PREFIX>_TARGETS` alone. The design (region around the part, §10.7 para 4 (lane/u3tgt)) is ruled; the finding is that the stamp sentences that describe portability were not re-read against it.
- Fix: ¶4 says FORMS names the rendered SIMD FORMS, not portability; portability is `_TARGETS` (`none:generic` = runs anywhere); ¶8 reword "the target's own text" rather than "bytes that depend on the target". Effort: a few sentences. Blast: doc; consumers that gate deployment on FORMS.

### EMIT-3 CONFIRMED (design, build break for consumers; gcc only) The region encloses the kit's `#include <emmintrin.h>`/`<immintrin.h>`, so gcc parses the intrinsic headers under the target's `#pragma GCC target`: any LATER SSE/AVX intrinsic use in the same TU outside that region fails to compile
- Repro 1 (consumer TU): `a.c` = `pcrec -p ra -fmemfn-simd=x86-64-v3 -o a.c --pattern '(?i)hello'`; `cons2.c` = `#include "a.c"` + `#include <emmintrin.h>` + a plain function using `_mm_loadu_si128/_mm_cmpeq_epi8/_mm_movemask_epi8`. `gcc -O2 -c cons2.c` -> `emmintrin.h:1460: error: inlining failed in call to 'always_inline' '_mm_movemask_epi8': target specific option mismatch` (rc 1). clang 21: compiles. BASE's same files: gcc rc 0.
- Repro 2 (two artifacts in one TU, the D-ruled multi-artifact use with distinct prefixes): `#include "a.c"` (v3) then `#include "b.c"` (`-p rb -fmemfn-simd --pattern '(?i)world'`, x86-64) -> gcc -O2 and -O0: `error: inlining failed in call to 'always_inline' '_mm_set1_epi8'` inside `rb_mf1_ofsskip__w16`. Reverse order (b then a) compiles; clang compiles both orders; BASE compiles both.
- Cause: emmintrin.h's include guard means its always_inline functions get the target node in force at FIRST inclusion (inside the v3 region: avx2,...); a function outside the region (or in a narrower sse2 region) cannot inline them. Holds at `-march=native` (consumer ⊇ v3), so it bites exactly the default-march consumer.
- Against the ruling: match_api §6.3.10 para 15 (lane/u3tgt) and interface sheet item 4 place the intrinsic `#include` lines INSIDE the region on purpose. The argument: gcc's own headers already wrap each ISA group in their own `#pragma GCC target` when the feature is off, so the include needs no region; placing it inside only changes the target node the inline functions carry. Fix: hoist the kit's header lines to file scope ahead of the region open (pcrec placement, or a kit text field split "headers" vs "body"); add the two repros as compile cells (§8's compile cells did not include a second TU user). Effort: small (placement + spec  para 15 (lane/u3tgt) clause + 2 cells). Blast: every gcc consumer that `#include`s a `-fmemfn-simd=x86-64-v3` artifact (examples/, single-TU builds, amalgamations) and uses intrinsics or a second artifact after it.

### EMIT-4 CONFIRMED (design/doc, ruled: U3 row "x86-64 admits w16 only"; not a defect, the give-ups listed so the ruling is read with them) What the SIMD-on path gave up
- (i) Plain `-fmemfn-simd` never reaches w32 now: BASE `(?i)hello -fmemfn-simd` carried w32+w16 under `#if __AVX2__`/`__SSE2__`, so a consumer building with `-march=x86-64-v3`/`native` ran w32; SUBJECT renders w16 only whatever the consumer's `-march` (diff: the w32 helper and the `#elif` cascade deleted; FORMS `vrun@w32+w16` -> `vrun@w16`). Getting w32 back needs regenerating with `=x86-64-v3`.
- (ii) BASE `=x86-64-v3` artifacts adapted to the consumer's `-march` (w16 at default, scalar at `-mno-sse2`); SUBJECT's run AVX2 unconditionally (region) and SIGILL on a pre-AVX2 CPU; and FORMS-none v3 artifacts carry VEX code too (EMIT-2).
- (iii) BASE `-fmemfn-simd` artifacts compiled anywhere (`-m32`, non-x86) falling back to `__body`; SUBJECT's `#error` at the guard (confirmed with gcc/clang `-m32`: the guard fires first, line 19, even before the libc headers; armv8-a artifact on amd64: `#error ... it needs defined(__aarch64__)` both compilers) - the declared  para 15 (lane/u3tgt) behaviour.
- (iv) speed, minor: gcc -O3 no longer inlines `rx_search` into a consumer function in the same TU for a `=x86-64-v3` artifact at default `-march` (target mismatch; BASE inlined it; with `-march=native` it inlines again). clang inlined neither.
- Ask: no spec sentence (cli.md §1.24, tuning §2.43¶3a, match_api ¶4) tells an existing `-fmemfn-simd` caller that (i)/(ii) changed; a one-line migration note beside ¶4's `vrun@w16` example would. Effort: one sentence. Blast: doc.

### EMIT-5 CONFIRMED (design, build break for consumers; gcc) A compound artifact's own `#include <string.h>` lands INSIDE the target region, so with glibc's fortify wrappers (on by default in Ubuntu's gcc at -O2) any consumer `memcpy` after `#include`-ing a `=x86-64-v3` compound artifact fails to compile
- Repro: `pcrec -p rx -fmemfn-simd=x86-64-v3 -o cmp.c --pattern '^\s+|\s+$'` (RX_COMPOUND "split"): `#include <string.h>` at line 214, between the region open (line 24-27) and close (574-576); the only `<string.h>` in the file and out.h (stddef/stdint only). Consumer `cons5.c`: `#include "cmp.c"`, `#include <string.h>`, `void cpy(char*d,const char*s,size_t n){memcpy(d,s,n);}`. `gcc -O2 -c cons5.c` (also with `-D_FORTIFY_SOURCE=2`/`=3`) -> `bits/string_fortified.h:26: error: inlining failed in call to 'always_inline' 'memcpy': target specific option mismatch` (rc 1). clang 21: rc 0. Same consumer over the `-fmemfn-simd` (x86-64, sse2) compound: rc 0 (the narrow region is a subset of the default ISA). With `--emit-main` the libc includes are hoisted to lines 22-23 ahead of the region and the driver builds.
- Scope: of 52 SUBJECT artifacts scanned (ci/lit/alt/dot/vm/cmp, the 13 answer-run patterns at x86-64 and v3), only the compound (non-`--emit-main`) has a libc `#include` inside the region; spec  para 15 (lane/u3tgt) places the region "before the artifact's first function", and the compound's second part's preamble include follows the first part's functions.
- Fix: same shape as EMIT-3, pcrec-side and smaller: hoist every non-kit `#include` of the artifact (the compound parts' preamble) to file scope ahead of the region open, as `--emit-main` already does; add a compile cell "consumer TU uses memcpy/intrinsics after including a v3 artifact, gcc -O2". Effort: small. Blast: every gcc consumer of a v3 compound artifact by `#include` (a separately compiled .o is unaffected).
