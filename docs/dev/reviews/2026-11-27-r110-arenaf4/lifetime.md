# CRITIC lifetime: arenaf4 (r110)

## Findings

### LIFE-1 (CONFIRMED by reading; design/doc; population 0 today) the count cannot see a REFUSAL through a lent channel, so "allocates OR REFUSES" (FIX SHAPE, Discipline row "K163 class") is true only of the allocating half
- Where: src/core/arena.c:64 `pcrec_err_chan` + its refusal-only callers; docs/design/arena_scopes.md D-7 "THE ONE CHANNEL ACCESSOR", "F4 AS A D203 FIX" FIX SHAPE ("catches any future member that allocates or refuses through an Arena or a StrBuf carrying a `.cx`"), Discipline table row "K163 class" ("an allocation or refusal through a lent Ctx's channel"); internal.h Ctx.lent comment ("an allocation or a refusal ... counted").
- Mechanism: a refusal is `pcrec_ctx_fail(pcrec_err_chan(cx), ...)`: the accessor counts, then `pcrec_ctx_fail` longjmps to `cx->jb`, which for a lent Ctx is the OUTER compile's setjmp. `pcrec_ctx_unlend` (compound.c walk_part) never runs, the count is never read, and the inner compile strands exactly as K163 did. The count is a NORMAL-RUN detector: it works for an entry that is called (and counted) on runs that do not fail. A REFUSAL-ONLY entry is "used" only on the run that fails, so it is invisible in every normal run and strands when it fires.
- Population of refusal-only channel uses (grep): arena.c `reg_fail` (:97; reached from `scope_check` in pcrec_scope_close/_malloc/_free/_sb/_arena, scope_open's child test, scope_close's post-condition, pcrec_scope_check_closed, pcrec_arena_hold-while-open), `pcrec_scope_calloc` overflow (:198); sb.c `sb_grow` abort_over (:51, ahead of the counting line), `sb_simd_fail` (:229, from simd_open/close and scaffold_open/close), `pcrec_sb_adopt` (:497) = 5 sites; plus the direct `sb->cx` refusals the design leaves "outside the count": enc.c 5 (`git grep -c -E "pcrec_ctx_(fail|nomem)\((sb|a|s->a)->cx" -- src` = enc.c 5, vm_stmt.c 11); plus every direct `pcrec_ctx_fail(cx, ...)` in the tree, should an outer Ctx pointer ever reach the inner by a struct (the design's own caveat: "`meas` hands the inner compile outer Job pointers"). Non-failing non-allocating registry ops on an outer arena (pcrec_scope_close, pcrec_scope_free, an sb append that fits, B13) are likewise uncounted.
- Failure scenario (future member): the inner compile receives an outer StrBuf (or a scope on the outer arena) and only appends within capacity / closes a bracket; one day its SIMD bracket is unbalanced (sb_simd_fail) -> longjmp to the outer point -> the inner Job, arena, dmemo strand; no count, no test sees it outside LSan; `lent` is LEFT TRUE on the outer Ctx (nothing clears it but the next attempt's memset; the FIT_FORCE_NEXT arm resumes the attempt without the memset).
- Expected vs observed: the design claims a counted, refused class for allocations AND refusals; the code delivers it for allocations only.
- General form + unlock (cheap, 3 lines): the stranding IS observable at the outer recovery point, because `lent` survives the longjmp: in compile_driver's `setjmp` arm, before `fit_walk`, `if (pcrec_ctx_lent_p(&cx))` -> an internal-error diagnosis "[K163] a refusal crossed a lent window" (it cannot un-strand, but it turns every refusal-shaped member, counted entry or bare `pcrec_ctx_fail`, from silent into a named diagnosis that W6/W7 and the sanitizer runs read), and clear it there. That covers every refusal through the outer Ctx whatever path reached it (accessor or not), closing the class at the one recovery point rather than at each entry. Without it, the doc fix: narrow the FIX SHAPE/Discipline wording to "allocates" and list the refusal-only entries as covered only by the member's allocating companion.
- Effort: doc 2 lines, or code ~5 lines + one W7/W6 control. Blast radius: none today (no inner handle on the outer channel after F4). D203: class = "a recovery point's channel reached from inside a nested recovery point"; house rule = src/core/CLAUDE.md error paths (a refusal lands at the recovery point that owns the stranded state); siblings: 5 (arena.c/sb.c) + 16 (enc.c 5, vm_stmt.c 11) above.

### LIFE-2 (CONFIRMED by reading + grep; maintenance/check-design; effort small) four of the five UNCONDITIONAL counting lines have no control: delete one and no gate, scanner rule or sabotage goes red
- Where: src/core/arena.c:105 (`rec_take`), sb.c:53 (`sb_grow` past capacity), sb.c:473 (`pcrec_sb_take`), sb.c:808 (`pcrec_sb_render_prefix`); the fifth, arena.c:277 (`pcrec_arena_alloc` entry), is controlled only because S3653's plant copies through `pcrec_sb_fragf` -> `pcrec_arena_alloc` on a first-fit block.
- Mechanism: the corpus's lent population is 0 by construction after F4 (W7 lent window: "0 trial points", my run below), so the count has nothing to count on any shipped path; the ONLY thing that makes a counting line observable is a plant that routes an inner use through that very entry. S3653 routes through one entry. The scanner's D-7 rule checks that REFUSALS take `pcrec_err_chan(` (S255/S256 neuter the refusal, not the count); no rule checks that the five named entries call `(void)pcrec_err_chan(` unconditionally, nor that a NEW allocating entry in arena.c/sb.c does (C11 was exactly that miss: rev 2 counted two). This is learnings §3's "a population nobody counts" (K35 shape): the property r103 C11 made a FIX-NOW is unguarded at 4 of 5 sites.
- Failure scenario: a later edit (say a fast path in `sb_grow`, or moving `rec_take`'s count below the calloc as "only on failure") drops a count line; every gate stays green; a future inner member that grows an outer StrBuf or takes an outer hold/scope record is not counted and, when it fails, strands (K163 again), exactly the "hid from W6" shape the design names.
- Fix (cheap, static, no new run): a scanner rule in tests/core/scratch_builder_check.py: COUNTED = {arena.c: pcrec_arena_alloc, rec_take; sb.c: sb_grow, pcrec_sb_take, pcrec_sb_render_prefix}; each must contain `(void)pcrec_err_chan(` before its first malloc/calloc/realloc/strdup/sb_store/pcrec_arena_alloc call; and any OTHER function in arena.c/sb.c that calls malloc/calloc/realloc/strdup (or `sb_store`) directly is a finding unless it calls a COUNTED entry first (today: `pcrec_scope_malloc` passes through rec_take; `sb_store`'s only caller is render_prefix). Fixtures: a planted deletion in each must FAIL. Alternatively a second sabotage per entry, which is heavier (each needs its own plant route).
- If the coordinator wants it CONFIRMED at runtime: PLANT = S3653 + delete arena.c `(void)pcrec_err_chan(a->cx);   /* D-7: a use, counted while lent, block or not */` in `pcrec_arena_alloc`; expect `^abc|x+$` (-p rx) to exit 0 (count misses the first-fit copy), proving the one control reaches that line; the same deletion in rec_take/sb_grow/sb_take/render_prefix on S3653 changes nothing (no route), which is the finding.
- Blast radius: none today; protects the class claim. D203: class = a guard with an empty population and a single route (K35); house rule = learnings §3 "a check whose population is 0 must have a control that reaches each site"; siblings: 4 uncontrolled counting lines of 5.

### LIFE-3 (CONFIRMED at runtime; check-design; effort small) the W7 lent window has no tree on which it SWEEPS: its "pre-fix control" role is unexercised; on S3653 it goes red for the count's reason, not for a stranding

- Observed vs expected: the row is described as the control that SEES a lent-window stranding (C0(d)'s 54 strandings at the copy); on every available tree it either has 0 points (subject) or cannot run its sweep because the count already refused the profiling compile (plant). - Blast radius: test-only. D203: class = a pre-fix control never run against a pre-fix state (K35 "populations nobody counts"); siblings: the W7 control row's planted hand-kept strand (PASS, has its own plant) is the right shape; the lent row lacks the equivalent.

### LIFE-4 (design; GENERAL FORM + UNLOCK; SIBLING OF A FAMILY) K163 is the second member of "a nested compile's state crosses the part seam into the outer's lifetime", and the general form is a STATIC seam rule, not only the runtime count
- Family (named): (1) K155 / F1 R2 / S3580: the part's heap TEXT lived past a later refusal with no owner -> fixed by an outer hold reserved before the part compiles (S3580 drops the store); (2) K163 / F4 / S3653: the part's FORMS copy was made through an OUTER handle (`PcrecPartFacts.into`, an `Arena *`) -> fixed by the same hold shape plus the count. Both are "the part seam carries a lifetime it should not": a result without an outer owner (1), an outer handle into the inner (2). F1's hold and S3580 are the same member at two dates, not a third; this is the third occurrence of the shape at the same seam if K155's original `AOwn` text counts separately.
- The seam today (checked): `PcrecEmitIn` and what it reaches for a part (`PcrecPartFacts`, `PcrecMeasInherit`, `PcrecDeriveReport`, `PcrecHarnessOptions`, `PcrecEntryReq`) carry NO `Arena *`, `StrBuf`, `Scope`, `Ctx *` or `Job *` field after F4 (awk over the struct bodies in src/core/internal.h: zero hits); `meas` hands only const data pointers (KsMeasSet, mf_measures, PcrecFindChain copied by value at rxt_find.c:313, mf_analysis read-only: memfn/src writes no field of it); `PcrecPartFacts.hold` is a store-only `void **`. So the class's population is 0 by a STRUCTURAL fact the code never checks.
- General form: "a nested compile's seam types carry no outer error channel" as a scanner rule (tests/core/scratch_builder_check.py, the readers-rule style): the struct bodies of PcrecEmitIn, PcrecPartFacts, PcrecMeasInherit, PcrecDeriveReport, PcrecHarnessOptions hold no field of type Arena*/StrBuf/Scope/Ctx*/Job*/mf_arena (fixture: a planted `Arena *into;`, which is exactly S3653's first edit, so S3653 would go red statically too). It catches BOTH the allocating and the refusal-only members (LIFE-1's gap) before any run, where the count catches only allocating ones at run time. The count stays as the runtime net for a handle that arrives by a route the scanner cannot see (a function pointer's closure: `.derive` is a function pointer, today pcrec's own derive.c, which writes static strings).
- U8's trigger ("a second cross-compile member, or a nested compile that must allocate into the outer"): observable today only for an ALLOCATING member (the count's internal error); a refusal-only member is not observable (LIFE-1), and "must allocate into the outer" is a design-time event nobody reads. With the seam rule, the trigger becomes a scanner finding someone must waive (an ALLOW row naming the field = the U8 trigger firing, visibly). Recommend: state U8's trigger as "an ALLOW row in the seam rule", which is observable by grep.
- Effort: scanner rule ~25 lines + 1 fixture. Blast radius: none (population 0). D203: class = outer lifetime reachable through the nested-compile seam; house rule = src/core/CLAUDE.md error paths + D-4's holder rule; sibling count: 1 seam (the only nested compile inside a compile is compound.c part_compile; `pcrec_compile_driver(` callers in src = 4, of which 3 are top-level entries: compile_defs.c:47, facts_dump.c:230, callouts_dump.c:151).

### LIFE-1 addendum (same finding, two more claim sites): docs/dev/known_issues.md K163 "Fixed" paragraph ("every refusal through an Arena's or a StrBuf's `.cx` ... reads the channel through `pcrec_err_chan`, which counts a use while the Ctx is LENT ... a future member that allocates or refuses through a `.cx` across the nested compile is caught") and src/core/internal.h's Ctx.lent comment ("an allocation or a refusal through an Arena or a StrBuf ... counted") carry the same overclaim; the refusal is counted but never read (the longjmp lands at the outer point before `pcrec_ctx_unlend`).
