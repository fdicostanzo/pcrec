PAR-2 CONFIRMED (speed, medium-low): the 120 s timeout is per-runner and SEQUENTIAL, not a shared deadline. scripts/m6read_check_sab_anchors.py: `for rel, pr in procs: ... pr.communicate(timeout=120)` -- each wait starts when the previous one returns. Repro (copy, 3 runners with `exec sleep 1000` as their --plant-check): pass took 376 s (~3 x 120 + 14 s mech half) and then went red correctly, naming all 3 ("--plant-check TIMED OUT (120 s)"). 4 hung runners = ~494 s inside `make test-codegen`. The message says 120 s, the pass costs up to 4x that. Fix: one shared deadline (deadline = time.time()+120; communicate(timeout=max(0,deadline-now))), since they all started together.

PAR-3 CONFIRMED (answer/hang, medium): a hang whose process is a CHILD of the runner bash (not exec'd) never surfaces. Repro (copy; run_g2_pres.sh --plant-check = `sleep 1000`, no exec): pass printed nothing and was still running at my 400 s cap (timeout rc 124). Cause: on TimeoutExpired the pass does `pr.kill(); pr.communicate()` -- kill hits only bash; the orphaned sleep holds the stdout/stderr pipes open, so the second communicate() blocks until the grandchild exits (unbounded; no timeout on it). Every current runner `exec`s python3 so today's runners are safe, but a future edit (a wrapper, `timeout`, boxlock, a non-exec'd python) makes it a silent infinite hang of make test-codegen, defeating the pass's own 120 s guard. Fix: Popen(..., start_new_session=True) and os.killpg(pr.pid, SIGKILL) then communicate(timeout=5) (or just close the pipes).
