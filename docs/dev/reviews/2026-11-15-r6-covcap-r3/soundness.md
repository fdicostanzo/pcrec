# SOUNDNESS — covcap-r3

## Findings

### SOUNDNESS-1 — the walk past `L` is unbounded work for a decision already lost (compile cost; §3.1 "TERMINATION AND COST")
CONFIRMED (rows counted by applying the rule; the rev-3 walk itself does not exist). Severity: speed (compile time) / design. Effort: small. Blast radius: every compile with an anchored machine reaching C7 whose first accept is deep and whose rows are many.
- Repro: `[ab]*a[ab]{10}-{2000}` today reaches C7 (`kp.sh`: `fixed-width`, an anchored machine exists, 1.5 s compile). Applying §3.1 to its emitted `-fno-scan-edge` anchored machine (`soundness/walkcost.py`, a python walk over the same rows): 4,048 states, `L = 11`, `k = 2011`, max 4,047 rows per depth, 6.1 M row visits = 1.56 G byte steps (`kn_walk` loops 256 BYTES, not classes, `known.c:149`). `[ab]*a[ab]{8}-{300}`: 812 states, L 9, k 309, 51 M byte steps.
- "`kn_walk` as it is, without `KN_CAP`" keeps its LINEAR successor dedup (`known.c:154-155`): per depth rows x 256 x rows, about 4e12 compares for the first witness (hours). Even with a hashed dedup it is ~1.5e9 `kn_step` calls on one compile. §3.1's "O(k x rows x classes), bounded by the machine" is true only as a bound (V <= `PCREC_ANCHORED_MAX_STATES` 4096, k <= MAX 4096, x 256 = 4.3e9 steps) and no row of §5.1 has a witness of this shape (the compile-time census row reads the population, where rows are few).
- The work past `L` decides nothing: once a depth below the first accept has two sets, C8 declines (`exact_len < k`) whatever `k` is, and `exact_len = L`. The only reader of the continued walk is C7's `why`/`k` ordering (C7 fires before C8) and §5.2's `k` (read from the `width` fact anyway).
- Also: §3.1 says the walk "goes on to find k ..., keeping only the sets, never the rows, past L" — finding `k` requires stepping the rows, so the sentence cannot be built as written.
- Fix: end the walk at `min(L, first accept, MAX)`; on `L` reached first, decline as `exact/machine-inexact` (C7's `fixed-width` keeps reading the `width` fact or moves after C8); state the dedup as a per-(state,count) mark, and add this witness (or the 812-state one) to §5.1's compile-cost row.
- Cite: `known.c:126-167`, design §3.1 TERMINATION AND COST, §3.3 C7/C8.

### SOUNDNESS-2 — outcome 4 is unreachable: the anchored machine's own state ceiling (4096) ends the exact stretch first, with a cliff; the `a{4097}` witness and plant (e) cannot work
CONFIRMED. Severity: design (G4 / D198 (c),(g) claim) + test (a delivery-bar row that is red in the correct build, a plant that cannot flip). Effort: small to state, a ruling to fix. Blast radius: §0 G4 form, §3.1 outcome 4 and the limit's derivation, §5.3 `facts` row `a{4097}`, §5.4 plant (e), §8 inventory, §9 Q2 (owner text).
- Repro (`kit/kp.sh`, today's trace build): `a{1000}`, `a{4094}`, `a{4095}` -> `fixed-width` (an anchored machine exists, C4 holds); `a{4096}`, `a{4097}`, `a{5000}`, `[ab]{4097}` -> `anchored-A` in both encodings (no anchored machine). The cause is `PCREC_ANCHORED_MAX_STATES` = 4096 (`src/core/limits.def:186`, "the optional anchored match-here machine's own DFA state ceiling"), applied before the scan-edge collapse.
- Consequences, each by the design's own rules: (i) `a{4097}` fails C4, so §3.3 states it `exact_len 0` (why `anchored-A`); §5.3's committed value `4096:` + 4096 x `97` is wrong in the CORRECT build, and plant (e) ("states 0") leaves it unchanged -> the plant never flips. (ii) Outcome 4 cannot fire at all: every row the walk holds is live, so from any row an accept is reachable within V - 1 steps; hence `k <= V - 1 <= 4095 < MAX` on every machine that exists (straight lines: `a{4095}` is the longest). `PCREC_MAX_EXACT_SPAN` is therefore never the binding limit and `fixed-width/over-max` has no witness. (iii) There IS a cliff, at 4096: `a{4095}` would state 4095 positions and `a{4096}` states 0 -- exactly the collapse §2/§9 correction 1 tell the owner rev 3 removes ("past the limit nothing collapses: the first 4096 positions are still proven"). (iv) G4's "ONE length limit on the exact path" and §8's inventory omit the binding one (`PCREC_ANCHORED_MAX_STATES`, kind "compile budget"), which also bounds rows per depth (SOUNDNESS-1).
- Fix options (owner/manager): name `PCREC_ANCHORED_MAX_STATES` as the exact path's real limit (drop `PCREC_MAX_EXACT_SPAN`, whose derivation then sits on the wrong row), or make outcome 4 reachable by a different MAX below the ceiling; either way re-pick the `MAX + 1` witness (it must have an anchored machine, e.g. a MAX below 4095) and correct §9's owner text.
- Cite: `src/core/limits.def:186`; design §0 (G4 form), §3.1 outcome 4 + derivation, §5.3 `facts`, §5.4 (e), §8, §9 correction 1 and Q2.

### SOUNDNESS-3 — X0 re-pointed to the listing (§3.6 Q2's first control) reads TRUE declined-row statements RED, and its only fix blinds it to overstatement
CONFIRMED. Severity: test/design (the one independent control on the listing's half of the reading). Effort: small-medium. Blast radius: §3.6 Q2 bullet 1, §5.1 X0 row, §3.3's listing rows for compiles that fail C7..C14.
- §3.3 states `exact_len` and `S_0..` for every compile past C1-C6, covers or not; ¶7c's claim is about prefixes of matches of ANY length. `x0.py stated` (the instrument the design re-points) explores `len(S)` = `exact_len` levels with horizon `len(S)` and `open_h` off (`x0.py:851`, `explore` default): a byte is "allowed" only if a complete match ends within the stated length.
- Repro: rows with the rule's TRUE values (`kit/machine.py` reads span 2 exact 2; libpcre2 agrees: `a`, then `b` or `c...`): `- ab|ac{10} 2 61;62,63` -> `RED {"kind":"exact","d":1,"pcre":[98],"stated":[98,99]}`; `- ax|ay[a-z]{8} 2 61;78,79` -> RED likewise (both decline today at C10 `end-at-k`, so both are listing-only rows under rev 3). Covers are fine (`ab|abc|ad` green; an overstated `62,63,64` RED), since a cover's matches all end at `k = exact_len`.
- The obvious repair (`open_h`, horizon reached = UNKNOWN) removes every byte with no short witness from the comparison -- and an OVERSTATED byte has no witness at all, so it becomes unknown and is never compared: the control cannot see the failure it exists for on non-cover rows. Passing horizon `k` instead does not help either (`ab|ac{10}`: k = 2).
- Also: `stated` checks only the sets; ¶7c's second half ("no match ends before d+1") is checked by X0's `part1_cover` tails, which runs on covers only. On listing-only rows nothing independent checks it.
- Fix: either restrict the listing's stated stretch (and X0's re-point) to covers, or give the instrument an unbounded witness search (x0pcre's Q with a horizon derived from the pattern's max width, decline on unbounded) and state which rows it can and cannot check (K35: count the uncheckable ones).
- Cite: `docs/design/kit_proof/x0/x0.py:231-282, 835-863`; design §3.3 THE LISTING, §3.6 Q2, §5.1.

### SOUNDNESS-4 — the design's own §5.3 `facts` witness `a{30}(?:b{30}c|d)` reads RED under the re-pointed X0 (SOUNDNESS-3, on a committed row)
CONFIRMED. Severity: test (the delivery bar's X0 one-off fails on a correct value). Effort: folds into SOUNDNESS-3's fix. Blast radius: §5.1 X0 row over the census population; §5.3 facts rows.
- Repro: `x0.py stated` (X0PCRE = kit/x0pcre, libpcre2 10.46) on `- a{30}(?:b{30}c|d) 31 61x30;62,64` (the value §5.3 commits, which the rule and libpcre2 both give: `a^30` then `b` or `d`) -> `RED {"kind":"exact","d":30,"pcre":[100],"stated":[98,100]}`: `b`'s only witnesses are 61 bytes long, past the horizon 31. `a{40}(?:b|cc)` (witness one byte past) reads green, so the failure is horizon-length dependent, not shape dependent: every stage-1 listing row whose stretch stops at a branch-free first accept with longer siblings is exposed (k = first accept, not every match's end).
- Cite: design §5.1 X0 row, §5.3 `facts`; `x0.py:851`.

### SOUNDNESS-5 — "Its controls, none sharing its code" is false for the `-fno-scan-edge` listing compare; it cannot see a fault in the rule, liveness or accept forms
CONFIRMED by reading. Severity: design/doc (control accounting, learnings §3). Effort: one sentence + K35-style statement of what each control can see. Blast radius: §3.6 Q2, §5.1 "scan-edge arm compare" row, §9 Q1's owner text ("checked ... against a second form of the same machine").
- Both arms run the same `kn_walk` (set rule, `kn_acc_any`, `kn_vnl`), the same `kn_liveness`, and the same C9-C11 rows (`known.c:52-167, 283-326`); only `kn_step`'s scan branch and the machine's shape differ. A fault in the per-depth rule, in liveness, or a missing accept form moves both arms identically, so the compare stays equal. Of §5.4's plants, (a), (b), (c) and (e) are all invisible to it (each is in shared code); it controls only the virtual-state half, which the design does name, but then counts it among controls "none sharing its code".
- C14 (`pcrec_cover_proof_diff`) is likewise not a control on the reading: it checks the kit's text EQUALS the statement, so a wrong statement passes it (S1131's own mechanism: the hull `ac|bd` stated exact goes through C13/C14 and is caught only by answers).
- What is left independent of the reading on every user compile: nothing (as the design says); in the build: libpcre2 answers on the `answer` witnesses, `test-axes` on corpus covers, and X0 -- whose listing half is broken (SOUNDNESS-3/4).
- Fix: list per control what it shares and which plants it can see; do not present the scan-edge compare or C14 as independent of the reading.

### SOUNDNESS-6 — plant (d) reaches `window_bounds_check` only after writing past `mf_wspan.set[]`
CONFIRMED by reading (the plant is not built). Severity: test (a sabotage row whose red is preceded by an out-of-bounds write; nondeterministic in a plain build). Effort: small. Blast radius: §5.4 (d).
- With C15 removed and `k` = 40, `cover_window` runs `pcrec_memfn_wpos_bits(&sp[0], d, e->set[d])` for d < 40 (`known.c:473`) into `mf_wspan.set[MF_WSPAN_POS = 32][32]` (`memfn/include/memfn.h:682`) -- 256 bytes past `sp[0]` (past the arena block when no context side is stated, n = 1) -- and only then calls `pcrec_memfn_window_stated` -> `window_bounds_check` (`known.c:481`, `memfn_sites.c:578-603`). The design's "goes red (`window_bounds_check`'s internal error)" is the likely but not guaranteed outcome; under ASan it is a heap overflow first. (At stage 1 `MkEnd.set` is `[MF_MAX_SPAN_POS][32]`, `known.h:27`: the "counted" `MkEnd` of §8 must also be sized, or C8's `memcpy` overflows first.)
- Fix: state the bounds before writing (check `k <= MF_WSPAN_POS` at the top of `cover_window`, or move `window_bounds_check` ahead of the position writes), so the plant's red is the named internal error.
