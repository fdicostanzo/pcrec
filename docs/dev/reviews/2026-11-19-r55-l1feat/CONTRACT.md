## Findings

### CONTRACT-1 — CONFIRMED — doc (D80) — tuning.md §2.27¶2 now states a derivation the build contradicts ("A lookaround's body is not descended into")

- Spec at SUBJECT: `docs/spec/tuning.md` [2.27¶2] "How the set is derived": "...a one-byte class is a singleton ... a node that consumes nothing (... a lookaround) contributes the empty set to the byte analysis ... **A lookaround's body is not descended into**: a lookbehind's bytes can lie before the window." Since 1e2a4f5db the walk DOES read positive lookaround bodies (E-5i's guards) and the TOP set step adds every narrowed one-byte run position to the necessary set, so the set gains members that no rule in ¶2 produces (a two-member class `[bc]` narrowed by `(?=b)` contributes `b`).
- Repro (caller-observable stamp moves): `$K/pc base|subject --features all --emit-facts=byte --pattern 'a(?=b)[bc]'` → base `req_set 97`, `RX_REQ_BYTE "97"`, `RX_REQ_RUN "none"`; subject `req_set 97,98`, `RX_REQ_BYTE "98"`, `RX_REQ_RUN "6162@1"`. Same on `ab[xy](?=(?<=x)y)[xy]` (base set 97,98 / RX_REQ_BYTE "98"; subject 97,98,120,121 / "120" — a NESTED lookbehind body is read too).
- tuning §2.28¶3 ("How the run is derived") likewise lists a lookaround only as a node that "does not [break the run], the bytes on its two sides abutting" and never states the narrowing (its worked examples are the spec's way of stating run values: `a(?=b)[bc]` would read `a[bc]` by its rules; the build reports `ab`), nor that the walk can prove `dead`.
- D-13 (span_arms §14.3) lists tuning §2.27¶4 and §2.28¶1 as "checked unchanged" but never ¶2/¶3; the subject's only spec hunk is facts_listing.md. The values are not promised, but ¶2's sentence is a false positive statement of the derivation, and D80 asks the contract to describe what a caller can observe (RX_REQ_BYTE/RX_REQ_RUN moved).
- Fix: rewrite §2.27¶2's last sentence (a positive lookaround's fixed bytes narrow the consumed positions they overlap and a narrowed one-byte position joins the set; a lookaround never adds a byte nobody consumes, so a lookbehind's out-of-window bytes stay out) and add the narrowing + `dead` clause to §2.28¶3 with one example (`a(?=b)[bc]` reports `ab`). Effort: 2 sentences. Blast radius: spec only.

### CONTRACT-3 — CONFIRMED — design/doc (medium) — `req_set`/`req_set_maxoff` (PF_CORE, "reading no prior and no other fact's choice") now depend on the run CHOICE, whose ties the byte-rate breaks: the necessary set differs by encoding on an ASCII pattern

- Code: `src/facts/req.c:1587` `rb_top_set_step(set, run)` adds only the one-byte positions of the CHOSEN run (`rb_top` -> `rn_better`, which reads `w->rate`). A narrowed position in a losing candidate run never joins. `src/facts/facts.def:52-53` keeps both facts `PF_CORE` (def at facts.def:16: "a walk of the sealed IR, reading no prior and no other fact's choice"); src/facts/CLAUDE.md: "the SET stays CORE (no prior)". ¶4a's `look` text says "every one-byte run position joins the necessary set" (reads as unconditional).
- Repro: `$K/pc subject --features all --emit-facts=byte,utf8 --pattern 'x(?=y)[yz].*qr'` → byte: `req_whole_run 7172 rate:builtin-prior`, `req_set 113,114,120` (no `y`); utf8: `req_whole_run 7879 rate:none(utf8)->rightmost`, `req_set 113,114,120,121`. BASE gives `113,114,120` under both. So the set (and `req_set_maxoff`) is now a function of the byte-rate prior / `--analysis` bundle, while its `why` carries no `rate:` token (¶4 says `rate:` is written "for a fact CHOSEN by a byte-rate rule"). Same on `x(?=y)[yz].*q(?<=q)r`.
- Sound either way (a subset), so severity is design/doc, not answer: but it breaks the CORE/DERIVED split the facts layer enforces and makes `RX_REQ_BYTE`/the VM whole-set pre-check (tuning §2.29¶3, one memchr per set member) vary with the prior in a way no spec sentence states.
- Fix (either): apply the set step to EVERY narrowed one-byte consumed position (at the meet in `rr_cat`, design D-3's CAT-SET as first written), which makes the set choice-free and strictly larger; or reclassify `req_set`/`req_set_maxoff` PF_DERIVED with a `rate:` why and say in ¶4a "of the chosen run". Effort: small (first form: move the step, ~15 lines + the census model). Blast radius: req_set values on lookaround patterns with two candidate runs.
