## General form + unlocks
Yes: this is the first per-compile override of a `selection knee` row of limits.def (the class tuning.md §2.20 / limits.md §8b¶1 describes: rows that steer a lowering, not acceptance). Its shape (an `int` field, 0 = the row's default, legal range refused never clamped, dial cell loses to an explicit value) is exactly the general "knee override" the three `--tune` knees of §8b already lack a per-knee spelling for. General form: one declared table of overridable selection knees (row name, legal range, the conjunct/decision that reads it), one `pcrec_options` slot list (or `--knee=NAME:N`) and one reader `knee_value(cx, ROW)` replacing per-knee `cover_width_limit`-style helpers. Unlocks: (1) timing sweeps of any knee without a rebuild (cover_cap §11.4's width cells are the first instance) -- TRIGGER: the second knee a timing plan wants to move per compile; (2) a dial cell per knee read through the same table (§11.7 unlock 1) -- TRIGGER: §11.4 measuring a width that differs by regime; (3) a class-only width (EMITTED-2's remedy, §9 Q8) becomes a second row, not a special case -- TRIGGER: §11.4's dense near-miss cells losing; (4) stamping/recording overrides once, generically, if the no-stamp ruling is ever reversed. ### CONTRACT-1 CONFIRMED (doc/design; severity doc on this branch, answer-neutral) -- the option cannot RAISE the width above 32 on this branch, yet every spec hunk promises it does, and the decline is named `width-limit` even when the caller's limit admits the cover
- Repro: `build/pcrec --emit-facts -p rx --window-search-width=4095 --pattern '[0-9a-f]{33}'` -> cover row `byte width-limit 33 33` (same at N=33). Expected per tuning.md §2.56¶1 ("It sets the widest fixed-width match the window search reports"), §2.56¶3 ("Settable both ways ... higher than the default"), limits.md §3.12¶3 (legal range to 4095, "no wider fixed width is ever reported, since the anchored machine's ceiling ends the stretch first"), lib/pcrec.h:1475-1481 ("Settable both ways, not raise-only"): `cover 33 33`.
- Cause: src/gen/known.c:295-296 `cc_fits` still ANDs the kit's three shape bounds (`MF_WSPAN_POS`=32, `MF_WREACH`=64, `MF_MAX_FWD`=33) with the caller's width; these lift only with list B (cover_cap.md §11.1 "THE SEAM IS THREE KIT BOUNDS", §11.5 ASK 1). So for N in 33..4095 the option is a no-op and the listing blames `width-limit` (kind `limit`, the CALLER's limit) for a kit-seam decline: D174 -- the name describes a cause the caller did not set.
- Mitigation already ruled: the branch lands only jointly with B (COMMON), so at landing the kit bounds should be >= 4095 and the spec becomes true. Ask: (a) the joint landing's gate must include a probe that N=33 admits `[0-9a-f]{33}` (a `W` kitproof row at width > 32 that reads `cover`), else a partial B ships a lying spec; (b) until then, either split C15's two reads into distinct details (`width-limit` vs e.g. `width-limit/seam`, facts_listing §4.5¶2 permits `id/detail`) so the listing never names the caller's limit for a kit bound, or state the interim in §2.56. Effort: small (one detail string, or one W row). Blast radius: listing readers, kitproof W rows, anyone timing widths > 32 before B (cover_cap §11.4's 36/40/64/500 cells would silently time the ENGINE on both sides if run on a part-A build).
- file: src/gen/known.c:290-297; docs/spec/tuning.md §2.56¶1,¶3; limits.md §3.12¶3.
