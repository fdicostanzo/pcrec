- Where: tests/kitproof/run_cover.sh:146-147 (review tree) — `"$CC" -O1 -std=gnu11 -I"$root/lib" -o "$tmp/width_opt" "$here/width_opt.c" "$root/build/libpcrec.a"`.

### CONFORM-4 `window_search_width` is inserted mid-struct in `pcrec_options`, against lib/CLAUDE.md's APPEND rule (CONFIRMED by reading)
- Where: lib/pcrec.h:1460-1469 (review tree): the field sits between `vm_entry_shape` and `frame_capacity`; `pcrec_options` runs on to :1742 (`measures`, `measures_dirs`, `allow_code`, `memfn_simd`, ... after it). docs/spec/match_api.md §8.2 mirrors the same position.
- Rule: lib/CLAUDE.md:10 "New `pcrec_options` fields are APPENDED so no existing offset moves (memset-zero = old behaviour byte for byte)."
- Consequence: every field from `frame_capacity` to the end changes offset; a caller object built against the base header and linked with the new libpcrec.a reads `frame_capacity` where `window_search_width` now is (a nonzero frame capacity, e.g. 64, then reads as width 64 — legal, so NOT refused: the C15 width silently becomes 64 instead of the default, while every later field shifts too). Pre-1.0 this is allowed only as a deliberate step (memory pcrec-abi-changes-pre-release: "ritual, not avoidance"); nothing in the branch records it as one.
- Mitigation for the manager's ruling: the precedent the design names (§11.2.1, `vm_entry_shape`, f135ab14c) was inserted at this same spot, so the rule has drifted once already; the design text says only "`int window_search_width;` in `pcrec_options`" and does not rule the position.
- Expected: append at the struct's end (and §8.2's listing at its end), or a recorded ruling that pre-1.0 mid-struct insertion is accepted and lib/CLAUDE.md's rule amended.
- Severity: design (library ABI). Effort: move two hunks. Blast radius: library embedders built against an older header; none for CLI or artifacts.
