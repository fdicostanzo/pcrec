Repro: the depth-128 atomic-star nest (`'(?>a|b|'*127 + '(?>a|b|c)*' + ')*'*127`, raise 1, features all), compiled by a growth_driver built from the subject (`gd one 0 0 1 all 0 PAT`), N copies at once on the 16-thread 7700X (load ~3.5 from others): driver `cpu=` alone 1.87 s; N=2 1.81/1.82; N=8 1.86..3.40 (two of eight over 2.7); N=16 3.21..3.53. Today's margin (300 s vs 45 s inflated) does hold; the wording is what is false.

## SIBLING OF A FAMILY
Growth is not the third member, it is at least the fifth, and the family already has two mechanisms, with the house's derivation rule written down for one of them:
- (A) KERNEL RLIMIT_CPU + wall backstop: tests/lib/gen_timeout.sh (D45's "ONE implementation", `ulimit -t` shim, SIGXCPU, `cpusecs` exported), reused by tests/fuzz/fuzz.py:70-82 and tests/vm/vm_oracle.py:74-82 through `gen_timeout.sh cpusecs`. Exact, per process, inherited by cc1/as/ld, no polling, and docs/testing.md records its value rule (~4x quiet, ~2x worst contended; sanitizer figure measured separately).
- (B) SAMPLED scripts/watchdog -c (tree sum, bash /proc poll): tests/counterk/run_counterk_tests.sh:341 (K32), tests/resource/run_resource_tests.sh:244/500/513 (K7, sizecap), tests/codegen/run_facts_checks.sh:598 (k159-width, -c 5), and now growth's CLI stage, gcc builds and matcher runs.
- (C) IN-PROCESS ITIMER_PROF + alarm: growth_driver.c lib mode only (new in this subject).
Growth uses B and C, and for gcc (where A is exact and B undercounts, CPU-4) it chose B. Recommendation: not a new shared mechanism now (the members bound different shapes: an exec'd tree, a pool of python subprocesses, one long-lived process), but ONE value rule and ONE exactness rule: bounds that decide a verdict use an exact clock (A for exec'd trees, C for in-process work), B is for RSS and diagnosis; and every member's value is derived by the D45 rule (quiet worst x contention ~2 x platform ratio), stated where the value lives.

## GENERAL FORM + UNLOCKS
General form: "a verdict-deciding time bound = an exact CPU clock owned by the bounded process (RLIMIT_CPU inherited, or ITIMER_PROF in-process) + a wall hang guard derived from the enclosing job's kill, both with a basis line; the supervisor polls only for memory." For growth that is: arm lib mode's arm_bound() in `one` mode too (the code exists), RLIMIT_CPU on gcc, watchdog at -i 0.5 for RSS + wall.
Unlocks, with triggers:
- U1 Exact per-point CPU for the doubling report, free of supervisor load (CPU-2/CPU-7). Trigger: the first REPORT line that a -j 1 re-run does not reproduce, or a missed step found by the complexity lens.
- U2 A cheaper sweep: ~0.45 core per concurrent run returned (CPU-7), so the pool's -j and every cloud shard's wall improve. Trigger: the next shard re-fold (cloud_units_plan) or the first shard near its 45 min kill.
- U3 Cell-named hangs everywhere (CPU-3): a guard derived from the job's kill and a progress line on stdout. Trigger: the next unnamed cloud job cut (shard 31's shape) in either stage.
- U4 One D45-style derivation table for every runner's bound (gen_cc, counterk K32, resource K7/sizecap, facts k159-width, growth), so a re-derivation after a cloud run is one table edit. Trigger: the first cloud run of this harness printing its `CPU:` lines (BOUNDS_BASIS already owes that re-derivation).
