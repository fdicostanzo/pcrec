## Findings

### SOUND-1 — the `range` row grows the TRAIL by one entry per candidate; `vm_cost_look` charges a constant 2, so a literal build answers `PCREC_ERR_FRAMES` where libpcre2 matches. CONFIRMED (by the machine's own sizing rule + model trace). Severity: answer (give-up on a matchable subject). Effort: small. Bears on: both A and B (B worse: every branch takes the row).

- Design: §5.1 (subject lines 322, 358-361 "Trail"), §5.2 lines 520-527 ("nothing in §5.1 depends on `hi_i`'s magnitude", line 524), §5.5 lines 656-662 (frames only; the trail is never priced). `vm_cost`/`trail` appear nowhere in the note (grep: 0 hits for `vm_cost`).
- Code: `src/gen/emit_vm.c:2858` `vm_cost_look` = body cost + `frames += 1 + nbranch; trail += 2` (its header: "an under-charge is the K27-class failure"). `vm_plan_capacities` (emit_vm.c ~8026) sizes `trail_frames = cost.trail + 1` for a bounded pattern. The emitted `RX_TRAIL` returns `RX_R_FRAMES` when `trail_depth >= trail_cap` (f1.c line 111-116 here).
- Mechanism, from the sketch as written: `D_i = min(..)` is one trailed `VK_SET`; every `L_adv_i` retry does `D_i = D_i - 1` (trailed) AFTER the pop rewound to the previous frame's mark, i.e. ABOVE nothing that will ever rewind it inside this evaluation. So an evaluation leaves `1 + (number of retries)` `D_i` entries per range branch tried, up to `1 + hi_i - lo_i`; an atomic cut does not rewind the trail (vm_look header, property 3). Total per evaluation: `sum over range branches (hi_i - lo_i + 1)`, linear in `hi`, versus today's constant.
- Witness: `(?<=[ab]{1,20})y` on `cccccccccccccccccccc` + `ay` (20 c's): libpcre2 [21-22]. Model trail depth at the success = 22 lookbehind-owned entries (mark, pos, `D` = 20 then 19 decrements down to 1) + the body's low-water slot. Today's sizing for the twin `(?=[ab]{1,20})y` / `(?<=[ab]{20})y` stamps `RX_TRAIL_FRAMES 4`. So the 5th `RX_TRAIL` returns `RX_R_FRAMES` -> `PCREC_ERR_FRAMES`. Smallest: `(?<=x|[ab]{1,3})y` on `caay` (libpcre2 [3-4]) needs 4 entries against today's 3 for `(?<=x|[ab][ab][ab])y`.
- Also: for growable (looped) lookbehinds the default 3072-entry trail now drains at up to ~257 entries per evaluation instead of 2, so any stamped `subject_ceiling` derived from the per-iteration trail charge is too generous unless `vm_cost_look` changes too. And §5.2's "correctness needs no cap ... nothing in §5.1 depends on `hi_i`'s magnitude" is false for the trail: at a raised cap (65535, [IFACE-PUSH]) one branch needs up to 65,536 entries, over `VM_MAX_AUTO_TRAIL_FRAMES` = 3072 (limits.def:211).
- Fix (one of): `vm_cost_look` adds `sum (hi_i - lo_i + 1)` over `range` branches (a bounded compile-time constant at the 255 policy) and §5.5 states the trail term; or make the decrement not grow the trail (e.g. write `D_i` once per candidate into a frame-saved field, or re-derive the candidate from a frame-saved value, so the trail stays O(1) per branch). Gate 1 would likely catch the literal build red (any cell whose first candidate fails), so the blast radius is build-time, but the text owes the term.
- Model: `sound/model.py`, cases `sound/w_trail.tsv` (trail column).

- The negative-arm difference is not answer-preserving in general: it is answer-preserving only under the premise "this end-check cannot fail on a correct compiler". §7's S136 re-aim (lines 846-854) is exactly the case where the two spellings differ in answer (decline -> a false-match-shaped `(3,4)`, versus `PCREC_ERR_INTERNAL`), so the note's own witness contradicts "Every rewrite preserves answers" (line 417). Fix: list a 5th rewrite ("negative arm: the decline becomes the hard return; sound because at `lo == hi` the end-check is unreachable on a correct compiler") and say it is a SELECTION, not an answer-free rewrite, which §5.3 already half-says.
- Labels: today's `vm_look_behind` pre-allocates `bl/bodl/endl` for every branch in one loop (emit_vm.c, `for (int i = 0; i < m; i++) { bl[i] = vm_label(v); ... }`). - Under answer B: §13 B says "The negative-lookbehind hard error stays tied to 'one length'" — so B still selects the end-check action by `lo == hi`, i.e. B keeps a one-column declared table; §13's "Benefit: one emission path, no table" is false as written. Either B retires INTERNAL (the "further contract change") or B's benefit line says "one loop, plus a one-column end-check table".

## PROBED-AND-HELD

**Method.** Hand-executions were mechanized in `sound/model.py`, a literal model of §5.1 + the §5.1b table composed with today's `vm_look` (emit_vm.c, as read in the review tree) over today's emitted primitives (`sound/f1.c`): `RX_SET` always trails (old value onto the trail); `RX_PUSH` saves (label, cursor, `trail_depth`); `rx_fail` pops, restores the cursor, rewinds the trail to the mark, and jumps; `RX_CUT` assigns `resume_depth`. Entry order per `vm_look`: mark (atomic or negative), POS (positive or behind), then the negative's `L_neg_ok` push. `L_ok`: negative = cut + fail; positive atomic = cut + restore; non-atomic = restore only. `one-length` rows are today's `vm_look_behind_branch` statement for statement; `range` rows are the sketch at subject lines 325-343 literally (guard -> `D_i = min(hi, pos)` -> `L_try` push -> back-step(`D_i`) -> sentinel `rx_fail` -> body -> end-check decline -> `L_adv`: `D_i == lo` -> next / `rx_fail`, else `D_i - 1` -> `L_try`). Bodies: a frames-rung backtracker in `vm_emit`'s continuation shape. Not modelled: budgets, prefilter, other rungs (answer-equivalent by their own gates). Oracle: libpcre2-8 10.46 via `sound/oprobe` (first match from a start offset, all groups).

**Composition facts read in the review tree that the design relies on and that hold:**
- The lookbehind body is emitted with `under_atomic = false` (`vm_emit` -> `vm_emit_node` -> `vm_rep(..., false)`, emit_vm.c:9238; only `vm_atomic` passes true, :6937), so no quantifier in a body is possessified by the assertion's own atomicity; possessify never enters a lookaround body (src/opt/possessify.c:1818). So the end-check's backtrack INTO the body (W3/W3b) has frames to reach.
- §3.2.1's `fmin = 0` inside the body is conservative for a hidden "end at POS" follow (prunes less, never more).
- `D_i` is never read across a subroutine call except after a pop or a fresh `VK_SET` (read only at `L_try_i` right after its own set/push, and at `L_adv_i` right after a pop), so it needs no membership in DD-14's activation-private restore set `W(g)`; self re-entry of a lookbehind is refused (err 125, §5.2).
- Mark-before-push (vm_look property 1) holds with the new frames: the `L_adv_i` pushes are above the mark, so the atomic cut and the negative arm's `L_body_won` cut remove them (W5 sabotage = exactly that cut applied to `(?<*`).
- The UTF-8 sentinel: between `RX_PUSH(&&L_adv_i)` and the sentinel test nothing else pushes, so `rx_fail` pops exactly `L_adv_i` (restoring the cursor and `D_i`), as the sketch says. Under the byte encoding `D_i <= scan_position`, so the sentinel is dead, as stated.
- §5.5 arithmetic: sum 1..255 = 32,640; sum 4..51 = 1,320; 1e9 / 32,640 = 30,637 (">= 30,600"). The frame charge `1 + nbranch` in `vm_cost_look` (emit_vm.c:2858) still over-covers the `range` row (at most one `L_adv`/`L_b` chain frame live per evaluation, plus `L_neg_ok`). The trail charge does not: SOUND-1.
- §5.6: `VK_WORK` already takes a string amount (`vm_work(v, expr, role)`), `VK_SEEK` carries `slotx` (vm_stmt.h:224) and `vm_r_seek`'s `VSK_BACKSTEP` arm ignores it today (vm_stmt.c:450-470), so the renderer-arm change the design names is the needed one.
