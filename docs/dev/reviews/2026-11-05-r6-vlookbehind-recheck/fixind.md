# crit-vlb2 fixind findings (fix-induced additions, rev 1)

## Findings

### FIX-1 — F1's `D_i` writes add TRAIL entries that the cost analysis (`vm_cost_look`, trail += 2) never charges: the sized trail overflows and returns PCREC_ERR_FRAMES on a matching subject
- **Status:** CONFIRMED by code trace + hand execution (no varying lookbehind compiles today, so no run).
- **Severity:** answer (a give-up, PCREC_ERR_FRAMES, where libpcre2 matches; and an over-promising `subject_ceiling` stamp). **Effort:** small (one cost term + a witness). **Blast radius:** every `range`-row artifact without `frame_capacity` set. **Owner Q1:** both (the `range` row exists under A and B; under B every lookbehind, fixed ones included, gains the extra entries).
- **Design:** §5.1 lines 322, 342-348, 358-362 ("`D_i` is set before each push and decremented after each pop"); §5.1b line 429-431 (names the count pass's push count, nothing else); §5.5 lines 636-668 ("Frames" only). The design never names `vm_cost_look` or the trail capacity.
- **Code (review tree):** `src/gen/emit_vm.c:2859-2864` `vm_cost_look`: `c.frames += 1 + a->u.look.nbranch; c.trail += 2;` (the header, :2836-2841, argues +2 is EXACT for the atomic form's two slot writes). `vm_plan_capacities` :8040-8041 sizes `trail_frames = cost.trail + 1` for a bounded pattern; the emitted `RX_TRAIL` (`if (run->trail_depth >= run->trail_cap) return RX_R_FRAMES;`) enforces it. `vm_cost_call`'s own header (:2882-2885) names this exact failure: "An artifact that under-sizes `trail_frames` returns PCREC_ERR_FRAMES on a pattern it can MATCH, which is S87/S95's exact failure mode."
- **Why the entries accumulate (hand trace of §5.1's own order):** pop of F_n rewinds the trail to F_n's mark, which was taken AFTER the previous `D_i` write; then `D_i = D_i - 1` (`VK_SET` = `RX_TRAIL` + store) writes a NEW entry at that mark; the next push's mark is above it, so the next pop never removes it. Net: one live trail entry per candidate tried, Σ_i (min(hi_i,cursor) - lo_i + 1) per evaluation, and an atomic cut does not rewind the trail (vm_look header property 3). They are released only by a pop below the assertion or the attempt reset.
- **Repro (hand-executed against today's emitted scaffolding):** `build/pcrec --features all -p rx --emit-main --pattern '(?<=ab|c)x'` emits `RX_TRAIL_FRAMES 3` (fixind/lb.h:271) and `RX_FAST_TRAIL 3` (fixind/lb.c:65), both = cost.trail 2 + 1, with entries LOOK_MARK0, LOOK_POS0. Under rev 1, `(?<=a{1,2})x` (one `range` branch, cost.trail still 2+body 0 = 2, capacity 3) on `bax`: entries MARK, POS, `D_0 = 2` (depth 3, cap 3: the third write already passes only because the check is `>=` before the write at depth 2); body `a{1,2}` at 0 reads `b`, fails, pop F1; `D_0 = 1` -> `RX_TRAIL` at depth 3 >= cap 3 -> `RX_R_FRAMES` -> `PCREC_ERR_FRAMES`. libpcre2: `printf '(?<=a{1,2})x\tbax\n' | R/tools/oracle_probe m` -> [2-3]. Expected under a correct cost: [2-3].
- **Same defect, second reader:** a lookbehind inside a growing quantifier (`(?:(?<=a{1,9})b)+`) feeds `vm_cost_rep` a per-iteration `pt` that omits the per-candidate entries, so the stamped `subject_ceiling` over-promises (the stamp's documented safe direction is the opposite).
- **Sibling fields left unstated by F1/F12:** `vm_cost_look`'s `frames` term (`1 + nbranch`) happens to stay a safe bound (one live retry frame per branch, last branch now pushes too: exact rather than over by one) — the design should say so; its `trail` term must become `2 + Σ_range (hi_i - lo_i + 1)` (or `+1 + (hi_i-lo_i)` per branch) and the §5.1b table needs a "trail entries per evaluation" column beside "work per candidate". §5.5's "Frames" bullet list needs a "Trail" bullet. A sabotage/witness row: a `range` lookbehind on a subject where every candidate fails before the last (W-trail), default capacities, expected = libpcre2's match, not -2/FRAMES.
- **Fix-induced?** Yes: rev 0's sketch (frame saved the candidate) also wrote `D_i`, but rev 1 re-sketched it and stated the trail ordering (lines 358-362) without following the entries to their consumer.

### FIX-3 — F12's "new slot family" names one property (allocated only for varying branches) and leaves its seven sibling readers unstated: placement in the layout, the legend name, the `--emit-ir` slot listing, the totals/`RX_NSLOTS` sum, the running-counter reset, `VmSnap`, and the count-pass/emitter shared predicate
- **Status:** CONFIRMED (code trace).
- **Severity:** maintenance (one omission is answer-class: an under-count is K27's out-of-bounds write in emitted code). **Effort:** small to medium. **Blast radius:** emit_vm.c slot layout. **Owner Q1:** both (under B every lookbehind with a varying branch takes the family; under B with "range everywhere" EVERY lookbehind branch would take a `D_i` unless the table keeps "only when lo<hi" — B's §13 text should say which).
- **Design:** §5.1b lines 424-428 ("`D_i` comes from a new slot family, allocated in the count pass (`vm_count_slots_look`) only for branches with `lo_i < hi_i`. An artifact with no varying branch allocates none, so its slot legend and numbering are unchanged").
- **The readers a new family has today, by the lookpos family's precedent (all in src/gen/emit_vm.c):**
  1. a base function (`vm_slot_lookpos` :1220, `vm_slot_splice` :1209) — every family's base is a sum of the TOTALS of the families below it. Where the family sits is unstated; if it is placed anywhere but the TOP, every base above it (`vm_slot_splice` at least) gains a term. "Numbering unchanged" holds for no-varying artifacts wherever it sits, but NOT for a varying artifact's splice slots if it sits below them — say which.
  2. `vm_slot_name` :1015-1090 — no arm => NULL => `vm_slot_expr` falls back to the bare number, which that function's own header calls "a bug rather than a naming gap"; and the legend stamp loop (:11741-11745) emits no `#define <P>_SLOT_...` for it.
  3. `vm_listing_slots` (:9823-9860) — the `--emit-ir` slot section lists guard/low/mark/revdet/lookmark/lookpos; a `D_i` family needs its row or the listing under-reports. (Precedent is mixed: the counter, pending and splice families already have NO listing row — a pre-existing gap, noted, not counted here.)
  4. the totals block `:10606-10634` — `n<fam>_total = v->n<fam>`, the reset `v->n<fam> = 0`, and the `nstate` sum (= `RX_NSLOTS`). Missing the sum is K27 (write past `RX_NSLOTS`).
  5. `VmSnap`/`vm_snap` (:7566-7579) — the callee-region save-set walk ranges over the families it lists (`lookmark`, `lookpos` among them). `D_i` can be left OUT soundly (it is read only immediately after its own `VK_SET` and after a pop that trail-restored it, never across a call), but the design must state that, since it is the one family-reader that is legitimately skipped and a builder following the lookpos precedent will add it.
  6. the count pass reads `nbranch` only today (:3053); the new allocation reads the WIDTH PAIR per branch — the same predicate `vm_look_behind` must read ("`vm_count_slots` and `vm_look` MUST agree exactly", :1227-1234). The design should name one shared predicate (`vm_lb_branch_varies(a, i)`) on the `vm_look_needs_mark/_pos` precedent, which is exactly the emission table's key.
  7. `Vm` struct fields `n<fam>` / `n<fam>_total` (:477-478 precedent).
- **Fix:** one sentence per reader in §5.1b (placement: top, above splice, so every existing base is unmoved; name `SLOT_LOOK_CAND<n>`; listing row; total + sum + reset; VmSnap excluded with the reason; one shared predicate).

## PROBED-AND-HELD
- **F1 sketch, hand-traced against today's emitted scaffolding (`fixind/lb.c`, `(?<=ab|c)x`) on positive atomic, negative, non-atomic, and atomic-negative forms** — the push-before-back-step order and the cursor-saving frame are today's order (lb.c: guard, `RX_PUSH(&&rx_L7, scan_position)`, charge, back-step, sentinel); every exit of a `range` branch leaves `scan_position` at the cursor (guard: unmoved; exhaustion and sentinel: the popped frame's saved position); the trail argument for `D_i` restoration holds (pop rewinds to a mark above `D_i`'s entry for that push); atomic/negative cut at `L_ok`/`L_body_won` discards `L_adv_i` (mark taken before every push, vm_look :7455-7461); non-atomic leaves it live and `POS` survives (set before every push). General form: a VM construct = a REFERENCE emission with run-time operands (here: `range`, count in a slot) plus declared ADMISSION rows that substitute a cheaper section where a stored fact makes it sound (here: `one-length`, count a literal); each row declares its columns for EVERY reader — slots, pushes, trail, frames, work, role text, listing — and one memoised row choice per node feeds all of them.
