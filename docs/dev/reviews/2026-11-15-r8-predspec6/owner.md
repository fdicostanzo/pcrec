CONFIRMED. Severity: design. Effort: S. Blast radius: §0 Goals table, §0.1, §2.1 REASONING, §13 O38. Location: §0 L61-76.

### OWNER-3 — `[ ]` carries two meanings ("any one entry" and "all entries, in order"), and the tuple rejection in §8/C25 rests on the first while join/each rest on the second
CONFIRMED. Severity: design. Effort: M. Blast radius: §5.4 table L736, §3.1, §3.4, §5.3, §8 L954-960, §13 C25, O47; acceptance cases E-WEEKDAY, E-IPV4, E-RFC, E-NEAR(c), E-HTTP, E-SEP (every `join([...])`). Location: §5.4 L736; §8 L955-956; §12 preamble L1098-1099.
Repro: §5.4 L736: `[ e1, e2 ]` = "ARRAY: ANY ONE entry". E-IPV4 L1138 `join([octet, octet, octet, octet], sep = ".")`: read as "any one entry" the array is `octet|octet|octet|octet` = `octet`; `join` instead uses ALL FOUR entries IN ORDER. The §12 re-check (L1098-1099) itself names the two readings: "every `[ ]` is an array read as any one entry ... or passed to a structural macro that reads its entries in order (`join`)". §3.4 explains the second as the STRUCTURAL view (spelling order is readable). But §8 L955-956 forbids `lex_ge([major, minor, patch], [1, 4, 0])` because "a `[ ]` is an alternation (any one entry, so its order is not part of the value)", and C25 (L1396-1404) builds a new feature (variable-length call record, O47) to replace it. Under §3.4 the order of `[1, 4, 0]` IS readable by a structural macro exactly as `join` reads `[year, month, day]`; CF:866 (4) forbids RECORDS as values, not arrays, so the ruling's words do not forbid `[1, 4, 0]` (CF:877 is the manager's TO CHECK, not ruled). The genuine defect of the rev 5 spelling is only its FIRST argument (bare label names as values, C13). Rule applied: owner's "operators that always mean the same thing wherever they are used". Observed: the bracket's meaning is chosen by the consumer, and the draft argues both ways.
Fix direction: state ONE meaning for `[ ]` that covers both (an rx whose spelling keeps its entries in order: extensional ops see the alternation, structural ops see the ordered entries; §3.4), drop the "order is not part of the value" argument, and re-evaluate C25/O47 (likely `version & lex_ge([1, 4, 0])`: ONE array parameter, the subject by `&`, no variadic call record).

### OWNER-4 — `${ }` with a subject-open macro: three sections give three meanings (guard / unapplied-macro error / "guard needs `&`")
CONFIRMED. Severity: design (a rule as written makes `${!B}` both legal and an error). Effort: S. Blast radius: §2.1, §2.2, §5.1, §11 HOLES, L21. Location: §5.1 L633-635; §2.2 L253-254; §11 L1055-1057, L1071-1072.
Repro: §2.1 L213: `!B` = "a macro with the subject open"; L210-213 a condition and a section are the same shape. §5.1 L634-635: in a hole "a macro with only its subject open (a condition, a section) is a GUARD (§11)". §2.2 L253-254: "A standalone `!B` where an rx is needed (`${!B}`, `C | !B`) is the unapplied-macro error" (and L21, L107, uses `${!<200}` as that error). §11 L1055-1057: a guard is written WITH AN EXPLICIT `&` (`(\d+)&${ <256 }`); a hole without `&` is a following item; L1071-1072: "a guard needs `&` so the hole rule has no exception (C4)". So `/(\d+)${!<200}/` is a guard by §5.1, an error by §2.2, and (as a hole without `&`) a following item by §11, which cannot follow for a macro. Rule applied: owner's "macro application has a specific meaning" (CF:850) and the one input rule (CF:860: `&` fills the subject). Observed: §5.1 adds a second, `&`-less way for a hole to fill a macro's subject.
Fix direction: delete §5.1's "is a guard" clause; a subject-open macro in a hole is the unapplied-macro error unless preceded by `&` (C4), which is then the ordinary `&` subject fill.

### OWNER-5 — A third input route beside "call fills parameters, `&` fills the subject": match-dependent bindings and `count()` take their match implicitly
CONFIRMED. Severity: design. Effort: M. Blast radius: §4.4, §8 `count()`, §5.1 (match-dependent vs pure), O19, L42; acceptance cases E-WEEKDAY, E-CAL, E-RFC, E-NEAR(c), E-HTTP (count spelling). Location: §2.1 L209-214; §4.4 L569-576; §8 L946-948; §12.2 L1128.
Repro: CF:860 / §2.1 L209-211: a macro takes input "two ways under ONE rule": a CALL fills parameters, `&` fills the one subject slot. But `weekday := weekday_of($year, $month, $day)` (E-WEEKDAY L1128), `dim := days_in($year, $month)` (E-CAL L1163), `d := days($b) - days($a)` (E-NEAR L1197) and `n := count((name: S))` (§8 L947, E-HTTP L1238) receive THE MATCH neither by a call nor by `&`: `$year` inside a binding reads a match that is supplied later, wherever the name is used as a label (`isodate & (weekday: 6)`), attached to "the pattern whose labels it reads" (L570; which pattern is O19). `count((name: S))` passes a condition (a subject-open macro) as a parameter and yields a number with NO subject ever supplied to it; its subject arrives when `n:` is later laid against `headers`. Under the two kinds such a binding is neither an rx (its value depends on the match) nor a macro applied by either route; the draft calls it a "computed LABEL" (§4.4), i.e. a third thing in practice, while §5.1 L632 says a binding names "an rx or a macro". Compare `occurs.exactly(1, (name: S))`, which IS a subject-open macro filled by `&`: the two spellings of one count (L42, "SAME") use different input routes.
Fix direction: state the computed label in the one-rule terms: a match-dependent binding IS a macro with its subject open (the pattern it reads), filled by `&`/`label:` like any condition; then `count((name: S))` is a macro yielding a number on its subject, and L42's two spellings share one route. Name the third route explicitly if that is not adopted.

### OWNER-6 — `&` and `|` each have operand-kind-dependent meanings the one input rule does not cover (macro & macro; rx | macro is an error while macro | macro is not)
CONFIRMED (the rule text); SUSPECTED as a user-visible split (confirm by writing the typing table of `&`/`|`/`!` over {rx, macro}). Severity: design. Effort: S. Blast radius: §2.1, §2.2, §3.5, §5.2 sections, L1, L21, L26; acceptance cases E-FILE (`alts & !startsWith("#") & !"" & length(<=20)`), E-HTTP (three `occurs` macros chained), E-CTX. Location: §2.1 L209-214; §2.2 L249-254; §3.5 L472-476; §5.2 L679-680.
Repro: CF:860/§2.1: "`&` fills its one SUBJECT slot with the rx on the other side". That covers rx & macro. The draft also uses: rx & rx = intersection (L249); macro & macro = "pointwise" combination (L254: "Macros in the filter role combine pointwise by `& | !`"; sections "compose", `(& isodate & (year: 2024))` L680; E-HTTP L1231-1233 chains three `occurs` macros); neither side of macro & macro is an rx, so the one rule says nothing. `|`: macro | macro is pointwise OR (`(major: 2) | (major: 1, minor: >=4)`, L502, L960), but rx | macro (`C | !B`, L254) is the unapplied-macro error, and an rx/macro MIXED array is an error (L475) though `t & [f, g]` with rx entries written as sections works. So `|` is: union (rx|rx), pointwise OR (macro|macro), error (rx|macro). Also §5.2 L679 makes `&` itself "a macro" whose section leaves the LEFT operand open, while CF:860 makes `&` the mechanism that applies macros: the rule is circular for `A & B` with no macro in it. Rule applied: "few operators that always mean the same thing". Observed: correct semantics, but three cases per operator, stated in three sections, with no single typing rule; the user cannot predict `C | !B` erroring while `(x: S) | !B` is fine.
Fix direction: one sentence in §2.2/§5.4: "an rx in the filter role is the constant macro (accept iff in the set); `& | !` on macros are pointwise; `X & M` with X an rx fills M's subject" — then rx|macro is pointwise too (or state why not), and the mixed-array error falls away.

### OWNER-7 — "Not a value" kinds in practice: the module/namespace, the run-time parameter and the `@` statement are bound or used like values while §5.1/§5.4 say `:=` binds only an rx or a macro
CONFIRMED. Severity: design. Effort: S. Blast radius: §2.1, §5.1 L631-633, §5.4 L741, §7 MODULES, §13 O46, §11 parameters; acceptance cases E-JSONL, E-IPV4, E-HTTP, E-DEPTH (`x := import(...)`), E-NEAR(b) (`anchor := param(isodate)`). Location: §5.4 L741; §5.1 L631-632; §7 L869-872; §11 L1058-1060; §13 C18 L1386-1390.
Repro: §5.4 L741: "`:=` binds a name to an rx or a macro"; §5.1 L631-632: "ONE kind of binding ... an rx or a macro (CF:858)". O46's lean A (§7 L871-872): a module is "a compile-time NAMESPACE that `:=` names, not a value". So every `json := import("json")`, `assert := import("assert")`, `occurs := import("occurs")` in §12 binds a third thing with `:=`, and `.` on it is name resolution (O46 L1561) although §3.2 L440 lists "module members `json.row`" under LABEL navigation in the map view. `anchor := param(isodate)` (E-NEAR L1194): a run-time parameter is neither a compile-time rx nor a macro awaiting input (§11 L1058-1060: "read-only per match, validated against their type"), i.e. a kind in practice. C18 (L1386-1390) shows the pressure: a named assertion is refused a binding because an assertion "is neither". The owner allowed a non-first-class STRUCTURAL type only for the record (CF:851-852: "ok with a purely structural type if it can't be bound directly"); a namespace that IS bound by `:=` is not that case. Rule applied: CF:858 "two kinds" + owner's "few types"; the brief's "add a type/kind in practice while calling it not a type". Observed: 2 value kinds + 1 non-value shape (record) as advertised, but in practice also namespace (bound), parameter (bound), statement, computed label (OWNER-5).
Fix direction: make the census honest: a KIND TABLE listing every thing a name or a mark can denote (rx, macro, record, namespace, parameter, computed label, statement), each marked value / bindable / passable and citing its ruling; then either make `import` and `param` produce one of the two kinds (a parameter = an rx known per match; a module's `.` = a separate name-resolution mark) or record the namespace as a ruled third bindable shape for the owner.

### OWNER-8 — `:` means "narrow silently" in a condition and "must already lie within, else error" in a definition head
CONFIRMED. Severity: design. Effort: S. Blast radius: §5.2 typed parameters, §5.4 `:` row, §4.1; no §12 case uses a typed parameter. Location: §5.2 L688-694; §5.4 L740.
Repro: §5.4 L740 gives `:` ONE meaning: "CONSTRAINS a label that EXISTS" in both `label: S` (condition) and `p: T` (head). §5.2 L688-691: `m(x: T)` "narrows x by T, and the POSITIONAL argument must lie WITHIN T; a broader or partly overlapping argument is an ERROR showing a dropped witness", while "a condition literal applied by `&` never gets that check: it always NARROWS the subject (`isodate & (year: <2000)` silently drops `5`)". So the same mark, `x: T`, silently narrows in one position and refuses in the other; the head form also DECLARES x (it does not exist before the head), contrary to "a label that exists". CF:863's "`:` constrains a label that exists" does not settle which behaviour; CF:706 (cited L698) ruled "`=` sets a parameter vs `:` filters", i.e. filtering, which is the condition behaviour. Rule applied: "operators that always mean the same thing wherever they are used". Observed: two behaviours under one mark; no look-alike row (`m(x: T)` vs `x & (x: T)`-style) records it.
Fix direction: either give the head `:` the condition meaning (narrow; dead-branch/empty diagnostics as at other narrowing sites, L692-694) or spell the containment check differently; add the pair to §0.1. No acceptance case needs typed parameters, so dropping them from phase 1 is also open.

### OWNER-10 — "A search returns an rx" makes `X[i]` and the array view mean a MATCH-TIME sequence on a search result and a COMPILE-TIME spelling everywhere else; `~` and `!~` produce different kinds; no acceptance case uses any of it
CONFIRMED. Severity: design. Effort: M. Blast radius: §2.6, §3.2, §3.4, G4, §0.1 L16-L17, O29, C29; no §12 case (0 uses of `~`/`!~`, `some(`/`all(` only as `@assert.some`). Location: §2.6 L336-348; G4 L69; §3.4 L462-463; §3.2 L431-435.

### OWNER-11 — `( )` has five roles, and "a record is never a value" has an exception (a `label: S` record in value position is a bindable, passable condition)
CONFIRMED. Severity: design. Effort: S-M. Blast radius: §5.4 table L737-738 and L745-747, §4.1 L509-511, §5.2 L669-672, O41, O45, L43-L46; acceptance case E-HTTP (`occurs.exactly(1, (name: ...))`, `count((name: ...))`). Location: §5.4 L737-747; §4.1 L509-511.

Fix direction: say it the other way round, once, in §5.4: "`( label: S, ... )` in value position IS a condition (a macro, CF:858), not a record; a record exists only in positions (a)-(c)" and drop "except" from the record row; give the section `(& f)` its own §5.4 row (today it is in "Other marks").

## PROBED-AND-HELD
- CENSUS (rev 6 as written). Value kinds advertised: 2 (rx, macro). Non-value shapes named: record, array view, map view, filter ROLE, operator SECTION (a macro), `@` statement. Kinds in practice beyond the advertised two (OWNER-5, -7, -10): computed label (match-dependent binding), module/namespace (bound by `:=`), run-time parameter, search occurrence sequence; number is an rx by LEAN (O40, held as consistent with CF:858). Marks/operators used: `&` `|` prefix-`!` `~` `!~` `< <= > >= ==` `+ - * %` `:=` `,` `( )` `[ ]` `=` `:` `.` `$` `${}` `/.../` `@` = 23 spellings; the case-needed kernel is ~14 (OWNER-12).
- COMMA (criterion b): 60 expression-language commas in §12 code re-parsed with rx literals and strings stripped: 60/60 inside `[ ]` or `( )` (the 2 apparent top-level ones are continuation lines of E-WEEKDAY's multi-line array). §5.4's comma row (L735) and every other section that mentions a comma (§4.1 L497-499, §3.5 L475, C5 L1365-1370, O43) agree: "next entry", no logic. HELD: comma has one meaning after rev 6; the residual multi-meaning is in the BRACKETS (OWNER-3, OWNER-11), not the comma.
- MACRO APPLICATION (criterion b): call = parameters / `&` = subject holds for: every §12 call (all fill parameters; no subject-as-argument call found in §12 or §§2-8 code), L5/L38/L40 errors, `leap($year)` refused vs `days_in($year, $month)` accepted (consistent: `leap` has no parameters), `each` filling a section's subject per entry, arrays of modifiers called `[padded, any_case](S)`. Exceptions found: hole-as-guard (OWNER-4), implicit match input (OWNER-5), macro & macro (OWNER-6).
- `=` (labels an entry) in arrays and calls: one meaning held across E-WEEKDAY, E-RFC, E-NEAR, E-SEP, E-HTTP, `sep =`, `of =`, `sha256 =` (OWNER-8 concerns `:`, not `=`).
- Prefix `!` turning a label-free rx into a macro (`!<200` vs `>=200`): a kind change by mark, already OPEN as O26 with L21; not re-filed.
- "Argues for something ranked as a constraint": the two ruled constraints (no alphabetic operators/keywords; `& | !` extensional) are respected throughout; O27's lean ("numeric vs text a property of the comparison") argues against the RULED "literal decides" (CF:43) but is filed OPEN, not adopted: held.
- G0 faithfulness: checked against CF:691 (G0 is faithful to the 11-14 criterion) and CF:846-850 (not stated as a goal): OWNER-1. Ranking checkability: OWNER-2.
- Rev 6 folds checked against CF:858-875 items (1)-(5): all five appear with RULED marks citing the right line; L44-L47, O41-O47 correctly marked LEAN.
