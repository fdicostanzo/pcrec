Line numbers: draft at aa9348f3d; CF at 8d3c348f2. Owner quote (CF:881-883): "The result of the search would be an array of all of the results. You could use count to check the number of results. You could treat it as an array. You could use the occurs module."

## Findings

### DRIFT-1 — §2.6 core sentence HOLDS; its "one entry per occurrence" LEAN is now owner-backed (status restatement)

### DRIFT-2 — CONFLICT: "the array tools apply" to a MATCH-TIME array; G4, §3.4, §3.2 and §5.3 make every array tool compile-time over SPELLING
CONFIRMED. severity: design. effort: M. blast: G0/G4 (L69), §3.2 (L431-441), §3.4 (L462-466), §5.3 (L709-710), §2.6 (L346 `s[i]`), §4.3 (L557-558), §14 (L1580-1581), every program indexing/counting a search result.
Repro: `$m` is a match value (§4.1 L490), so `d := $m ~ /.../` is a MATCH-DEPENDENT binding (§5.1 L636-637) and its number and content of entries exist only at match time. The note (CF:883-885): "`count(...)` gives the number of results, indexing and the other array tools apply". But the draft defines the array tools as compile-time structure over the spelling: G4 L69 "STRUCTURE IS COMPILE-TIME ONLY ... every structural evaluation (each, join, records, indexing, imports, enumerate) is finite"; §3.4 L463 STRUCTURAL = "indexing, `each`, `join`, `where`, `.label`, `enumerate`, entry counts" which "read the SPELLING"; §5.3 L709 macros "FENCED: compile-time only, over finite declared arrays"; §4.3 L557-558 "`alt.x[1]` (first in the PATTERN, compile time) differs from `$x` (the MATCH's value)". So `d[2]`, `count(d)` (an entry count) and `each(f, d)` on a search result are, by the draft's own words, structural reads of a spelling that does not exist at compile time. §2.6 L346 "`s[i]` indexes occurrences (§3.2)" points at a section whose rule cannot produce that meaning. Observed: one bracket `X[i]` with two meanings (spelling position at compile time vs i-th occurrence at match time) — G0 territory, and G4's checkable form ("every structural operator ranges over finite declared things") is false for a search result.
Fix: state two populations once: an array is SPELLED (entries known at compile time; structural tools as now) or MATCH-TIME (a search result; entries per match); on a match-time array `[i]` with literal/bounded i, `count`, `&` filtering and `occurs.*` are match-time tests (regular, counters; CF:62's cost rule), while `each`/`join`/`where`/`enumerate`/`.label` are a compile error naming the match-time source. Restate G4 as "structure of SPELLED things is compile-time only".

### DRIFT-3 — CONFLICT: `~` yields an ARRAY (an rx), `!~` yields a CONDITION (a macro); L16/L17 "SAME" and "`!~` expands without a special case" no longer hold
CONFIRMED. severity: design (G0). effort: M. blast: §0.1 L16 (L102), L17 (L103), §2.6 L347-348, §11 L1046-1047, §13 O12 (L1431).
Repro: under the note `$m ~ /^err/` is the array of occurrences, an rx: for $m = "error" it is {"err"} (one entry), else empty. `m: startsWith("err")` is a CONDITION, a macro with the subject open (§2.1 L210-212). L16 marks them SAME and L17 marks `$m ~ /^err/` SAME as `m: contains(/^err/)` — a value of one kind against a value of the other kind. Placed in the filter role they differ: `P & ($m ~ /^err/)` intersects P's language with the occurrence strings (keeps P-matches whose whole text is "err"; §3.2 tool 2: `&` filters by LANGUAGE), while `P & (m: startsWith("err"))` keeps P-matches whose label m starts with "err". And `!($m ~ r)` (the complement of the occurrence rx: every string that is not an occurrence) is not `$m !~ r` (sugar for the condition `(m: !contains(r))`, L347-348). So `~`/`!~` look like a pair (L17's own claim "`!~` expands without a special case") but produce different kinds, and `!` of the one is not the other. The draft never states how an rx-valued `~` serves as a TEST (non-empty?), and the two-kinds picture has no boolean (§2.1 L220-221) to carry it.
Fix: say once what a search result does in the filter role. Candidates: (a) `~` is only a value producer; the test spelling is the condition `(m: contains(r))`, `!~` its complement, and L16/L17 are rewritten as DIFFERENT (value vs condition) with a named error for a bare `$m ~ r` in the filter role; (b) define "a search result in the filter role = non-empty", which adds an emptiness-to-test coercion seen nowhere else (`"2024" & leap` is a set, not a test). Lean (a): it keeps `&` pure and needs no new rule; drop or keep `!~` (O12) on that basis.

### DRIFT-4 — RESTATE: `count(...)` now takes two argument kinds (a CONDITION over a repeated label; a search-result ARRAY); `occurs.*` likewise gets a second population
CONFIRMED. severity: design (G0 "operators that always mean the same thing", CF:846). effort: M. blast: §8 L941-953, §0.1 L42 (L128), §2.6 L358, §4.3 L551-553, E-HTTP §12.9 L1228-1239, §13 C21 (L1332), O40 (L1516-1518).
Repro: §8 L946 "`count(c)` yields the number of occurrences meeting `c`", c a condition (a macro), e.g. `count((name: any_case("Host")))`, counting iterations of a REPEATED LABEL inside one match; `occurs` L941 "filters over a repeated label's occurrences". The note: "You could use count to check the number of results ... You could use the occurs module" (CF:882-883): the argument is now an ARRAY (an rx, the search result), counting ENTRIES. One name, two argument kinds and two populations (label iterations in one match vs search occurrences in a value). E-HTTP and L42 still HOLD as written (they count label iterations), but no sentence says what `count(d)` / `occurs.exactly(1, ...)` mean on `d := $m ~ /.../`, nor how occurs' condition argument is laid against a search result (by `&` as the subject? as a parameter?). §2.6 L358 "`count` over an occurrence set: §8" points at a section that only describes conditions.
Fix (general form, an unlock): make the search result a REPEATED LABEL: `$m ~ P` behaves as the value matched against `(?:.*?(P))*.*` with one iteration per occurrence (PCRE iteration order, §2.6). Then ONE population: count/occurs/the sequence rule of §4.3 (`(d.year: S)` = all occurrences, bare `$d.year` an error naming the quantified forms) cover search results and repeated captures alike — the owner's own pairing at CF:75 ("REPEATED CAPTURES ... as a set of iterations: count(x.item)"). Then `count(X)` = number of entries of a match-time array, and `count(c)` = `count(<labels> & c)`, one meaning.

### DRIFT-5 — OPEN (part b): what `d.year` means across several entries — four readings and their consequences
CONFIRMED (the gap); readings are analysis. severity: design. effort: M. blast: §2.6 L340, §3.1 L404, §3.2 tool 4 (L440), §4.3 L557-558, §5.4 `:` row (L740 `d.year: S`), §13 C29 (L1411-1416), O29.
Repro: rev 6 L340 "`d.year` = the set of the occurrences' years" (from CF:873 RECORD (5), a manager gloss the owner accepted); the note's manager line (CF:886-887) says it "must be stated once" now that d is an array. Readings, each under the rev 6 rules (two kinds; record never a value; `&` fills the subject; structure compile-time only):
- (A) UNION (rev 6 text): `d.year` is one rx, the set of all occurrences' year strings. Kind: rx, fine. Consequence: entry boundaries and multiplicity are lost (`count(d.year)` is not the number of results; `d.year[2]` is meaningless); `x & d.year` = "x equals SOME occurrence's year" (CF:52's "bare s.year = s.some.year" lean); `(d.year: <2000)` cannot say "every result" or "the same result as `d.month`". Collides with §4.3 L557, where `alt.x` on a duplicate label "returns EVERY entry labelled x as an array" — one dot, a set here and an array there.
- (B) PROJECTION ARRAY: `d.year` is the array with one entry per result, `d.year[i]` = `d[i].year`. Kind: an array of rx = an rx; EXTENSIONALLY equal to (A) under `& | !` (an array of rx is their alternation, §3.5), differing only under `[]`/count (the L25 pattern, by design). Consequence: keeps multiplicity and order, so `count(d.year)` = `count(d)`; but it is a match-time array (DRIFT-2) and pairing `d.year[i]` with `d.month[i]` needs the same index (bounded or VM, CF:62).
- (C) PER-ENTRY ONLY: `d.year` is an error on a multi-entry array; write `d[i].year` or a quantifier. Consequence: strictest; needs a static "at most one occurrence" fact to allow bare `d.year`; makes the one-result case read differently from the many-result case (G0 cost).
- (D) REPEATED LABEL (DRIFT-4's general form): `d.year` is a label with one iteration per result: `(d.year: S)` = every result (the §4.3 sequence rule), `occurs.some((d.year: S))` = some result, `count(...)`, `$d.year` an error naming the quantified forms. Consequence: no new rule at all — the §4.3/§8 machinery already defines every use; conditions over several fields in ONE record (`(d.year: <2000, d.month: 2)`) need the per-iteration reading of a record (both fields of the same result), which §4.3 does not yet state for two labels in one iteration (§13 O28/O29 neighbourhood).
Lean: (D), extensionally agreeing with (A)/(B) where they overlap; it is the only reading that adds no rule and answers "same result" questions.
Fix: one sentence in §2.6 choosing the reading; update C29's argument (DRIFT-7).

### DRIFT-6 — OPEN (part b), and a TWO-MEANINGS defect: `(x, y) := $m ~ /.../` over an array of results
CONFIRMED (the gap and the collision). severity: design (G0). effort: M. blast: §0.2 L162-163, §2.6 L341-343, §5.1 L633, §5.4 `( )` row (c) (L737), §13 O41 (L1526-1530), §0.1 L44.
Repro: rev 6 L341-343 "lays a record over the same rx's fields (by position: the search pattern's labels in group order), so x and y each name an rx (the set of that label's strings over the occurrences)" — reading (iii) below. Under "an array of all of the results" four readings exist:
- (i) PER ENTRY, names bound to arrays: x, y = the projection arrays `d.<g1>`, `d.<g2>` (DRIFT-5 B), paired by index. Kinds: rx, legal; no record bound. Consequence: x and y are separate values, so `x & S` and `y & T` filter independently and lose "same result" unless re-paired by `.index` (§3.5 L477) or by index; inherits DRIFT-2 (match-time arrays).
- (ii) ONE INDEXED ENTRY: `(x, y) := (d)[i]` style, x, y one-result values; bare `(x, y) := $m ~ P` is an error unless the result has at most one entry statically. Consequence: correlation kept, count known; adds the "at most one occurrence" static fact; with no index written it is either an error or an implicit `[1]` (a FIRST rule the owner never ruled; CF:51 listed FIRST as a different answer from SOME).
- (iii) UNION per field (rev 6 text): x, y = sets over all results. Consequence: legal under the kinds, but drops correlation and multiplicity, and is then NOT "the fields of each entry" (CF:886) — it is neither of the manager's two candidates.
- (iv) POSITIONAL OVER ENTRIES: x = result 1, y = result 2 (Python `x, y = re.findall(...)`). This is LEGAL under rev 6's own rules: §3.1 L408 "Unlabelled entries are index-labelled", so an array's entries ARE fields, and §5.4 row (c) lays a record "against a result's groups/fields". Consequence: the SAME spelling has two meanings (record over the entries' groups vs record over the array's entries), the defect the owner's criterion names (CF:846); count mismatch is a match-time fact, so no compile-time check.
- Under (D) of DRIFT-5 (repeated label): `(x, y) := ...` names the two repeated labels; `(x: S, y: T)` then reads per result if a record over iterations is per-iteration.
Fix: state ONE reading in §2.6 and say which of "a record is laid against FIELDS" (groups) vs "entries are index-labelled" wins for a record on the left of `:=`; lean: laid against the search pattern's GROUPS only (never the entry positions), per-result via (D). Phase-1 impact: none (§0.2 L162-163 keeps it out; no §12 case needs it — re-checked, still true).

### DRIFT-8 — RESTATE: `some(s)` and the "same occurrence" rule (§2.6 L345-347) read differently once s is an ARRAY ("any one entry")
CONFIRMED. severity: design (G0). effort: S. blast: §2.6 L345-347, §0.1 L31 (L117), §13 O29 (L1470-1473), C28.
Repro: §2.6: "`some`, `all` are library names over a set ... Every `some(s)` over the same set in one predicate denotes the SAME occurrence". Under the note s is an array, and §5.4 L736 / §3.5 L474 give an array "ANY ONE entry" in the filter role, so `x & s` already means "x is one of the results" and `some(s)` adds nothing extensionally (CF:243: the owner asked "is `x & some(array)` the same as `x & array`?", the manager answered yes). The note names `count`, indexing and `occurs` as the tools, not `some`/`all`; and `occurs.some` (§8) picks its own witness (O29 lean). Result: three spellings of "some result" (`x & s`, `some(s)`, `occurs.some(...)`) with two witness rules (same-occurrence for `some(s)`, independent for `occurs.some`).
Fix: drop `some`/`all` over a search result in favour of the array's own "any one entry" and `occurs.*` (one witness rule, O29's lean), or state `some(s)` = `s` and delete the same-occurrence sentence; C28/O29 then close together.
