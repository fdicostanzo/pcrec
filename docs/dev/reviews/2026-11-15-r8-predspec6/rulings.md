### RUL-1 — §5.1 (rev 6 rewrite) admits a condition/section in a hole as a GUARD, against CF:362's owner words and §2.2/§0.1 L21
CONFIRMED. §5.1 L634-635 (new in rev 6): "a macro with only its subject open (a condition, a section) is a guard (§11)". But: the owner's own words at CF:362 ("`(x: ...)` can only be applied, via intersection, to another rx; not usable as `${x: digit}`"); §2.3 L283-284's unapplied-macro error ("filter `x: digit` has no target"); §2.2 L253-254 ("A standalone `!B` where an rx is needed (`${!B}` ...) is the unapplied-macro error"); §0.1 L21 ("`${!<200}` the unapplied-macro error"); §11 L1055 (a guard is `(\d+)&${ <256 }`, a full rx `<256`, with an explicit `&`, C4 RULED CF:573). `!<200` IS "a macro with only its subject open" (§2.1 L213), so §5.1 makes `${!<200}` a guard while §2.2/L21 make it an error. Rev 5's text ("filter -> guard") was replaced, not removed. Severity: design (two rules disagree on one program). Effort S. Blast: §5.1, §2.2, §2.3, §11 holes, L21, O26. Fix: §5.1 says a hole takes an rx only (a macro in a hole is the unapplied-macro error); a guard is `&${rx}`.

### RUL-5 — §8 / C25: "the type picture forbids" the `[ ]` tuple; it does not, and the stated reason contradicts §3.4 and every `join([...])` case
CONFIRMED. §8 L954-956: `lex_ge([major, minor, patch], [1, 4, 0])` "passed tuples as values, which the type picture forbids: a `[ ]` is an alternation (any one entry, so its order is not part of the value) and a record is never a value (CF:863, CF:866)"; C25 L1398-1399 the same. (i) CF:866 (4) forbids RECORDS as values; `[ ]` is an ARRAY, which the ruling keeps as a value (CF:863-864). The claim that (4) forbids it is the manager's TO CHECK note (CF:876-877, "not ruled"), adopted here as fact. (ii) "its order is not part of the value" contradicts §3.4 L462-464 (structural operations read the spelling; `/a|b/` and `/b|a/` differ under `[1]`), §3.1 (array view = alternatives in order) and E-WEEKDAY/E-IPV4/E-RFC/E-NEAR/E-SEP/E-HTTP, whose `join([year = ..., month = ..., day = ...])` relies on exactly that order (CF:548: "join takes an ordinary array, no tuple type"). A structural `lex_ge` reading its array arguments in order is the same shape as `join`. What remains true is review OWN-9's point (`[1,4,0]` is `&`-equal to `[0,1,4]`), a G0 look-alike, not a type-picture prohibition. Severity: design (a candidate rewrite + O47 variadics are motivated by a non-rule). Effort S. Blast: §8, C25, O47, §12 preamble L1100, §14 L1584 ("no ... tuple ... values" RULED). Fix: restate C25 as OPEN between "structural macro over arrays, like `join`" and the `version & lex_ge(1, 4, 0)` shape; drop "forbids"/"order not part of the value".

### RUL-7 — map-view tools (`where_group`, `each_group`) are left returning a MAP, which point (4) makes impossible; and `each_group(&, ...)` passes the subject as an argument

### RUL-8 — consequence of (5) not drawn: `(x, y) := $m ~ /.../` loses the pairing of x and y across occurrences
CONFIRMED (undrawn consequence). §2.6 L341-343: `(x, y) := ...` makes "x and y each name an rx (the set of that label's strings over the occurrences)", per CF:871-873 (`d.year` = the set of the occurrences' years). With two occurrences `2024-01` and `2025-02`, x = {2024, 2025}, y = {01, 02}: the binding no longer says which year went with which month, while `d & (year: 2024, month: 02)` (a condition on d) does. The owner's motive was "bind values from a search" (CF:852); a reader expects x, y from ONE occurrence. Nothing in §2.6, §0.1 or O41 says so; it is a G0 look-alike (`(x, y) := s` then `x & ...`, `y & ...` vs `s & (x: ..., y: ...)`). Severity: design (G0 row missing). Effort S. Blast: §2.6, §0.1 (new row), §0.2 (design-only item). Fix: add a §0.1 row DIFFERENT (destructuring forgets the pairing) with a diagnostic when the search can occur more than once, or state that destructuring requires a single-occurrence search.

### RUL-9 — consequence of (5) not drawn: the array view of a search result is a MATCH-TIME structure, against G4 / §5.3 "structure is compile-time only"
SUSPECTED (confirm: is `$m ~ ...` ever compile-time only?). A search inside `$m` runs per match (`$m` is a captured value, §4.1), so its occurrence set and "the ARRAY view ... the occurrences in order" (§2.6 L338-340) exist only at match time. But G4 (L69: "STRUCTURE IS COMPILE-TIME ONLY") and §5.3 L709 ("FENCED: compile-time only, over finite declared arrays") forbid structural operations at match time, while §2.6 L346 offers `s[i]` and CF:871 offers the array view. Either `d[2]`/`each(f, d)` on a search result are errors (then the array view of a search result is unusable and should say so), or they are match-time structure (then G4 needs an exception). Severity: design. Effort S. Blast: §2.6, G4, §3.2, §5.3, O29. Fix: state that on a match-dependent rx only extensional operations and `.label` navigation are allowed (structural ones are a compile error naming why), or carve the exception into G4.
