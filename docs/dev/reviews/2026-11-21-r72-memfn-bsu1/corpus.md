### CORPUS-1 — the `\b[0-9a-f]{32}\b` block's `mc` case expects 0, so find-all continuation is never exercised for the bench's bounded pattern
SUSPECTED weakness (CONFIRMED fact, judgement on strength). gen_span_seed.py `findall_subject` concatenates full+full(shift 1)+near-miss, which §10.1 calls "two back-to-back matches followed by a near-miss". For `\b...\b` the two 32-hex runs abut into one 64-byte word run, so no `\b` falls between them: the emitted line is `mc <96 bytes> 0` (the only `mc` of the 41 that is 0; the other 40 are 2; verified by libpcre2 find-all). Python and pcre2 agree, so the expectation is right, but the §10.1 intent (a find-all that continues after a match) has no positive witness for this pattern; its only positives are the `m` start cases. Fix: for `bounded` patterns separate the matches with a non-word byte (e.g. space). Severity: test strength (low). Effort: 3 lines + regenerate (re-pin the three census counts only if case count changed; it would not). Blast radius: tests/memfn only. Where: tests/memfn/gen_span_seed.py findall_subject; tests/memfn/span_seed.rxt the `mc` line of the \b block.

Severity: design (the U1 identity claim at 4095 is not repeatable from the tree). Effort: low if the gate lands with U2 as §10.1 says; only the U1 wording needs to say "run once by the lane". Where: block_span.md §14 U1.
