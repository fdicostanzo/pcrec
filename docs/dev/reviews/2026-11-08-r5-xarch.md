### Build (consumer-facing; no answer moves)
- **X-1 = EMIT-3** (emit; verified + fix tried). The region encloses the kit's `#include <emmintrin.h>/<immintrin.h>`, so gcc parses the
  intrinsic headers under the target pragma; a consumer TU that `#include`s a `=x86-64-v3` artifact and then uses SSE intrinsics, or that
  includes a v3 artifact and THEN an x86-64 one, fails under gcc -O2/-O0 ("inlining failed ... target specific option mismatch"). BASE
  compiles; clang compiles. Verifier's hand fix (intrinsic includes moved ahead of the region open) compiles both TUs and still compiles
  under `-mno-sse2`. Against match_api §6.3.10 para 15 (lane/u3tgt) / sheet item 4 (includes INSIDE the region, ruled): the argument is that gcc's headers
  carry their own target pragmas, so placing them inside only changes what their inline functions carry.
  **PROPOSED FIX-NOW**: hoist the kit's header lines to file scope ahead of the region (a kit text field "headers" vs "body", or pcrec
  placement), amend  para 15 (lane/u3tgt), add the two repros as compile cells (gcc). Kit + pcrec, small.
- **X-2 = EMIT-5** (emit; verified). A compound (`^\s+|\s+$`, `-p` artifact, not `--emit-main`) at `=x86-64-v3` has its `#include <string.h>`
  INSIDE the region; with Ubuntu gcc's default fortify, any consumer `memcpy` after `#include`-ing it fails to compile. clang compiles.
  **PROPOSED FIX-NOW** (pcrec, small): hoist every non-kit `#include` to file scope ahead of the region open, as `--emit-main` already does;
  same compile cell. Fold HOUSE-5 here (one helper owns open/close).
