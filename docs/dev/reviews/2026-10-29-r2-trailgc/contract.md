# CON (contract) critic findings: trailgc @ 801ad1214

## Findings

### CON-1: the answer is not monotone in the trail capacity below the plain high-water; the spec's "ceiling" wording reads as a threshold
- status: CONFIRMED. `build/pcrec -p rx --features all --engine=vm -o gen.c --pattern '(?:(a)(b){1,3}){2,40}+c'`, subject `"abbb"*20+"c"` (81 B), `rx_search_in` with 1M frames and trail capacity t for t = 0..300: rc is -3 for t < 19, **1 at t = 19, -3 at t = 20, 1 from t = 21** (plain high-water 100). `^((a)(?:(?1)|(b))*+c)$` on `"a"*20+"c"*20`: answers 239-243, gives up 244-249, answers 250-255, gives up 256-267, answers from 271 (hw 432). Driver: scratch `contract/src/map.c`. Cause: the quarter rule is a one-way latch ("stops compacting for the attempt") evaluated at whichever checkpoint first crosses the floor, so a capacity that happens to put that first crossing at a fatter kept-set latches off and a smaller one does not.
- severity: doc (no answer changes; "never gives up where the plain trail answered" holds: every hole is below the plain high-water).
- effort: one sentence in limits.md §4 paragraph 3 (lane/trailgc) and/or match_api §10.3/§10.6: below the plain run's high-water, whether a capacity answers is not monotone in the capacity; the `4n + 17` / `min(nframes/2, (ntrail-17)/4)` ceiling is the specimen's, measured monotone there (n = 7..1200 sampled, no hole). blast radius: callers that search for the smallest working buffer (bisection, "+1 and retry"); "double and retry" (§10.3¶3) still terminates because every capacity >= the plain high-water answers.
- location: docs/spec/limits.md §4 paragraph 3 (lane/trailgc) ("it only moves the give-up later"); docs/spec/match_api.md §10.6¶3 ("the ceiling is predictable from the emitted numbers"); src/gen/emit_vm.c vm_emit_trail_compact (`(size_t)-1` latch).

### CON-2: each compaction walks EVERY live resume frame, so the work is not "four entry visits per trail write": live frames x writes / capacity, unbudgeted (65 s where the same artifact answers in 0.075 s)
- status: CONFIRMED. `build/pcrec -p rx --features all --engine=vm -o gen.c --pattern '^(?:a|ab)*(?:(?>(b))c)*+d'` (one checkpoint); subject `a`x na, `bc` x nb, `d`; `rx_search_in` with 8M frames (driver scratch `contract/src/perf.c`, gcc -O2):

  | na = nb | trail cap | rc | time |
  |---|---|---|---|
  | 1M | 40M | 1 | 0.036 s |
  | 1M | 3,072 | 1 | 2.35 s |
  | 2M | 40M | 1 | 0.075 s |
  | 2M | 3,072 | 1 | 10.9 s |
  | 2M | 512 | 1 | **65.5 s** |

  `(?:a|ab)*` leaves one live frame per `a` (no trail entries in their segments); every compaction (`for (f = 0; f <= run->resume_depth; f++)`) walks all of them to free about `floor - kept` entries, so the cost is about na x nb / cap frame visits: quadratic in the subject. Neither `RX_STEP_BUDGET` nor `RX_WORK_BUDGET` is charged for the walk, so no give-up bounds it. Before K134 the two small-capacity runs returned `PCREC_ERR_FRAMES` at once.
- severity: speed (and doc: the stated bound is false). Answers are right. limits.md §7¶3 already says no single number bounds total match time, so this is not a broken promise of the budgets; it is a false per-write bound in D183/the emitter comment and an unpriced superlinear path that §3.1's work counter (which charges a cut's discarded frames) does not see.
- argues against D183's Why ("The quarter rule caps the work at four entry visits per trail write"), the emit_vm.c comment ("at most four entry visits per trail write, plus the byte map") and limits.md §4 paragraph 3 (lane/trailgc) ("so the work is bounded"): the quarter rule amortises the TRAIL part only; the frame part is O(resume_depth) per compaction with no amortisation, and `resume_depth` is bounded by `nframes`, not by the trail. The emitted comment's "the cost is the trail plus the live frames" is accurate per call but the per-write claim drops the frames term.
- reach: needs nframes >> ntrail. The un-suffixed entries (fast 63/94, deep 2048/3072) keep the ratio below 1, so it is the `_in` entries with a caller buffer (match_api §10, whose own §10.6 example is 1.68M frames) and any artifact whose stamped trail is small against its frames.
- effort to fix: small-to-moderate. Either price the walk into the quarter rule (stop compacting when `resume_depth` exceeds a share of the freed entries, i.e. require `cap/4` freed entries per `cap/4 + resume_depth` visits), or keep a watermark of the lowest frame whose segment changed since the last compaction and start the walk there, or charge `resume_depth` to the work budget. Then state the bound with both terms.
- location: src/gen/emit_vm.c `vm_emit_trail_compact` (the frame loop; the comment's cost paragraph); docs/dev/decisions.md D183 Why; docs/spec/limits.md §4 paragraph 3 (lane/trailgc).

## PROBED-AND-HELD

All probes: review tree build/pcrec at SUBJECT 801ad1214, `-p rx --features all --engine=vm`, generated C + scratch driver `contract/src/diff.c` (gcc -O1; one batch -O2 ASan+UBSan). Per subject the driver runs `rx_search_in` at 1M frames / 4M trail (the reference, trail high-water read off a canary), diffs it against libpcre2-8 (match/no-match and every capture span), then runs EVERY trail capacity 1..400 and ~128 steps per doubling up to the high-water (each must give up with PCREC_ERR_FRAMES or equal the reference rc and full capture array), runs find-all (`rx_iter` + `rx_iter_buffers` + `rx_next`, up to 64 matches) at a capacity ladder against the same at 4M, and the un-suffixed `rx_search` (fast tier + escalation) against the reference.

- **Readers of trail indices, enumerated in emitted C and emit_vm.c (held).** Only three things hold a trail index: `run->trail_depth`, each frame's `trail_mark` (written by `_PUSH`/`_CALL`, read by the fail label's unwind and by the region return's `run->trail[run->resume_stack[run->call_top].trail_mark + j]`), and nothing else: cut marks, the revdet/lookbehind `frame_mark` locals and the work charges hold RESUME depths; `reset_for_next_attempt` unwinds the whole trail; no slot ever stores `trail_depth` (grep of all 1,248 generated artifacts: every `RX_SET`/`RX_TRAIL` slot argument is a constant `RX_SLOT_*`, so `slot_index < NSLOTS` and `seen[]` is in bounds). The compaction rewrites marks for frames 0..resume_depth-1 only; a call frame is live for as long as its activation (every cut mark is taken inside the construct whose cut uses it, so no cut crosses a live call; the base would already overwrite a dead call frame on the next push). `(*COMMIT)/(*PRUNE)/(*SKIP)/(*THEN)/(*ACCEPT)` are refused by this compiler (out of scope / module 'verbs'), conditionals and `(?|...)` refuse as not implemented, so they have no reader to break. `_trail_gc_at` is a local of `<prefix>_match_anchored`, which the attempt loop (`emit_vm.c:13872`, the only caller of `reset_for_next_attempt`) calls once per attempt, so it resets per attempt, per tier (each tier rebinds and re-runs) and per `_next` step. `--allow-code c` artifacts `#undef` the new `RX_TRAIL_CHECK` before the user's code (held).
- **Hand cases, 46 patterns / 196 subjects** (c1/c2: possessive and atomic loops with captures, nested possessive, positive/negative/non-atomic `(?*...)` lookahead and lookbehind with captures in loops, backrefs in loops and across calls, bounded repeats/counters incl. nested `{2,5}+` in `{3,100}+`, lazy and greedy non-possessive loops, `\K` in loops and in recursion, empty-iteration guards, recursion with captures (`^(\((?:[^()]|(?1))*+\))$`, named `(?&p)`, mutual `(?1)/(?2)`, backtracking INTO a returned call after a compacting loop, callee containing atomic/possessive, calls inside atomic/lookahead/lookbehind), utf8 and utf8 `-i`, byte `-i`): ~30,000 capacity runs, 0 answer or capture mismatches, 0 find-all mismatches, 0 default-entry mismatches, 0 libpcre2 disagreements. 44 of them re-run at -O2 under `-fsanitize=address,undefined`: clean.
