### F3. The §5 pragma spelling fails to compile in two common setups (design; hard build failure of a correct artifact)
- (a) `#pragma GCC target("arch=x86-64-v3")` fails when the consumer compiles ABOVE or beside v3: `-march=native` on Zen 4, `x86-64-v4`, `znver4`, `-mavx512f`.
  - The error is `inlining failed in call to 'always_inline' 'memcpy' / '_mm_and_si128': target specific option mismatch`, with and without `_FORTIFY_SOURCE`.
  - `arch=` replaces the TU's ISA set, so file-scope callees compiled for a larger ISA cannot inline.
  - An ADDITIVE ISA list (`target("avx2,bmi,bmi2,fma,...")`) compiles at every flag tried and answers equal (2.36M checks).
  - Consequence to state: under a consumer `-march=native`, the "v3 variant" may carry AVX-512 code. So "planned for its declared target" holds only when the consumer compiles at or below the target, and §7 needs an above-target compile cell (PROBE-1; verified as HOLDS).
- (b) clang ignores `#pragma GCC target`: 20 errors on the v3 variant. Today's `-fmemfn-simd` artifact compiles under clang.
  - `#pragma clang attribute push(__attribute__((target(...))), apply_to=function)` works (0 errors, answers equal).
  - Fix: a compiler-capability `#if __clang__` pair, which is the class §4 already exempts. Per-head attributes would contradict §2's "the kit never writes an attribute": attributing only the kit helpers leaves them out of line (PREM-5, PROBE-2; verified as HOLDS).
- **PROPOSED: FIX-NOW (rev 1 §5, Q4).** Q4's leaning must name the compiler question and the additive form.

- Found by: PREM-2, PROBE-3, SEAM2-6, SEAM2-7, RULE2-14, RULE2-15. Verified: HOLDS.

### F11. The target table: one fact with several homes (design; one SIGILL-class hazard)
- (a) features, attribute string and probe string can disagree, and nobody checks.
