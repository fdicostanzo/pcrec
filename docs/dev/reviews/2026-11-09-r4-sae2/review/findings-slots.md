### SLOTS-3 — T3's rows do not carry their description; the arm re-decides E-1 vs E-4 by a kind test (`a->k == A_EMPTY`), so the table is half a table

### SLOTS-5 — under `\K`, `<PREFIX>_REQ_BYTE` can now be a byte the reported match does not contain; match_api §6.3.7¶4 ("a byte every match must contain") and R-d are not held, and E2 widens the pre-existing case
CONFIRMED. severity doc (answers held: libpcre2 bounds equal on 40 probes); effort small (spec wording, or a pick restricted to after the last `\K`); blast radius callers reading the stamp as a property of the REPORTED match.
Repro: `worktrees/crit-sae2/build/pcrec -p rx --features all --emit-main -o D/rx.c --pattern 'z\Keee'` -> `RX_REQ_BYTE "122"` ('z'), `RX_REQ_RUN "7a656565@0"`; BASE gives `"101"` ('e'), run `656565@2`. libpcre2: `z\Keee` on `zeee` reports (1,4) = "eee", which holds no 'z'. Pre-existing in BASE for the SET alone: `zq\Ke` BASE -> `RX_REQ_BYTE "122"`. Argument against R-d as stated in COMMON ("a byte every match contains"): ¶5 says REQ_BYTE IS the run's scan member where exact, and ¶6 (E2's rewording, R-c) now lets the run lie "partly or wholly before the reported start", so ¶4 is false whenever the member sits before `\K`. D191 ¶2's wording "a byte every match CONSUMES" can be read as attempt-consumed, which would hold; then ¶4 needs the same attempt clause as ¶6 (E2 owns the run-definition wording, R-c, and ¶4/¶5 are the run's member). Also ¶6's own code example comment still says "every match contains \".tar\"" (harmless, but now narrower than the paragraph). Decide: (a) reword ¶4 to "every successful attempt consumes" with a pointer to ¶6, or (b) restrict pcrec's REQ_BYTE pick to positions at or after the last `\K` (D191 ¶2: "chosen by pcrec").
