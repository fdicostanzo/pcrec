### HOUSE-4 — wrapped-malloc live-heap counter (GROWTH_HEAPCAP) can drift negative and turn the cap into "refuse everything"
SUSPECTED (not run: the ASan build is disallowed; reasoning). correctness of the ASan-stage ladder (not verdict; a refusal always passes the ladder, so the failure is a silently weakened cap, which is a 'population nobody counts' lens issue); severity answer-weakening, effort small (count with a (size_t) clamp or wrap strdup, or take usable_size at free only for pointers the wrap allocated); blast radius lib stage under ASan only.
growth_driver.c:121-148 / src/core/sb.c:441: pcrec_sb_take() calls libc `strdup("")` (an UNWRAPPED allocation: --wrap only redirects undefined references in the linked objects, and strdup's internal malloc is inside libc) and the result is later released by `free()` in pcrec objects, which IS wrapped: `__wrap_free` subtracts malloc_usable_size (>=24) that was never added. heap_live is a `long` shared across the whole lib-mode process and never reset (set_cap(0) only zeroes heap_cap). Each such pair drifts it down by ~24-32 B; once it goes below zero, `(size_t)heap_live + add > heap_cap` in over() is true for every allocation, so every CAPPED cell thereafter refuses at its first allocation: the ladder cells pass trivially and the "cap" tests nothing (the same shape as the check-design lesson: a control sharing a source with what it controls). The comment at l.109-111 admits "approximate", but approximate-up/down is not the same as sign-flip-then-total-refusal. Confirm with: count `heap_live` at series end (print it in job_report under GROWTH_HEAPCAP) and check it is >= 0 and < ~1 MB; and that a cap-128M cell on a deep pattern that compiled under the plain build still compiles in the ASan stage. Also `calloc` overflow guard returns NULL without setting errno (fine), and `realloc(q,0)` frees via real_realloc and subtracts correctly.

### HOUSE-6 — hazards in the driver's alarm path and thread teardown
