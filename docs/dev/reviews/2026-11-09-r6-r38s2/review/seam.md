### SEAM-4 — the run pin is a THIRD decider of the run's stretch, and it is pcrec's: §2.5's "pcrec picks nothing on either site" is false
- CONFIRMED. Severity: design (contradicts §2.5 and §12a/D191 item 2's "the kit picks"). Effort: S-M. Blast radius: the window site's run statement; Goal 2's caller-check story. Sheet §2.5 ("§12a's 'one decision' holds on the pcrec side (pcrec picks nothing on either site)"), §4.2.
- Code, the inputs that DECIDE the window site's run stretch (enumerated from the code, not the sheet's list):
  1. `pcrec_run_pin` (`src/facts/kset.c:294-318`): a RATE PICK `x = pos[pcrec_find_pick(rate, cand, NULL, nc, 0)]` (:305) over the exact positions in reverse order (ties rightmost), then the stretch = the maximal EXACT stretch around `x` (:306-307), then the walk fit (:310-316). Inputs: the run as given (`len`, `mask`, `bytes`; today the cut, i.e. also everything `pcrec_find_run_window_start` read), the byte-rate answer `rate` (encoding, `--analysis`), the k-set walk (`k[].count`, `k[].byte`, `nwalk`, bound `PCREC_PREFIX_K_MAX`).
  2. `pf_window_of` (`src/gen/emit_dfa.c:6815-6870`): the pin, then `walk_proves` growth of `[lo, hi)` over `r` (:6838-6839, cubes admitted), gated by `us->kind`, `PCREC_NO_OFFSET_SKIP`, `PCREC_NO_RUN_PREFILTER` (:6823-6824), `parked`/`offer`/`bounded`/reseed (:6820, :6840-6847); it STATES `[w+lo, hi-lo)` to the kit (:6862-6866).
  3. the kit's `mf_wdecide` reply (`run_member`/`run_lo`/`run_len`), read by `ofs_test_of` (:7419-7423, `t->run_bytes = r->bytes + (w->run_lo - (pin.o - pin.at))`).

- So beside `run_decide` (pre-check) and `mf_wdecide` (window site), pcrec's `pcrec_run_pin` picks a scan member by rate and chooses WHICH exact stretch the window site may see (on a run with a masked position, the stretch holding pcrec's `x`); with the whole run (§4.2) this pick is kept, not removed. The stretch the kit sees on the window site is therefore cut by pcrec (around its own pick, and by the walk), on a seam statement (`pcrec_memfn_wspan`, :6864), which §12a ("A run is one contiguous fact: pcrec never splits it") covers as much as the pre-check's.
- `decider_census.tsv` (§2.5) lists `mf_wdecide` beside `run_decide`; it does not list `pcrec_run_pin`.

## Answers to the round's questions

### (a) Q7 — the stamp where no pre-check run part renders: REVERSE the `@` half, ADOPT the row retirement

**Verdict: REVERSE the "no `@`" recommendation as worded; ADOPT retiring `req_run` into `req_whole_run`.**

- Population measured (SEAM-1, build tree, 31 compiled patterns, DFA route): 17 artifacts render no pre-check run part. 12 of them (8 `cover`, 4 `run-pinned`) DO scan a run position, by the window site's kit decision, and today's `@` names exactly that position (every one checked against the emitted `memchr`/starred offset). Only 2 (`rev-end`, `one-attempt`) scan no run position at all; 3 (`landmark-walk`) `memchr` REQ_BYTE. On the VM route (12 patterns) every run artifact is `emitted` except `one-attempt`, so Q7 is a DFA-route question.
- Readers that need the `@` there: `run_encoding_checks.sh` `cover_pick_stamped` (holds the cover find to the stamp's `@`), the [FINDINGS] c2a reader (20 of its 25 committed reach rows are no-part artifacts), the spec's own §6.3.1¶5a/§6.3.7¶7 (SEAM-1, SEAM-2). No pcrec-bench reader parses `@` (opaque string).
- Alternatives judged:
  - the sheet's (whole run, no `@`): drops a real kit scan on 12/17 artifacts, makes C4's population shrink to the emitted ones, blinds `cover_pick_bad` and c2a. Rejected as worded.
  - `@` of pcrec's REQ_BYTE position: a pcrec pick printed as if it were the scan; it agrees with the window site's member only by today's coincidence of rules (`kit_run_member` least mass vs. the window rule's least-mass EXACT, and from L2 REQ_BYTE is consumed-only) and repeats REQ_BYTE. It gives `@` two meanings. Rejected.
  - **WINNER: `@` = the run position THIS artifact's search reads, taken from the reply of the site that renders that search; no `@` only where no search reads a run position.** As a first-match table (memory `pcrec-decisions-as-first-match-tables`): (1) the pre-check run part renders (link tested) -> the Job's `cls.run.scan` (where `has_scan`); (2) a window-site search reads a run member (`run-pinned` prefilter, `cover` find) -> that site's `mf_wreply.run_member` (whole-run index); (3) otherwise -> no `@` (`rev-end`, `one-attempt`, `landmark-walk`: REQ_BYTE already names its byte). One meaning everywhere ("the kit's scan of a run position in this artifact"), so it is Q2 (b) applied to every site, not only to the pre-check; the hex is the whole run in every row (§12b Q3's one run value; Q3 itself is about the run's reach, not the `@`). D124 holds: the `@` is a stamp in the listing's `decisions` section (it already lists `RX_REQ_RUN`), never a fact.
  - C4 then reaches `cover` and `run-pinned` too, against the rendered text (the existing `cover_pick_stamped` is that check's cover half).
- The `req_run` row: ADOPT retirement into `req_whole_run`. After K38-2 its value would be the whole run (= `req_whole_run`) and it may hold no `@` (D124; the ruled F2 "`--emit-facts` lists pcrec's run"); keeping it would be a second spelling of one fact. Readers to move in the same hunk: `tests/codegen/reqcube_check.py:250-259` (reads `idx` from the fact; it must read `@` from the stamp, and its stamp==fact equality becomes hex-equals-`req_whole_run`), `facts_listing.md` §4.1.2¶8/¶8b, and `req_run_maxoff` (read equal to `req_landmark_maxoff` on the 3 rows I listed: `xabcdefghijkq` 5/5, `error: segmentation fault at` 3/3, `[a-z]abcdefghijklmnopqrstuvwx[0-9]` 10/10; once K is position 0's offset both are `whole_maxoff`, so the same one-value argument applies: say its fate in the same hunk).

### (b) §4.2 — the run pin reads the WHOLE run: KEEP the direction (do not reverse), but NOT as written

**Verdict: KEEP "no private 8-window" (reversing keeps a pcrec cut AND pcrec's own rate pick, against §12a); REJECT the text as written, which loses pins (SEAM-3) and keeps a pcrec-side pick (SEAM-4).**

- What moves, measured/derived at the build tree: on run-pinned artifacts whose whole run ends inside the walk (4 of 7 in my samples: `[a-z]abcdefghijkl\d+`, `\w\wabcdefghijklmnop[0-9]+x`, `(?:a|b)abcdefghijklmn\d*z`, `[a-z]abcdefghijklmnop\d+`): the pin offset (PREDICTED from the whole run's offset: `run_pin` 5 -> 1, 7 -> 2, 6 -> 1, 6 -> 1: the stretch grows to the whole exact run), the stated window-site stretch, so `RX_DFA_PREFILTER_OFFSETS` and the compare length (8 -> 12..16 bytes when the kit compares what it is given), and possibly the starred member (`mf_wdecide` over more positions). On runs ending past the walk (3 of 7: `error: segmentation fault at`, `[a-z]abcdefghijklmnopqrstuvwx[0-9]`, `[a-z]{6}abcdefghijklmnopqrstu\d+`) the pin is LOST: `run-pinned` -> another prefilter and `RX_REQ_WHY` `dominated` -> `emitted` (a route flip, a pre-check pass added; SEAM-3).
- Speed: a longer pinned compare costs only on candidates that pass the scan (one or two extra word loads per candidate on a hit-dense subject, fewer false candidates elsewhere): UNMEASURED, small, no route change. The LOST pin is the real cost: a weaker candidate test plus a whole-subject pre-check pass on a common log-literal shape. Not timed (no timing runs in a critic round).
- Inputs that decide the pin and the window site's run stretch (enumerated from code, SEAM-4): the run as stated (bytes, masks, length), the byte-rate answer (`pcrec_find_pick`, encoding and `--analysis`), the k-set walk (`nwalk` <= `PCREC_PREFIX_K_MAX` 24), `us->kind`/`us->cand`, `PCREC_NO_OFFSET_SKIP`/`PCREC_NO_RUN_PREFILTER`, parked/offer/bounded/reseed, then the kit's `mf_wreply`. **Yes, the pin is a third decider of the run's stretch** beside `run_decide` and `mf_wdecide`, and it is pcrec's (a rate pick at `kset.c:305`), so §2.5's "pcrec picks nothing on either site" is false today and stays false under §4.2 as written.
- Recommended form for K38-2's brief (the general form, removing the third decider rather than counting it): the pin states only the run's PLACEMENT on the window site, a fact: the attempt offset of the run's position 0, found where the walk's singletons equal any exact stretch of the run (no rate pick, no "around `x`"), and `pf_window_of` states the WHOLE run at that offset (cubes included, positions past the walk too: the run is contiguous, so a pinned position 0 pins every position). `mf_wdecide` alone then picks the member and the compared stretch (its own priced choice, as the sheet already grants the pre-check). Movers stay one counted population (§5.1 item 4) and now include the `run_pin` row's meaning (position 0's offset) and every pin GAINED on runs that today pin no 8-window inside the walk; no pin is lost by length. Check before adopting: `ofs_test_of` fails loudly when the reply's STOP lies at or past the walk (`emit_dfa.c:7409-7413`, `w->stop >= wk->nwalk`) and when a plan offset OUTSIDE the run term is off the walk (:7436-7438); offsets inside the run term are exempt (:7432-7434). So the window site may state run positions past offset 24, but its scan member must stay inside the walk: either the kit's window rule is told the walk bound as a stated fact, or pcrec's reader is widened; and the kit's guard must hold `c + omin + len <= n` for positions past offset 24 (a W-K-style in-bounds witness). If main prefers the smaller step, the minimum fix is: the stretch is clipped to the walk (`l = min(e0, nwalk - w) - s0`), stated as a CUT pcrec still makes (named in §2.5 as the third decider and listed in the decider count), never silently.
