# CONTRACT findings

## Findings

### CONTRACT-1 — CONFIRMED — a backreference inside a lookbehind is refused with the shape-7 "unbounded" sentence, not the shape-5 capability refusal the spec, D189 and §9¶2 promise
- Severity: doc/diagnostic tier (D26 tier 1-2: "whether a construct is REAL" is exact). Effort: small (a separate LbVerdict arm, or a has-backref test ahead of `la_widths`). Blast radius: every lookbehind holding `\N`, `\g{N}`, `\k<n>`, a `${var}` (module vars), or a `(?C"f,consume")`.
- Spec: pattern_language.md §2.4 shape-5 row: "this instance is beyond what pcrec builds (a backreference inside a lookbehind, §7.4 ...)"; §7.4¶5: "So is a lookbehind containing a backreference (`(a)(?<=\1)`, shape 5)"; §9¶2 lists it among "capability and grammar refusals" of accepted syntax. D189 (SUBJECT decisions.md:10068): "A backreference inside a lookbehind stays refused until stage 2." Shape 7 is "the pattern is not well-formed, or over a PCRE2 length limit ... PCRE2 refuses it too".
- Repro (SUBJECT build/pcrec --features all, byte; libpcre2 10.46 via own ctypes):
  - `(a)(?<=\1)x` -> pcrec "every alternative of a lookbehind must have a bounded length (this one is unbounded) (pattern offset 3)"; libpcre2 ACCEPTS.
  - `(a)(?<=b|\1)x`, `(a)(?<=\1{0,2}b)x` -> same sentence; libpcre2 ACCEPTS.
  - `(?<=${x})a`, `(?<=b?${x})a` (vars) -> same sentence.
  - BASE said "variable-length lookbehind is not implemented: ... (this one is unbounded)", i.e. it was at least worded as a capability limit; the subject drops the "not implemented" framing, so the caller is now told the pattern breaks a PCRE2 length rule, which it does not.
- Code: src/parse/mod_lookaround.c:365-373 comment "EVERY ARM IS A REFUSAL PCRE2 MAKES TOO ([VLOOKBEHIND] stage 1, pattern_language.md §2.4's shape 7)" and :589-591 "EVERY REFUSAL HERE IS ONE PCRE2 MAKES TOO" — false for the backreference/var arm, which reaches LBW_UNBOUNDED through pcrec_cwmax's saturating answer for A_BREF (la_widths :312).
- Expected: a capability sentence for the backreference (what is not built: "a backreference inside a lookbehind is not implemented"), keeping "unbounded" for the cases libpcre2 also refuses (err 125). The spec text needs no change; the code and its two comments do.


### CONTRACT-2 — CONFIRMED — limits.md §3.1¶5's "about K² steps per position" holds only for a single-repeat body; a body that backtracks internally gives up far earlier
- Severity: doc. Effort: one sentence. Blast radius: the spec's only stated bound for the new give-up.
- Spec: limits.md §3.1¶5 "A varying lookbehind that fails at most positions of a long subject is therefore bounded by the step budget, at about `K`² steps per position for an alternative of up to `K` characters".
- The three quoted figures are EXACT (own driver over SUBJECT artifacts, `rx_search` on n bytes of `a`, step budget 500,000,000): `(?<=a{1,254}b)` 7889 -> 0, 7890 -> -2; `(?<=a{1,127}b)` 30842 -> 0, 30843 -> -2; `(?<=a{1,32}b)` 473506 -> 0, 473507 -> -2. 500e6/7890 = 63,371 vs 254² = 64,516, so K² is right FOR THAT SHAPE.
- Counter-examples (byte, all-`a` subject): `(?<=(a{1,120}){1,2}b)` (K = 240, K² predicts ~8,700 bytes) -> PCREC_ERR_STEPS already at 1,000 bytes; libpcre2 answers no match at 1,000 (2.35 s), 7,890 and 20,000. `(?<=(?:a{1,15}){1,15}b)` (K = 225) -> STEPS at 1,000 (libpcre2: -47 match limit). The per-candidate cost is the body's own backtracking, times up to K candidates, so the per-position cost is K × (body cost), not K².
- Still within contract elsewhere: §9¶3 allows a give-up where libpcre2 answers, and no case gave FRAMES or a wrong answer. Fix: "at about `K`² steps per position for a body that is one repeat of a one-character item; a body that backtracks within itself multiplies that by its own cost".

### CONTRACT-4 — CONFIRMED — width-refusal wording names the wrong fact in three corners (D26 tier 3; one is a false statement)
- Severity: doc (diagnostic). Effort: small. Blast radius: patterns with saturating or mixed-violation lookbehinds.
- (a) A BOUNDED alternative whose width saturates is called unbounded: `(?<=(?:(?:a{65535}){65535}){65535})x` -> "must have a bounded length (this one is unbounded)"; libpcre2 err 187 "lookbehind assertion is too long". Same for `(?<=(?1))x((?:(?:(?:a{65535}){65535}){65535}){65535})`. (BASE said "unbounded" too, but BASE's arm was a capability refusal; now the sentence asserts a fact about the pattern.) Two levels (`(?:a{65535}){65535}` = 4,294,836,225) report correctly, so it is the PCREC_W_UNBOUNDED saturation at mod_lookaround.c:312 conflating "too big to count" with "unbounded".
- (b) A VARYING alternative over the ceiling uses the fixed-form verb: `(?<=(?:a{0,65535}){65535})x` -> "(this one has 4294836225)"; the cap arm says "can match up to".
- (c) Alternatives are checked last-to-first (mod_lookaround.c:309 `for (int i = nbr - 1; ...)` returns at the first violation), libpcre2 reports the first: `(?<=a+|(?:b{65535}){2})x` -> pcrec ceiling "has 131070", libpcre2 err 125 unbounded; `(?<=(?:b{65535}){2}|a+)x` -> pcrec unbounded, libpcre2 err 187. Offsets agree (0). Tier 3, courtesy only; listed because "this one" then names a different alternative from PCRE2's.
