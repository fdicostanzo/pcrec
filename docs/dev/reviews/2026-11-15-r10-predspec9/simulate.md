## Findings

### SIM-1 CONFIRMED (answer; effort M; blast: §2.6 req. 1 + HAND CHECKS method, §8 search bullet, §4.5 "a search's hits are that parse's", L52/L55/L57/L58 wherever the argument carries a group read by a backreference or conditional)
Location: §2.6 lines 596-600 ("That is PCRE2's find-all order ... for an argument that cannot match empty") and 628-633 (the loop "UNROLLED into nested optionals with one capture group per iteration (equal to the loop in priority for an argument that cannot match empty)").
Claim tested: for a NON-nullable argument, the loop's hits = PCRE2 find-all = the unrolled form. FALSE when the argument's own group is read by a backreference or a conditional: PCRE keeps a group's capture from an EARLIER iteration of the loop, while find-all and the unrolling start each hit with the group unset.
Repro (simulate/oracle.py + adv.py, libpcre2-8 10.46 public API, ANCHORED|ENDANCHORED; python `re` agrees on the loop):
- x = `(?:(?<c>a)|b)c(?(<c>)a|d)` on `acabcd`: body `(?s)(?:.*?(?<hit>x)){0,}.*` -> last hit (0,3), i.e. ONE hit `aca` (iteration 2's conditional sees c = `a` from iteration 1 and fails); find-all and the unrolling -> TWO hits `aca`@0, `bcd`@3.
- x = `(?:(?<c>a)|b)\k<c>?c` on `ac bac`: loop's last hit = `bac`@3 (the backref reads iteration 1's c); find-all/unrolled -> `ac`@0, `ac`@4.
So the draft's definition (PCRE's parse of the loop, RULED "always") and its stated equivalents (find-all, the unrolled hand-check method) give different hit sets and counts. Fix options: (a) state that hits are the LOOP's parse and drop "= find-all" / "unrolling = loop" except for arguments with no backreference/conditional on their own groups; or (b) refuse such arguments in `search` (like the nullable refusal); or (c) specify a per-iteration capture reset (then it is not PCRE's own parse of the written body). Backreferences to finite groups are default-level ([BACKREF-FINITE], §11) and conditionals are not in the strict-subset refusal list, so the case is reachable.

### SIM-2 CONFIRMED (design; effort S; blast: §2.6 "the argument's labels inside it", §4.2/§4.3 unset-vs-repeated boundary, L36/L52/L55, §2.6 owner's example `$m.hit[2].g`)
Location: §8 line 1531-1532 ("each hit ... is one iteration of the repeated label `hit`, with the argument's labels inside it"); §4.5 line 1044-1047 (a condition reads PCRE's own parse).
An argument label inside an OPTIONAL part is not unset on a hit that skips it in PCRE's parse: it keeps the value of an earlier iteration, LYING OUTSIDE the hit. x = `(?<g>a)?b` on `abb`: loop (libpcre2 and python `re` agree) -> last hit `b` (2,3) with g = (0,1), i.e. hit 2's "g" is hit 1's `a`. The unrolled form gives hit 2 g UNSET. So `(m: search(/(?<g>a)?b/) & (g: "a"))` ("every hit has g = a") holds on `abb` if g is read from PCRE's parse literally and fails/warns `label.unset` under the per-iteration reading the draft's hand checks use. The draft does not say which; §4.2's "`?` makes n SET ONCE, here UNSET" (L56) suggests the latter, §4.5's "PCRE's own parse" the former. Needs one sentence (a label of a hit is read within that hit's iteration, unset if the iteration did not set it), and that sentence is then a stated departure from PCRE's raw capture state, same root as SIM-1.

### SIM-3 CONFIRMED (doc; effort S; blast: §2.6 line 563, §8 lines 1515-1516 and 1529-1530, every hand-check claim "run on libpcre2")
Location: §2.6 line 563 `search(x, min = 0) := /(?s)(?:.*?(?<hit>${x})){${min},}.*/`; §8 line 1516 `endsWith(s) := /(?s).*?${s}/`, `startsWith(s) := /${s}(?s:.*)/`; the disclaimer line 569-570 ("it does not reach into the hole, a literal's flags are never inherited by a hole's pattern").
The bodies are correct ONLY under §11's hole semantics (own flags, own group numbering, a hole is one sub-pattern); EXECUTED AS THE TEXT THEY ARE WRITTEN IN (spliced, as anyone reproducing the hand checks would), libpcre2 gives other answers:
- `(?s)` leaks into the hole: `search(/a.b/, min = 1)` on `a\nb` -> hit `a\nb` (True) spliced; with the hole scoped `(?-s:a.b)` -> rejected, which is what `/a.b/` as a set says (False). `endsWith(/a.b/)` on `xa\nb`: spliced True, scoped body `(?s:.*?)a.b` False.
- endsWith/startsWith put the hole UNGROUPED: `startsWith(/a|b/)` on `ax` spliced (`a|b(?s:.*)`) False, grouped True; `endsWith(/a|b/)` on `xb` spliced False, grouped True.
- numbered groups renumber: `search(/(.)\1/, min = 1)` on `xaay` spliced -> REJECTED (`\1` now names `hit`); find-all finds `aa`@1.
- `search(/(?<hit>a)/)` spliced -> compile error "two named subpatterns have the same name" (O55's placeholder collides with a user label).
startsWith already uses the scoped `(?s:.*)`; writing all three bodies with SCOPED gaps (`(?s:.*?)`) and `(?:${x})` around each hole makes the text mean what it says and removes the dependence on O32 for the gap flag. At minimum say the hand checks wrapped the argument (they pass only for the eight table rows because none has `.`, top-level `|` outside `(?<hit>...)`, or a numbered group).

### SIM-4 CONFIRMED (doc; effort S; blast: §2.6 line 586-589, the claim "`contains` accepts exactly the values with a substring in x")
Location: §2.6 lines 588-589: "What it accepts is unchanged from rev 8's own body `/(?s).*${x}.*/`: as SETS both are the values with a substring in x."
For an ANCHORED argument this contradicts §11/L17 in the same draft: x = `/^err/` read as a set is {`err`}; `x err` has the substring `err` in it (oracle: True), yet `contains(/^err/)` on `x err` is REJECTED (loop: False; L17 = `startsWith("err")`). Same for `(?m)^`/`$` arguments. The sentence holds only for arguments without `^`/`$` (edge lookarounds and `\b` are refused, so those are the only exceptions). Fix: "the values in which x matches IN PLACE (its `^`/`$` reading the value's ends)", or scope the sentence to anchor-free arguments.

### SIM-5 CONFIRMED (design; effort S; blast: §11 THE FILTERED SPAN, §2.6 THE ANCHORED ARGUMENT, the unwritten mirror of L17)
Location: §11 "In a filter, `^` and `$` mean the START and END OF THE SPAN BEING FILTERED"; §2.6 lines 612-616.
PCRE's `$` (no `(?m)`, no DOLLAR_ENDONLY) also matches BEFORE A FINAL NEWLINE. Under the one reading (PCRE's own parse of the body) `contains(/err$/)` on the value `err\n` ACCEPTS (loop hit (0,3)), while `endsWith("err")` on `err\n` REJECTS and `/err$/` as a whole filter on `err\n` REJECTS (ENDANCHORED). So the mirror of L17, `contains(/err$/)` vs `endsWith("err")`, is DIFFERENT on values ending in `\n`, and a hit can end one character before "the span's end". The draft never says whether `$` in a filter is `\z`-like (span end) or PCRE's `$`; E-FILE and E-CTX-7 suggest values that may carry line breaks. Fix: state `$` in a set position = the span's end exactly (DOLLAR_ENDONLY-like), or add the L-row as DIFFERENT with its class.

### SIM-6 CONFIRMED (answer; effort S; blast: §12.9 E-HTTP's expected answers; §12 preamble "Subjects are searched ... unless the program anchors"; any `occurs.exactly`/`at_most`/`none` over a `list_of` in a SEARCHED program)
Location: §12.9 (program `headers & occurs.exactly(1, ...) & occurs.at_most(1, ...) & occurs.none(...)`; "Expected: ... two `host:` lines -> no"); §12 preamble line 1718-1719; D196 (freeze 782502e99, decisions.md:10203-10206: "leftmost start, then the left operand's first-preferred end the right operand accepts").
Applied literally: the program has no anchor and E-HTTP (unlike E-CAL's "(whole subject)" and E-IPV4's "whole-subject test") states no whole-subject mode, so it is SEARCHED. At start 0 `headers`' greedy preference offers the 2-header end first (rejected: two Host), then shorter ends; the 1-header span `Host: a` is in `headers` and meets all three counts, so D196 reports it. Oracle (ex12.py: `headers` as `token:[^\r\n]*(\r\n token:[^\r\n]*)*`, ends tried longest first, counts checked per span): `Host: a\r\nhost: b` -> MATCH `Host: a` (0,7) where the draft expects NO; likewise `Host: a\r\nTransfer-Encoding: chunked` -> MATCH `Host: a`, though the `occurs.none` is plainly meant to reject that block. Fix: anchor the final pattern (`/^${...}$/` or `/\A...\z/`, as E-JSONL does) or state "whole subject" in the case. Not a rev-9 regression (the case is token-identical since rev 7), but the rev-7/8/9 re-checks only asked about ambiguity/some-parse and missed it. A count filter over a repeated label is NOT upward-closed, so in search mode a shorter span always escapes it: worth a sentence (or a warning) in §4.3/§8 near `occurs`.
