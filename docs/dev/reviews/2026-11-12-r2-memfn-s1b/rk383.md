### RK383-1 [r1s1 S1-10] The arm-ENTRY cells name a counter that cannot see layouts L or A
CONFIRMED by reading `$W/memfn/tests/g2/g2_pres_run.c` and `run_g2_pres.sh` one_pass (:262-287).
- The recording build's reads are live only while `g_active` is set: in `measure()` (layout U direct calls) and in `g2p_rec` when `g_call` is non-NULL. `uses()` sets `g_call = lay == LAY_U ? "entry" : NULL` (:538, :545), and `g2p_rec` returns `fn(...)` untouched when `!g_call` (:220). So in layout L no load is counted (`rd`/`rdv` return on `!g_active`). `g_vec` today is therefore a layout-U count.
- Layout A (`lay_a`, :561) is compiled only under `G2P_ASAN`. The ASan build (`-fsanitize=address,undefined -DG2P_ASAN`, run_g2_pres.sh :280-282) has no `G2P_REC`, and the recording build's `-fsanitize=kernel-address` cannot be combined with `-fsanitize=address`. Userspace ASan's `__asan_load*` belong to its runtime, so the driver cannot intercept them.
- The row says the cells count, "per (level, layout), the calls ... that execute a load of the level's width W, counted by width in the recording build (`G2P_REC`, :178-194, already sees every kit load)". That holds for layout U only. It is false for both cells the row names (L and A). `g_vec` also counts every load of 16 bytes or more in one total (:186), not per width. That part is build work, but the row should say so.
- Expected: the row names the vehicle. Either the recording build runs layout L with reads live (set `g_active` without writing records) and also runs a layout-A placement loop (no poisoning; only the entry count), or the cell uses a different counter.
Severity: answer (a cell specified on a counter that reads 0 or nothing for its population; the "w32 layout-A measures 0" claim cannot even be measured as written). Effort: S (text, plus a small driver change at build). Blast: K38-3 item (1) only. Where: span_runs_sheet.md §5 K38-3 row, the `[r1s1 S1-10]` "cells count arm ENTRIES" sentence.

GREEN (NOT DETECTED)` unless the runner also reads asan.log. `plant_expect` would also need an ASan-report pattern, not a `FAIL:` one. Both K38-3 plants make the arm load below `s` whenever floor is small: W-K4a's `floor - 1` at floor 0 reads offset -1; W-K4b's `(s + floor) & ~(W-1)` reads below `s` when the floor is less than s's misalignment. The row's expected detectors (a fault in layout L; an ASan report in layout A) would then not be the ones that red, and the runner prints "RED BUT NOT BY ITS DETECTOR". The proof that W-K4b's ASan witness can red never shows. Confirm with: one `--plant` run of either plant, G2P_NOASAN=1, oracle.log grep `VIOLATION 4`.

Or it confines the plant to layout L/A (e.g. a test-only guard on the planted arm that only fires on a page-aligned or block-aligned `s`), so each witness is the one that reds. The review's own alternative ("re-aim the plant at a detector the no-ASan runner has") may be cheaper: if item 4 reds both plants, the ASan opt-in and mech arm may buy little.
Severity: answer (a plant whose stated detector is never shown red). Effort: S-M. Blast: K38-3's W-K4a/W-K4b plants, the `g2pres-asan` arm's cost justification. Where: §5 K38-3 row, plant column, `[r1s1 S1-11]`.
