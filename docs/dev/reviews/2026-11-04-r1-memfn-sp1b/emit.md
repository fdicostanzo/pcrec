# Critic lens `emit` (emitted-vs-replaced), round memfn-sp1b

SUBJECT cca35ffd1 vs BASE b0f3d0339. Question: does any emitted byte or MFTRACE REACH line move, and where would the new code decide differently from the code it replaces?

## Findings

### EMIT-1 (CONFIRMED by reading; maintenance; effort S; blast radius: every future kit_mass caller) -- `kit_pos`'s zero value is the FULL ALPHABET, not "nothing" or "one byte"
- Where: memfn/src/kit.h:331-334 (`kit_pos`), memfn/src/presence.c:73-88 (`kit_mass`).
- The defect: a position is `{ .set, .t, .mask }` with `mask` meaning "the bits that are fixed"; `.set == NULL` selects the cube. So a designated initializer that omits `.mask` (or a `.set` that ends up NULL) is the cube t|f over f a submask of 0xFF: all 256 bytes. The deleted `cube_mass(rate, t, mask)` took the mask as a required positional argument, and `kit_set_*` dereferenced the set (a NULL would crash, not silently price). Today all five cube call sites state `.mask = 0xFFu` or go through `run_pos` (presence.c:141, 160, 172, 190, plus `run_pos`), and every `.set` site passes an array member (window.c:136 `set[32], yset[32]`, :1097; presence.c's stack `set`) -- so NO emitted byte moves (held by the probes below). The hazard is the next caller: `kit_pos b = { .t = x }` prices x as the whole alphabet (rate sum ~1e6, NONE 1,000,000) with no diagnostic, and a mass that is too LARGE does not fail any answer check (it only demotes a candidate), so only a byte-identity sweep would catch it.
- Repro (reading): with rate NULL, `kit_mass(NULL, &(kit_pos){ .t = 'a' }, 1, KIT_MASS_SUM)` = 256*1e6/256 = 1,000,000, where the author meant 3,906.
- Fix sketch: store the FREE bits (`free`, 0 = exact byte) instead of the fixed mask, so the zero value of a cube position is the exact byte `t`; or a `kit_pos_byte(b)` constructor beside `run_pos` and a rule that cubes are built only through the two constructors. (D186's "no emitted byte moves" holds either way; this is a pre-1c hardening, since 1c adds readers.)
