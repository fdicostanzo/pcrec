# EMIT — crit-sae1
## Findings
### EMIT-1 (CONFIRMED, speed/design, small) — the unit tests the BODY's width, not the REPEAT's: `abc{0}de` still breaks the run that `ab(?:c{0}){3}de` joins
- Repro: `probe.sh byte 'abc{0}de'` -> BASE = SUBJECT `RX_REQ_RUN "6465@0"`; `probe.sh byte 'ab(?:c{0}){3}de'` -> SUBJECT `"61626465@1"`. Both patterns match exactly the same strings (`abde`).
- Cause: `src/facts/req.c` `rb_rep_width0` reads `b->runs.maxw` (the body's) and `rb_rep_unit_into`'s comment states the general fact as "a subtree that consumes nothing"; a repeat with `rmax == 0` of a consuming body (`c{0}`, `(?:xyz){0}`) is also a subtree that consumes nothing, but falls to row 3 (gap of width `rr_rep_w(0,1) = 0`, `all = false`). Likewise a never-matching class (`[^\x00-\xff]` byte) has maxw 1 so `(?:[^\x00-\xff])*` stays a gap (identical B/S).
- Not an answer issue (sound either way); a missed opportunity and a seam in the "width 0" predicate: the general form is "the REPEAT's max width is 0" (`rr_rep_w(rmax, body) == 0`), which subsumes the body test and `X{0}`. Population is tiny (`X{0}` is rare in real patterns), so severity low; ruling-compatible (it widens row 1, it does not move the m>=1 half).
- Effort small (one predicate); blast radius: T2 row 1 only.

### EMIT-2 (CONFIRMED, maintenance, small) — row 1's two halves disagree on the PIECE description: m=0 joins, m>=1 keeps the body's cut
- Repro: `build/pcrec --features all --emit-facts --pattern 'ab(?:\b)*cd'` -> `req_pieces declined decline:one-group` (one joined group `abcd`); same with `'ab(?:\b)+cd'` -> `req_pieces declined decline:not-fixed-width` (cut at the repeat). `req_whole_run` is `61626364` for both.
- Cause: `src/facts/req.c` `rb_rep_unit_into`: at `rmin == 0` `rb_init(v)` makes the desc `pcrec_pd_unit()`, at `rmin >= 1` `*v = *b` copies the body's desc, which for an assertion is `pcrec_pd_none()` (a CUT, `rb_assert_into`). Only `v->runs.all` is forced; the desc half of "consumes nothing, so its two sides abut" is applied at m=0 only. The function's comment says "either way" for the whole value.
- Sound both ways and `req_pieces` is inert today ([RUN-POS-SET] 2p, no pass reads it), so no emitted-C or answer effect; but `walk_arms.def` lists PF_REQ_PIECES as an output of this arm, so the restored-arm sweep and a later piece reader inherit an m-dependent asymmetry nobody chose. Fix: at `rmin >= 1` also set `v->desc = pcrec_pd_unit()` (the body has no bytes, so its desc carries nothing but the cut), or say in the comment why the desc keeps the cut.
- Effort small; blast radius PF_REQ_PIECES of width-0 m>=1 repeats.
