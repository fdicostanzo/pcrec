### MEM-1 — plan_term widened to uint16_t at the seam, but the kit counts compares in uint8_t: wraps at 256
CONFIRMED (kit level, SUBJECT). Severity: maintenance/answer-latent (a reply field lies; no current reader misreads). Effort: small (two types). Blast radius: every mf_wreply reader of plan_term; pcrec only after the raise.
- memfn/src/window.c:227 `uint8_t *pterm;` (wf_dec), :1290 alloc of pcap BYTES, and c_run's counter `uint8_t term = 0;` (window.c:1144, `d->pterm[i] = term++` at :1169). mf_wreply.plan_term is uint16_t since MF_SITE_ABI 30 (memfn.h:1801) precisely so a plan of up to MF_WPLAN_MAX entries can name its compare; the producer still wraps at 256.
- Repro: memsafe/drv2.c (ASan+UBSan build of memfn/src/*.c at SUBJECT). One NONE alternative, 32 verify-YES spans (spans 1..9 of 31 positions, the rest 1 position), every position a 3-member non-shape set; mf_wdecide(NONE) with mf_rows_need's caps -> rc 0, nplan 301, plan_term runs 0..255 then 0..44: plan[0]=1 and plan[256]=265 both carry term 0 (45 non-adjacent pairs share a term id). Expected 0..300 distinct.
- Inside wf_check's bounds at SUBJECT (32 spans x 32 positions); pcrec's own statements at SUBJECT stay <= ~34 plan entries, so pcrec is not reached now. With the HELD raise (MF_WSPAN_POS 4095) a window statement of >256 lone (non one-member, non-cube) positions plans >256 compares and hands its reader a wrapped plan_term; pcrec reaches that only once its own stage 2 states covers past 32 (the COMBINED approximation still routes no cover past 32: 40 sanitized compiles of k 33..4095 in PROBED-AND-HELD took no cover route), so this is latent for pcrec and live for any kit-level caller now. The kit's own find_groups/translate read only ADJACENT equality, so they are unaffected; the defect is the reply contract.
- Fix: `uint16_t *pterm` and `uint16_t term` (or unsigned), alloc pcap * sizeof *pterm. Also worth a static assert MF_WPLAN_MAX <= UINT16_MAX next to the field.

### HOUSE-1 — writers chained inside short-circuit predicates (the shape that produced MEM-2 (a)); OOM read as "differs"
CONFIRMED by reading (consequence CONFIRMED in MEM-2 (a)). Severity: maintenance. Effort: small. Blast radius: memfn/src/window.c wdecide_framed, compose.c define_sel (MF_TRACE).
- window.c:2799-2801: `if (fp->plan_test && !wf_frame_of(...) && !(use && emit_use_refused(...)) && !reply_of(d, out, rows) && !reply_frame(fp, out, rows)) rc = 0; else memset(out, ...)`. Plan B moved the two caller-storage WRITERS (reply_of, reply_frame) into this predicate; a later conjunct refusing after an earlier one wrote is exactly MEM-2 (a), and the `else` repairs `*out` only. House rule (guide: no side effects in predicates; coding.md §4 q1 "one semantic level"): check the storage preconditions (plan, plan_term, plan_test, plan_cap) once, then write in statements.
- compose.c:1380-1384 (MF_TRACE): `int differs = !qr.proof || ask_sel(...) || !kit_class_same(...)` folds a calloc failure (`!qr.proof`, 131,328 B) into "the define-time query's class differs from the define's (r17b_prime.md §4.5 rule 2)", a false invariant breach under memory pressure. Split: OOM -> its own message (or the art's "out of memory"), then the compare.
### HOUSE-2 — the proof range's minimum is spelled twice (mf_rows_need and kit_proof_open)
CONFIRMED by reading. Severity: maintenance (a drift fails LOUD: every minimum-sized caller gets R-cap, pcrec_ctx_fail). Effort: small. Blast radius: memfn/src/compose.c.
- compose.c:1205-1209 (mf_rows_need): `end = min(last + 2, MF_MAX_FWD); if (end < 1) end = 1; proof_cap = end - MF_PROOF_LO`. compose.c:422-427 (kit_proof_open): the same `min(last_s + 2, MF_MAX_FWD)` as R-short's `want`, and the same floor `if (end < 1) end = 1` on `end`. Two spellings of one rule (r45_reply §1 "the range always reaches one past the statement"); the shared abstraction is one `kit_proof_min_rows(last_s)` (or `min_end`) that mf_rows_need returns and kit_proof_open uses for `want` and the floor. R-short stays a self-check of `end` (it already shares its source with `end` by design, so routing `want` through the helper changes nothing about its independence). Not a correctness defect today: 44,966 driver checks found need == proof_n at every case (PROBED-AND-HELD).
### HOUSE-3 — kit_proof_st's storage MODE is encoded by NULL-ness, with two near-identical spellings of opposite meaning
CONFIRMED by reading. Severity: maintenance (a future caller can silently get a proof-less class). Effort: small (an explicit mode enum). Blast radius: kit_class / wf_plan_class callers (compose.c, window.c, tests/memfn/proven_check.c).
- memfn/src/kit.h:604-614 and compose.c:432-445: `st->rows` = caller storage (R-cap); else `st->a` = arena; else a non-NULL `st` with both NULL = "the verdict only" (returns NULL, proof NULL, proof_n 0); a NULL `st` = refusal "no storage". So `&(kit_proof_st){0}` and `NULL` differ only by one indirection, and the first one yields a class that PROVES NOTHING with no refusal, the second refuses. ask_sel (compose.c:1162-1163) has to build both `st` and a separately-NULLed `stp` to land on the right one; kit_legacy_arm (:339) relies on the all-NULL spelling. That is a 4-way if-chain over an implicit mode (coding.md §4 q3: data/enum, not inferred from pointers). Suggest `enum { KIT_PROOF_REFUSE, KIT_PROOF_CALLER, KIT_PROOF_ARENA, KIT_PROOF_VERDICT } mode;` in kit_proof_st, one switch.
- Also: r45_reply rev 6 §5 says kit_legacy_arm takes "a kit-internal scratch of the ceiling size, freed before it returns"; the code uses the verdict-only mode instead (no rows). Equivalent for the verdict (the clip keeps old-field FIND refusal-free) and cheaper, but the design text and the code disagree (doc).
### HOUSE-4 — pcrec_memfn_wspan truncates `len` silently, and the two bounds comments still guard an `mf_wspan.set[]` that no longer exists
CONFIRMED by reading; unreachable today. Severity: maintenance/doc. Effort: small. Blast radius: src/gen/memfn_sites.c, src/gen/known.c.
- src/gen/memfn_sites.c:566-579: the host storage is allocated for the int `len` (n entries) but the span records `w->len = (uint16_t)len` and `core_len = (uint16_t)len`; window_bounds_check (:616-637) runs LATER (pcrec_memfn_window_stated) and reads the TRUNCATED value, so a len of 65,537 would be stated as 1 and pass. Since plan B the host's storage is sized by `len`, so the bound check is now the only line between a truncation and a mis-statement, and it reads after the cast. All 12 present writers stay in bounds (grep: known.c:602/607, emit_dfa.c:1471/6913-6962, every j < len) and every caller's len is <= 34, so nothing moves today. Fix: refuse len outside 1..MF_WSPAN_POS inside pcrec_memfn_wspan, before the allocation and the cast (one site instead of relying on order).
- src/gen/known.c:329-331 (cc_fits: "so `cover_window` never writes past `mf_wspan.set[]` (K7)") and :586-588 (cover_window: "never an overrun of `mf_wspan.set[]`"): stale rationale. Since MF_SITE_ABI 30 the set is pcrec's own arena allocation of exactly `len` rows, so no overrun is possible; what the checks hold now is the KIT's refusal bound (MF_WSPAN_POS/MF_WREACH). Respell the why (coding.md §4.2: comments carry the invariant).
- Note for every sanitizer claim on pcrec's side: the host lists live inside pcrec's arena blocks (64 KB, src/core/arena.c:6), so an over-write by a few rows inside a block is INVISIBLE to ASan; my 110 sanitized compiles (PROBED-AND-HELD) prove only block-boundary safety for these lists.
### HOUSE-5 — wf_stated_offsets heap-allocates a 4,104-byte "seen" table per call, with a silent degraded path
CONFIRMED by reading. Severity: maintenance (minor). Effort: trivial. Blast radius: mf_rows_need (every pcrec ask calls it, src/gen/memfn_sites.c:186).
- memfn/src/window.c:3993: `uint8_t *seen = calloc(MF_WPLAN_MAX, 1)` (4,104 B, one byte per offset) inside a PURE sizing query; on calloc failure it silently counts every position (duplicates included) instead of distinct offsets. The over-count is SAFE (more storage), so this is not a memory defect, but a bitmap of MF_WPLAN_MAX bits (513 B, under R-28's 4 KB frame bar) on the stack removes the allocation and the second behaviour. Out-of-range positions are also counted per occurrence (:4000) — safe for the same reason, but worth one comment line saying the count is an upper bound by design.
