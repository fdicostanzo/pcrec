## Findings (consolidated, with PROPOSED dispositions)

### L1. SIMULATE-1 + CHECKS-1: the layout twin is a whole-.text shift by a multiple of the TU's alignment; it keeps the base's 32-B phase on 20/20 step-1 twins. VERIFY V1 HOLDS.

- `build_cell` links a separate pad object (`pad_object`, `.skip 1040`/`2080`) FIRST, so the linker re-aligns the
  artifact TU's `.text` to that TU's own alignment: L1 shift 1056 (align 16/32 TUs) or 1088 (align 64); L2 2080
  (align 32), 2096 (align 16), 2112 (align 64). Every text symbol moves by ONE uniform shift (38/38): relative layout
  is identical. Step-1 twins: 20/20 == 0 mod 32, 8/20 == 0 mod 64 (uuid36, abc60, lit40 and the A/A lit16: `aa` and
  `aa-twin` share every line phase). L2: 12/18 == 0 mod 32. `.rodata/.data/.bss` move by 0 (16) or exactly 4096
  (22): page offset unchanged; L1 and L2 of a base put data at the same address. `main` (`.text.startup`) moves in
  0/38 (the comment's "and its driver" is not exact; harmless, main is cold and calls `call` out of line in 80/80).
- So the twin perturbs only address bits above the in-line phase (L1i set, BTB index, 4K aliasing), never the
  32/64-B phase of hot loops nor relative layout, which is what a head's different body changes.
- r39 K1: fixed as ruled in FORM (byte-different, timed, gated, printed); the ruling left the perturbation to the
  lane, and this one does not represent the comparison kind it stands for (fix-induced).
- **PROPOSED: FIX-NOW (design, S), with L2.** A twin that moves the in-line phase and the relative layout: an in-TU
  prelude (a file-scope `.skip 16*j` inside the TU, so the TU's own alignment cannot absorb it) with j chosen so L1
  and L2 differ from the base and from each other mod 64, and/or I compiled with another `-falign-functions`/
  `-falign-loops` (another relative layout of the same semantics; the gate proves answers). `dry` prints each twin's
  shift mod 32/64 and REFUSES a twin congruent to its base mod 64. Correct the "and its driver" comment.
