# EMIT findings (crit-covs2code)
## Findings
### EMIT-1 CONFIRMED (contract/answer: compile REFUSED) — a long cover whose emitted code passes the 500,000-byte CODE cap fails the compile instead of running the engine, against limits.md section 3.12¶4 / tuning.md section 2.56¶2
- Repro: `build/pcrec -p rx --window-search-width=4095 -o x.c --pattern '[0-9a-f]{3400}'` -> rc 1, `pattern too large: ... bytes of emitted code (limit 500000) ... A repeat's body is replicated ... try --unroll=1, or raise --max-emit-code-bytes`. Same for `{4000}` (598,546 B), `{4094}`, `{4095}` (612,507 B); `\w{2000}` (515,368 B). `--size-cap=degrade` also rc 1 (`[0-9a-f]{4000}`).
- Expected (spec): limits.md section 3.12¶4 "a width whose artifact exceeds `PCREC_MAX_EMIT_BYTES` also runs the engine, through the size-cap ladder (§8.4), stamped size-cap-retry; the compile does not fail"; tuning.md section 2.56¶2 same. Observed: the ladder does not catch the CODE-bytes cap (PCREC_MAX_VM_EMIT_CODE_BYTES) for the cover route; the compile fails. The same pattern at default width compiles to 19,827 B via the engine (`unanchored`).
- Crossover: [0-9a-f] ~147 B/position (k=3300 ok, 3400 refused); \w ~258 B/position (k=1000 = 260,855 B; 2000 refused); [a-z]/\d ~83-85 B/position. So the legal range 1..4095 is not usable for multi-range classes past ~1900 (\w) / ~3330 (hex).
- The diagnostic is also wrong for this cause (blames a replicated repeat body and suggests --unroll=1, which does not apply to the cover).
- Severity: contract (a spec'd "does not fail" is false; a width the option accepts refuses patterns the default compiles). Effort: small-medium (route the code-cap overflow of a cover artifact into the ladder, or decline C15 by an emitted-size estimate). Blast: opt-in only (default width 32 never reaches it). Site: the cover emission + size-cap ladder (src/gen/emit_dfa.c size check), limits.md section 3.12¶4.

### EMIT-2 CONFIRMED (speed shape; against a ruled item, argued) — the long cover is O(n*k) on a dense near miss; at long k the option is a 100x-1000x regression the spec does not state
- Ruled context: cover_cap.md §11.2 [R-45 reply] "Dense near miss is O(n*k) ... No fix in the first build" (measured at k=32: x6.65). Argument: the ruling's evidence is k=32; the option admits k to 4095, where the per-byte cost scales with k, and the spec (tuning.md section 2.56, limits.md section 3.12) states ANSWER-IDENTICAL and the two cliffs but says nothing of speed, so a caller choosing the option cannot know.
- Repro (gcc -O2 timer over rx_search find-all, 1 MiB subject of ('a' x R + 'g') repeated; no match exists):
  `[0-9a-f]{1000}`: R=500: cover 15.3 ms vs engine 0.4 ms; R=998: cover 72.0 ms vs engine 0.5 ms (x145).
  `[0-9a-f]{3000}`: R=1500: 161.7 ms vs 0.4; R=2999: 499.2 ms vs 0.5 ms (x~1000).
  On match-dense or no-candidate text both are equal (R=1000/100000: 0.3 vs 0.4 ms).
- Mechanism (emitted C, k=40 shown): the horspool skip reads s[c+k-1]; on an in-class byte the verify tests positions 0..k-2 inline with && and on failure shifts by rx_mf1_sh[b] = 1, re-testing up to k-1 positions per byte.
- Also gcc cost: k=3000 cover artifact gcc -O2 1.97 s / 184 MB vs engine 0.35 s / 32 MB.
- Severity: speed (opt-in only). Effort: doc now (one sentence in section 2.56/section 3.12: near-miss cost grows with k), fix is the kit's ASK (4). Blast: callers of --window-search-width > 32.

### EMIT-1 addendum (mechanism, CONFIRMED by the trace compiler)
- `PCREC_MF_ROUTE_TRACE=1 trace/subject/pcrec -p rx --window-search-width=4095 -o a.c --pattern '[0-9a-f]{3400}'` -> rc 1; CANDTRACE shows the ladder took only `drop-premul` (`fallback size drop-premul ... sdr=2`, `attrib size-cap-retry from=drop-premul`), never `drop-anchored`, then refused at 510,342 code bytes. So rung 3 (`fit_anchored_applies`, src/core/compile.c:1150: `anchored_ok && pcrec_cand_drop_anchored_shrinks`) does not apply to the cover artifact, contrary to cover_cap.md §11.1 "compile cost" / §11.2 "A SECOND CLIFF" (rev 5.2 FIND-1), which is the premise limits.md section 3.12¶4 and tuning.md section 2.56¶2 were written from. The total-bytes cap fails the same way: `--window-search-width=4095 --max-emit-code-bytes=3000000 '\w{4000}'` -> rc 1 `1027604 bytes of emitted C source (limit 1000000)`, also with `--size-cap=degrade`.
- The design also named the wrong binding cap: it extrapolated against PCREC_MAX_EMIT_BYTES (1,000,000, "no width up to 4095 reaches it"), but PCREC_MAX_VM_EMIT_CODE_BYTES (500,000) binds first at ~3330 hex positions / ~1900 \w positions.

### EMIT-3 CONFIRMED (maintenance, duplication) — the cover span's kit bounds are checked in four places, three of them now unreachable
- src/gen/known.c cc_fits: `k <= cover_width_limit && k <= MF_WSPAN_POS && k + 1 <= MF_WREACH && k < MF_MAX_FWD`; known.c cover_window: `e->k < 1 || e->k > MF_WSPAN_POS || e->k + 1 > MF_WREACH` -> internal error; memfn_sites.c pcrec_memfn_wspan: `len > MF_WSPAN_POS` -> internal error; plus the new seam `_Static_assert(PCREC_ANCHORED_MAX_STATES - 1 <= MF_WSPAN_POS && ...)` beside cc_fits.
- With the seam assert and `cover_width_limit <= PCREC_ANCHORED_MAX_STATES - 1` (compile.c refusal + limits.h static assert), the three kit-bound conjuncts in cc_fits can never be false; C15's `why` can only ever mean the width limit, yet its comment still says "until the seam carries a counted span the kit's own shape bounds with it". Shared abstraction: the build-time seam assert is the one statement of "a cover fits the kit"; the one run-time refusal is the writer (`pcrec_memfn_wspan`); cc_fits reads only `k <= cover_width_limit(cx)` and cover_window's pre-check goes (or stays only as the writer's). Effort: small; blast: none (0 movers expected; S1131/S3223/S3266 plant anchors would need re-reading). Severity: maintenance.
