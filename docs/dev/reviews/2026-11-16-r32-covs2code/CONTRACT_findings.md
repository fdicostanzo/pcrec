# CONTRACT findings (crit-covs2code)
## Findings
### CONTRACT-1 CONFIRMED (answer / design; high) — a wide cover past the emitted-code cap REFUSES the compile instead of running the engine
- Spec: limits.md section 3.12¶4 "a width whose artifact exceeds `PCREC_MAX_EMIT_BYTES` also runs the engine, through the size-cap ladder (§8.4), stamped `<PREFIX>_ENGINE_SEL "size-cap-retry"`; the compile does not fail." tuning.md section 2.56¶1/¶2 (ANSWER-IDENTICAL; "also runs the engine").
- Repro: `build/pcrec -p rx --window-search-width=4095 -o a.c --pattern '[0-9a-f]{3400}'` -> rc 1, `pcrec: pattern too large: 510342 bytes of emitted code (limit 500000) ...`. Same with `--size-cap=degrade` (rc 1). `[0-9a-f]{4000}`: rc 1, 598542 bytes. At the default width (and with `--memfn=no-window-search`) the same patterns compile rc 0, 19,822 bytes, `unanchored`. Measured growth: {1000} 157,126 B; {2000} 304,124 B; {3000} 451,124 B (all `cover`, ~147 B/position), so the cliff sits near k~3,330 for a 16-byte class.
- Expected: the size-cap ladder retries without the cover (or C15 declines) and the artifact ships `unanchored`/`size-cap-retry`; observed: a compile that succeeds at the default width FAILS at a legal wider width, i.e. the option is not answer-identical (it changes success to refusal) and the section 3.12¶4 sentence is false. Either the ladder has no rung that drops the cover (the sentence was written, not tested), or the cover's bytes are counted after the ladder decision.
- Effort: small-medium (a ladder rung "decline cover" before refusal, or a C15 size estimate); or narrow the spec. Blast radius: every caller passing a wide width on a long fixed-width pattern; with `--window-search-width=4095` the axes W arm, if run over a corpus with long fixed-width patterns, would see compile refusals.
- NOTE: cover_cap.md's own header lists this as OPEN (review r27 READ-3, lane covs2c) for `[0-9a-f]{4095}`; this probe adds that it fires from k~3,330 on a 16-byte class (well inside the legal range), that `--size-cap=degrade` does not rescue it, and that the design's §11.1/§11.2 claim ("drop-anchored ... rc 0", "no width up to 4095 reaches it") is wrong because the failing cap is PCREC_MAX_VM_EMIT_CODE_BYTES (500,000 code bytes), not PCREC_MAX_EMIT_BYTES. Until closed, the spec sentence must not ship as written.
- Where: src/gen/known.c cc_fits (no size term) / the size-cap ladder (limits.md §8.4-8.5) has no cover rung.

### CONTRACT-2 CONFIRMED (speed / doc; medium) — the caller-facing contract for a wide width omits the O(n*k) worst case; at 4095 an untrusted subject drives the cover ~1000x slower than the engine
- Spec: tuning.md section 2.56 / limits.md section 3.12 describe the option as a width choice with "the same answers" and a "cliff"; nothing tells a caller that the cover's worst case is O(n*k) (the kit's own reply, quoted in cover_cap.md §9 Q8 / §11.2: "Dense near miss is O(n*k) ... No fix in the first build", ruled near-miss-fix-later = NO). At the default 32 this is bounded (k small); the stage-2 option lets any caller set k to 4095, where it is not.
- Repro (timing driver calling rx_search in a find-all loop, gcc -O2, subject = ("a"*(k-1)+"g") repeated to 9 MB, no match): `[0-9a-f]{3000}` `--window-search-width=4095` (`cover`): 4.144 s; same pattern at the default (`unanchored`): 0.004 s. k=1000 cover: 0.617 s; k=32 cover: 0.001 s. 900 KB subject: k=3000 0.454 s, k=1000 0.061 s, k=500 0.013 s, k<=257 <1 ms. Time is linear in n (1.8 MB: 0.798 s) and grows superlinearly in k (~460 ns/byte at k=3000).
- Not a ruling challenge (the no-fix ruling stands): the defect is that the caller-facing spec of an untrusted-input-relevant lever states no cost, while every other "answer-identical" axis is a pure speed/size trade. Fix: one sentence in tuning.md section 2.56 (and the lib/pcrec.h comment) naming the near-miss worst case O(n*k) per search, or bound the option below the measured knee until the kit's skip lands. Effort: trivial (doc). Blast radius: any caller passing a large width with attacker-controlled subjects.
- Where: docs/spec/tuning.md section 2.56¶1-¶3; lib/pcrec.h:1732-1742.

### CONTRACT-3 CONFIRMED (doc; low) — the limit's unit reads `positions` while the contract says the width counts BYTES
- `--list-limits` row: `PCREC_DEFAULT_WINDOW_SEARCH_WIDTH 32 positions selection knee flag+-D 3.12`; limits.md section 3.12¶1 "= 32 (positions, ...)" then "(the width counts BYTES of the subject: under -e utf8 a character counts its encoded length, so é{4} has width 8)". Behaviour is bytes (verified: `-e utf8 --window-search-width=7 'é{4}'` -> unanchored, `=8` -> cover; `\x{100}{2047}` cover at 4095, `{2048}` unanchored). Under utf8 a reader of the unit column (limits.md §3.4a¶4 "a count of a thing") takes `positions` as character positions. Fix: unit `bytes` (the row is a byte count; `PCREC_MAX_REQ_RUN_SCAN` already uses `bytes`), drop "positions" from section 3.12¶1. Effort trivial; limits_check.sh reads the unit column, so the doc and row move together. src/core/limits.def:187; docs/spec/limits.md section 3.12¶1.

### CONTRACT-4 CONFIRMED (doc; low) — match_api.md §8.2's struct block and prose do not match lib/pcrec.h for the new field
- Spec block (match_api.md ~3344) puts `window_search_width` directly after `allow_code`; lib/pcrec.h:1742 has it after `memfn_simd`, which the spec's struct block omits (pre-existing omission: BASE's block had no `memfn_simd` either, only its ¶7d prose). A caller reading the spec block gets the wrong layout order (designated initialisers are unaffected; positional initialisers are not). Also §8.2 gives every sibling field (`memfn_simd` ¶7d, `allow_code`, ...) a prose paragraph; `window_search_width` gets only the struct comment pointing to tuning.md/limits.md, so §8.2 states neither the -1/"invalid window_search_width" refusal nor "never clamped" itself. Fix: add `memfn_simd` to the block (fixes order) and one §8.2 paragraph. Effort trivial.
