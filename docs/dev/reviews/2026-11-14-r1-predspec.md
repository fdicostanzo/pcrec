## The first question: Model A (context-marked sets) vs Model B (string sets + context kind)

Consolidated from Q1R-1..13, Q1X-1..9 (verifier: all HOLD; V2 notes "A = B2" is by construction, not measured).

1. **Three candidates, not two** (Q1X-2). "Model B" splits into B1 (value-scoped: a set use reads only the value,
   = rev 0's lean and D193 add. 3) and B2 (a context kind, composed in context). Model A coincides with B2 on every
   match-time `&`, label condition and pattern hole (a context-free pattern's triples are its strings; a
   context-bearing operand is checked against the real subject). A vs B2 differ only where a context-bearing value
   lands where NO SUBJECT EXISTS. The answer-bearing contrast is A/B2 vs B1.
2. **Per rule** (Q1R-1, 25 rows): 12 same under both; 7 different; 6 UNDERDETERMINED under A, every one a place with
   no subject position: `$x ~ rx` (Q1R-6), transform images (Q1R-7, Q1X-6c), computed labels, `enumerate` (Q1R-8,
   Q1X-6b: `enumerate(/(?<=a)[bc]/)` re-joined is not the original), assertions (`@assert.none("5" & /(?<=\$)\d+/)`
   FAILS under A though `5` never matches, Q1X-5), `records` entries and name sets (`@warn.off(/^dead\./)` suppresses
   nothing, Q1R-8). A also has two readings of "context inside the match" (A-s/A1 = the subject; A-m/A2 = the match
   text) with different answers (Q1R-2, Q1X-4); A-m makes a condition's truth depend on how much text the
   enclosing pattern consumed before the label.
3. **The draft's reasoning for A does not discriminate** (Q1R-12 = Q1X-1): `/(?<=\$)\d+/` as a lone literal and
   E-JSONL's `/^${q}$/m` sit in the FINAL pattern, which is searched in the subject under every model. The only real
   argument for A is "a name means the same everywhere" (Q1R-3), which B2 delivers identically at match time.
4. **No §12 example decides Q1** (Q1X-9): 10 of 11 are model-neutral, E-FILE needs a context-stripping rule under A;
   no example puts a context assertion in a condition, transform, `enumerate`, assertion or `!`.
5. **Silent failures under A/B2 (the owner's named defect class)**, all CONFIRMED with the kit:
   - `x: /^S\w*/` after text never matches while `x: startsWith("S")` / `x: /S.*/` match (Q1R-2, Q1X-3(i)); and
     "a set is the strings it matches ENTIRELY" makes `/^S/` = {"S"}, so even at the subject start `x: /^S/` fails
     on "Sab".
   - `\w{3} & /\w+\b/` on `foobar` silently MOVES the reported match foo -> bar (Q1X-2 row 2).
   - repeated label: a `^` condition passes a one-header block and fails a two-header block; adding `m` to the
     condition literal flips it; the program is non-empty, so a never-match check misses it (Q1R-4).
   - complement: `alts & !/^#.*/` keeps `#x` mid-line; `$m !~ /^err/` is always true (silent ACCEPTANCE, Q1R-5).
   Under B1 different look-alikes break instead: `p := /(?<=\$)\d+/` finds `12` when searched but `n: p` can never
   pass; a hole `/a${num}/` vs its pasted text differ; boundaries vanish at hole edges (Q1X-3 (iii)-(v)).
6. **Cost** (Q1X-8, probes reproduced by V12): context-free uses cost the same under every model (no context state;
   A does NOT force context state onto every named rx, only onto uses whose pattern has an EDGE assertion). An edge
   lookbehind in a condition is small as an automaton (`(?:USD |EUR |\$)\d+` 8 states) but today's engine sends
   multi-char lookbehind and EVERY lookahead to the VM, so under A/B2 those conditions are default-level compile
   errors until D196 add. 2's regular-lookaround lowering exists, which §7's named build prerequisites do not list;
   an edge lookahead under A1 can outlive the reported end (deferred acceptance, a tag or reverse pass). B1: zero.
   No §12 example leaves automaton code under any model.
7. **The divergence is statically decidable** (Q1X-3): every disagreement needs an assertion that can read OUTSIDE
   the value (`^`/`\b`/lookbehind reachable from the value's start through a nullable prefix; `$`/`\b`/lookahead
   before its end). Assertions strictly inside agree under all models.
8. **Context-aware nullability is A's one real gain** (Q1R-9): as string sets `/\b/` and `/(?=a)/` are EMPTY, so B1
   would let them escape the `empty.search` rule while they yield empty finds. Any B must compute nullability on
   the pattern in context (A's definition). Also: whether a `^` in the pattern counts as "anchored" for that rule is
   unstated (`(?m)^\d*` yields an empty find per line).

**Proposed answer for the owner (the coordinator's synthesis; the launcher and owner rule):** foundation = STRING
SETS (Model B), with ONE refusal rule for the divergent cases: in a SET POSITION (an `&` operand, a label
condition, a filter body, a hole's set, a compile-time set), an EDGE ASSERTION (one that can read outside the value)
is a COMPILE ERROR naming the fix ("`^` in the condition on x reads text outside x: write `startsWith("S")`, or put
`^` in the pattern that places x"). Values, transform images and compile-time sets are context-free by definition.
Nullability is computed in context. A named in-context form (a library call, no keyword) is added only on a measured
need (D77). Under this rule look-alikes either agree or one is refused: no silent failure, no outer-pattern
dependence, no unbuilt lowering at the default level, and D193 add. 3 (RULED: `^`/`$` in a predicate's regex test
bind to the label) stands instead of being superseded. Two critics proposed different diagnostic shapes: Q1R a
`label.context` WARNING (compare the in-context and isolated readings, show a witness: the twin of
`label.ambiguous`), Q1X an ERROR. The ERROR is proposed because the warning leaves the PARTIAL case (Q1R-4: fails
for some subjects only) working-but-surprising, which the owner's framing names as the defect; the warning remains
the fallback if the owner keeps A. If the owner keeps A: rule A-s (delete "inside the match"), state the three
context-stripping rules (Q1X-6), and add `label.context`.
