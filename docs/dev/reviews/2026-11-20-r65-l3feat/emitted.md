# CRITIC EMITTED: l3feat (r65)

## Findings

### EMIT-1 — CONFIRMED (stamps) / speed SUSPECTED-mixed: the BACK row displaces a K >= 0 run that BASE handed off, and R-1's decline then demotes the forward scan (unpredicted prefilter movers)
- **What.** On movers where BASE's run had K >= 0 and `RX_DFA_PREFILTER "handoff"`, the subject's run pick prefers a BACK run (K < 0); `req_k_reentry_sound` (R-1) then refuses the handoff row, so the prefilter falls to a start-byte row. The comparator (`rn_cmp`/TOP's BACK row, src/facts/req.c) ranks the BACK run without knowing that, on the default route, a K < 0 run can no longer drive the forward scan. Neither §14.2 nor §14.4 L3's census list names a prefilter mover; the REV 3.3 addendum's "of the census's 57 movers no stamp changes under the decline" compares decline vs no-decline, never vs BASE.
- **Observed (sweep 2, 250 lookbehind patterns):** byte default: `(?<=qz)x?a:` handoff -> memchr (run `a:`@K1 -> `qz`@K-2, consumed extent EMPTY); `(?<=a)\Kb`, `((?<=a)z)`, `(?>(?<=a)b)` handoff -> memchr-bounded. utf8: `(?<=qz)x?a:` handoff -> memchr. `-i`: `(?<=foo)bar`, `(?<=e{10})eeeeeqzx`, `(?<=item )done`, `(?<=a{20})b{8}zb{11}` handoff -> byte-class (with `RX_VM_RESEED adaptive-dense -> adaptive`). Repro: `$K/pc base|subject --features all -p rx [-i] --emit-facts --pattern '(?<=qz)x?a:'` and read `RX_DFA_PREFILTER`, `RX_REQ_HANDOFF`, `RX_REQ_RUN`.
- **Measured** (`perf stat -e instructions:u`, `taskset -c 7`, 5 repeats, spread 0.00%, find-all over 1 MB; answers identical base/subject on every cell): `(?<=qz)x?a:` on uniform `[a-z ]` text with no `:`: absent 225,064 -> 2,325,063 (x10.3), rare 250,738 -> 2,276,297 (x9.1); on uniform text WITH `:`/digits/punctuation: 2,097,946 -> 1,831,377 (0.87); on English-frequency text: 361,176 -> 266,960 (0.74). `(?<=item )done -i`: uniform absent +3.9%, rare +4.4%; English absent 2,767,025 -> 1,788,856 (0.65). `(?>(?<=a)b)`: 0.64-0.87 everywhere. So the loss is a function of the subject's byte distribution (the builtin rate prior ranks `qz` rarer than `a:`), worst case x10 when the consumed run's rare byte is absent and the lookbehind's bytes are common.
- **Why it is worse than BASE in principle:** at K >= 0 BASE had BOTH the forward-scan handoff and the run; the subject keeps only the run's VM pre-check, and for `(?<=qz)x?a:` the subject's run has an empty consumed extent, so nothing consumed is scanned at all. A pick that knew the decline (price a K < 0 run as not-handoff on the DFA-prefilter route, or keep the best K >= 0 run for the forward scan) would lose neither.
- Severity: speed (distribution-dependent, worst x10 measured). Effort: small-medium (a row in the comparator or the prefilter table reading the K >= 0 runner-up). Blast: 9 of 182 mover cells (4 streams) in my population; any lookbehind pattern whose consumed part has a short rare run separated from the lookbehind. Site: src/facts/req.c (`rn_cmp`, TOP's BACK row) and the prefilter table's `handoff` row with `req_k_reentry_sound` (src/gen/emit_dfa.c). Design: §14.4 L3 REV 3.3 addendum (R-1) rules the decline loss for `(?<=foobar)\d*x` (where BASE had NO handoff; measured below: subject FASTER than BASE there), not this displacement.

### EMIT-2 — CONFIRMED (speed, find-all heavy): the L3 per-call cost is a whole second scan per call, not "§5.5's per-call step back" of B bytes
- **What.** Where BASE judged the run pre-check `dominated` (e.g. `(?<=foo)bar`: run `bar`, `RX_DFA_PREFILTER "run-pinned"` already scanning `bar`), the subject's BACK run `foobar`@K-3 is no longer dominated, so `rx_search` now calls `rx_reqrun` (memchr for `b` at pos+3, two 4-byte compares, the K < 0 clamp and move) BEFORE the run-pinned prefilter, which then scans the same bytes again. Emitted diff (`perf/a01.{base,subject}/rx.c`): +`rx_reqrun__body`/`rx_reqrun` and `handoff_position = rx_reqrun(subject, subject_length, (search_from >= 3 ? search_from - 3 : 0)); ... rx_prefilter(subject, subject_length, handoff_position, window)`; `RX_REQ_WHY "dominated" -> "emitted"`.
- **Measured** (1 MB, a match every 64 bytes = 16,381 find-all calls; 5 repeats, spread 0.00%): `(?<=foo)bar` 5,141,255 -> 6,063,824 (+17.9%, ~56 instructions per call at B = 3); `(?<=qz)ab` +9.1%; `(?<=a{20})b{8}zb{11}` +10.0%; `(?<=foo)bar --engine=vm` 3,411,092 -> 3,654,513 (+7.1%); `(?<=e{10})eeeeeqzx` +1.9%. The same artifacts win on the decoy subject (consumed part frequent, lookbehind rare): `(?<=foo)bar` 4,371,780 -> 2,063,550 (0.47), and are neutral when the run is absent (0.99).
- **Against the design.** §14.4 L3's measurement card names the cost row as "§5.5's per-call step back in a find-all regime", capped by `lb_bytes`. The measured cost does not scale with B (56 instructions per call at B = 3): it is a second scan per call that a dominated-by-the-prefilter test no longer suppresses, so the cap does not bound it, and the bench cell the card names will measure the wrong mechanism unless it is stated. Either the card is restated (the cost is the newly emitted pre-check in front of an equivalent prefilter), or the dominance rule learns that a BACK run whose consumed extent equals the prefilter's pinned run adds only the lookbehind check (which could be done once on the prefilter's hit instead of by a separate scan).
- Severity: speed (+7..18% on find-all-dense subjects) and doc (card). Effort: doc small; code medium. Blast: every lookbehind mover whose BASE `RX_REQ_WHY` was `dominated` (89 `RX_REQ_WHY` moves in 182 mover cells). Site: src/gen/emit_dfa.c (the entry `emit_req_handoff_rest` before the prefilter call), §14.4 L3 "Measurement card".

### EMIT-3 — CONFIRMED (unpredicted mover; doc/design, not slower): `RX_REQ_BYTE` moves 122 -> 97 on `(?<=xyz)a+xyz`
- **What.** BASE run `axyz` (K unbounded, `req_byte` `z` = 122); SUBJECT picks the BACK run `xyza`@K-3, whose consumed extent is the single `a`, so `req_byte` (read only from the consumed extent, D-5/D-6) becomes `a` = 97, a byte the builtin prior rates far more common than `z`. Same on `--engine=vm` and `-e utf8` (`rate:none(utf8)->rightmost`). §14.2 predicts no `RX_REQ_BYTE` mover at L3 (its only `req_byte` remark, `(?<=qz)ab`, "stays 97 or 98"), and §14.4 L3's census list does not hold it.
- Repro: `$K/pc base|subject --features all -p rx --emit-facts --pattern '(?<=xyz)a+xyz' | grep -E 'RX_REQ_(BYTE|RUN|HANDOFF)'`.
- Measured: not slower (absent 2,825,690 -> 1,584,169; common 0.82; decoy 0.33), so the stamp move is the finding, not the speed: the pick trades the consumed run's rarest byte for a K-bounded run, and with R-1 the bounded K is used only by the VM attempt loop. A census row (and a rule line in §14.2) is owed; a pick that compared consumed-extent quality as well would keep `z`.
- Severity: doc (+ design question). Effort: small. Blast: 3 cells (byte, vm, utf8) in my population. Site: src/facts/req.c (TOP's BACK row vs the consumed runner-up).

### EMIT-4 — CONFIRMED (unpredicted mover vs §14.2's own row; doc): `(?<=ab)(?<=cb)c` gains a run although §14.2 says L3 leaves it "none, why `dead`"
- BASE: `req_whole_run` none, why `dead`, `RX_REQ_WHY "dominated"`. SUBJECT: `req_whole_run` `6263` (`bc`) with why STILL `dead`, K -1, `RX_REQ_WHY "emitted"`, `RX_REQ_HANDOFF "-1"`: the BACK row joined the two guards' shared byte `b` and dropped the contradicting position −2 (`a` vs `c`) instead of keeping the dead verdict. §14.2's row: "`(?<=ab)(?<=cb)c` | none; 0; dominated | none, why `dead` (guard against guard at −2) | same". Answers fine (`diff3.sh '(?<=ab)(?<=cb)c' 'abcbcab' ''` -> both OK). Same shape: `y(?<=ab|cd)z` (`797a` -> `61797a/fdffff`, why `dead` both, pre-check newly emitted). `never_matches` stays `no` on both.
- Effect: a never-matching pattern now carries an emitted pre-check (harmless; if anything faster). Either the row in §14.2 is corrected, or the walk should keep `dead` (no run) when the BACK join meets an empty position.
- Severity: doc. Effort: small. Site: src/facts/req.c / kset walk; design §14.2 row.

### EMIT-5 — CONFIRMED (unpredicted stamp mover; speed mixed): the 32-byte run clip keeps the lookbehind and drops consumed bytes, `RX_DFA_PREFILTER_OFFSETS` shrinks 20 -> 12
- `(?<=aaaaaaaaaaaaaaaaaaaa)bbbbbbbbzbbbbbbbbbbb` (byte): BASE run = the 20 consumed bytes `b{8}zb{11}`, offsets `0..19` (8*); SUBJECT run = `a{20}b{8}zbbb` (32 bytes, K -20), the clip at the stored bound cuts the consumed tail: `RX_DFA_PREFILTER_OFFSETS "0,...,19" -> "0,...,11"`, `run_pin 0 -> 0:20+12`. §14.2 rules the clip for `(?<=a{32})b` (lookbehind-only run) but names no case where the clip REMOVES consumed positions BASE had; the offsets stamp is not in any predicted list.
- Measured: absent 1,715,525 -> 1,485,649 (0.87), rare 0.87, common +10.0%, decoy 0.97. Under `-i` the same pattern also takes EMIT-1's handoff -> byte-class demotion.
- Design question: when the joined run exceeds the bound, clipping from the LEFT (dropping lookbehind bytes, which nothing but the pre-check reads) keeps every consumed position the pin and the prefilter offsets read.
- Severity: design/speed (minor). Effort: small. Site: src/facts/req.c (the clip in TOP's BACK row).
