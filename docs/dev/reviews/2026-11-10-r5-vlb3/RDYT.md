## Findings

### RDYT-1 — SV2 is NOT seen only by the VALID_LB compare: the cap-boundary cell in the same gate also sees it (the sabotage row cannot prove the new check is needed)
CONFIRMED (by construction from the build tree's code + oracle). Severity: maintenance (check design). Effort: one line in §6.2.7. Blast: SV2's mech verdict. Design §6.2.7 SV2, §6.2.6 gate 3.
SV2 is "the column's `hi` + 1 on a varying row". §6.2.6 gate 3 says EXTRA "gains every cell of §6.2.5", which includes the cap boundary `(a{1,255})(?<=\1)x` (libpcre2 ACCEPT lb 255, checked). With `hi`+1 that row's hi is 256 > LA_LOOKBEHIND_VAR_MAX, `la_widths` rule 3 refuses (mod_lookaround.c:334-339), pcrec refuses, libpcre2 accepts → `pcre2only` grows → `VLB_ACC_EXPECT` (run_lookaround_diff.sh:444) goes red WITHOUT the VALID_LB compare. Also `(a{1,127})(?<=\1\1)x` (254 → 256 summed) and gate 1's cap-class cells. So mech scores SV2 DETECTED even with the VALID_LB compare deleted: the control shares a source with what it controls (learnings §3). The doc itself half-says this ("the classification control sees it only at the cap").
Fix: state SV2 as "+1 only where the row's `hi` < 254 and no cap-boundary cell is reached" (or plant `hi+1` only when `hi+1 <= 255` after summing), and say the witness's detector is the compare "and, for cap-boundary cells, the accept-set pin". Then "ONLY" is true for the planted shape.

### RDYT-6 — spec hunk gap: the reference-free lexical-bound refusal `(?<=(?:a+){0}x)y` is stated only inside the new BACKREFERENCE paragraph ¶5c, while ¶5's own sentence says the opposite
CONFIRMED (text + libpcre2 err 125 at offset 0). Severity: doc (D80 contract). Effort: one clause. Design §6.2.8 (¶5, ¶5c bullets); build tree pattern_language.md:480.
§7.4¶5 says "An alternative that can match an unbounded number of characters is refused". `(?:a+){0}x` matches exactly one character, so a reader of ¶5 concludes `(?<=(?:a+){0}x)y` compiles; stage 2 refuses it (and libpcre2 does). The hunk lists it only in ¶5c ("backreferences"), where a reader of a reference-free lookbehind will not look. It is a STAGE-1 rule change (the stage-1 sibling of F5).
Fix: ¶5's sentence gains "boundedness is read from the pattern's text, so an unbounded repeat under `{0}` still refuses (`(?<=(?:a+){0}x)y`), though it counts 0 characters (`(?<=(?:a{1,300}){0}x|b{1,2})y` compiles)"; ¶5c keeps the reference examples.

### RDYT-7 — spec hunk gap: a duplicate-name refusal REACHED through a group or a call is in no hunk
CONFIRMED (libpcre2 err 125 at the lookbehind's offset: `(?J)(?<n>a)(?<n>b)?(c\k<n>)(?<=\3)x` offset 27, `(?J)(?<n>a)(?<n>b)?(?(DEFINE)(?<g>\k<n>))(?<=(?&g))x` offset 41). Severity: doc (D80). Effort: one bullet. Design §6.2.8 (§7.3¶6, ¶5c, §2.4 shape 7).
§6.2.2 rule 1 refuses an `nrefs > 1` reference "on the width path of the body or of any reached row". The hunks state only "a backreference INSIDE a lookbehind ... by name, to a duplicated name, is refused" (§7.3¶6) and shape 7's "a backreference by a duplicated name". In both cells above no reference is written inside the lookbehind, yet they are refused. ¶5c lists the unbounded and re-entry reach rules but not this one.
Fix: ¶5c gains "it is refused when its length reaches a by-name reference to a duplicated name, inside it or through a referenced or called group (`(?J)(?<n>a)(?<n>b)?(c\k<n>)(?<=\3)x`); a reference under a nested lookahead is not followed".

### RDYT-8 — gate 7's "a refusal given for the wrong reason turns a row red" holds across THREE sentences, not across the nine classes

That is the G3 design (one fact), so nothing is broken; the F8 claim should be narrowed to "a refusal given under the wrong SENTENCE", and the per-class rows described as compile-vs-refuse witnesses.
