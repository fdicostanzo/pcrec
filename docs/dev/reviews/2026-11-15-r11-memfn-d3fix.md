### D3F-2 - the gate pins COUNTS, so a membership swap is green; the recorded reason "counts suffice" is refuted. FIX SOON

Run G (runG_inplace_swap.log): an in-place edit of one corpus file that LOSES a census witness (`0x[0-9a-fA-F]+` ->
`0x0fA`) and GAINS another (`\S+@\S+` -> `0y[0-9a-fA-F]+`), compile count unchanged:

    D3-FLOOR byte/c-default compiles=5030 failed=486 records=380 census=78 floor=78 ... ok
    (all four cells ok; byte/c-vm records 1056 inside the records band)   32/32 plants   rc=0

NOTES.md / the d3_floor.py docstring now say "the counts suffice in the gate: pin <= census_floor <= census". They do
not: a lost witness paired with any gain is green. The realistic path is the RE-PIN itself, not a coincidence. With D3F-1
fixed, every corpus addition demands a re-pin, and the procedure ("rerun, copy the numbers") silently absorbs any loss
that landed in the same interval (run C's shape: lose one, add one, re-pin to the same numbers). The same holds for the
`failed` pin: a crash in one pattern plus one new deliberate reject keeps it exact.

Disposition: pin the census as a SET, not a count. A committed per-cell list of pat_hex (about 620 lines total), checked
as "every pinned member still hits" (lost = red, named by pattern) with gains printed as info. The same for "compiled at
pin time and now fails". A `--repin` mode writes the files and prints the member diff, so a re-pin shows what it absorbs.
This retires the bands and most of the count pins (the population checks for empty/truncated sweeps stay), and corpus
growth stops being a red. The movers relation (movers in census) then becomes a subset check on a file, which is cheap to
add to the gate. PLAN row if not done in this landing; the NOTES/docstring sentence "the counts suffice" must go now
either way (it is false).
