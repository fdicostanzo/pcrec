### SLOT-1 — `fused` and the stream renderer table both answer "who renders the stream" on E-stmt PF-arm sites (CONFIRMED by the design's own text; severity design; effort S; blast: 3.0b's G2 agreement and Goal 5)
§2.6.1 lists the composer's `fd_renderers` arms (pf_memchr, pf_walk, ...: `compose.c` :272-289 at a678d0a4e) as SEARCH renderer rows, "a search only; the caller restarts and checks", and §2.6.2 gives that frame the stream row S-caller. §2.6.3 then lists the same PF arms as FUSED rows on E-func/E-stmt ("the PF arms"), and §2.3 sets `fused` = `mf_result.form_id` on every E-func/E-stmt ask (3.0b's G2 asserts `form_id = fused`). By §2.3's own definition a fused renderer "renders search, stream and check as one piece". So on an E-stmt translated site that T-FIND routes to D1 (pf-memchr), the reply says `method` D1, `stream` ONESHOT (from S-caller's composition) AND `fused` "pf-memchr" (the triple is not composed): two slots answer one question with opposite answers, and `fused` can never be `""` on E-func/E-stmt, so §2.8's "fused empties as fused rows are re-expressed" cannot be reached for the composer at all (arms[] is a named exception whose trigger is "a kit request adds an arm").
Repro: read plan_frame.md §2.6.1 row `composer`, §2.6.2 row S-caller, §2.6.3 row "E-func, E-stmt", §2.3 `fused`; `git show a678d0a4e:memfn/src/compose.c | sed -n 1309,1316p` (form_id = r->arm->id for every arm). Expected: one of the two homes. Fix: either the composer's PF arms are composed (fused `""`, method + S-caller + "the caller's check") or they are fused (drop the composer rows from the search/stream renderer tables and keep `fd_renderers` as part of arms[]'s exception). The first is the general form; it is what §2.6.1 already says.

### SLOT-2 — the renderer tables key on a frame vocabulary ("composer") that is not T-FRAME's; the reply's `frame_row` cannot look a row up (CONFIRMED by text + code; severity design; effort S)
T-FRAME's rows are E-func, E-stmt, E-find, E-generic (`window.c` :1601-1621 at a678d0a4e, `wf_erows`). The search and stream renderer tables (§2.4, §2.6.1, §2.6.2) are keyed by {E-find, E-generic, `composer`}; `composer` is defined as "the arms that render E-stmt's translated site AND every non-plan FIND site" (§2.4), i.e. part of E-stmt (and E-func) plus sites that have no T-FRAME row at all. So two vocabularies answer "which frame": the reply's `frame_row` and the renderer tables' key, and no table maps one to the other. §2.3 claims "(`frame_row`, `method`, `stream`, check) determine the renderer rows through the renderer tables" (a Rust emitter rereading the reply, memory pcrec-plan-as-text-seam): for `frame_row` E-func or E-stmt there is no row under that key, and E-func/E-stmt have no stream renderer row, though Table S still answers ONESHOT for them (§2.5.3). §2.5.4 rule 2 ("the frame has a stream renderer row for it") therefore never holds on E-func/E-stmt either. Fix (general form): key the renderer tables by T-FRAME's row ids, with the non-plan FIND sites named as arms[]'s exception (their own key, outside the reply), so the reply's ids ARE the lookup keys. Trigger to go further (a frame row per non-plan site): arms[]'s own ("a kit request adds an arm").

### SLOT-3 — "this frame renders stream X" is read in three places with three different rules; Table S's row order is an unmeasured choice (CONFIRMED by text; severity design; effort S)
(i) §2.4's renderable set: a pick is renderable iff a search row exists AND a stream renderer row exists for ONE of its supported streams; (ii) Table S's S-mask reads "the frame has a MASK stream renderer row", while S-shift ("support is {SHIFT}") and S-oneshot ("supports ONESHOT, or no search") read no frame fact; (iii) §2.5.4 rule 2 re-requires a stream renderer row for Table S's pick. These are one fact answered three ways, and they can disagree: a future search whose support is {SHIFT, ONESHOT} fails S-shift (not exactly {SHIFT}) and is silently given ONESHOT by row order; one supporting {ONESHOT, MASK} on a frame with a MASK renderer gets MASK by row order with no evidence. That second case is a CHOICE change under D186 (which unit where; bar: per-regime evidence), yet §2.5.3 calls Table S "a rule, not a priced row" and §6 says the two-stream choice is row 1's priced row. As declared, the first MASK stream renderer row (the inline one-member finder's unit, §6) would flip every MASK-capable site to MASK through S-mask's position, unmeasured (memory pcrec-no-silent-defaults: a default that gets USED). General form: Table S's input is support(pick) INTERSECT renderable-streams(frame), computed once (the renderable set already needs it); 3.0's rows are "exactly one stream -> it" and "none -> refuse"; a set of two or more is refused until a row with evidence exists (row 1's priced row, or a hand row with D186 evidence). Trigger: the first search with two supported streams on a frame that renders both.

### SLOT-4 — in 3.0 `stream` is a derived slot: a pure function of `method` through the support table; the third piece is the kit's reading, not the owner's ruling (CONFIRMED by text; severity design; effort S to rule; blast: one seam member, Table S, MASK, the stream renderer table)
Every BUILT pick in §2.5.2 has exactly one supported stream (LIBC, LIBC_BACK, WALK, PAIR: ONESHOT; HORS: SHIFT); only the italic, unbuilt rows have two. Table S's S-mask never holds (§2.5.3). So `stream` = SHIFT iff `method` = D-hors, else ONESHOT (§2.3 says so), i.e. the reply carries one fact in two members, and the support table is in substance a column of the search (keyed by `fd_form`, the pick), not a separate piece. The owner's words (COMMON) are "Candidate search and candidate validation are two different primitive pieces that are composed": TWO pieces. The record's "The kit's reading is a triple" is the kit's gloss; §R1 is honest that "the kit manager reads this as a TRIPLE". The design then builds on the third piece as if ruled: `mf_wstream` with a MASK value no producer reaches (D77: built ahead of need, defended only by "a second seam event later", §6 and Q8), Table S, a stream renderer table, a support pin "from the ruling's text" (SLOT-8), and G2 floors per stream. Consequence if the owner meant two pieces: the stream is the search's property (how its candidate state survives a rejection), stated as a column of T-FIND's pick or of the search renderer row, and the reply needs no `stream` member until a search has two streams on one frame. That is also where the owner's own examples sit: "vany plus the caller's verify is the one-shot composition" names a SEARCH and a CHECK, with one-shot as the way they are joined. Ask the owner in plain words before 3.0b freezes the seam: "Is the way the text moves past a rejected candidate (restart at the next byte, take the next bit of the mask, or skip by the table) a third piece you choose separately, or part of the search?" Recommendation: part of the search, as a declared column, until a search supports two streams (the trigger); then a stream choice row with evidence (SLOT-3). The extra seam event later is the price of D77, and MF_SITE_ABI events are routine pre-1.0 (memory pcrec-abi-changes-pre-release).

### SLOT-5 — HORS on the composer stays filtered by TWO mechanisms; "PAIR and HORS are then filtered by one mechanism" (§2.4) is false for HORS, and its renderable-set branch has no witness (CONFIRMED by code; severity maintenance; effort S)

Sabotage C witnesses only PAIR's branch; no row removes the renderable-set check and sees HORS reach a composer pick, because the absent fact still blocks it. Same F5 defect, re-created for the second pick. Fix: either state D-hors's window facts from Table A's stop for both askers once the composer states an `fd_stop` (deferred: F5's second half, its trigger "a kit request adds an arm"), and say so in §2.4 as a named second filter with that trigger; or name it now as the residue (the claim "one mechanism" withdrawn). A witness is impossible until then, which the design should state rather than claim.

### SLOT-6 — "the positions the search proved" has no table: T-VERIFY's C-stop answers it for finds, the search renderer's `*skip` out-parameter for D-hors's probe, and §2.7 adds a third (vrun's mask); the reply's check group is therefore not the rendered check on D-hors sites (SUSPECTED; severity design; effort M)

Consequence for the reply: the decision group (`plan[]`) is frame-independent and computed before the E-find pick, so on a D-hors site it still lists the probed offset that the rendered test skips; (`method`, `stream`, check) then does not determine the rendered check, contrary to §2.3. ### SLOT-7 — the new tables have no question-table home: the census's `answers` vocabulary has no stream question, and the check renderer rows and fused rows are not counted (CONFIRMED by grep; severity maintenance; effort S)

### SLOT-8 — the support pin is not independent: most of its rows come from the kit's reading, not the owner's text (CONFIRMED by text; severity maintenance (check design); effort S)

The owner's sentence names no stream; the ruled record's (1) states only "libc memchr is one-shot only" and "the skip-table SHIFT is a third", and that is in the kit's gloss. Better control: derive the pin from base's emitted artifacts (the resume spelling per E-find renderer row in G2's hors/pair/walk/libc census sites), which is the measured truth the support table claims to reproduce; keep the ruling's one clause (memchr one-shot only) as a separate assertion with its source quoted.

Unlocks: (a) a Rust emitter replaces only the renderer tables keyed by the reply's own ids (SLOT-2; trigger: the first non-C emitter, or [IR-FORM]); (b) the stream becomes a choice row with evidence (SLOT-3/4; trigger: the first search with two streams on one frame); (c) vrun and the inline finder take their trim from PROVES (SLOT-6; trigger: Q9's unit).
