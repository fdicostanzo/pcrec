## Findings

### SIMULATE-1: `/^foo/`-style filters are NOT `startsWith`: L41, L13, L15 (and §11:1898, E-CTX-5) claim SAME but the rev 10 anchoring rule gives the one string
CONFIRMED. Severity: answer. Effort: small (rewrite the forms with a trailing `.*`, `/^foo(?s:.*)/`, or change the verdicts to DIFFERENT). Blast radius: L41, L13, L15, §11:1898-1899 prose, §2.7's `padded(/^5/)` = `padded(startsWith("5"))` (draft:1915), E-CTX-5 (draft:2254, 2268); L7 and L11 hold only in context.
- Rule applied: "A filter applied directly is ANCHORED AT BOTH ENDS (a set of WHOLE strings: `m & /^err$/` = `m & /err/`)" (draft:1893-1894; RULED BY ACCEPTANCE, CF:991-993) and STRING SETS "the strings it matches ENTIRELY" (draft:1887); compile-time sets: "`^`/`$` are the string's own ends" (draft:1904).
- So `/^foo/` as a filter is `/foo/` = the ONE string `foo`, while `startsWith(s) := /(?:${s})(?s:.*)/` (draft:1734) is every string starting `foo`.
- Oracle: `whole('^foo','foobar')` -> None; `whole('(?:foo)(?s:.*)','foobar')` -> [(0,6)]. `whole('^5','57')` -> None vs `whole('(?:5)(?s:.*)','57')` -> match. `whole('^dead\.','dead.x')` -> None vs startsWith -> match.
- Observed vs claimed: L41 "`/\w+/ & /^foo/` vs `/\w+/ & startsWith("foo")` SAME" (draft:250) and §11 "`/\w+/ & /^foo/` accepts the words that start with `foo`, exactly as `/\w+/ & startsWith("foo")`" (draft:1898): the first accepts only `foo` (searched in `foobar` it reports `foo`, D196 shorter end; the second reports `foobar`). L13 `padded(/^5/)` vs `padded(startsWith("5"))` SAME (draft:222): on `57` (or `057`) the first rejects, the second accepts; the same for E-CTX-5's "same as `x & padded(startsWith("5"))`" (draft:2268). L15 `@warn.off(/^dead\./)` vs `@warn.off(startsWith("dead."))` SAME (draft:224): the first switches off only the name `dead.`, the second every `dead.*` name.
- L7 (`/^S\w*/`) and L11 (`!/^#.*/`) carry their own tail, so they are SAME only on spans the tail covers: `S-1` (L7: `/^S\w*/` rejects, startsWith accepts) and `#a\nb` (L11: `.` has no `(?s)`, `/^#.*/` rejects, startsWith accepts). They hold in their cases' contexts (E-CTX-1's x is `\w+`; E-FILE's alts are lines) but the rows state no context.
- Why rev 10 missed it: the "SAME ROWS RE-CHECKED" paragraph (draft:308-314) re-checked these rows under the one reading only ("compare filters no condition reads"), not under the anchoring ruling folded in the same rev.

### SIMULATE-2: the second ARGUMENT REFUSAL is broader than its stated reason: it refuses backreferences that cannot see another hit (`(.)\1`, E-SEP's own pattern), whose loop answers equal find-all
CONFIRMED (the over-breadth); severity: design (a refused program that the stated reason does not cover; a G0 look-alike `/(.)\1/` searched vs `contains(/(.)\1/)`). Effort: small (state the refusal as "a backreference or conditional reachable where its group may be UNSET in the current iteration", a static property) or say the broad form is deliberate. Blast radius: §2.6 (draft:701-716), §8 (draft:1756-1757), L62's reason, and the splice note's own example (draft:651).
- Draft: "PCRE's LOOP over the body agrees with find-all hit for hit EXCEPT where one iteration can see another" (draft:701-702); the refusal itself: "a pattern whose backreference or conditional names a group of the SAME hit is refused" (draft:711-712), i.e. every backreference to the argument's own group.

- Only a backreference/conditional that can run while its group is unset IN THIS ITERATION sees an earlier hit (the draft's two witnesses both do: `(?:(?<c>a)|b)...`). The group set earlier in the same iteration on every path (`(.)\1`) is invisible across hits.
