## BLOCKER

**1. `run.sh`'s `rxt_escape` awk fallback emits the INDEX into `CTRL`, not the
byte value — leg B mis-encodes every control byte from 0x0b up, and passes 0x7f
through RAW.** `tests/harness/run.sh:458-459`.

```awk
n = index(CTRL, c)
if (n > 0) out = out sprintf("\\x%02x", n)
```

`CTRL` is `\x01..\x08 \x0b \x0c \x0e..\x1f` (no `\x7f`), so `index()` is 1-based
position, which coincides with the byte value only for 0x01..0x08.

MEASURED (ran the exact awk from the file over `A\013B\014C\177D`):

```
input : A <0x0b> B <0x0c> C <0x7f> D
output: A\x09B\x0aCD
```

- `0x0b` -> `\x09` — which **decodes to a TAB**. The escape exists to stop a tab
  splitting the row; this path manufactures one.
- `0x0c` -> `\x0a` — decodes to a NEWLINE.
- `0x0e..0x1f` -> off by two (`\x0c..\x1d`).
- `0x7f` -> **emitted raw**: the guard `*[$'\x01'-$'\x08\x0b\x0c\x0e'-$'\x1f\x7f']*`
  includes `\x7f` but `CTRL` does not, so `index()` returns 0 and the byte falls to
  `out = out c`. `src/parse/rxt_source.c:996` (`if (*q < 0x20 || *q == 0x7f)`) and
  `verify_rxt.py:369` (`DUMP_CTRL` includes `0x7f`) both escape it. Legs A and C
  agree; leg B is the odd one out.

Witness: any `.rxt` block whose `pattern` line carries a literal VT/FF/DEL, e.g.
`pattern a<0x0b>b`. Leg A dumps `a\x0bb`, leg C dumps `a\x0bb`, leg B dumps
`a\x09b`. The C1 differential compares legs pairwise, so this surfaces as a
disagreement — but the *reason* printed will be a wrong-value escape, and the
0x7f case silently reduces to "raw byte in a TSV field".

MEASURED that the corpus cannot reach it: the file's own comment says 0 corpus
patterns carry any control byte other than TAB, and the fallback `case` guard
excludes 0x09/0x0a/0x0d. So it is a latent, unreached bug — which is exactly the
population this review was asked to look at.

What closes it: build the mapping from the byte, not from the position — an
explicit lookup table, or `printf '%d'` per byte — and add `\x7f` to `CTRL`.
Better: derive the guard's character class and the table from ONE string, since
today they are a control and its subject sharing no source, which is why the
mismatch survived.

**10. Grammar vs spec: a blank line inside a `config` body silently ENDS the body,
and the following indented lines are then a hard error — while a block scalar
treats interior blank lines as part of the value. The spec says they are one
rule.** `src/parse/rxt_source.c:544-546` vs `:352-356`, against
`docs/spec/rxt_format.md:83-86`.

Spec:
> IN THE HEAD, INDENTATION MEANS CONTINUATION … a `config` body and a block
> scalar's own lines **are the same rule**. A head construct ends at the first
> non-indented line.

Code, `config` body:
```c
const char *nx = L->v[*i + 1];
if (!line_indented(nx)) break;        /* "" is not indented -> body ENDS */
```
Code, block scalar:
```c
while (end < L->n && (line_indented(L->v[end]) || L->v[end][0] == '\0'))
    end++;                            /* "" is INSIDE the value */
```

Witness:
```
config dev
  flags i
<blank>
  engine vm
```
Leg A: the body ends at the blank line; the main loop skips the blank
(`line_blank_or_comment`, `:717`); `  engine vm` is indented and `in_body == 0`,
so it hits `:730-738` -> **hard error** `"indented line continues nothing (the
declaration above it takes no continuation)"`. A reader is told their `engine`
line continues nothing when what actually happened is that a blank line closed
the block two lines earlier.

Meanwhile:
```
description |
  first
<blank>
  second
```
is accepted, with the blank preserved inside the value. Two opposite readings of
"a non-indented line", in one file, for a rule the spec says is one.

INFERRED (cannot run). MEASURED that no corpus file reaches it: 0 indented and 0
whitespace-only lines corpus-wide (`grep -rlnP '^[ \t]' --include='*.rxt' tests/`
and `'^[ \t]+$'` both empty).

What closes it: pick one. Either blank lines are interior to *both* head
continuations (change the `break` to also accept `nx[0] == '\0'`, with the same
trailing-blank trim `parse_prose` does), or blank lines end *both* — and the
spec sentence "the same rule" is then honest either way. Today it is honest about
neither.

**11. An indented `#` comment inside a `config` body is a hard error with a
confusing diagnostic, and `line_blank_or_comment`'s comment arm is dead there.**
`src/parse/rxt_source.c:100-105`, `:547`.

```c
static int line_blank_or_comment(const char *s)
{
    const char *p = s;
    while (*p == ' ' || *p == '\t') p++;
    return *p == '\0' || *s == '#';        /* '#' tested on the RAW first byte */
}
```

Inside `parse_config`, the call at `:547` is preceded by `if (!line_indented(nx))
break;` — so `nx` always starts with whitespace, so `*s == '#'` is always false.
The arm can only ever fire on a whitespace-only line. An indented `# note` in a
config body therefore reaches `vocab_find` and errors as
`"'#' is not a config-block directive"` (`unknown_token` uses `tok_len`, which
stops at the space, so the token printed is literally `#`).

This is spec-conformant in the letter (`rxt_format.md:78-80`: "A `#` anywhere but
column 1 is data") but it means the head — the one region where indentation is
structural — is the one region where you cannot comment a line. Given the head is
where `config` bodies and block scalars live, that is the place an author most
wants a comment.

Witness: `config dev` / `  # the CI build` / `  flags i` -> hard error on line 2.
INFERRED.

What closes it: either allow a column-1-relative `#` inside indented head
continuations (and say so in the lexical rules), or leave it and at least make
the diagnostic say "comments must start in column 1" rather than
"'#' is not a config-block directive".
