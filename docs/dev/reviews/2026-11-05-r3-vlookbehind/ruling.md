## Findings

### RULING-1 — stage 2 rule accepts duplicate-name / branch-reset references that libpcre2 REFUSES (accept set leaves PCRE2's)
CONFIRMED. Severity: answer (accept-set, G1 / gate 3). Effort: small (one refusal arm). Blast radius: stage 2 only. Design §6 stage 2 ("union over duplicate names; unbounded if any is").
- Oracle (libpcre2-8 10.46, `R/tools/oracle_probe c`): `(?J)(?:(?<n>a)|(?<n>b))(?<=\k<n>)x` REJECT 125; `(?J)(?<n>a)(?<n>b)?(?<=\k<n>)x` REJECT 125; `(?J)(?<n>a)|(?<n>bc)(?<=\k<n>)x` REJECT 125 — even when every candidate group has the SAME fixed width. Branch reset: `(?|(a)|(b))(?<=\1)x` REJECT 125, and `(?|x)(a)(?<=\1)x` / `(?|(a)|(b))(c)(?<=\2)x` REJECT 125 — ANY `(?|` in the pattern refuses every lookbehind backreference, whatever group it names. A NUMBERED reference to a group that merely has a duplicated name is accepted: `(?J)(?<n>a)|(?<n>bc)(?<=\1)x` ACCEPT maxlookbehind=1.
- Public doc (man pcre2pattern, "Lookbehind assertions"): "PCRE2_MATCH_UNSET_BACKREF must not be set, there must be no use of (?| in the pattern ..., and if the backreference is by name, the name must be unique." A documented restriction, not a PCRE2 bug, so the D26 addendum does not license accepting.
- Design: "union over duplicate names" compiles the first three (gate 3 red). pcrec at the review tree accepts `(?J)` (it reaches the lookbehind width refusal, p13) and refuses `(?|` as not implemented, so the branch-reset half is latent until [branch-reset] lands — but the rule must be written so it refuses then too.
- Fix: stage 2's rule is "a by-name reference whose name is duplicated, or any reference in a pattern that uses `(?|`, is unbounded (err-125 shape); otherwise the one group's width". The "union" sentence goes. Gate 1-3's stage-2 cell set must include the five refusal cells above.

### RULING-2 — stage 2 names only `cwmax(A_BREF)`; with today's `cwmin(A_BREF) = 0` a reference to a FIXED group becomes a VARYING branch and the 255 cap refuses patterns libpcre2 accepts
CONFIRMED (oracle + code reading). Severity: answer (accept set: pcrec refuses what PCRE2 compiles; G1). Effort: small (the cwmin arm, same memo). Blast radius: stage 2; every reader of `pcrec_cwmin`. Design §6 stage 2, §5.2; code `src/opt/mrl.c` `pcrec_cwmin`'s `A_BREF` arm ("A backreference's minimum is 0 EXACTLY").
- libpcre2 classifies a reference by its group's [min,max]: a FIXED group makes a FIXED item, outside the 255 cap: `(a{300})(?<=\1)x` ACCEPT maxlookbehind=300; `(a{65535})(?<=\1)x` ACCEPT 65535; `(a)(?<=\1|b{300})x` ACCEPT 300; `(a{300})(?<=\1|b)x` ACCEPT 300; forward: `(?<=\1)(a{300})x` ACCEPT 300. A varying group makes a varying item: `(a{1,256})(?<=\1)x` REJECT 200; `(a|bc)(?<=\1|b{300})x` REJECT 200; `(a{300})(?<=\1|b{1,2})x` REJECT 200 (fixed ref, but another branch varies -> every branch capped, §5.2's rule holds).
- The unset case does NOT pull the minimum to 0 in libpcre2 (an unset reference fails, it does not match empty, absent PCRE2_MATCH_UNSET_BACKREF): `(a)?(?<=\1)x` ACCEPT maxlookbehind=1 and on `x` nomatch. The group's own minimum is what counts: `(a|)(?<=\1)x` is [0,1].
- Design as written (cwmax = widest group, cwmin unchanged at 0): `(a{300})(?<=\1)x` reads [0,300], varies, > 255 -> refused; `(a)(?<=\1|b{300})x` reads branch 1 as [0,1], varies, so b{300} is capped -> refused. Both are accepted by libpcre2. (`(a)(?<=\1)x` would compile, as a VARYING branch: answers equal, but it emits the loop, not the one-point fold, and LB 1 still matches.)
- Fix: stage 2 sets BOTH ends: `cwmin(A_BREF)` = the named group's cwmin and `cwmax(A_BREF)` = its cwmax, read through the same post-resolve memo; the mrl.c header sentence "`pcrec_cwmin` answers 0 EXACTLY" is retired for this consumer (its safe-direction argument — under-estimate only over-rejects — is exactly the over-rejection shown here). Stage-2 cells: the five ACCEPTs above.

### RULING-3 — stage 2 is a TIMING change the design does not state: forward references and self-reference need DD-14.LB's deferral, a group-width memo, and K127's cycle refusal
CONFIRMED (oracle + code reading). Severity: design (stage 2 under-specified; one wrong code comment). Effort: medium (a second deferral customer, a per-group width memo). Blast radius: stage 2; `pcrec_postresolve`'s customer list. Design §3 row "backreference inside" ("needs only a width (B+)"), §6 stage 2; code `src/opt/mrl.c` `pcrec_cwmax` header (A_BREF bullet) and `src/parse/mod_lookaround.c` (the `pcrec_has_call` deferral, `pcrec_lookaround_fix_widths`).

Stage 2 is therefore also closing a gap on FIXED-width lookbehinds (the "today's fixed-width cases" the owner asked about: there are none pcrec accepts), which the design's §8 count ("stage 2 brings 36") does not separate.

## Answers to the owner's questions

**"Is that a back or forward reference?"** Both, and also inside. libpcre2 10.46 accepts a reference to a group BEFORE the lookbehind, INSIDE it (even written before its group, `(?<=\1(a))x`), and AFTER it (a true forward reference, `(?<=\1)(a)`), by number, relative number or unique name, in fixed and variable lookbehinds. A forward reference sees the group's value from an EARLIER iteration of an enclosing repeat and simply fails when the group is unset. What libpcre2 REFUSES (err 125, "not limited") is: a reference by a DUPLICATED name, any reference when the pattern uses `(?|` anywhere, a reference to an unbounded or recursive group, and a reference to the group that contains it. The width it counts is the referenced group's own [min, max] — a reference to a FIXED group is a FIXED-width item, outside the 255 cap (`(a{300})(?<=\1)x` compiles, maxlookbehind 300).

pcrec at the review tree refuses all 29 reference shapes tried, every one with "variable-length lookbehind is not implemented ... (this one is unbounded)"; 23 of them libpcre2 accepts, including the fixed-width ones (`(a)(?<=\1)x`). So there is no fixed-width backreference case pcrec accepts today, and the `pcrec_cwmax` comment that says libpcre2 agrees is wrong (RULING-3).
