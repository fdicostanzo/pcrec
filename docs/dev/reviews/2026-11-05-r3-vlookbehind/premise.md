### PREMISE-1 — PCRE2 has a SECOND lookbehind ceiling (65535 characters, err 187, fixed or not) that §5.2 does not state; pcrec's accept set is already outside PCRE2's today
CONFIRMED. Severity: answer (accept set, G1) / doc. Effort: S (one more refusal arm in `la_widths`' caller + a `limits.def` row). Blast radius: patterns with a fixed lookbehind longer than 65535 characters (none in the population). Design §0 G1 ("the accept set stays inside PCRE2's"), §5.2, §6 gate 3, §7 W8/W9.
Repro (`premise/capprobe`, libpcre2 10.46, default context and with `pcre2_set_max_varlookbehind(cc, 4294967295)`):
`(?<=a{65535}b)x`, `(?<=(?:a{65535}){2})x`, `(?<=(?:a{1000}){66})x` -> REJECT 187 "lookbehind assertion is too long" at EVERY max_varlookbehind setting; `(?<=(?:a{1000}){65})x` -> ACCEPT maxlookbehind=65000. Review tree: `build/pcrec --features all -p rx --pattern '(?<=a{65535}b)x'` rc=0 (23499-byte artifact); same for the other two (rc=0).
So PCRE2's rule is two-tier: (i) an absolute per-branch ceiling of 65535 characters on any lookbehind; (ii) `max_varlookbehind` (default 255) on every branch's maximum once any branch varies. §5.2 copies only (ii). `la_widths` (src/parse/mod_lookaround.c:293-307) refuses only unbounded and `> INT_MAX`. Gate 3 as written ("the same generator plus the cap boundary cells") would not find this unless the generator reaches 65536; W8/W9 sit at 255/256 only. Pre-existing (not caused by the design), but the design states G1's accept-set property as if it held today and copies a cap rule that is half of PCRE2's.
Proposed: §5.2 states both tiers; the new `limits.def` row family gets the 65535 ceiling as well (it is the one bound in the pair that is NOT a caller setting in PCRE2); add the cells `(?<=(?:a{1000}){65})x` accept / `{66}` refuse to gate 3.

### PREMISE-2 — "Context before the start is read" (§2) is a byte-mode fact; under PCRE2_UTF libpcre2 clips at `startpos − LB` and pcrec deliberately does not (D142, match_api.md §9.4¶8): gate 1's "0 differences ... startpos > 0, byte and UTF-8" collides with a stated divergence the design never names
CONFIRMED. Severity: design/doc (gate definition; no answer is wrong). Effort: S. Blast radius: gate 1's generator; spec §9.4¶8's class grows with every variable body whose reach exceeds its widest maximum. Design §2 bullet 2, §6 gate 1, §7 W7/WD5/WD6, §10.
Repro (`premise/sp`, own probe, libpcre2 10.46, `pcre2_match` from offset 3):
`(?<=\ba{1,2})x` on `baax` from 3: byte nomatch, PCRE2_UTF (3,4). The fixed twin `(?<=\baa)x` does the same (byte nomatch, UTF (3,4)), so this is D142's class, not new semantics. `(?<=^a{1,2})x` stays nomatch under both (`^` is not clipped), `(?<=a{1,2})x` is (3,4) under both.
Why it matters: `\b`/`\B` at the START of a varying body reaches one character past LB (LB counts the body's maximum, §9.4¶2: "never summed"), exactly D142's "backward reach exceeds LB" condition, and §2's context cells and W7/WD6 are the shapes a generator built "from §2's cells" will emit at `startpos > 0` under UTF-8. The design cites neither D142 nor §9.4¶8, so a build lane following gate 1 literally either reds on a ruled divergence or "fixes" it into PCRE2's clip. `grep -n 'D142\|9.4' subject` = 0 hits.
Proposed: gate 1 states that UTF-8 cells with `startpos > 0` whose body reach exceeds LB are compared against the D142 rule (pcrec = the byte-mode answer), routed to `tests/utfcheck`'s `CLIP` class if they are pinned there; §10 lists §9.4¶8 as a sentence to re-read (its "three patterns in the pinned set" count is a reader of the class).

### PREMISE-3 — §5.1's "the fold for lo == hi is natural ... today's NEXT-BRANCH continuation push" is not true of the loop AS SKETCHED: today's push precedes the back-step and saves the CURSOR; the sketch's push follows it and saves the CANDIDATE, which also leaves the next branch back-stepping from the wrong place
CONFIRMED by reading (sketch vs review-tree code; no build exists). Severity: design (G2 identity, and an answer bug if built literally). Effort: S (re-sketch). Blast radius: every lookbehind with two or more branches. Design §5.1, §13 Q1, G2/G3.
Today (`src/gen/emit_vm.c:7117-7246`, `vm_look_behind_branch`): guard `scan_position < k` -> `vm_push(bl[i+1])` with `scan_position` = the CURSOR -> `vm_work(k)` -> `VSK_BACKSTEP` k -> sentinel -> body -> end-check. The next branch `L_b(i+1)` is reached by popping that frame, so it starts from the cursor because the frame saved the cursor (header note 2, :7307-7315, says exactly this).
Sketch (§5.1): back-step FIRST, then `L_try_i: RX_PUSH(&&L_adv_i, scan_position)` with `scan_position` = the candidate start, then `RX_CHARGE_WORK`, then the body; `L_adv_i: if (d == lo_i) goto L_b(i+1)`. Two consequences:
(a) Identity: for `lo == hi` the sketch emits back-step, push, work in a different order from today's guard, push, work, back-step, so the one-point case does NOT reduce to today's text by evaluating `d == lo_i` at compile time; it reduces only if the general loop is itself written in today's order. The claim "a loop whose remaining trip count is statically zero has no back edge" is true but is not the whole difference.
(b) Answer: on exhaustion of branch i the sketch jumps to `L_b(i+1)` with `scan_position` restored from the L_adv_i frame = branch i's last candidate start, not the cursor; `L_b(i+1)` back-steps "from the cursor" only if it re-reads the POS slot, which today's code never does (it relies on the frame). E.g. `(?<=a{1,2}|bc)x` on `bcx`: branch 1 exhausts at candidate 1 (d=1), branch 2 would back-step 2 from position 1, fail the clamp, and answer nomatch where libpcre2 answers (2,3) [`printf '(?<=a{1,2}|bc)x\tbcx\n' | tools/oracle_probe m` -> `[2-3]`].
Proposed: write §5.1 in today's order: guard on `lo_i` -> push the retry frame saving the CURSOR -> work -> back-step `d` -> body; `L_adv_i` reads the cursor back from the frame, `d--`, back-steps `d` again (or advances one character from a second, trailed candidate slot); `L_b(i+1)` always starts from the restored cursor. Then the one-point fold IS today's text (push target `L_b(i+1)`, no `d` slot, no back edge), and the claim in §5.1 becomes true by construction rather than by gate 2.

## Answers to the owner's questions

### (1) "Does there need to be a cap at all?"

**(a) What correctness needs: no cap, and not even boundedness.** §5.1's loop needs, per branch, a finite number of candidates and a body that terminates from each. The candidates are `d = min(hi_i, characters before the cursor)` down to `lo_i`; `d` strictly decreases on every `L_adv_i`, so the loop terminates for ANY `hi_i`, including "unbounded", because the clamp (the subject start) bounds it at run time. Each body run is ordinary `vm_emit` code under the existing step/frame/work budgets. Nothing in the emitted loop depends on the VALUE of `hi_i` except one constant in the guard/back-step: the loop is one body copy per branch whatever `hi_i` is (G4), so compile size does not grow with the cap. The only representational limits are the `int` width table (`la_widths` refuses `> INT_MAX`) and PCRE2's absolute 65535-character branch ceiling (PREMISE-1), which pcrec does not enforce today. Readers of the width outside the loop: only `u.look.widths` (emit_vm.c) and LB (`<p>_VALID_LB`, `-futf-check`'s window start); an unbounded LB would just mean "validate from 0".

**(b) What the cap is FOR.**
- *Accept-set compatibility* (the real reason). PCRE2's rule, measured (PROBED-AND-HELD): a per-branch cap on every branch's maximum, switched on when any branch varies, in characters, nested quantifiers multiplied, nested lookbehinds capped separately, default 255, settable by the caller from 0 up to the 65535 absolute ceiling (err 187 applies to fixed branches too). A pcrec default of 255 makes pcrec's accept set EQUAL to PCRE2's default accept set for bounded variable lookbehinds, which is what makes G1's gate 3 cheap and exact. Under D26 + its 2026-10-24 addendum ("compatible ... not 'the same as pcre2' because we're going beyond") accepting MORE would not be a defect (tier 2 forbids refusing what PCRE2 accepts, not accepting what it refuses), so 255 is a choice, not an obligation; the owner's ruling (default only; a setting at [IFACE-PUSH]) mirrors PCRE2's own knob exactly, which is the most compatible shape available: the one hole until then is a PCRE2 user who raised `max_varlookbehind` above 255.
- *Resource bound.* Measured PCRE2 cost (`premise/capmatch`, 4000-byte all-`a` subject, `(?<=a{1,hi}b)a`, lookbehind evaluated and failing at every position, one scan): hi=16 2.0 ms; 64 17.6 ms; 255 0.22 s; 1000 3.1 s; 4000 22.6 s; the possessive `a{0,hi}+b` form is the same. That is O(min(hi, p)^2) per evaluated position, i.e. O(n * hi^2) per scan, the cost model §5.5 assumes for B (up to hi candidates, each a body run of up to hi characters). So in PCRE2 the cap is a work bound; in pcrec the run-time work budget (`RX_CHARGE_WORK`, `PCREC_ERR_WORK`) already bounds it whatever the cap, as a clean give-up rather than a hang. For candidate D the cap is ALSO a compile-size bound, because a counted body's reverse machine grows with hi (measured proxy, review tree, `cnt.py`: `xa{1,255}` 257 states, `x\w{0,1000}x` 2003 states / 227 KB artifact, `xa{1,4000}` 4002 states), while an UNBOUNDED body's machine is tiny (`xa+` 3 states, `x\w*x` 3 states).

**Unbounded lookbehind as an extension (`(?<=a+)b`, `(?<=\w*x)y`).**
- *Semantics are defined, and testable.* For a subject of n characters `(?<=a+)` is exactly `(?<=a{1,n})`, so pcrec's extension would be the bounded semantics continued (farthest first, branch order, non-atomic retry), NOT JavaScript's/.NET's right-to-left capture semantics. An oracle exists without PCRE2 accepting the pattern: libpcre2 with `max_varlookbehind = 65535` on the bounded twin (`(?<=a{1,65535})b`) for subjects under 65535 characters (cap-65535 acceptance measured above).
- *B can do it as is*: hi = "to the subject start"; per evaluation up to p candidates each an O(p) body run, O(p^2), so O(n^3) per scan in the worst case (PCRE2's bounded twin at hi=4000 on 4000 bytes: 22.6 s). Correct and budget-bounded, but a give-up generator on long subjects.
- *D does it better than its bounded case*: the reverse machine is small (3 states above); the walk's floor is 0; with the EXISTENCE exit (stop at the first accept walking back) `(?<=a+)b` and `(?<=\w*x)y` cost O(1) per evaluation (both accept after one or two bytes back); bodies whose nearest accept is far (`(?<=x\w*)y` over a long `\w` run) cost O(distance) per evaluation, O(n^2) per scan; captures/atomic/non-atomic still need the forward finisher over up to p candidates, O(p^2) per evaluation in the worst case, as B.
- *The linear form is [ENG-LOOK]'s `Σ*·L` forward machine* (PREMISE-8): existence at every position in O(1) amortized, unbounded or not, and a sound filter for the finisher otherwise.
- *Is the non-goal "unbounded (both refuse it, err 125)" worth questioning?* Its REASON is: "PCRE2 refuses it" is true but is the weakest argument after D26's addendum. The non-goal itself stands for stage 1 on better grounds: zero demand (no row in the population, no bench pattern; [UTF-RW]'s harvest, just moved up, is where demand would first show), B's O(n^3) worst case without a filter, and an LB/`-futf-check` contract sentence to write. I recommend restating the reason and filing it as a held unlock, not deleting it.

**Recommendation.** Keep 255 as pcrec's default (owner ruling) and say in §5.2 that it is a POLICY limit for accept-set equality with PCRE2's default, not a correctness or size limit of the `range` mechanism; add PCRE2's 65535 absolute branch ceiling as a second `limits.def` row (PREMISE-1; G1 then holds for fixed lookbehinds too, by the design's own ranking over G2); write the loop and the clamp so nothing depends on `hi_i`'s magnitude (no type narrower than the width table, no per-length unrolling, the one-character back-step loop rather than an `upto(hi)` entry), so that [IFACE-PUSH]'s setting, and a later "unbounded" value of it, are one-row changes. File unbounded lookbehind as a HELD extension row with trigger "a real pattern needs it" (harvest or user), whose mechanism is the existence filter ([ENG-LOOK]'s forward machine, or D's existence exit) in front of `range`'s finisher, never B alone. Argument: correctness never needed the cap; PCRE2 users need equality at the default; pcrec's run-time budget, not the cap, is what bounds work; and the mechanism that makes unbounded cheap (an automaton filter) is the same one that makes WIDE bounded bodies cheap, so it should be built once, under a measured need, for both.
