# CRITIC MODECLOSURE: predspec25 (rev 25 re-check)

## Findings

### MODECLOSURE-1 (CONFIRMED; design/doc; effort small; blast radius: pass-start-read's rule sentence and its "PCRE's capture" claim)
pass-start-read is stated and run at ONE depth only; at two depths the one rule, libpcre2 and the "previous item" intent part.
- Rule quoted (line 914-916): "INSIDE A LOOP BODY A CONDITION READS THE LABELS AS THEY STAND AT THE POINT WHERE IT IS WRITTEN: before its label's group, the previous pass's value (unset in the first pass); after it, the current pass's." Line 910: "Here the one rule gives PCRE's capture's answers." Use stated (916-917): "comparing an item with its predecessor."
- Repro (modeclosure/x1.py; engine = predspec244 rule 244, control = libpcre2 with the same callout): the sorted-list callout ("h unset, or n >= h") one loop deeper, `/(?:(?:(?=(?<n>\d))(?C)(?<h>\d);)*,)*/`. WHOLE `7;,3;,`: engine HOLDS (entering the inner loop in the second outer pass resets h, so the condition before `3` reads UNSET), libpcre2 FAILS (carries 7), the intent "items non-decreasing" FAILS; `3;4;,1;2;,` likewise HOLDS / FAILS / FAILS. SEARCHED `7;,3;,` engine `7;,3;,`@0 (libpcre2 `7;,`@0); FIND-ALL differs on the same texts (1 / 1 / 1 of 5,461 over `17;,` length <= 6, first `7;,1;,`: the pool is short; every list of two groups with a descent across the comma differs).
- So at two depths "the previous pass" means "the previous pass OF THE INNER LOOP SINCE IT WAS LAST ENTERED", "unset in the first pass" holds for the first inner pass of EVERY outer pass, and line 910's "the one rule gives PCRE's capture's answers" is true only for the single loop PART PS ran. The owner was shown only the one-depth table (line 917). Not a rule change needed; the sentence must name the depth (and §R.8 could ask whether a predecessor comparison across outer passes is meant to see the previous outer pass's last item; the one rule says no, PCRE says yes). Mode: all three modes move alike (top level); in an `occurrences` argument the same holds with "hit" as the outer pass.

### MODECLOSURE-2 (CONFIRMED; design; effort medium (a ruling-shaped choice for FIND-ALL places); blast radius: §2.6 THE TWO ARGUMENT REFUSALS, R.1.9 (1), the hit list, every `occurrences`/`contains` argument with a condition)
pass-start-read is RULED for loop bodies and the draft extends it to `occurrences` arguments, where it is a THIRD way one iteration sees another, which §2.6 says does not exist; the FIND-ALL places then disagree with one another.
- Rules quoted: R.1.7 line 1039-1041: "A condition inside the loop body (§11's hole rule) or inside an `occurrences` argument, AFTER its label's group ... reads the labels its own pass has set so far (before them, the previous pass's value: **pass-start-read**, RULED rev 25, above)". §2.6 line 3162-3163: "PCRE's LOOP over the body agrees with find-all hit for hit EXCEPT where one iteration can see another, and there are exactly two ways it can" (nullable; a backreference/conditional run while its group is unset in this hit). R.1.9 line 1089-1091: "THE HIT LIST IS THE ONE-PATTERN SEARCH MADE ATOMIC ... its hits are those of a plain search". §2.6 line 3188-3189 (REV 24.2 mark, unrevised): "a condition inside the body reads only its own pass's".
- Repro (modeclosure/x2.py, libpcre2 only; the condition as a callout, which reads PCRE's carried capture = the one rule at one depth, PART PS's own equivalence): r := `/${c}(?<h>\d)/`, c := "h unset or h < 5" (i.e. `NOT (h: >= 5)` written before the group). On `3 7 1`: FIND-ALL of r at top level (PCRE2's global loop, R.1.2) [`3`@0, `7`@2, `1`@4]; `occurrences(r)` (R.1.9's one-pattern lazy-gap loop, `(?:[\s\S]*?(?<hit>r))*[\s\S]*`) hits [`3`, `7`] (the third hit's condition reads the previous hit's 7); `hits(r)` (the ruled model, atomic, `\A(?>...)\z`) [`3`, `7`], not the plain search's three. On `7 3`: plain [`7`, `3`], occurrences and hits [`7`]. 
- So in FIND-ALL places: (a) "exactly two ways" is false; (b) "its hits are those of a plain search" is false for any `hits(r)` whose r carries a condition before its label's group; (c) the same r gives different hit lists as a top-level FIND-ALL program and as an `occurrences` argument, a difference the draft's L53/L62 rationale treats as refusal-worthy ("a construct whose PCRE meaning inside the body is not what `occurrences` promises", line 3185-3186). A DEFAULT written before the group, `(h = d: ...)`, is by R.1.6 PCRE's conditional `(?(<h>)...)`, i.e. literally §2.6's second refused shape: refused there, admitted and ruled by R.1.7. The draft must choose per place: extend the second refusal to conditions (then pass-start-read does not reach `occurrences` arguments, contradicting line 1039-1041), or delete "exactly two" and the plain-search sentence and state that a predecessor comparison works across hits in `occurrences`/`hits` but not in top-level FIND-ALL. Also the REV 24.2 mark at 3188 must be revised (it states the superseded "own pass only" reading as the rule in substance).

### MODECLOSURE-3 (CONFIRMED; design/doc; effort small; blast radius: R.1.13 (2), hole-reading (1), **sequence-numbers**' option table)
"A composed pattern and a literal have the same label behaviour" is false for NUMBERS through a HOLE, silently (not an error), and the sequence-numbers row prices only the pure-SEQ case.
- Rules quoted: R.1.13 (2), line 1156: "A COMPOSED PATTERN (the sequence operator, a hole, a loop of a part) AND A LITERAL HAVE THE SAME LABEL BEHAVIOUR". Hole-reading (1), line 1233-1234: "the inserted pattern as a WHOLE, in a non-capturing group, matched where it stands ..., keeping its own flags and its own group numbering". Line 1203-1204: "numbers are local to each pattern literal (a hole or a bound pattern keeps its own numbering)". R.1.13 line 1199-1207: a name and its number are "TWO NAMES OF ONE LABEL" (TRIED). §R.8 sequence-numbers, line 1740: "(b) NONE ... `1` is the unknown-label error ... (b) REJECTED x3 ... either vs (b) every text".
- Repro (modeclosure/x3.py, libpcre2, WHOLE): literal `/(\d),(\d)/ & (1: <5)` on `3,7` HOLDS (1 = `3`), `7,3` FAILS. The same pattern with its first group through a hole, `/${A},(\d)/`, A := `/(\d)/`, under the RULED hole text (own numbering; the outer literal's own group 1 is the one after the comma): `3,7` FAILS (1 = `7`), `7,3` HOLDS. Opposite answers on every text where the digits straddle 5, with no error; under reading (c) (nearest literal) the same. Only reading (a) (written-out numbering) keeps composed = literal, and (a) is the one the row says shifts "with what precedes it".
- Flags make the same split: with `(?n)` (PCRE2's no-auto-capture) in the outer literal, `/(?n)(\d)x/` has no group 1, while `/(?n)${A}x/` keeps A's own flags and so A's capturing group 1: `& (1: ...)` is the unknown-label error in one spelling and a test in the other.
- So: R.1.13 (2) needs "for NAMES" (or the numbering rule must change), and sequence-numbers must add the HOLE-in-a-literal-with-groups case, where (b)/(c) do not reject but read a different group. Mode: all three modes alike (compile-time numbering); also in a FIND-ALL place (`occurrences(/${A},(\d)/ & (1: ..))`) and the filter role, since numbering is per literal everywhere.

### MODECLOSURE-4 (SUSPECTED; design (a ruling-shaped gap); effort small; blast radius: R.1.13 (4) and every two-author `&` program)
`aa.h` is defined only by one worked example; it is UNDEFINED when the label on the part has two mentions, and the draft's own advice relies on an unstated reset rule for it.
- Rules quoted: R.1.13 (4), line 1170-1172: "a part's own label is reached through a label given to the part, `[aa = A] & B & (aa.h: ...)`; a BINDING's name is not a path (`A.h` is an error)". His point 4 (line 1148-1149): "A is a binding not a label and could be ambigous if its used multiple times in an expression". R.1.13 (3), line 1168-1169: "To keep A's value: label the part (`[aa = A]`, `aa.h`)". R.1.7 (2)-(3), line 844-847: entering a branching "resets every label whose group lies inside it"; "IN A SEQUENCE THE LAST MENTION WINS".
- (a) TWO MENTIONS of one part label: `[aa = A] SEQ "," SEQ [aa = /x/] & (aa.h: <5)`, A := `/(?<h>\d)/`, WHOLE `3,x`. By R.1.7 (1) `aa` is one label, the last mention: aa = `x`. `aa.h` then reads either (i) the label whose groups are the h copies inside ANY `aa` group: `3` (modeclosure/x4.py, the engine with that copy named `aa_h`: aa = `x`, aa.h = `3`), so `aa` and `aa.h` name DIFFERENT parts; or (ii) the h inside the part that `aa` names (the last mention, `x`): unset, so `(aa.h: <5)` FAILS; or (iii) an error, by the very reason the owner gave for `A.h` ("could be ambigous if its used multiple times"). The same arises for `([aa = A] SEQ ",")* SEQ [aa = A2]` (a list whose last item is spelled differently) and in a FIND-ALL place (`occurrences([aa = A] SEQ [aa = A2])`).
- (b) RESETS: line 1168's advice works only under reading (i)-style naming (the h copy inside aa is a separate name): `[aa = A] SEQ B`, B := `/(?:,(?<h>\d))?/`, on `3`: h is UNSET (B's optional is entered, line 1162-1163), aa.h = `3` only if B's optional does not reset aa.h; under (ii) (aa.h = "h, restricted to aa's text") the one label h was reset and the advice fails. The draft never states which names a branching resets when the name is a path.
- Needed: one sentence defining `aa.h` as a name under the one rule (the h groups lexically inside an `aa` group, own resets) and what two mentions of `aa` do (error, as `A.h`, is the owner's own argument).

### MODECLOSURE-5 (SUSPECTED; design/doc; effort small; blast radius: R.1.13 (4) with R.1.4's filter role and §4.1's lookup)
The ambiguous-reference error has no PLACE scope: a condition written INSIDE one side (a hole condition in A, a condition in a parenthesised filter, an `occurrences` argument) is not addressed, and two texts answer the parenthesised case differently.
- Rules quoted: R.1.13 (4), line 1170-1171: "a compile error WHERE IT IS REFERENCED (a condition, a `$`)". §4.1, line 3678-3680: "In a chain `P & Q & (x: ...)`, x is looked up in the other operands of the chain (`P & Q`; `&` is order- and grouping-free, so the whole flattened chain); a label in both is AMBIGUOUS". Zero-place, line 763-765: "from the perspective of B, the subject is now whatever A matched ... That's its whole world. So all numbers are labels of groups in that world". Pass-start-read, line 914-915: a condition "READS THE LABELS AS THEY STAND AT THE POINT WHERE IT IS WRITTEN".
- Cases, A := `/(?<h>\d)\d/`, B := `/\d(?<h>\d)/` (PART LF's pair): (1) `A & (B & (h: <2))`: §4.1 flattens -> the error; zero-place ("B's whole world") and the nested filter role -> B's h (WHOLE `12` FAILS, `21` HOLDS, PART NUM's B line). (2) `/(?<h>\d)${c}\d/ & B`, c reading h, written INSIDE A: by pass-start-read c reads A's h only (B has not run); by the letter of (4) it references a name both sides surface -> the error. (3) `A & occurrences(B & (h: <5))`: §2.2 (line 2924) makes `occurrences` "a macro ... never an operator with a position in the chain", so its inner chain is B alone; (4)'s letter again makes it ambiguous. In every mode (compile-time), and the answer differs by place.
- Needed: state that the error applies to a reference whose READING POINT sees both sides' labels (after the chain), and that a condition inside one side reads that side, or rule the flat reading; then reconcile §4.1's "grouping-free" with zero-place for names (for NUMBERS the draft already took "the nearest pattern", line 1192).

### MODECLOSURE-6 (CONFIRMED; doc; effort small; blast radius: the array form, `sorted`/`distinct` on it)
"Every setting of the name in order" does not say WHICH order, and with a lookahead the setting order is not the text order; rev 25 made the distinction explicit for the label (pattern order) but not for the array.
- Rules quoted: R.1.7 line 962-963 "(c) THE ARRAY FORM ... every SETTING of the name in order"; array-slot, line 970: "the array form is the list of the name's SETTINGS, in order"; R.1.13 (3)(ii), line 1164-1167: "when a lookahead makes A's `h` name text AFTER B's, B's is still the label ... the item last in PATTERN ORDER".
- Repro (modeclosure/x4.py, engine rule 244): `AL SEQ BL` on `1,2,3` SEARCHED `1,2`@0: label `2`, array [`3`, `2`] (setting order); text order would be [`2`, `3`]. `sorted(h-array)` then FAILS where a reader of the text expects it to hold. The array's last entry equals the label only in setting order, which argues for it; the sentence should say so (and lookahead-labels, §R.8, now carries the array too). Mode: every mode, and in an `occurrences` place across hits.
