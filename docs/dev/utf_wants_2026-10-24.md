# What Unicode regex users want that plain regex cannot easily do (survey, 2026-10-24)

Lane utfwant. Research only: no design, no syntax proposal, no plan rows.
Asked by Frank 2026-10-24 ahead of [COMPAT-FOLD]. Class key: **A** a plain-regex
workaround exists and is fine; **B** a workaround exists but is painful, slow
or error-prone; **C** not expressible in ordinary regex (engine or
preprocessing support needed). pcrec status is read from docs only
(pcre2_compliance.md, spec, plan.md, third_party/ucd-16.0.0), with greps to confirm.

## Headline (stop-rule note)

**Direct evidence of demand for NFKC compatibility folding inside a regex
engine is thin.** No engine surveyed offers it (compat_fold_facts section 7
already said so; this survey found nothing to the contrary), and I found no
issue-tracker or forum request for it. The adjacent demand is real but is
met OUTSIDE the engine: search-index folding (ICU/Lucene folding filters)
and spoof detection (UTS #39 skeleton, which is NFD + a confusables table,
not NFKC). [COMPAT-FOLD] is therefore a pcrec novelty, not a catch-up item.
That does not say it is wrong, only that it should be weighed as a
differentiator, and that the same engineering (UCD-derived tables resolved
at compile time) buys wants that ARE heavily evidenced (below). My search
tools could not query GitHub/StackOverflow issue lists directly, so "found
no request" means the web searches listed in Sources returned none, not
that none exists.

## Demand table

Demand evidence is graded: **spec** = a Unicode spec level engines advertise;
**multi** = shipped by several mainstream engines; **ask** = a request or a
recurring question found; **none** = not found.

## Ranked by evidence times (B or C)

1. **Grapheme clusters (#1).** The only item that is a Level 2 requirement,
   offered by every full-featured engine except Rust (which refuses by
   design), and not approximable. `\P{M}\p{M}*` fails on emoji ZWJ sequences,
   flags, Hangul jamo, Indic conjuncts; counting or splitting "characters"
   is the commonest practical Unicode complaint. pcrec has it marked
   `PLANNED-HARD` and the data (GCB, Extended_Pictographic) is not yet
   vendored.
2. **Binary and remaining property coverage (#3), with its two uses:
   emoji (#4) and default-ignorable / bidi (#13).** Property coverage is
   the most heavily advertised Unicode feature (TR18 RL1.2, RL2.7; ICU
   "all of them"; PCRE2 10.4x), the open Go request, and the `\p{Emoji}`
   digit gotcha. pcrec refused binary properties as "no measured demand";
   this survey is the first outside evidence against that. Cheap for an AOT
   compiler (only the used property is emitted) and is the prerequisite for
   #4 and #13.
3. **Class set operations (#2).** Required (RL1.3), nearly universal, the
   JS committee shipped it in 2023-era `v` as a headline feature. Workaround
   exists (lookahead) so class B, but it is the item with the highest
   demand-to-cost ratio for pcrec: interval algebra at compile time, no
   engine change. Already `PLANNED`.
4. **Full case folding (#5).** Required (RL2.4), mechanical (104 entries),
   and a correctness gap against the ICU and Python `regex` behaviour users
   expect (`ß`/`ss`). Hand workaround exists but does not extend to
   classes or backreferences. It also changes pcrec's width facts, so it
   deserves a design note before [COMPAT-FOLD] shares the same fold
   machinery (the 1:n mapping question in the [COMPAT-FOLD] row is the same
   question).
5. **Canonical equivalence (#6)** ranks next on demand (recurring
   questions, Java ships it) but it is hard in the general case and the
   standard advice is to normalize outside. It, rather than NFKC, is the
   stronger neighbour for [COMPAT-FOLD] to be designed with: a literal's
   NFC/NFD alternatives and its compatibility alternatives are the same
   kind of table lookup.

Below those: UAX #29 word boundaries (#8, real demand but hard and
partly covered by [UCP]); script runs and confusables (#9, #10: security
niche; confusables is where "look-alike" demand really lives); Turkish
tailoring (#11, cheap for AOT, modest demand); the rest are A-class or
low-evidence. UTF-16/32 (#17) is a legitimate platform want but it is an
encoding backend, not a regex feature.

## Notes for [COMPAT-FOLD]

- Demand is weaker than for items 1 to 5 and the chosen differentiator is
  unmatched by any engine; that cuts both ways (no prior art to copy, no
  competitor).
- Three items share its machinery (UCD-derived compile-time tables with
  1:n expansions): #5, #6, #10. A design that covers the 1:n mapping once
  serves all of them.
- Unicode version pinning: vendored UCD is 16.0.0; Unicode 18.0.0 data
  exists upstream (UTS #39 fetched at 18.0.0). Every new table increases
  the cost of a version bump; an AOT compiler pins the version at compile
  time, which is also the guarantee (a given artifact never changes behaviour).
