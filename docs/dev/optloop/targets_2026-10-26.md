# Optimization targets, candidate table (2026-10-26, lane targets26)

Fact gathering only: no design, no build, no timing taken here. Every number is the bench's, read from
`pcrec-bench/reports/` (matrix and tsv files, computed here as ratios of the bench's own medians) or from this
repo's existing gap reports. The manager ranks; this file supplies the columns.

## How to read the numbers

- **Ratio** is pcrec time / peer time, so ratio > 1 means pcrec is slower. "x2.4" = pcrec takes 2.4 times as long.
- **The 2026-10-26 window** (Zen 4, `ryzen7700x`, pcrec 9ae59f5d4 vs 6b2dbd3e, same window) has NO non-pcrec
  engine except in `sentinel-0.1` (short subjects only, 15 patterns) and `subst-0.1`. Every other set is pcrec
  vs pcrec, judged against the bench's null band (`null_band` rows: capability large >=1 us +-33%, short
  100 ns-1 us +-12.6%, large <100 ns +-11%; every other set also reads "null of N cells").
- **The 2026-10-13 `*-handoff-6b2dbd3e` reports** (Zen 1, `budu-ryzen1600`, pcrec 6b2dbd3e; bounded at 00c97769)
  carry ONLY libpcre2 (jit, interp) as a non-pcrec engine. They contain **no re2, rust, hyperscan or
  vectorscan column.** capability@10-13 has no non-pcrec engine at all; email-specimen@10-13 has jit/interp and
  no pcrec column. So "loss vs jit" below is from 10-13 (Zen 1); "loss vs best non-pcrec" for re2/rust comes from
  the newest report that holds them: the **2026-09-27 `fullroster` reports (Zen 1, pcrec 751b9c6d, ~4 weeks
  older than 9ae59f5d4)** for altwide/bounded/email/loglines/syntax/utf8, and the 10-11 gap report
  (`docs/dev/optloop/judgement_gapreport_2026-10-11.md`, pcrec b8337c33, capability peers from 10-08) for
  capability. Each cell below names its source. All of these are STALE against 9ae59f5d4; abi 67..84 landed since
  (NULLABLE-ANCH, rev-end, compound, find-all scaffold).
- **Zen 1 vs Zen 4 are not comparable in absolute ns.** Only ratios inside one report are meaningful.
- vectorscan (utf8 09-27 reports) is excluded from "best peer": its cells are block-mode, no-captures,
  and read x80..x26000 against pcrec on large utf8 subjects, which looks like a different question being timed
  (bench question Q5).
- "pin delta" = 9ae59f5d4 / 6b2dbd3e on pcrec's own median, 10-26 Zen 4, auto-caps. All pin deltas for these
  rows are inside the null band except the one regression listed in section 2.

- [SUBST-CLEANUP], [SUBST-NAMECHK], [SUBST-INPLACE], [SUBST-STREAM], [CLI-OUTKEEP] are not speed rows.

  T3 (lookaround, VM route). A target for them lives under those rows, not a subst row. If the manager wants
  them named in the subst plan, [SUBST-SPEED] could be re-titled or a pointer added; that is a manager call.
- The pcrec compile time (about 137-280 ms of gcc per case) is a separate column and not a run-time loss.
- The roster is `simdna` for the library tier as for everything else in the window.
