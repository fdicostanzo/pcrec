## Kind row and shards

Row: `growth`, command `GROWTH_SHARD={shard} GROWTH_UNITS=build/cloudout/units.tsv GROWTH_MAKE_J=$(nproc) bash tests/growth/run_growth.sh`,
selector tests/ci/cloud_growth_shards.tsv (shards `table`), max_parallel 20, limit_min 45, needs `-`, owners `*`, suite 0 (on
request; it is hours of runner time), population `run_growth.py --shard-check --table {selector}`, measured
tests/ci/measured_growth.tsv, reweigh `cloud_units_plan.py growth ...`.

How the shards are weighted: LPT (longest first onto the lightest shard) over each cell's weight in shard seconds. A cell's weight
is, in order: its measured seconds in measured_growth.tsv; else the MEAN of the measured cells of its class (a matrix cell by
quantifier and kind, any other cell by family and kind); else a static class default. The shard count is
ceil(total work / (600 s target - 120 s ASan build - 70 s setup)); more than max_parallel shards run in waves (as mech's do).
Run 1's table used static defaults only (11 shards, predicted slowest 522 s) and was off by 4-5x. Run 2's table: 54 shards,
predicted slowest 609 s of step (679 s with setup), indivisible floor 679 s (the heaviest single cell, matrix/group.poss.first.bref@250,
about 489 s).

ASan placement: INSIDE each shard's run, not its own shard set. Why: the library pass bounds each in-process compile by 20x that
cell's CLI wall read from the same runner (no walls file crosses shards), which needs the CLI stage on the same shard; and the
brief asks for one row. The wall evidence (shard 2/11, 137 cells, 17:38:13 to 18:19:45) is that ASan dominates: CLI 5.5 min, plain
library 8.2 min, build-asan/ build plus ASan library 27.8 min. That makes the shard count large (54) but a separate ASan set would
carry the same total work and lose the sharp per-cell bound (a cell unseen gets the 300 s floor).
