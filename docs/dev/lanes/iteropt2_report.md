## 1. What changed (commits 923187ac8, 35ddea481, 0a651d60c)

- **(c) the cursor.** `<p>__step` and `<p>__one` take the subject, `*lop` and (with the retry)
  `*flp` as parameters (`cursor_params`/`cursor_args` in `src/gen/emit_iter.c`) instead of
  reading and writing `rx_iter` fields. `<p>__one` no longer binds. A new `always_inline`
  `<p>__one_call` (the body of `_next`, and of `<p>__one_local`) binds and passes the
  iterator's own `&it->lo`/`&it->flags`. `_next_n` binds once (after `if (k == 0) return 0;`,
  which still runs nothing in every state), holds `s`/`n`/`lo`/`flags` in locals across its
  k-loop and stores `lo`/`flags` once at the end.

  I1's `rx_next` body) cannot hold once `__one` takes a cursor and no longer binds. The gate
  now pins this lane's body (`tests/findall/one_body/*.one_body.txt`, `git mv` of the
  `*.i1_next_body.txt` files, regenerated by this compiler), so it still catches any
  unreviewed change to the one shared body. The reason is in commit 0a651d60c's message.
- **Mech anchors re-aimed** (VALIDATE_ONLY 6/6, each anchor found once): S1300 (the
  `*lop = %s__next_pos(...)` line), S1309/S1310/S1311 (the new `while` line), S1313 (the

- **Readers:** `tests/partlayout/writers.tsv` (always_inline row `^P__(step|step_own|one|one_call)$`),

Cause (e) variants, measured on top of (c), none adopted:

| variant | effect vs (c) |
|---|---|

| e4 do-while k-loop | identical to (c) |

- **(c) kept.** I is identical everywhere (a first staging, s1, with a local `lo` in
  `_next`, cost I +4..+5 because gcc kept `lo` in a stack slot; using the iterator's own
  fields as `_next`'s cursor removed that). N4, N64 and F improve 3-9% per match on dense
  cells. N1 is slightly worse on most cells (+2..+6) and better on c4.
- **Why (e) stays.** The k-loop's spills are register pressure: `it`, `i`/`k`, the caps
  pointer, `lo`, `s`, `n` and the attempt body's own state are live across the
  memchr/search call, more than the 6 callee-saved registers. Of N1's ~22 over I, ~7 is the
  bench driver's own batch loop (from e3: N1 − I − the 15-instruction wrapper) and ~15 is
  generated code. Closing it needs fewer live values across the call, which is (d)'s
  part-layout question rather than a loop shape.
