## FINDINGS

### (1) What pcrec already states
- The necessary run is stated: `req_run` (window, `hex@idx`) and `req_whole_run`, with `req_run_maxoff` / `req_landmark_maxoff` as a decimal or `unbounded` (docs/spec/facts_listing.md 4.1.2 p8, p8b; src/facts/req.c). `unbounded` is carried as a DECLINE (`why decline:unbounded`), i.e. as the absence of the handoff's K, not as a positive fact.
- The soundness statement "every match contains the run as a contiguous substring, at or after the attempt start" is NOT a listed fact. It lives in the header of src/facts/req.c (lines 1-70: the check is sound because every byte of every match lies in `[search_from, subject_length)`; lookaround bodies, lookbehind in particular, are deliberately not descended into, so no run byte lies before the match start) and in docs/design/reqpos_2b.md section 0 ("not a start bound, not an offset from the match start"). The spec states only the handoff consequence for a FINITE K (tuning.md 2.41 p1, match_api.md 6.3.7 p11: "every match begins at most K bytes before an occurrence of the landmark").
- Verdict: "this run is required at an unbounded distance after the match start" is IMPLIED (run present + maxoff unbounded + the req.c soundness rule), never stated as a contract sentence.
- Kit side: memfn/include/memfn.h carries the site frame `mf_site.handoff` (`MF_H_ASSIGN` and friends, memfn.h 355-368, 748), `mf_need` MF_REQUIRED/MF_OPTIONAL (402) and the PRES window limits (PCREC_MAX_REQ_RUN_SCAN 32 / EMIT 8, 242). No kit-side field mentions distance or K: per tuning.md 2.41 p7a the origin ("K, the moved start, the re-entry") is pcrec's, and the kit only answers presence plus the kept position of the landmark. So the kit is handed no distance fact at all today; the request does not need one either (Q4).

### (2) Routes with such a run, and whether any stops past the last occurrence
Both existing handoff rows demand a FINITE K:
- DFA scan / hybrid prefilter: `req_handoff_applies` (src/gen/emit_dfa.c 8861-8873) returns false for `k < 0 || k >= PCREC_W_UNBOUNDED`; the re-entry (`DFA_PREFILTER "handoff"`, tuning.md 2.41 p8a) shares the predicate.
- VM attempt loop with no DFA scan: `req_handoff_entry_applies` (emit_dfa.c 8946-8957) requires `whole_maxoff` finite; `req_handoff_attempts_applies` (8962) adds `req_parts_in_whole`. tuning.md 2.41 p8b says so in prose ("K is finite").
- On every unbounded run the pre-check is only the entry gate (least hit `>= startpos`, none answers no match; `RX_REQ_HANDOFF "none"`), its position is discarded, and the search proceeds from startpos. DFA route: one forward scan runs to the subject end after the last occurrence (no per-position attempts, so the saving is the tail bytes of that scan). VM route: one attempt per position after the last occurrence, each failing (the share the row's trigger is about). Find-first vs find-all: the pre-check is re-asked per call from the new startpos, so find-all re-gates each call but does not stop within one.
- grep for "last occurrence / past the last" over src and docs/spec finds nothing relevant. Conclusion: NO route stops past the last occurrence today.
- Unbounded patterns where the stop could apply need: pre-check emitted (`RX_REQ_WHY "emitted"`), unanchored (one-attempt anchors have nothing to skip), not `dominated` (reverse-end walk proves no-match itself).

### (4) What pcrec must add, and the draft kit request
pcrec side (a later build row, NOT done here):
1. State the fact. Cheapest: one spec sentence in facts_listing.md 4.1.2 p8 (and tuning.md 2.41): "a necessary run (`req_run`/`req_whole_run`) occurs inside every match, at or after the attempt start, whatever `req_run_maxoff` is; `unbounded` says only that the distance has no finite bound", plus the lookbehind exclusion. No new fact column is required: `req_run` plus `req_run_maxoff` already say it; the sentence turns the implication into the contract. A positive companion (`req_run_after_start yes`) is only worth adding if a second reader (the kit, a bench) needs to query it.
2. Use it: a new `req-use` row (sibling of `handoff-attempts`, tuning.md 2.41 p8b) for K unbounded: after each failed attempt, re-ask the pre-check from the attempt position; none ends the search with no match; a hit leaves the attempt position unmoved (no `c - K` jump; K is infinite). This is exactly `handoff-attempts` with the move step dropped, so it should be a degenerate form of that row, not a parallel mechanism (memory pcrec-general-mechanisms-not-special-cases). Same applicability gates apply (emitted, unanchored, `req_parts_in_whole` so a re-ask is amortized linear). DFA/hybrid route: the same re-ask in the forward scan's restart sites, or only at the entry (then the tail saving is nil); a design question for the row. Give-up note: like tuning.md 2.41 p9a, skipped attempts spend no steps, so a step give-up may become the unbounded answer, never the reverse.
3. A deny flag only if it can be slower (memory pcrec-flag-follows-caller-effect): a re-ask per failed attempt that finds a hit adjacent each time costs a compare per attempt; on dense hits it could lose, which the row's trigger cell must price.

Draft kit request (facts only, for the manager to file as R-41):
> R-41 (pcrec to kit): re-find cost of a presence site asked repeatedly from advancing positions. FACTS: (a) a pcrec VM attempt loop may ask an existing run-presence site (the same site, same run, `MF_H_ASSIGN` keeping the least hit position, or the same site returning `n` on none) once per failed attempt, with a search start that is non-decreasing and advances by one character (one byte under byte encodings, one UTF-8 character under `-e utf8`) between asks, up to the subject end; (b) the run is necessary for every match at or after the attempt position, at any finite or unbounded distance, so a returned hit position `c >= start` is meaningful and `n` means no match is possible from `start` on; (c) every other part of the site is a byte or slice of the run (the `req_parts_in_whole` condition, already stated for R-30). QUESTION: for such an ask sequence, over a subject of length n, is the total work of the asks O(n) or better (each ask resuming from the previous hit while it is still ahead), or can one ask rescan to a distant hit again, for the sites the R-30 whole-run layout produces? State the worst case as a number of bytes examined per ask and per sequence, for the run length range 2..32, under both `-fno-memfn-simd` and `-fmemfn-simd`. If an ask resumes only when pcrec passes the previous hit (pcrec keeps the last hit and compares positions, as the bounded `handoff-attempts` row does today), say that this suffices and no kit change is wanted.
No distance, no stop rule and no loop shape is stated to the kit; those stay pcrec's. A likely answer is "already linear, no change", in which case R-41 is a confirmation and the row is pcrec-only. Because the bounded row already depends on that same property (`req_parts_in_whole` doc comment, emit_dfa.c 8990-9000), the request may be redundant with R-30's note; the manager can skip it and rely on that comment.
