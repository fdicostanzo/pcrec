# mechreach — triage of the stage-4 battery's five UNREACHED-UNEXPECTED mech rows

Lane `mechreach` (sonnet), branch `lane/mechreach`, worktree
`worktrees/mechreach`. Brief: the stage-4 battery's mech stage
(`build/battery_20260908_stage4/mech.log`, run at `a0eb21fc`, `PROCS=6`)
scored five rows `UNREACHED-UNEXPECTED` — S-U1, S-U2, S-U3, S-U11, S200 — all
sharing the shape "the witness probe exited N and 1 of its 1 expected strings
are absent". The tension to resolve: lane `utf8s4`'s own delivery had
validated S-U1/2/3/11 as DETECTED the same day. Read all five in full and ran
the actual mechanism by hand before touching anything (`docs/dev/learnings.md`
§3 / `[MECH-REACH]`: a witness that stops reaching its site certifies
nothing).

**Every root cause was an authoring bug in the row's own definition, present
since the row was WRITTEN (all four utf8 rows: commit `a3ba7de7`, the same WIP
commit; S200: pre-existing, unrelated commit) — none of the five ever worked
under `run_sabotage_matrix.sh`'s real mechanism.** None is (a) a matrix-context
vs. solo difference, (b) a commit landing mid-battery-run (the mech scratch
trees the trailer cited were already cleaned up, but the sabotage row files
were byte-identical between the battery's measured SHA `a0eb21fc` and current
HEAD `9a2170e0` — checked directly with `git diff`), or (c) a general
tab/glob-eating bug in `run_sabotage_matrix.sh`'s own parser. Four different,
independently-diagnosed bugs; one general mechanism gap.

## Per-row root cause and fix

### S-U1, S-U2, S-U3 — an unreachable literal, never reachable

`SAB_REACH_EXPECT='Pattern:  */'` (note the TWO spaces — an EMPTY pattern
between the header comment's colon and its close). `emit_pattern_comment`
(`src/gen/emit_dfa.c`) never emits that: it always writes the pattern's own
text there. The real headers for these three probes read:

    S-U1  /* Generated by pcrec. Pattern: [^k] */
    S-U2  /* Generated by pcrec. Pattern: k */
    S-U3  /* Generated by pcrec. Pattern: [a-z] */

Confirmed by running each row's exact `SAB_REACH` command by hand (both
through the interactive shell's own `grep` shim and, since that shim does NOT
propagate into a plain `bash -c` child, through the REAL system grep too —
irrelevant here since the probe never calls grep, but load-bearing for S200
below). All three literals were fixed to the real header text.

### S-U11 — three bugs stacked in one probe, plus a matrix-mechanism gap

1. `SAB_REACH='grep -c "check_1n_fold()" tests/registry/pc4_check.c'` used a
   **relative path**. The probe's cwd is `$REACH_TMP`, a fresh scratch
   directory under `$MECH_SCRATCH` — never the tree root — so the file was
   never there. `grep`'s own exit code on a missing file is 2, exactly the
   code the battery's mech.log recorded ("the witness probe exited 2").
2. `SAB_REACH_EXPECT='^1$'` is matched as a **literal substring**
   (`grep -qF` inside the driver, by design — see `run_sabotage_matrix.sh`'s
   own header, "ONE REQUIRED LITERAL SUBSTRING PER LINE"), never as a regex.
   `^1$` can only ever match the three literal characters `^`, `1`, `$` in
   sequence, which `grep -c`'s own output (a bare `1`) never contains. Fixing
   bug 1 alone would still have left this row UNREACHED.
3. **A third, deeper bug surfaces once 1 and 2 are fixed**: `SAB_SUITES`
   was `"registry"`, and `run_sabotage_matrix.sh`'s `registry` arm builds and
   runs `tests/registry/registry_check.c` — never `pc4_check.c`, the file
   this sabotage actually edits and the file `check_1n_fold()` (S-U11's own
   detector) lives in. This is not a staleness bug: `tests/mech/CLAUDE.md`
   and `tests/mech/run_sabotage_matrix.sh`'s own header have documented PC-4
   as deliberately NOT wired into this matrix's suite dispatch since
   MOD-0.8c ("no sabotage's ONLY signal is a semantic differential today.
   Add it the day one is, with the sabotage that needs it."). S-U11 is that
   day — its sole detector is `check_1n_fold()`, and no existing arm reaches
   it.

Fix: corrected the path and the literal (row-local), then registered a new
`pc4` suite arm in `run_sabotage_matrix.sh` (a mechanism-level change,
documented below) and pointed `SAB_SUITES` at it.

### S200 — the [MACPORT] `grep -P` trap, unfixed on this one row

`SAB_REACH='grep -cP "^pattern .*\\t" "$TREE/tests/base/bounded_repeats.rxt"'`
uses `-P` (PCRE). The path is correct (uses `$TREE`), but the driver's actual
execution environment resolves the REAL system `grep` — `/usr/bin/grep`, BSD
grep 2.6.0-FreeBSD on this Mac — which has no `-P` at all: `grep: invalid
option -- P`, exit 2. Again, exactly the exit code the battery's mech.log
recorded.

**This is not a new trap.** `run_sabotage_matrix.sh` itself hit the identical
shape in its own results-table extraction and was fixed at [MACPORT] (see the
script's own comment: `# [MACPORT] was 'grep -P ...' — BSD grep has no -P, so
on this box the row filter emitted a usage error and ZERO rows...`). That fix
was never applied to this one sabotage row, which is why S200 is a row-local
fix rather than a second mechanism change — `grep -P` appears nowhere else
under `tests/mech/sabotages/` (checked directly).

Fixed with `-E` (BSD grep supports ERE) and `$(printf "\t")` for the literal
tab, rather than bash's `$'...'` ANSI-C quoting — the latter would need a
nested single quote inside the already-single-quoted `SAB_REACH` field, which
`tests/mech/sabotages/CLAUDE.md`'s own "Traps that have actually been hit"
section names explicitly ("Nested single quotes in SAB_REACH break the
assignment quietly... found while retrofitting S17/S18/S19").

**A note on the diagnostic detour that did NOT pan out**: my first read of
`which grep`/`grep --version` inside this session's own Bash tool reported
`ugrep` with `-P` support, which looked like it contradicted the BSD-grep
theory. That was the interactive shell's own `grep` — a Claude Code
convenience function that shadows the real binary and does not propagate into
a plain `bash -c` child process (verified directly: `env | grep -c
BASH_FUNC_grep` is 0, and a fresh `bash -c 'type grep'` reports
`/usr/bin/grep`). `run_sabotage_matrix.sh` always runs as a plain script, so
it always sees the real BSD binary — matching the battery's own exit code.

## Was this ever really DETECTED before?

`docs/dev/lanes/utf8s4_report.md` and the `83f7175b` merge commit both state
"S-U1/2/3/11 DETECTED" the same day these rows were authored. Given the reach
bugs above are unconditional (never reachable, from the same WIP commit that
wrote them), that DETECTED status cannot have come from a real
`run_sabotage_matrix.sh` run of these rows through their `SAB_REACH` gate — a
failing reach check exits before the sabotaged tree is even built. The most
likely explanation, consistent with this project's own convention
("the implementation lane does not run the matrix (the manager does)"), is
that the validation was a HAND application of `SAB_BEFORE`/`SAB_AFTER` against
a scratch tree, run through the harness directly — which is a real and valid
measurement of the sabotage's DETECTABILITY, but never exercised the reach
mechanism this same commit also wrote into the row definitions. Not
investigated further: it does not change any fix above, and the fully wired
mechanism now reproduces those exact fail counts (22/26/30/22) itself.
