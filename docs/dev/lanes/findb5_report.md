## 1. What landed

| area | content |
|---|---|
| kind | `cpfreq` is a BUNDLE schema row (`rxt_schema.def`). Its `row` key is `U+HHHH`..`U+HHHHHH` (uppercase, four to six digits, no leading zero past the fourth — the analyzer's own spelling), a Unicode scalar value (surrogates and > U+10FFFF refused), strictly ascending; at most `PCREC_MAX_FIND_CPFREQ_ROWS` (new limits row, 65,536) rows. Rows are stored sparse (`PcrecFindCp`), in the reader's block, the resolved chain's link copy and the pre-parsed store table (`findgen` writes a `cps` array; `counts` is NULL for a `cpfreq` block). |
| derivations | `encode-utf8`/`encode-latin1` implemented in `src/core/findings.c` beside the closed derivation VOCABULARY, which moved there from `rxt_source.c` (`pcrec_find_deriv`, the table's one home, as its old comment asked). `pcrec_find_derive_counts` (block rows → 256 byte counts, + latin1's drop total) and `pcrec_find_block_byte_rate` (derive + §2.5 normalize) are the ONE path the compile's accessor AND `--list-analysis`'s resolution row read — the dump no longer normalizes `fb->counts` itself. |

## 6. B5 and the UTF-8 byte-rate goal (F3, B1's utf8 tie lottery)

The goal as briefed: B5 is the road to UTF-8 byte rates, which should fix
F3 and B1's utf8 tie lottery (utf8attrib (B) item 5: under `-e utf8` the
default is NONE, the offset-k MASS falls back to cardinality, and ties pick
by order — `@é` -> 0xC3, `user@` -> `s`). **What B5 delivers and what it
does not, measured:**

1. **The mechanism is complete.** A `-e utf8` compile can now read a
   measured byte-rate: `cpfreq` + `encode-utf8`, through the one accessor,
   stamped, listed, checked against an independent derivation. A user with
   a non-ASCII exemplar (`pcrec_analyze.py --scan freq,cpfreq`) gets real
   utf8 rates by naming it.
2. **The default path does not move** (identity 0 changed): `default`
   still declares `byte` only (D123-5, "byte-identical as authored"), so a
   compile naming nothing still has NONE under `-e utf8` and **F3/the
   lottery are NOT fixed on the default path by B5.** Fixing them there
   needs the default chain to carry a utf8-serving block — the design's
   separate "default regeneration" row (D123-5), or a ruling that the
   default `include`s a shipped bundle for `utf8`. That is Frank's.
3. **FINDING — the shipped corpora are pure ASCII, and that makes them
   HARMFUL for non-ASCII literals under `-e utf8` as things stand.** Every
   byte >= 0x80 is at the 2 ppm floor in both bundles, so all non-ASCII
   bytes TIE; the run reader's data tie rule is LEFTMOST
   (`pcrec_find_run_scan_index`: "the run in order, ties to the leftmost"),
   while its NONE answer is RIGHTMOST ([OPT-REQRUN-ENC], chosen precisely
   because a run's leftmost byte is a LEAD byte shared by a whole script
   block — O-60). So naming `weblog`/`log` re-creates O-60's lead-byte pick:
   measured, `кириллица+ -e utf8` scans 0xD0 (the Cyrillic lead byte) under
   `weblog`/`log` where the default's NONE scans the run's last byte;
   `[a-z]+@é` scans 0xC3 under `weblog` (0xC3/0xA9 tie at the floor,
   leftmost wins). Answer-identical (every member is necessary), a SPEED
   hazard. Two general fixes, either one a separate measured row, NOT built
   here (outside B5, and it moves `-e byte` artifacts wherever data ties
   exist):
   - **a tie carries no information, so a PICK's data tie rule should
     equal its NONE answer's order** — for the run reader, ties to the
     rightmost. The set reader already is consistent (its candidate 0 is
     the rightmost); the run reader is the one inconsistent spelling. This
     also bears on B4's owed [r3 F4] tiebreak population. **Recommended.**
   - or ship a code-point corpus with real non-ASCII text for utf8 (the
     "UTF-8 byte rates" proper), which the default-regeneration row would
     want anyway.
   Until one lands, the report's advice for users is: name `weblog`/`log`
   under `-e utf8` for ASCII-literal patterns only.
