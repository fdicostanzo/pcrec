# I-114 — the [OPT-HYB-RESEED] re-seed hand-twin, self-contained for the bench

Lane `reseedtwin`, 2026-09-27, sonnet, packaging only (nothing under `src/`
or `tests/` changes). Written so the bench dev — who cannot read pcrec's
tree — can reproduce the twin, confirm the mechanism on x86, and decide
whether it is worth a bench cell. Everything needed travels in this file:
the pcrec pin, the exact compile commands, the three unified diffs, the
subject generator, and the Mac scratch numbers.

Context: `docs/dev/utf8_attrib.md` (A) rows 1/10/11 and its "Finding: the
hybrid's retry never re-seeds without an MRL clamp". `[OPT-HYB-RESEED]`
(drafted in that file, `docs/dev/plan.md`, STATE:not-started) is the general
fix: the VM hybrid's attempt loop re-seeds `attempt_position` from the
prefilter after EVERY failed attempt, not only when an MRL (minimum-
remaining-length) clamp exists. Today, on a hybrid whose prefilter is
LOOKAROUND-ERASED (over-approximates the pattern's real language), a failed
attempt makes the loop step one character at a time to the subject's end
instead of asking the prefilter where the next real candidate is.

## The three patterns and the exact compile commands

```
pcrec --features all -p rx -e utf8 -o row1_varwidth.c  --pattern '(?<=a|é)x'
pcrec --features all -p rx -e utf8 -o row10_neg.c      --pattern '(?<!日)本'
pcrec --features all -p rx -e utf8 -o row11_fixed.c    --pattern '(?<=é)x'
```

(`--features all` is the bench adapter's own configuration; `-e utf8` per
the utf8@0.1 roster; no `--emit-main` — the twins are timed with a separate
driver, below.) All three compile clean, no warnings, at `gcc-16 -O2`.

All three artifacts share ONE shape at their unanchored retry loop
(`rx_search_run`, near the end of the file, after
`rx_reset_for_next_attempt(run)`):

```c
        rx_reset_for_next_attempt(run);
        if (attempt_position >= subject_length) return 0;
        /* [K49] The retry advance is this ENCODING's step, not `+ 1`: ... */
        attempt_position++;
        while (attempt_position < subject_length
               && (subject[attempt_position] & 0xC0) == 0x80) attempt_position++;
    }
    if (capture_spans) rx_report_captures(run, capture_spans, attempt_position, result);
```

The one-byte-then-continuations advance IS the defect once a lookaround has
erased the DFA prefilter's exactness: once ONE candidate fails, this loop
walks every remaining character boundary to the subject's end without ever
asking the prefilter again.

## The twin: one block, inserted after the advance, in all three files

The hand edit is the SAME text `src/gen/emit_vm.c`'s `retry_win` already
emits at the search ENTRY (and, today, at the retry ONLY when
`v->nclamp > 0`) — moved to fire at the retry UNCONDITIONALLY, whenever a
prefilter exists at all:

```c
        /* HAND TWIN (reseedtwin, [OPT-HYB-RESEED]): the same three lines as
         * the entry call, emitted unconditionally here instead of only under
         * v->nclamp > 0. */
        {
            ptrdiff_t window[1][2];
            if (rx_prefilter(subject, subject_length, attempt_position, window) != 1) return 0;
            attempt_position = (size_t)window[0][0];
        }
```

inserted immediately after the advance's `while` loop, before the `for(;;)`
loop's closing `}`. Because none of these three patterns carries an MRL
clamp, there is no `window_end` line to add — that's the whole reason each
diff is 8 lines.

## The driver

Find-all, `pos = end` on a non-empty match / `pos = rx_next_pos(...)` on an
empty one (none of these three patterns can match empty; the branch is kept
for correctness). Best-of-5 wall time in µs, plus a match count and an
FNV-1a hash of every `(start,end)` pair so two builds' ANSWERS can be
compared without printing every span.

```c
/* drv.c */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stddef.h>
#include <stdint.h>
#include <time.h>

extern int rx_search(const unsigned char *subject, size_t subject_length,
                      size_t search_from, ptrdiff_t (*capture_spans)[2]);
extern size_t rx_next_pos(const unsigned char *s, size_t n, size_t pos);

static uint64_t now_ns(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (uint64_t)ts.tv_sec * 1000000000ull + (uint64_t)ts.tv_nsec;
}

static void run_once(const unsigned char *s, size_t n,
                      long *out_matches, uint64_t *out_hash) {
    size_t pos = 0;
    long matches = 0;
    uint64_t h = 1469598103934665603ull; /* FNV-1a 64 offset basis */
    const uint64_t prime = 1099511628211ull;
    ptrdiff_t caps[1][2];
    while (pos <= n) {
        int ok = rx_search(s, n, pos, caps);
        if (!ok) break;
        ptrdiff_t start = caps[0][0], end = caps[0][1];
        matches++;
        h ^= (uint64_t)start; h *= prime;
        h ^= (uint64_t)end;   h *= prime;
        if (end > start) pos = (size_t)end;
        else pos = rx_next_pos(s, n, pos);
    }
    *out_matches = matches;
    *out_hash = h;
}

int main(int argc, char **argv) {
    if (argc != 2) { fprintf(stderr, "usage: %s SUBJECT_FILE\n", argv[0]); return 2; }
    FILE *f = fopen(argv[1], "rb");
    if (!f) { perror("fopen"); return 2; }
    fseek(f, 0, SEEK_END);
    long sz = ftell(f);
    fseek(f, 0, SEEK_SET);
    unsigned char *buf = malloc((size_t)sz);
    if (fread(buf, 1, (size_t)sz, f) != (size_t)sz) { perror("fread"); return 2; }
    fclose(f);

    long matches = 0;
    uint64_t hash = 0;
    double best_us = -1.0;
    for (int i = 0; i < 5; i++) {
        long m; uint64_t h;
        uint64_t t0 = now_ns();
        run_once(buf, (size_t)sz, &m, &h);
        uint64_t t1 = now_ns();
        double us = (double)(t1 - t0) / 1000.0;
        if (i == 0) { matches = m; hash = h; }
        else if (m != matches || h != hash) {
            fprintf(stderr, "NONDETERMINISM run %d: matches %ld->%ld hash %llx->%llx\n",
                    i, matches, m, (unsigned long long)hash, (unsigned long long)h);
        }
        if (best_us < 0 || us < best_us) best_us = us;
    }
    printf("matches=%ld hash=%016llx best_us=%.3f\n",
           matches, (unsigned long long)hash, best_us);
    free(buf);
    return 0;
}
```

## The subject generator, deterministic, inline

Three synthetic subjects — call them `synth-1m`, `synth-64k-asc`,
`synth-dense` to keep them apart from the bench's own `t-1m`/`t-64k-*`
files, which this lane never read. Fixed seed (`20260927`) so the bench can
regenerate them byte-identically without this file's binaries.

```python
#!/usr/bin/env python3
# Deterministic subject generator for the reseedtwin lane.
import random

SEED = 20260927

def gen_mixed_1m(seed=SEED):
    """~1 MiB mixed subject: ASCII prose with 'a'/'x'-bearing words, a
    minority of accented Latin words, and a CJK-word minority."""
    rng = random.Random(seed)
    ascii_words = ["the","quick","brown","fox","jumps","over","lazy","dog",
                   "cat","apple","exit","axiom","next","index","excess",
                   "extra","annex","exam","text","context","example"]
    latin_extra = ["café","déjà","naïve","élan","exposé","protégé"]
    cjk_words = ["日本語","東京都","本州","京都府","本日","日本"]
    out, size, target = [], 0, 1_000_000
    while size < target:
        r = rng.random()
        if r < 0.85:   w = rng.choice(ascii_words)
        elif r < 0.95: w = rng.choice(latin_extra)
        else:          w = rng.choice(cjk_words)
        out.append(w); out.append(" ")
        size += len(w.encode("utf-8")) + 1
    return "".join(out).encode("utf-8")[:target]

def gen_64k_ascii(seed=SEED+1):
    """64 KiB pure-ASCII subject: frequent 'x' (~8%), rare 'a' (~0.5%),
    zero 'é'/CJK (impossible in ASCII)."""
    rng = random.Random(seed)
    letters = "bcdfghijklmnopqrstuvwyz "  # no 'a', no 'x'
    out, size, target = [], 0, 65536
    while size < target:
        r = rng.random()
        if r < 0.08:    ch = "x"
        elif r < 0.085: ch = "a"
        else:           ch = rng.choice(letters)
        out.append(ch); size += 1
    return "".join(out).encode("ascii")[:target]

def gen_match_dense(seed=SEED+2):
    """200 KB match-dense synthetic: repeats of 'ax', 'éx' (utf-8), '日本',
    '本', '日' so all three lookaround patterns get frequent real matches."""
    rng = random.Random(seed)
    units = ["ax", "éx", "日本", "本", "日", "x", "a"]
    out, size, target = [], 0, 200_000
    while size < target:
        b = rng.choice(units).encode("utf-8")
        out.append(b); size += len(b)
    return b"".join(out)[:target]

if __name__ == "__main__":
    import sys, pathlib
    outdir = pathlib.Path(sys.argv[1] if len(sys.argv) > 1 else ".")
    (outdir / "synth-1m.bin").write_bytes(gen_mixed_1m())
    (outdir / "synth-64k-asc.bin").write_bytes(gen_64k_ascii())
    (outdir / "synth-dense.bin").write_bytes(gen_match_dense())
```

Sizes produced: `synth-1m.bin` 1,000,000 B, `synth-64k-asc.bin` 65,536 B,
`synth-dense.bin` 200,000 B.

**Read this table carefully before comparing it to `docs/dev/utf8_attrib.md`
(A)'s ×25/×48/×124 numbers — those DO NOT reproduce on these subjects, and
the reason is subject composition, not a wrong twin.** `docs/dev/utf8_attrib.md`
measured against the bench's own `t-1m`/`t-64k-*` files, where `x`/`a`/`é`
sit at ordinary English/Latin letter frequencies. This lane's own
`synth-1m`/`synth-64k-asc` generator (above) was written without reading
those files (scope mandate: read-only reference at most, and this lane
never touched pcrec-bench) and its ASCII word list happens to be
`x`-HEAVY (`fox`, `exit`, `axiom`, `next`, `index`, `excess`, `extra`,
`annex`, `exam`, `text`, `context`, `example` — most of the pool contains
an `x`). A dense candidate byte means: (a) the walk-to-end defect only
has to skip a SMALL fraction of positions before hitting the next real
candidate anyway, so the win shrinks (`asr-lb-varwidth`/synth-dense,
`asr-lb-neg`/synth-dense), and (b) the twin's extra `rx_prefilter` call at
EVERY retry costs something even where the walk it would skip is short — on
`asr-lb-fixed`, whose only real matches are in synth-dense and whose two
`x`-only subjects have ZERO matches, that extra call is pure overhead and
the twin is measurably SLOWER (0.90x, 0.81x).

This is not a wash: `asr-lb-neg`/synth-1m (×11.09) and both
`asr-lb-varwidth` cells with sparse candidates (×3.06, ×3.52) show the
mechanism clearly and in the predicted direction, and every cell's answer
is unchanged. It is a demonstration that the win's SIZE is a function of
how rare the prefilter's candidate byte is relative to how often the
lookaround discards it — exactly `docs/dev/utf8_attrib.md`'s own framing
("the prefilter OVER-approximates whenever the VM route's reason is erased
from the DFA") — and this lane's synthetic subjects were not built to
match the bench's real letter frequencies, so they under-state (and on
`asr-lb-fixed`, invert) the effect relative to the ×25-×124 the doc reports
against the bench's own `t-1m`.

## What to measure on x86

1. **The bench's OWN utf8@0.1 subjects for these three cells**
   (`asr-lb-varwidth`, `asr-lb-neg`, `asr-lb-fixed` — `bench/utf8/throughput/
   t-1m.bin`, `t-64k-asc.bin`, `t-64k-cjk.bin`, `t-64k-lat.bin` etc., not
   read by this lane) are the numbers that matter for the bench ledger; this
   lane's own `synth-*` subjects are a portability/correctness check only,
   not a substitute.
2. **This lane's three `synth-*` subjects too**, regenerated from the
   Python script above (seed `20260927`, byte-identical wherever Python's
   `random.Random` implementation is used — CPython's Mersenne Twister,
   which is what generated the Mac numbers) — as a cross-machine sanity
   check that the mechanism (not the magnitude) reproduces.
3. **Confirm the answer-identity claim independently**: `matches`/`hash`
   from `drv.c` above must agree between the original artifact and its twin
   on every subject × pattern cell. Any disagreement is a finding in
   itself and should be reported before any timing number.
4. **If x86 shows the same subject-composition sensitivity** (dense
   candidate byte narrows or reverses the win), that is itself worth
   reporting back — it bears on `[OPT-HYB-RESEED]`'s D77 gate
   ("census the VM-hybrid artifacts with `nclamp == 0` … split by whether
   the prefilter language is exact … or over-approximate") and on whether
   the general fix should be unconditional or itself density-gated.
