# R10 — MOD-0's design, reviewed before a line of it was built

**Target:** decision D29 (docs/decisions.md, 2026-08-11) and the eight MOD-0
substeps in docs/plan.md. **No code existed to review.** This is the first
panel in the project run against a DESIGN rather than an implementation, and
that turns out to be the most valuable property of it: every finding below is a
defect that would otherwise have been found after it was built, or not at all.

**Panel:** five critics, ~2,400 lines of findings, five distinct lenses, all
read-only against the repo (none ran `make`; all probes were compiled in
scratchpad). Baseline verified green before dispatch — `make` and `make test`
both exit 0 with statuses captured directly, zero `FAIL:` counted UNANCHORED
(wake §0.5's lesson applied), suite counts 1012 / 85 / 397 / 164 / 143 / 29 / 7.

| critic | lens | outcome |
|---|---|---|
| C1 | the ambiguity guard | 4 design-breaking, 1 needs-answer, 1 recorded |
| C2 | the verdict taxonomy under compile OPTIONS | 3 design-breaking, 3 needs-answer |
| C3 | can the pure/impure split be built | 2 design-breaking, 2 REFUTED attacks |
| C4 | a control sharing a source with what it controls | 6 design-breaking, 1 needs-answer, 5 refuted |
| C5 | re-derive every measured number | 1 WRONG, 1 IMPRECISE, 6 CONFIRMED |

**Verdict: D29's spine survives; the guard that justified its central trade does

the retirement of `check_tail_precedence`, both proposed controls, and four

## The finding that matters most: the repository had already written the warning

**C3-1.** `src/parse/registry.c:62-72`, written 2026-08-10 — the day before D29:

> `\ddd` is an octal escape or a backreference depending on how many capture
> groups the parser has seen SO FAR. `(a)\12` is octal 012; with twelve groups
> it is a backreference to group 12. [...] A row can say "this doorway belongs
> to module X"; it cannot say which construct X should build. **Do not design a
> handler signature that assumes it can.**

D29 does not cite it, does not answer it, and specifies exactly the signature it
forbids. C3 pinned the behaviour rather than trusting the comment:

    (a)x11 \12        octal (consumed LF)
    (a)x12 \12        BACKREFERENCE to group 12
    (?n)(a)x12 \12    octal again — (?n) suppresses the capture
    (?n:(a)x12)\12    octal — scoped option
    \Q(a)x12\E\12     octal — parens inside \Q..\E do not count
    [()](a)x12 \12    parens inside a class do not count
    \12 (a)x12        FORWARD groups do not count

and `\1..\9` is a DIFFERENT rule again — whole-pattern count, not count-so-far:
`\8(a)x8` compiles, `\8(a)x7` is error 115, `\8` alone is error 115.

So one doorway byte is two constructs owned by two modules, discriminated by a
running capture count under scoped option state. `(pat, patlen, at, ctx_flags)`
cannot compute it and a `static const` row cannot declare it. Module attribution
is tier 2 and EXACT under D26, so this is not a rounding error.

Second-order, and it is D29's own "Revisit when" trigger reached before the first
module ships: when octal escapes get the row `registry.c:305` already records as
owed, bucket `1` holds two recognisers that must BOTH claim `\12`, and pcrec
reports an internal error for a pattern PCRE2 compiles.

**This is D27's mechanism exactly.** The knowledge was in the repository,
correct, dated, and specific — in a comment that no check reads and that the
author of D29 did not act on. SPEC-classes-F1 was the same shape (the fact sat in
the `\N` row's own `note`). D27 says tests derived from the code inherit the
code author's alphabet; R10 adds that DESIGNS derived from a reading of the code
inherit the reader's attention.

## The central mechanism, refuted three ways

### C1-1 / C1-3 — "exactly one may answer" fires on a CORRECT registry

D29's acceptance test is described wrongly. The `\N` bucket has THREE rows, not
two (`registry.c:223` says so in its own heading), and the prefix-related pair
that longest-tail-wins actually resolves is `{` vs `{U+` — the REJECTED row
against the module row — not the pair D29 names. Written honestly, those two
recognisers return REFUSE and CLAIM on `\N{U+0041}`: two non-DECLINE answers,
guard fires, and the table is correct — `build/pcrec` answers that pattern right
today.

It generalises. Measured by iterating `pcrec_registry()`: all four tailed buckets
have exactly one tail-less FALLBACK row, and the honest recogniser for a fallback
row is "always matches" — the very recogniser D29 calls naive and presents
tripping the guard as the guard working. It is not naive; it is the row. In two
of the four buckets the fallback and a tailed sibling carry OPPOSITE verdicts:

    \N bucket    fallback CLAIMs (classes),  the `{` row REFUSEs  -> on \N{name}: two answers
    (?P bucket   fallback REFUSEs,           the `<` row CLAIMs   -> on (?P<n>a): two answers

The only way to silence the guard is to write each recogniser as "`{` **and not**
`{U+`" — longest-tail-wins, hand-encoded per row, in code no check can see.
**D29 retires the rule and keeps the obligation.**

And the guard is *vacuous* over the bucket with the most `tail_default` rows:
`(?P`'s three tails (`<`, `=`, `>`) are single bytes and can never overlap, so
"the ambiguity guard polices it for free" buys exactly nothing there.

### C1-2 — a UNIQUENESS guard was traded for a REACHABILITY guard

`check_tail_precedence` has two halves and D29 discusses one.
`registry_check.c:461-469` is reachability, and says so in its own failure text:
*"fell through to the tail-less row — a tail that matches must win, or a tailed
construct is unreachable"*. D29's replacement fires only on TOO MANY answers.
Nothing fires on ZERO answers, which is the more likely authoring error, because
a shape written from memory is too tight rather than too loose.

**D29's own `-\d+)` collapse is an instance.** Measured:

    (a)(?-1)     ok
    (a)(?-1      err 114 missing closing parenthesis   <- malformed body, STILL the construct
    (a)(?-1x)    err 114
    (a)(?-1:x)   err 114

`-\d+)` requires the `)`, so it DECLINEs on all three; the bare `-` option-run
recogniser declines too; zero answers; pcrec falls to the `(?` catch-all. Today,
with the retired rule, all three correctly report module `recursion`. **The
proposed simplification is a tier-2 regression**, and D29's own principle —
"a malformed body is still the construct" — is what it violates.

### C4-4 / C4-5 — the runtime half is disarmed by `break`, and is monotone toward deletion

The guard is a loop that must keep going after the first non-DECLINE answer. The
disarming edit is `break`, it is silent, it is the natural performance edit, and
**D29 itself supplies the pressure to make it** (its own landmine section notes
the class-bracket doorway is on the base-tier path). The project has already run
this experiment: `src/parse/CLAUDE.md` records that "reducing find() to
first-matching-tail produced ZERO failures repository-wide".

D29 asserts "a runtime guard cannot narrow silently the way a check can". That is
backwards. A check can assert it had something to observe — `check_tail_precedence`
does exactly that (`registry_check.c:473-479`) and fails loudly when its subject
disappears. A runtime guard emits nothing when it holds, so its success is
indistinguishable from its absence. **The trade is a check that FAILS when it has
nothing to watch, for a check that PASSES when it has nothing to watch** (C4-7),
on the one axis this project has been burned on repeatedly.

And uniqueness is satisfied more easily as the table SHRINKS: one recogniser in a
bucket is never ambiguous, zero never is. R5's recorded incident — deleting seven
rows left all seven suites green, and "the parser and the table AGREED IN UNISON
that the wrong answer was correct" — is invisible to it.

## The verdict taxonomy: right instinct, wrong axis

**C2-3.** D29's table has one discriminating column, "PCRE2's behaviour", and it
does not determine two of the three answers: "recognises the construct, body
valid or not" and "errors" are BOTH true for every malformed body — the case D29
spends its longest paragraph on. Measured pairs where the observable is the same
shape and D29 demands opposite answers:

    [[:foo:]]    [122] unknown POSIX class name        -> FIX-2 decided REFUSE
    (?i-m-s)     [194] malformed option setting        -> D28 measured CLAIM
    \N{U+0041}   [193] supported only in UTF mode      -> registry says CLAIM

The real discriminator is **did PCRE2 DISPATCH** — which is D28's axis, the one
D29 demotes to "a sub-distinction inside CLAIM". It is not a sub-distinction:
`SYN_NOT` vs `SYN_{OK,MALFORMED}` IS the CLAIM/not-CLAIM line, and
DECLINE-vs-REFUSE is a SECOND, ORTHOGONAL axis. Two bits, four cells.

**C2-6 — and the fourth cell is occupied.** `[^]` under `PCRE2_ALLOW_EMPTY_CLASS`
compiles: PCRE2 does not dispatch (not CLAIM), it errors (not DECLINE), and an
option makes it valid (not REFUSE). pcrec's current answer agrees with PCRE2's
default by accident, since the reasoning that would justify it is absent.

**C2-1 — REFUSE's second clause is measurably false.** "no module can ever make
it valid": `\U` and `\u` compile under `PCRE2_ALT_BSUX`, an option that exists
for that exact purpose, and `\N{name}` compiles under
`PCRE2_EXTRA_BAD_ESCAPE_IS_LITERAL`. **PCRE2 itself already ships the module**,
for a construct pcrec carries an `RS_REJECTED` row about. Nothing in D26, D28 or
D29 mentions compile options at all, and the one outside authority is
constitutionally unable to see this: `pcre2_check.c:50` — *"ALL COMPILES USE
options = 0"*.

**C2-7 — and the tier-1 version.** DECLINE means "PCRE2 compiles it as something
else", and WHAT something else is also option-dependent: `\x{41}` is `A` by
default and NUL-plus-literal-`{41}` under `ALT_BSUX`, same verdict both times. A
differential that compares VERDICTS is blind to it by construction — D26's own
"the assertions project onto a SUBSET OF THE OUTPUT FIELDS", with the blind field
being the emitted matcher. Under `PCRE2_LITERAL` every one of 2005 flipping
patterns compiles, which is the reductio: **"PCRE2 compiles it" is satisfiable
for any byte string by choosing an option, and D29 binds no option set.**

## Both proposed controls are the defect they were meant to cure

**C4-2 — `--explain` never enters a doorway.** It is a mutual-prefix match of the
query against the `syntax` COLUMN, printing other columns of the same row
(`syntax_dump.c:225-274`; no `ext_` or `registry_find` reference exists in the
file). D29's own worked example does not run:

    $ build/pcrec --explain '(?i-m:'
    pcrec: no construct matches '(?i-m:' — it is either base syntax or not a construct pcrec knows

So MOD-0.7 is not "point an existing consumer at new fields", it is "replace a
table self-join with a live invocation of the parser front half" — and once
rewritten it prints `recogniser(query)`, so a test on it asserts only that the
recogniser agrees with itself.

**C4-1 — and the existing assertion style cannot dissent.** C4 demonstrated it:
swapping the module attribution between two rows of `--explain '(?<'` — a tier-2
error — leaves all three of case10's assertions green, because `assert_contains`
tests the whole output blob and the count assertion is satisfied by any four
rows. Repeated on D29's own flagship `\N` case (C4-1b): swap `classes` and
`unicode-props` between the `\N` and `\N{U+0041}` rows, four assertions, four
passes.

D29 argued from wake §6 (seven columns no check reads) that a printing consumer
fixes the problem. But `--list-syntax` already PRINTS all seven of those columns
— they are counted as unread anyway, because the only assertion on that dump is a
FIELD COUNT. **D29 proposes as the cure the thing §6 measured as the disease.**
§7 states the correct test and D29 does not quote it: *"which suite reads this
FIELD of the output?"* — not "is there a reader" but "can the reader dissent".

**C4-3 — probes travelling with the module is co-location applied to a
circularity problem.** They are opposite failures with opposite cures.
`pcre2_check.c:40-50` states the anti-circularity rule D29's scheme has no
analogue for: the candidate POOL comes from libpcre2's own binary, and *"EVERY
name pcrec claims must be produced by source (1) independently, or this fails.
Without that last rule the pool can quietly become pcrec's own table."* A corpus
shipped in the module's own `.c` is by construction the module author's list, so
whatever libpcre2 says about each probe, **the SET is pcrec's**. The repo has
already been shown author-supplied probes are gameable — `wrapper_is_load_bearing`
exists because a critic hid a fabricated row's syntax inside a PCRE2 comment
(R8/C1-F3) and satisfied two guards at once.

Keep the co-located corpus as documentation of a module's measured grammar; do
not let it be the differential's INPUT SET.

## Refuted attacks, recorded so they are not re-run

- **`PCRE2_UTF` flips no construct verdict** (C2). All 1792 UTF flips in the
  generated space are pattern-encoding errors (negative codes); filtering those
  leaves ZERO. This CONFIRMS the wake §6 claim C2 was briefed to falsify.
  Likewise `UCP`, `CASELESS`, `MULTILINE`, `DOTALL`, `UNGREEDY`, `AUTO_CALLOUT`,
  `ALT_VERBNAMES`, `ALT_CIRCUMFLEX`, `MATCH_UNSET_BACKREF`, `NEVER_UCP` and every
  `EXTRA_ASCII_*`: zero verdict flips over 4096 generated probes and all 80 row
  probes. The option-dependence is concentrated in a small nameable set, which is
  what makes an explicit "the mode pcrec compiles for" statement cheap.
- **`(?x)`/`(?xx)`/`(?i)`/`(?J)`/`(?n)` move NO doorway recognition boundary**
  (C3-3), and PCRE2 does not apply extended-mode stripping inside `(?` or `(*`
  sequences (C2, zero EXTENDED flips over 4096 doorway probes).
  **Reconciling C2 and C3, who appear to disagree:** C2's `(?x)(a#)` and
  `(?xx)[ ]` are real, but they are BASE-GRAMMAR lexing changes (comment
  consumption, class content), not doorway recognition. Both are right about
  different things, and the distinction shrinks C2-4 and enlarges C3-1.
- **Name- and group-number-dependent constructs are SEMANTIC, not recognition**
  (C3-4) — with `\12`'s module IDENTITY (C3-1) the exception that is not.
- **A recogniser returning the module would be a second home** — refuted, D29 is
  right and for the right reason (C4/R-5). This is the one place the
  shared-source lens returns a clean result, and C4's constructive suggestion is
  to EXPLOIT the row/recogniser separation rather than merely preserve it.
- **Twelve option rows sharing one recogniser re-creates the Q2 catch-all** —
  refuted (C4/R-4); D29 rejects the byte-SET row for exactly the right reason and
  applies wake §7's lesson unprompted.
- **CLAIM vs DECLINE is ambiguous** — refuted (C1/R1): DECLINE is by definition
  not an answer, so CLAIM+DECLINE is well-defined. The ambiguity is specifically
  CLAIM-vs-REFUSE.
- **Removing `tail` breaks `wrapper_for`** — refuted (C4/R-2): D29 keeps the
  field and changes only its reader.
- **The tail region loses all generated coverage** — refuted for the GROUP
  doorway (C4/R-3): `check_group_tails` (`pcre2_check.c:1772-1845`) survives
  MOD-0.2 untouched. It survives for the ESCAPE doorway, where no sweep exists.

## The best idea the panel produced

**C4-6, constructive:** under recognisers, the strongest single check available
is *a row's own `syntax`, fed to its bucket, must be CLAIMed by exactly that
row's recogniser and by no other.* It is genuinely cross-source — `syntax` is
data, the recogniser is code, written at different times for different reasons —
and it delivers REACHABILITY (C1-2's retired half) and ATTRIBUTION (C4-1's hole)
in one assertion. It is the successor to `registry_check.c:170-176` and it is in
neither D29 nor MOD-0.1.

**C1-4, the constraint on any sweep that replaces it.** Measured: today's four
generated sweeps supply 0-2 bytes after the selector and land on ZERO of the 18
tailed rows. The project's deepest generated suffix space is the option-run
sweep, whose alphabet is HAND-LISTED (`pcre2_check.c:1687`,
`"JUaimnrsxDPSTW-^ZqQ0."`, 21 symbols with `)` and digits 1-9 excluded) — so
D29's own `-\d+)` boundary is unreachable from it, and D29 cites wake §7's
"generate, never list" as the reason to trust it. Uniqueness also has NO external
oracle available even in principle, because libpcre2 has no opinion about pcrec's
buckets.

## Reflection

**A design review found more, and cheaper, than any implementation review this
project has run.** R9's panel found thirteen findings in built code; R10 found
comparable severity in a document, before any of it was written, and every fix is
an edit to a paragraph. The panel was also the first to be pointed at a target
where the author had NO code to hide behind — every claim in D29 was an argument,
and arguments are falsifiable in a way that implementations resist.

**Three of the five critics found the same defect from different directions**, and
that convergence is the result rather than any single finding: D29's three
defences are all LIVENESS arguments — is there a reader, does the loop run, is the
space generated — where every failure this project has recorded is a VALUE or a
SET argument: can the reader dissent, can the loop be disarmed, who wrote the set.
That is a sharper statement of the R4-R9 pattern than D27 reached, and it is worth
carrying forward as the question to ask of any new guard: **not "does this check
run" but "what would have to be true for it to fail, and who chose that input".**

**The author reproduced the exact failure D27 describes, one day after writing
D27.** The `\ddd` warning was in the repository, dated, specific, and addressed to
precisely the decision being made. D27 says knowledge the code does not act on is
invisible to tests derived from the code; R10 adds that it is equally invisible to
DESIGNS derived from reading the code, and that reading `registry.c` for its data
while designing a signature is exactly the reading that skips a comment about
signatures.

**And the measurement lesson repeats in its purest form.** "17 tailed rows,
measured" was measured — by one grep, for a macro name, on a table containing one
row not written through a macro, and that row was the centrepiece of the argument
the number supported. Two critics found it independently, by iterating the table
instead. wake §7 already says GENERATE the input space rather than listing it;
R10's corollary is that **counting a population by the syntax used to write it
counts the syntax, not the population.**

## Dispositions

Nothing was built, so nothing is fixed. The panel's output is a specification for
what D29 must answer before MOD-0.1 begins:

1. **Guard.** "Exactly one may answer" is withdrawn. A bucket's rows must be
   resolvable in a way that is EXPLICIT and CHECKABLE, and reachability must be
   guarded separately from uniqueness — C1-2 and C4-7 are the constraints, and
   C4-6 is the strongest candidate instrument. `check_tail_precedence` is NOT
   retired until its replacement demonstrably catches what it catches.
2. **Verdict.** Relabel the discriminating axis to "did PCRE2 DISPATCH" (D28's,
   restored), treat DECLINE-vs-REFUSE as a second orthogonal axis, and account
   for the occupied fourth cell (C2-6).
3. **Options.** Bind the option set. REFUSE's "no module can ever" is false as
   written; state "the mode pcrec compiles for" as PCREC'S OWN decision rather
   than as a claim about PCRE2 (C2-1).
4. **Identity vs shape.** Answer `registry.c:62-72` explicitly. The digit buckets
   are out of reach of a pure recogniser and must be named as such in the
   decision, not discovered during MOD-0.4 (C3-1).
5. **`\p{...}`.** Replace "property names are length-bounded" with the measured
   algorithm: normalise while scanning, count SIGNIFICANT characters, stop at 49.
   48 belongs in `limits.h`'s PCRE2-internals section (C3-2).
6. **Controls.** Drop `--explain` and module-shipped probes as controls. Both may
   exist; neither may be the check (C4-1, C4-2, C4-3).
7. **Facts.** 18 tailed rows, not 17. Correct the `\N` acceptance-test
   description — the prefix-related pair is `{` vs `{U+`, not bare `\N` vs
   `\N{U+`. Remove the "breaks no interface and changes no test" sentence.
8. **Deferred.** The `-\d+)` collapse does not land until the malformed-body
   cases (`(a)(?-1`, `(a)(?-1x)`) are answered (C1-2).

was prodded per the standing lesson; it then produced 233 lines, and after the
lead had already READ those 233 lines and begun writing this review, it tripled
again to 739 with four more findings — including the one below that corrects
D29's central justification. **This review was drafted, and a commit was
minutes away, on two thirds of one critic's output.** wake §1 step 3 says do not

### C3-7 — "recognition must not depend on the body parsing" is FALSE as written, and D29 contradicts it two paragraphs earlier

D29's founding justification for the port split. The `(?i:(` observation behind
it is correct; the generalisation is not. **PCRE2's recognition depends on the
body in five constructs pcrec already ships**, measured:

| written | verdicts | the recognition question the BODY answers |
|---|---|---|
| `[[.a.]]` err 113 / `[a[.b]` **OK** | REFUSE vs **DECLINE** | does `.]` appear before the class ends? |
| `[[:alpha:]]` OK / `[[:foo:]]` err 130 | CLAIM vs REFUSE | is the body a known name? |
| `(?i-m-s)` err 194 / `(?iZ)` err 111 | CLAIM vs REFUSE | does the option RUN parse? |
| `(*LIMIT_MATCH=4294967289)` OK / `=4294967290` err 160 | CLAIM vs REFUSE | the argument's MAGNITUDE |
| `(*pla:x` err 114 / `(*ACCEPT:x` err 160 | CLAIM vs REFUSE | is the argument terminated? |

and in the base tier `a{1}` is a quantifier while `a{x}` is four literals,
decided by `try_quant` (`parse.c:372`).

**D29 contradicts itself two paragraphs earlier**: it nominates
`pcrec_ext_class_bracket` as the shipped implementation of the three answers,
and that function's entire body is K4's three-rule forward scan over the
construct's BODY, whose `return`s ARE the DECLINE. **The model implementation of
recognition is a body scan, in the decision that forbids recognition from
depending on the body.**

**The correct, narrower sentence — and it survives every probe C3 ran:**

> recognition must not depend on parsing a NESTED PATTERN — it must never reach
> back into `p_alt`.

Because there is no `(?...)` construct PCRE2 DECLINEs at all (every `(?` either
CLAIMs or REFUSEs), so no nested-pattern parse can change a `(?` verdict; and
the one doorway that CAN decline decides by an opaque byte scan, which is D29's
own type-1 body and needs no recursion. Recognisers scanning opaque bodies is
not merely permitted — **it is mandatory, and three shipped rows already do it.**

D27's lesson applies directly: a spec-first writer reading D29's sentence would
write tests asserting `[a[.b]` is CLAIMed.

### C3-6 — `p_alt` is not a usable callback as the code stands

D29 names the callback precisely ("the semantic port recurses into `p_alt`,
`parse.c:500`") and the code does not support it:

- **The group node is ERASED.** `p_atom`'s group case returns the body with no
  wrapper (`parse.c:275`), so `(a|b)|c` and `a|b|c` build the identical AST —
  verified end to end, the generated C is byte-identical apart from the pattern
  comment. PCRE2 needs exactly that distinction for a construct D29 lists as
  type-2: `(a)(?(1)(a|b)|c)` and `(a)(?(1)a|(b|c))` compile while
  `(a)(?(1)a|b|c)` is error 127, "conditional subpattern contains more than two
  branches". **A `conditionals` port calling `p_alt` back cannot recover the
  top-level branch count**, so it cannot produce error 127.
- **The depth DECREMENT is on a path a module never reaches.** `cx->depth--` sits
  at `parse.c:266`, after the doorway call at `:259`. D29's "one depth counter,
  not two" is right as a rule and unimplementable against today's control flow.

So MOD-0 includes a parse.c change, which D29 does not price — and D29's own
"parse.c call sites changed: 0" lineage (SR-9's design note) no longer holds.

### C3-5 — `(?[...])` is a type-3 body that NESTS, with a PCRE2 depth cap of 13, inside a function specified to have no failure path

D29 assigns `(?[...])` set algebra to "owned end to end" by a pure recogniser.
It nests, and PCRE2 caps the nesting at 13. So a "pure, no failure path"
recogniser has to carry its own bounded stack and its own depth rejection —
which is a second depth budget, in the layer D29 just finished saying must have
exactly one.

### C3-10 — the bare-fallback problem is FOUR buckets, not one

Confirming and widening C1-3 from the other lens. The hazard is not
prefix-related tails; it is **a tail-less row sharing a bucket with tailed
rows**, because `tail_default(NULL)` claims everything in its bucket. Four such
buckets exist (`\N`, `(?-`, `(?<`, `(?P`), so D29's "`\N` is the case that
cannot use it... and nowhere else" understates the migration by a factor of
four.

### Refuted, and closed harder than asked

- **C3-3b:** `(?x)` set MID-PATTERN and SCOPED still moves no recognition
  boundary. C3's first sweep set the option as a leading prefix; the sharper
  question was re-run with it set in every position that leaves it in force —
  `a(?x)`, `a(?xx)`, `a(?x)b#c\n`, `z((?x)y)`. No boundary moves. This is the
  strongest form of the refutation and it is what makes C2-4's leftward
  dependence narrow and nameable rather than pervasive.
- **C3-8:** `\Q...\E` does not break the class delimiter scan.
- **C3-9:** D29's proposed collapse of `pcrec_ext_class_pair_opens` HOLDS, and
  the shipped scans agree with libpcre2. This is the one D29 opportunity the
  panel confirmed rather than withdrew.

### Dispositions, amended

9. **Fix the founding sentence** to "recognition must not depend on parsing a
   NESTED PATTERN". As written it forbids the delimiter-pair scan, the option-run
   scan and the verb-argument scan that pcrec already ships (C3-7).
10. **MOD-0 includes a parse.c change** — a group node that survives, and a depth
    discipline a module can participate in. Conditionals cannot be a type-2 body
    until the branch count survives `p_alt` (C3-6).
11. **`(?[...])` needs its own bounded nesting budget** inside a recogniser with
    no failure path, or it is not type-3 (C3-5).
12. **Four bare-fallback buckets**, not one, and D29's migration estimate is
    understated accordingly (C3-10, C1-3).

## ADDENDUM 2 — and C1 and C2 had also grown after being read

The process finding above repeated twice more. At the point Addendum 1 was
written, C1 had grown 645 -> 758 and C2 393 -> 680 since each was read. **Three
of five critics delivered material after the lead had read their files and begun
compiling.** Re-polling every file after the last prod is now part of the
procedure, not a courtesy: see the amended rule at the end of this review.

That late material contains the panel's only LIVE PRODUCT DEFECT and its
strongest single design finding.

### C1-7 — a LIVE tier-2 defect, in the row MOD-0's acceptance test is built on

**Recorded as K10** (docs/known_issues.md), verified independently by the lead
before recording. `\N{U+hhhh}` inside a character class is refused as
permanently-invalid; libpcre2 gives error 193 in every class position including
as a range endpoint, which is recognition-then-mode-refusal, not rejection. The
`{U+` row carries `RF_CLASS_INVALID` while **its own `note` says error 193 is
"recognition, not rejection"** — the row contradicts itself, and R9's
SPEC-classes-F1 fix landed the flag on an eleventh row when it named ten.

Four nets miss it, and the fourth is the interesting one:
`registry_check.c:875-876` EXEMPTS `RF_CLASS_INVALID` rows from the in-class
sweep, so **the flag exempts the row from the one check that would contradict
it** — a control taking its scope from the field it controls, which is this
project's signature defect appearing in a new place.

This is the third independent thing wrong with the row D29 nominates as the
acceptance test (C1-1: not one of the two rows D29 names; C1-5: not in D29's
count of 17; C1-7: its class flag is wrong). Writing that test "first" against
this bucket without measuring the bucket is how all three survive into MOD-0.

### C2-8 — the `(*` doorway ALREADY has four answers, adopted and pinned, and three of them are not D29's

The strongest design finding in the panel, and it needs no compile options.
**D25 is titled** *"the `(*` doorway gets NAME tables, and a 'not a known name'
outcome DISTINCT FROM 'requires a module'"* and its decision sentence specifies
**four** outcomes. `(*MARK)` is the contradiction: PCRE2 recognises `MARK` — that
is why the message is "(*MARK) must have an argument" rather than "not
recognized" — so under D29's CLAIM row (*"recognises the construct, body valid or
not | name the module"*) pcrec owes "requires module 'verbs'". It deliberately
does not, and that behaviour is pinned in three independent places
(`tests/reject/run_reject_tests.sh:562`, `pcre2_check.c:413`,
`registry.c:563`).

**One enum cannot carry "CLAIM the construct but do NOT name a module", and that
cell is occupied by shipped, tested code.**

Why it was missed is the sharpest methodological point the panel makes: D29
derives its three answers from ONE doorway — *"`pcrec_ext_class_bracket` already
implements exactly three"* — a sample of size one. D29 cites D27 three sections
later and applies it to the recogniser SIGNATURE (*"shape it against at least
`unicode-props` and the EXISTING `verbs` scan, not against `modifiers` alone"*)
and then does not apply it to the VERDICT ENUM. **The same document states the
rule and breaks it, two pages apart.** It lands on MOD-0.4, the step the plan
calls the migration test.

### C2-11 — a SCHEDULED window where `modifiers` exists and `classes` has not been told

At options = 0: `[a- ]` is error 108, range out of order; `(?xx)[a- ]` COMPILES,
because `xx` deletes the space. The range endpoint is exactly what the previous
commit (`3fca0d8`, SPEC-FA) fixed. MOD-0.3 (`modifiers`) is scheduled BEFORE
MOD-0.5 (`classes`), and **pcrec is safe today only because it rejects `(?x)`
outright — the guard is the unimplemented-ness, and MOD-0.3 removes it.** That
is a sequencing hazard the plan created and did not notice.

### C2-9, C2-10, C2-12 — how far REFUSE's "ever" has to be quantified

- `(*CR)` compiles and `a(*CR)` is error 160, so `verbs` WILL make `(*CR)` valid
  — just not there. REFUSE must range over (construct, POSITION, context flags,
  option set, PCRE2 VERSION) and D29 names none of them.
- Under `PCRE2_EXTRA_BAD_ESCAPE_IS_LITERAL` alone, **1896 of 8960 generated
  patterns move from error to COMPILES** — `\o@`, `\k@`, `\g@`, `\p{@}`, `\c@`,
  `\N{@}`. The `\` doorway holds ~60 of pcrec's 100 rows. Recorded to establish
  the SIZE of what binding the mode binds: not a corner, most of a doorway.
- Constructs have changed answer across PCRE2 versions, which is D29's
  interaction with D26's upgrade rule and is unaddressed.

### C1-3 addendum — 3 of 4 buckets collide, and the exempt one indicts the others

| bucket | input | answers | collides |
|---|---|---|---|
| `\N`  | `\N{U+0041}` | CLAIM(classes) + REFUSE + CLAIM(unicode-props) | **yes, three** |
| `(?<` | `(?<=a)`     | CLAIM(named-groups) + CLAIM(lookaround) | **yes** |
| `(?P` | `(?P<n>a)`   | REFUSE + CLAIM(named-groups) | **yes** |
| `(?-` | `(a)(?-1)`   | DECLINE + CLAIM(recursion) | no |

**D29's rule holds exactly in the bucket where the fallback is not a fallback** —
`(?-`'s bare row already has a real recogniser, the one Q2 wrote. And `(?<` is
the plainest case, unmentioned in D29: two rows, two DIFFERENT modules, both
CLAIM, on a pattern pcrec answers correctly today. Two CLAIMing rows in one
bucket is two module attributions for one construct — the exact thing D29's own
"the ROW names the module" paragraph forbids, arriving not from a recogniser
returning a module but from the guard having no way to order them.

### Dispositions, amended again

13. **The verdict is not a three-valued enum.** The `(*` doorway ships four
    answers and D25 adopted them deliberately. Model the answer as
    (dispatched?, compiles?, whose message?) per C2-3/C2-8, or add the fourth
    cell explicitly — "CLAIM the construct, name no module" (C2-8).
14. **REFUSE must state its quantifier**: over construct, position, context,
    option set and PCRE2 version (C2-9, C2-10, C2-12).
15. **Reorder MOD-0.3 after MOD-0.5, or gate it** — implementing `modifiers`
    before `classes` opens a window where `(?xx)` deletes bytes at the class
    range endpoint SPEC-FA just fixed, and today's only guard is that `(?x)` is
    unimplemented (C2-11).
16. **K10 is live and scheduled with MOD-0.6.** Fix the flag only together with
    the in-class tail sweep, or the same four nets stay blind.
