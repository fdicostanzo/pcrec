# R7 — FIX-1: K5 and K6, the two brace miscompiles

Checkpoint review (D6) of commit `8a2ff36`, the first of the four steps in
docs/plan.md's AGREED ORDER. Four critics, four lenses, each pinned to `8a2ff36`
with `git archive` and required to append findings to a scratchpad file as they
confirmed them.

Baseline before the work, all five green in place and from a fresh clone:
805 corpus / 73 CLI / 211 reject / 127 registry + 2 SR-4 doc checks / 29 codegen
/ 7 trie-identity, verify_rxt 796/796, fuzz seed 1 zero divergences, bench zero
budget failures.

**The one-line summary: the panel found a third miscompile of the same class, in
the same function, one space away from the two the commit had just fixed** — and
it was invisible to the instrument that certified them.

---

## What was built

Two base-tier miscompiles — the one class the charter rules out — both in
`src/parse/parse.c`.

**K5, a count above 65535.** `try_quant` DECLINED on overflow, and declining is
what made the `{` literal, so `a{65536}` compiled a matcher for the eight
literal characters. It now REMEMBERS the overflow and raises PCRE2's error 105
only at the points where it would have returned true.

**K6, a well-formed `{m,n}` with nothing to quantify.** `try_quant` is only
reached from `p_rep`, i.e. AFTER an atom, so a `{` in atom position was never
asked whether it is a quantifier. `p_atom` gained a `case '{'` beside the
existing `* + ?` case: rewind, ask, raise error 109 on a yes.

**The shape both fixes share is the point.** Each is two-phase, and each would
over-reach without the second phase. The forms that must stay literal are
exactly the forms `try_quant` declines, so the over-reach guard is structural
rather than a second list that can drift.

Three orderings were measured against libpcre2 10.46 rather than assumed, and a
plausible implementation gets each one wrong: too-big beats out-of-order
(`a{65536,1}` is 105, not 104 — and the clamped accumulator makes that pair look
out-of-order internally); in atom position `{65536}` is 105 and `{3,1}` is 104,
neither is 109; and the reported offset is where the offending NUMBER's digits
ran out.

49 forms were differentially probed before the panel; all agreed.

## Findings

Labelled CONFIRMED (reproduced, with the repro) or SUSPECTED, and triaged
FIX-NOW | PLAN | DOC | REJECTED | NOTED. Everything marked FIX-NOW was fixed in
this checkpoint and is covered by a test and a sabotage.

### The headline — a third miscompile the fix's own instrument could not see

**C1-F1/F2/F3, C3-F1 (CONFIRMED, two critics independently) — FIX-NOW, fixed as
K8.** PCRE2 10.46, following Perl 5.34, tolerates SPACE and TAB inside a repeat
quantifier. `try_quant` declined on the first non-digit, so every such form was
silently demoted to literal text:

    a{ 1}  a{1 }  a{ 1 }  a{1, 2}  a{1 ,2}  a{<TAB>1}
        -> PCRE2: a quantifier, matches ONE 'a'
        -> pcrec: five or more literal characters

plus 90 outright verdict disagreements in atom position (`{ 1}` is PCRE2 error
109; pcrec accepted it), and K5 itself bypassed by one space — `a{ 65536}` was
error 105 in PCRE2 and accepted by pcrec.

**Why the session's own probes missed it, which is the transferable part.** In
QUANTIFIER position both engines exit 0. A verdict-only comparison — which is
what all 49 probes were — sees nothing; only the compiled language differs. The
critic found it by GENERATING the brace space combinatorially (364 bodies per
context, 15 contexts) instead of listing the forms it could think of. Listing
finds what you already suspect.

The rule was then measured gap by gap rather than guessed, and both halves
matter: space and tab only (0x0a/0x0b/0x0c/0x0d/0xa0 all leave the brace
literal), in all four gaps, never inside a number (`a{1 2}` is literal, not
`a{12}`) and never in place of one (`a{ }`, `a{ , }` stay literal). Full record
in docs/known_issues.md K8 and docs/upstream_issues.md U6.

### Claims of mine that were false

**C4-F1 (CONFIRMED) — FIX-NOW, fixed.** I wrote python's repeat ceiling as
4294967296 in four files. Measured, it is **4294967294** (2^32 − 2):
`a{4294967294}` compiles, `a{4294967295}` does not. I had inferred the round
number from python's own error message and never checked it — in four files,
which is the exact habit this project keeps catching.

**C2-T-4 / C1-F7 (CONFIRMED, two critics) — FIX-NOW, fixed by changing the
code.** The commit claimed "verdicts AND offsets now agree with libpcre2
throughout". False for one of the twenty rows: `{3,1}` was offset 0 where PCRE2
says 4, because out-of-order reported the `{`. That behaviour predates FIX-1;
the claim did not. Rather than carry a documented wart plus a comment
apologising for it, the offset was aligned — one token, all three brace
diagnostics now agree with PCRE2, pinned by name. Secondary and NOT changed:
pcrec says "number too big in {m,n} quantifier" where PCRE2 says "in {}
quantifier". The commit said these rows "carry PCRE2's own wording"; they carry
pcrec's, and 104/109 happen to match verbatim.

**C4-F2 (CONFIRMED) — FIX-NOW, fixed.** The `# pcre2-only`/`perr` invariant the
commit declares FALSE was corrected in two files and left standing, unflagged
and in the present tense, in a THIRD: `docs/pcre2_compliance.md`'s "How this
survey earned its keep". Correcting a claim in the places you happen to be
editing is not correcting it.

**C4-F3 (CONFIRMED) — FIX-NOW, fixed.** `tests/reject/CLAUDE.md`'s own Files

`tests/CLAUDE.md`. Two files, one fact, one updated.

**C1-F6 (CONFIRMED) — FIX-NOW, fixed.** `docs/pcre2_compliance.md`'s Braced
Items row scoped whitespace-in-braces to `\g{2}` and dismissed it as "reached
only via constructs that are themselves rejected". The repeat quantifier is
base-tier and very much reached — the dismissal was wrong for exactly the case
that mattered, and had it been right K8 would not exist.

### Held, and worth the space

**C1-F8 (CONFIRMED verdict disagreement) — NOTED, not a defect.** `(^){10000}`
and up: PCRE2 answers error 120 "regular expression is too large", pcrec
accepts. The anchor-group wrapper makes `(^)` repeat to nothing, so pcrec's
state guard never sees a size. Both engines have a limit in different places;
err 120 is PCRE2's own ceiling, which `tests/fuzz/` already excludes as
not-a-divergence, and `(a|b){65535}` and `($){65535}` reject cleanly in both.
It does mean "pcrec and libpcre2 agree on brace syntax" needs the qualifier.

**C1-F9 (CONFIRMED) — DOC, K7 sharpened.** K7's threshold is ~20k–25k, not
65535, and `a{0,20000}` already costs 4.7 GB to ACCEPT. The `>32000 states`
guard is UNREACHABLE for this shape — which is the sharper statement of the bug:
not "large repeats crash" but "the cap that exists to prevent this cannot be
reached by the shape that needs it". No crash of a different shape was found.

**C3-F2 (CONFIRMED, minor) — DOC, recorded in the code.** The cost model "one
more try_quant call" undercounts: the old digit loop also bailed after six
digits, so bytes scanned rose up to 286x on 999-digit runs while calls rose
exactly 2.00x. Still linear, and provably rather than observably: digit runs
are disjoint across `{` positions and each `{` is examined at most twice, so
total bytes are bounded by `2 * patlen` — a bound the measurement now saturates
where it used to use 0.7% of it.

## Reflection

**The instrument that certifies a fix is the thing to attack.** K5 and K6 were
measured against 49 hand-picked forms and both fixes are right. K8 sat one space
away from every one of those forms and survived, because the probes compared
VERDICTS and the bug lives where both engines say yes. A generated sweep found
it in minutes. "I probed it thoroughly" and "I probed it along the axis the bug
uses" are different claims, and only the second is worth anything.

**Three of the panel's findings were the same finding.** T-0, T-1 and T-2 all
reduce to: the code keeps state whose only purpose is an offset, and no test
reads an offset. The general form — *what does this code compute that nothing
observes?* — would have found all three from the diff alone, and it is a cheaper
question than any sabotage. It belongs next to R5's "which of my new branches is
invisible?".

**A count cannot defend itself, and now it does not have to.** R6 recorded that
exact counts disarm themselves; R7 measured the disarm on the single row the
commit called irreplaceable, in a two-line diff, following the failure message's
own instructions. The manifest is the first mechanism here that names what must
exist rather than how much of it there is. Its first version was vacuous through
substring matching — which is the same lesson one level down, and is why it is
written up in the file rather than quietly fixed.

**My own sabotage harness lied to me, in the way the journal keeps recording.**
The `isspace()` sabotage came back 0/0 and I nearly wrote "the guard holds": the
patch had applied its `#include` and not its substitution, and my vacuity check —
"did the file change?" — passed on the include alone. A harness that reports
success when it has not run is now four sessions old as a theme. The fix was to
assert an exact occurrence count per replacement before building, and it
immediately turned the same sabotage from 0 into a real result: the corpus guard
I had just written for it was itself vacuous, because a `.rxt` pattern line
cannot carry a raw control byte.

**Over-reach guards need to be as symmetric as the code.** T-5 is the cleanest
example: three accept-controls, all exercising the same half of a two-sided
rule, and the other half was a one-line mistake away from rejecting patterns
PCRE2 compiles, silently. The question to ask of any guard is not "does it cover
the bug" but "does it cover the bug's mirror image".

**On correcting a claim in only the files you happened to open.** The
`# pcre2-only` invariant was corrected in two files in the same commit that left
it standing, present-tense, in a third. `grep` the claim, not the directory.
