# R5 — adversarial review of SR-2, SR-3 and SR-4 (2026-08-10)

Three critics, three lenses, run against commit `c596710` (SR-2) with SR-3 and
SR-4 landing while they worked. Each was briefed to **attack the defence, not
the artifact** — the instruction that paid off best at R4 — and to write
findings to a scratchpad file incrementally. All three did; all three delivered.

The lenses: **behaviour preservation** (is SR-2 really a pure restructure?),
**spec-to-code gap** (does pcrec agree with libpcre2 10.46?), and **attack the
test suite** (which branches can no test see?).

## Headline

SR-2's byte-identity claim HELD under a stronger instrument than the one that
made it. Everything else found was pre-existing, and there was a lot of it:
**four confirmed bugs, two of them miscompiles**, plus one false claim in my own
comments and one silent hole in my own harness.

That distribution is itself the finding, and it is the same one the project
recorded five checkpoints ago: the compiler is not where the bugs are. Every
defect below came from reading PCRE2's behaviour against ours, or from asking
which branch no test can see. None came from the corpus.

## Findings

### Confirmed bugs (all pre-existing; recorded as K3–K6)

| id | what | direction |
|---|---|---|
| K3 (extended) | the `:` row lacks both halves of `RF_CLASS_DELIM`: pcrec over-ACCEPTS `[:alpha:]` and over-REJECTS `[a[:b]` | both |
| K4 | the delimiter-pair terminator scan runs to the end of the PATTERN, not the class — `[.a]x.]` rejected, PCRE2 accepts | over-rejection |
| K5 | `a{65536}` silently becomes literal text; PCRE2 errors 105. **Compiles a matcher for a different language** | MISCOMPILE |
| K6 | `{1}` with nothing to quantify silently becomes literal text; PCRE2 errors 109. pcrec gets `*a`/`+a`/`?a` right and only `{` wrong | MISCOMPILE |

K3's over-rejection half and K4 were found INDEPENDENTLY by two critics, which is
the strongest signal in this review. K5 and K6 violate the project charter
directly ("never miscompile") and are the two to fix first.

### F-3 — a false claim in my own comments, in three places

SR-2's `noreturn` attributes were documented as a forcing function: "gcc will
reject the attribute at that moment", "a lie that fails the build is better than
a comment nobody reads". The critic wrote SR-6's shape and watched `make`
succeed. `WARN` is `-Wall -Wextra` with no `-Werror`, and this particular
warning has **no controlling `-W` option**, so only a blanket `-Werror` would
promote it — verified: `-Werror=invalid-noreturn` does not exist in gcc 15.2.

Fixed by rewording all three places to what is true. Whether to adopt `-Werror`
and make the original claim real is **R5-Q1**, an open question for Frank: it is
a project-wide policy change, not a local one.

The lesson is not "check your flags". It is that **a comment asserting a guard
that does not exist is worse than no comment** — it stops the next reader from
looking.

### F-5 — a silent hole in my own byte-identity harness

`emit_identity.sh`'s doorway sweep built each byte with `b="$(printf ...)"`, and
command substitution strips trailing newlines — so for byte 0x0A the variable
was the EMPTY STRING. Eight cases across eight contexts silently tested a
different, shorter pattern and reported as passes: `B/esc/10` probed `\`
(trailing-backslash error) instead of `\<LF>`. 0x0A is the single byte most
likely to behave specially in a regex parser.

Closed rather than merely noted: 240 further cases — 0x0A, 0x0D, TAB, VT, FF and
space across ten doorway contexts and four flag modes — compared byte-exactly
through python (no shell stripping) between the pre-SR-2 and post-SR-4 builds.
Zero differences. `registry_check.c`'s own sweep never had the hole; it builds
patterns with `snprintf("%c")` in C.

### F-6 — SR-4's iteration is circular, measured, and the hand-written rows are what save it

Confirming the design argument SR-4 was landed on, with numbers:

| sabotage | reject | registry |
|---|---|---|
| `\R`'s row `misc` → `classes` | **FAIL (2)** — the hand-written row | FAIL |
| `(?0)`'s row `recursion` → `misc` | ok — **blind** | FAIL |
| delete the `(?0)` row | ok — **blind** | FAIL |

`\R` is caught only because a human typed the module name into the file.

**And what caught rows 2 and 3 is a drift detector, not a control.**
`compliance_section.py --check` fails, but its own remedy is `--write`, which
regenerates the doc from the sabotaged table and turns the suite green. It
catches "changed the table and forgot the doc"; it cannot catch "changed the
table on purpose and regenerated". That distinction is now written into
tests/registry/CLAUDE.md so nobody reads it as a guarantee it does not give.

Fixed here: the nine numeric recursion rows now have hand-written entries.

### The `at_class_open` finding was framed wrong, and the critic corrected me

SR-2's commit message says deleting that guard "changes 0 of 4173 cases and
breaks no test", and calls it "that invisible branch". The second half is true
of the repo's tests. The first half is a property of MY HARNESS, not of the
guard, and saying otherwise credits the sabotage battery with a limitation it
did not have.

Five one-line patterns expose it — `[:]`, `[:a]`, `[::]`, `[:a:]`, `[:-:]` —
i.e. any class whose FIRST member is `:`. The critic then verified why nothing
saw them, rather than guessing: no corpus pattern opens a class with `:`, the
reject suite's only `[:` row is `[[:alpha:]]`, and `registry_check.c`'s sweep
template is `"[[%ca%c]]"`. **Every existing probe of this doorway in the entire
repo puts a literal `[` between the class bracket and the delimiter byte, so all
of them test doorway 4b and none tests 4a.** `at_class_open` is precisely the
argument distinguishing them.

Closed here: `accept '[:]'` and `accept '[:a]'` in tests/reject/ — both accepted
by libpcre2 10.46 as well, deliberately NOT `[::]` or `[:a:]`, which PCRE2
rejects and pcrec wrongly accepts (K3); pinning those would cement the bug.
Re-measured: the sabotage that was undetected now fails 2 checks.

The 4a SWEEP the critic also suggested cannot be added until K3 is fixed — it
would fail today, correctly, on the `:` row.

### The pure-restructure claim survived 137,378 further independent cases

The behaviour critic did not stop at closing my harness's gaps. Beyond the 8790
cases covering those, it ran **97,818 EXHAUSTIVE short-string cases** — every
string of length ≤3 over a 30-byte metacharacter alphabet and every string of
length 4 over a 16-byte one, so no human decided what to try — and **30,770
structural cases**: the 250-paren cap straddled at 245..255 with a doorway
inside the nest, offsets to 20000, a delimiter pair whose closer sits 20000
bytes from its opener (the one place SR-2's moved scan could have changed its
bound), real multi-byte selectors, 20 real verb NAMES (the first name-level
probe of a doorway every existing sweep tests byte-wise), real `.c` and `.h`
files compared on disk, patterns containing raw newlines and high bytes, and
30000 seeded fuzz patterns.

Zero differences, on stdout, stderr, exit status, `.c` and `.h`. Its verdict:
"I could not break it."

### Two latent traps in SR-2's own shape

**FINDING 3 (fixed here).** `pcrec_ext_class_bracket` returned `bool`, no path
could produce `true`, and both callers discarded it. A return type that cannot
take its second value is a worse lie than the `noreturn`s are honest about:
when SR-6 gives a class-bracket row a handler returning "consumed, carry on",
both callers would ignore it and fall through to member parsing with nothing in
the build objecting — and this is the doorway with the weakest coverage. Changed
to `void`, so SR-6 adding a value forces both call sites to be looked at.

**FINDING 2 (no action).** `pcrec_ext_escape` tests `RD_FIXED` before
`in_class`, an ordering with no pre-SR-2 counterpart, so a hypothetical
`FIXED(RK_ESC, ...)` row would lose the in-class/atom distinction old parse.c
could not lose. Dead today. The critic checked whether the project would notice
instead of assuming it would not: `check_table_to_parser` fails immediately on
such a row. Guarded; recorded for completeness.

### Branches no test could see

The sabotage matrix over `ext.c` found five. Two were real coverage gaps and are
now closed by hand-written reject rows: **the in-class "unknown escape" message**
(`[\q]` — deleting it changed nothing anywhere in the suite) and **the
end-of-pattern selector** (`(?` and `(*`, where `c2 == -1` collides with
`REG_SEL_ANY`). Three were defensive branches whose input cannot occur — the
`BAD_ROW` guards and the `if (!r)` NULL guards. Rather than delete the defence
or leave it untested, the INVARIANT it guards is now asserted in
`registry_check.c`: which diagnostic shapes each doorway can render, and which
doorways must have a catch-all row (`(?`, `(*`) versus must NOT (`\`, `[`,
which have to be able to decline). Both sabotage-validated.

### N-1 — a negative finding worth keeping

The critic predicted SR-2 had made a documented sabotage result stale: rewording
the collating message used to fail 2 registry checks when parse.c held the
literal, and after SR-2 both sides read it from the row. It measured anyway, and
was wrong — the two hand-written `expect_msg` calls at the end of
`check_table_to_parser` still catch it. Those two are now **the only
non-circular assertion about message TEXT left in `registry_check.c`**. If
someone later tidies them into the derived loop, `registry` loses the ability to
see any message change at all. Recorded so that tidy-up does not look like one.

### F-7 — the headline: `make test` could not tell K3-FIXED from K3-unfixed

The tests critic ran 38 sabotages against a pinned `git archive c596710`
snapshot through all seven suites. **20 were invisible to the entire suite.**
Nine of those are unreachable internal-error branches (F-10, arguably fine).
The other eleven are not, and two are serious:

- **F-7a `cb_delim_always`** — replacing `if (r->flags & RF_CLASS_DELIM)` with
  `if (1)`. All seven suites green. That one-token edit **fixes K3 and its
  over-rejection half**, moving pcrec strictly closer to PCRE2 on both. So the
  suite could not distinguish K3-fixed from K3-unfixed **in either direction**:
  whoever lands the fix would get no confirmation, and a later refactor undoing
  it would raise no alarm. Nothing anywhere asserted that the `:` row does *not*
  carry the flag either — the column was unguarded both ways.
- **F-7b `cb_closed_loose`** — dropping the `&& pat[i+1] == ']'` half of the
  terminator test. Invisible. Every collating accept-control either has no
  second delimiter or has a real `.]`.

Three independent defects in one ten-line function — an unbounded scan (K4), an
untested terminator half, and an untested flag test — all invisible.

**Closed here** with a new `KNOWN-WRONG, pinned` block in tests/reject/ that
asserts what pcrec does TODAY for four measured disagreements with libpcre2
(`[:alpha:]`, `[a[:b]`, `[[:alpha]`, `[.a]x.]`), labelled as bugs, with
instructions to move the lines into the real tables when K3/K4 are fixed. Plus
`accept '[.a.b]'`. Re-measured: `cb_delim_always` now fails 4 checks,
`cb_closed_loose` 1.

This is the answer to F-4's problem. `tests/known_fail/` structurally cannot
hold any of these — a `.rxt` `perr` block needs the PYTHON oracle to fail too,
and python accepts all four — so the pin lives where the oracle is libpcre2 and
the assertions are hand-written.

### F-8 / F-9 — floors with slack, and what the slack buys

`tests/reject/` guarded `nrej >= 90` against 93 actual. Delete three checks,
then change `\R`'s row from `misc` to `classes`: pcrec now tells the caller to
enable the **wrong module** — the single fact the diagnostic exists to carry —
and all seven suites stay green. The registry check cannot object because since
SR-2 both sides read the same row, and the feature/module bijection stays a
consistent pair.

`registry_check.c` guarded `total < 60` against 67 rows. Deleting
`GROUP('3')`..`GROUP('9')` in one edit was invisible: seven documented
constructs stopped being described, and because the lookup then falls back to
the `(?i)` catch-all, the parser routed `(?3)` to 'modifiers' and the table
agreed, in unison, that this was correct.

**A floor guards a COUNT; the thing worth guarding is a SET.** Both are now
EXACT counts with a "if this was deliberate, bump the number in the same commit"
message. The exactness caught my own wrong guess immediately (I wrote 108, the
actual count was 106).

### F-10 — nine unreachable branches, and a fair charge of inconsistency

Deleting any of nine internal-error branches in `ext.c` changes nothing. That is
defensible for internal-error guards — but D24 deferred the `handler` field in
the *same commit* on exactly the grounds that it "would be dead code no test can
reach". The asymmetry is real and worth naming rather than explaining away.

Two of the nine were not internal-error guards. `if (c2 < 0) return` in
`pcrec_ext_class_bracket` was **redundant, not defensive** — the `if (!r)` on
the next line already handles it — and is now deleted. And `if (!r)` in
`pcrec_ext_escape` is the one LIVE null guard: deleting it segfaults, caught
only by `tests/registry`'s sweep via SIGSEGV, because tests/reject had no
unknown-escape case at all until R5 added one.

### F-11 / F-12 — sweeps have exactly one byte of lookahead

`shown = c2 < 0 ? '?' : c2` deleted → `printf("%c", -1)` renders byte 0xFF into
a user-facing diagnostic. Invisible at c596710: the corpus *does* contain
`pattern (?`, but a `perr` block asserts only THAT it fails, never what it says.
Already closed by R5's `reject '(?'` row.

F-12 corrected a caveat I had inherited and repeated. tests/registry/CLAUDE.md
said the `(*` doorway is weaker than its three neighbours. Measured, that is
wrong in both directions: the `(*` sweep DOES vary the first name byte and
catches a branch on it, while **both** `(*` and `(?` are blind to any branch
keyed past the first byte — `(?P=` vs `(?P<` was invisible. The honest scope is
"one byte of lookahead is all any sweep in this repo has", which is now what the
file says.

### F-4 — the known-fail ratchet cannot hold any of this

`tests/known_fail/` is empty and structurally cannot hold K3–K6: the `.rxt`
`perr` form requires the PYTHON oracle to also fail, and python `re` accepts
every one of these patterns. **All five bugs of this shape the project has ever
found** — `\v`, collating elements, K3, K4, and now K5/K6 — are un-ratchetable
in the mechanism built to ratchet deferred bugs. The gap is the oracle, not the
runner: a known-fail tier keyed on *pcrec's verdict versus libpcre2's* would
hold all of them. Folded into PC-3.

## Reflection

**The most productive question of the session was not on any checklist.** It was
"which of the branches I just added can no test see?" — asked because a sabotage
returned zero. The answer was one branch, and behind it sat K3. Every other bug
in this review was found by pointing the same question at something else.

**An identity proof cannot see a bug that both sides share.** SR-2's 4173-case
proof was correct and worth having, and it reported "no change" for K4 because
K4 was faithfully carried across. The proof answers "did I change anything",
never "was it right to begin with". Those need different instruments, and this
session needed both.

**Two of my three self-inflicted errors were in the tooling, not the code** —
the multi-line `grep -F` guard, the empty-replacement guard that passed
vacuously, the `$(...)` newline strip. All three had the same signature: a check
that reports success when it has not run. MECH-1/MECH-2 have been in the plan
for two sessions precisely for this, and I hand-rolled the machinery again
instead of building them. That is now the highest-value process item by some
distance.

**Briefing critics to attack the defence worked a second time**, and better than
at R4: the tests critic pinned its baseline to a commit on request, disclosed
which rows predated that pin, and produced a negative finding it had predicted
would be positive. The habit to keep is requiring incremental writes and asking
for the sabotage EDIT rather than the count.
