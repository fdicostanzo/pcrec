# R9 — FIX-2: the panel that ran late, and what the instrument was actually probing

Checkpoint review (D6) of `29a0517`, the third step in docs/plan.md's AGREED
ORDER. **This panel is the one process step FIX-2 shipped without.** The change
was committed, green and fully documented on 2026-08-10 and the session was
reset before its critics ran; they ran in the next session, against the
committed tree rather than a working one.

Four critics, four lenses, each in its own clone of `29a0517`, each required to
append findings to a scratchpad file as it confirmed them. Two ran on a smaller
model (the record/harness and name-table lenses); two on the larger one.

Baseline before the panel, verified green in place: 876 corpus / 83 CLI / 328
reject checks / 129 registry / 81 PC-3 / 29 codegen / 7 trie-identity, `make
strict` clean, verify_rxt 844/844, fuzz seed 1 zero divergences.

**The one-line summary: the fix was right and the instrument was not.** Every
critic that attacked the RULE found it correct — one of them over 1.24 million
generated patterns, another over 2.4 billion name probes. Every critic that
attacked the CHECKS found something, including undefined behaviour inside the
differential FIX-2 added, in the one shape written to exercise the one rule that
a verdict differential cannot see.

## The baseline check that was not one

Before any finding: the first baseline run in this session reported `exit 0`
from `make && make test 2>&1 | tail -30`. That exit code is `tail`'s. `make
test`'s real status was never read, and the 30 lines that survived showed only
the last two suites.

It was re-run capturing the status properly and was genuinely green — but the
project's own recurring defect is *an assertion that projects onto a subset of
the output*, and the very first command of a panel convened to look for it did
exactly that. Recorded here because it cost nothing this time and is the
cheapest possible instance to learn from.

## C1 — the instrument

**C1-F1 — the nested-opener shape generated no nested openers, and the way it
failed was undefined behaviour.** CONFIRMED, fixed.

`CLS_SHAPES[9] = "[[%ca[%cb%c]%c]]"` is the only shape in
`check_class_brackets` written to exercise K4's scan rule 2. It takes four `%c`
and no `%s`; the call site passed `*d, CLS_BODIES[bi], *d, *d, *d`. So the
second `%c` consumed a `const char *` as an `int` — UB, and in practice the low
byte of a string-literal address. The source comment asserting this was safe
("every shape takes at most four %c and one %s; snprintf ignores the extras it
is not given") is true only when the specifiers appear in the argument list's
order, and shape 9 is the one shape where they do not.

The critic extracted the generator verbatim and printed what it produced: the
byte between `[` and `b` was `\x14`, `t`, `z`, `\x84` — never a delimiter. At
`-O0` it was sometimes NUL, truncating 21 of the 168 shape-9 probes to the
five-character stub `[[=a[`. **Which patterns the "1680-pattern differential"
probed depended on `.rodata` layout** — on optimisation level, on compiler, on
any future edit that moves a literal — while the header kept printing 1680.
`-Wall -Wextra` cannot see it (non-literal format string; it needs
`-Wformat-nonliteral`), so `make strict` was clean.

Measured consequence: of the whole 1680, exactly 42 patterns contained a
same-delimiter nested opener, all 42 from the body `x[:y`, all 42 at delimiter
`:`. **For `.` and `=` — the two collating rows, where rule 2 is precisely the
offset-only branch the commit message calls out — the sweep contained zero.**

FIX-2's commit message explains rule 2's near-invisibility by saying a verdict
differential cannot see an offset-only change. True, and not the whole reason:
the sweep was also not generating the construct.

*Fixed* by replacing the varargs call with a positional expander (`cls_expand`),
which has no argument list to fall out of step with and leaves no non-literal
format string. The sweep went to 98 / 56 / 56 nested openers for `:` / `.` / `=`
and still reported zero divergences — so this was an instrument defect, not a
compiler defect. (C2-F3 later added two more shapes for the same rule at doorway
4a, taking the sweep to 2016 patterns and 210 / 168 / 168; see the third wave.)

*And the guard added for it was wrong first.* A per-delimiter liveness floor was
added requiring a nested opener for every delimiter. Its first detector returned
true on ONE occurrence of `[`+delimiter, which counts `[x[=a=]]` — an ordinary
inner bracket, doorway 4b — so it read 511/504/504 and **stayed green when the
nested shape was sabotaged away.** A control measuring something adjacent to
what it names, written by the author of this review, inside the fix for a
finding about exactly that. Caught only by running the positive control before
believing the green. The corrected detector requires TWO occurrences (the pair
being scanned, plus the one that wins) and reproduces C1's measurement exactly
under sabotage: 42 / 0 / 0, two failures.

## C2 — the rule

**A negative result worth more than most findings.** The critic built a verdict
differential whose pattern space is written from first principles — nothing read
from pcrec's tables, tests, or libpcre2 — driving pcrec through the library API
so non-UTF-8 bytes never touch argv (this box's `timeout` exits 125 on those).

1,239,480 patterns: all strings of length 0..7 over four bracket alphabets, 0..5
over `[]\:.=^a`, negated forms, 0..8 over `\]:.`, an alphabet that can spell
`:alpha:`, three trailer shapes, classes not at offset 0 and inside groups,
every byte 0x01..0xff in the delimiter slot of 11 shapes, and a name sweep of 16
real and near-miss names across 12 injections, every position, 9 shapes.

    probed=1239480  agree=1239480  deferred=5966  over_accept=0  over_reject=0

**No verdict divergence.** On the axis FIX-2 claims, K4's three rules hold far
past the committed 1680. The critic proved the instrument sensitive before
believing it: deleting rule 3 gives 3075 over-accepts, rule 2 gives 3678
over-rejects, rule 1 gives 10795, the pre-FIX-2 scan gives 15164.

**C2-F1 — "the close check comes first" is provably arbitrary, and its stated
reason cannot occur.** CONFIRMED, fixed.

The comment claimed the close check must precede rule 1 "because a delimiter
immediately before `]` IS the closer, and rule 1 must not consume that `]` out
from under it". Rule 1 tests the byte at `i`; the close check tests
`pat[i] == c2 && pat[i+1] == ']'`. The predicates are disjoint whenever
`c2 != ']'`, and `c2` can only be `:`, `.` or `=`. The critic moved the close
block after rule 1 and got byte-identical totals across all 1,239,480 patterns,
including liveness — against a battery where every other sabotage produced
thousands of divergences.

Low severity as a bug; nothing is wrong today. It matters as the project's shape
in miniature: a branch ordering whose stated reason is untestable, in the one
function the commit is about, which the next person to add a fourth
`RK_CLASSBRACKET` row will read as a tested constraint.

*Fixed* the way the critic proposed: the comment now says the order is arbitrary
and why, and the property that makes it true — no class-bracket row may use `]`
as its delimiter — became an assertion in `registry_check.c`, where it belongs,
because it is a fact about the TABLE and not about the function.

## C3 — the name table

**C3-F1 — `close_at - from` underflows for a row that carries RF_CLASS_NAMED
without RF_CLASS_DELIM; unreachable today, unguarded for tomorrow, and
memory-safe only by accident.** CONFIRMED, fixed.

`close_at` was initialised to 0 and assigned only inside the `RF_CLASS_DELIM`
block; the RF_CLASS_NAMED check then computes `close_at - from` as a `size_t`.
Today the one RF_CLASS_NAMED row also carries RF_CLASS_DELIM, so it never fires.
Nothing enforces the pairing.

The critic added a `#` row with RF_CLASS_NAMED and no RF_CLASS_DELIM, built the
whole project under `-fsanitize=address,undefined -O0`, and ran eight patterns
through the doorway. **No sanitizer report** — and the explanation is the
finding: `pcrec_registry_posix_known` compares `strlen(entry) == len` before
`memcmp`, and no entry's length equals a value near `SIZE_MAX`, so `memcmp` is
never reached and the function returns "unknown". Verified directly against an
8-byte buffer at `SIZE_MAX-2` and `SIZE_MAX`: no crash, both return 0. The
subtraction is also well-defined C (unsigned wraparound), so UBSan is correctly
silent.

So the bug is real, currently manifests as a silent wrong answer rather than an
OOB read, and is held safe by an implementation detail of a *different*
function that nothing ties to this one. The natural "optimisation" of that
function — copy `len` bytes into a buffer, then compare — turns it into an
out-of-bounds read.

*Fixed* twice over, because the coupling was accidental: `close_at` now starts
at `from` (so an unmeasured extent asks about a zero-length name), and
`registry_check.c` requires every RF_CLASS_NAMED row to carry RF_CLASS_DELIM.
The pairing is the real invariant — a named construct whose extent is never
measured is meaningless, not merely unsafe.

**C3-F2 — the 16-name POSIX table is complete and correct.** CONFIRMED as a
negative result, no action.

Verified against libpcre2 10.46 by a generator written from first principles
that never reads pcrec's table, printing its own provenance at runtime
(`libpcre2 10.46 2025-08-27 loaded from /usr/lib/.../libpcre2-8.so.0`).
Exhaustive: all 253 single bytes, all 64,009 pairs, 73³, 73⁴, 73⁵ (2.07 billion,
279 s), and 26⁶ — roughly 2.4 billion compiles.

The critic found and fixed a correctness pitfall in its own probe before
trusting it: raw "did it compile" produced hundreds of false positives, because
`[[:X[:]]` and `[[:X]:]]` compile for any X. It established that "unknown POSIX
class name" is always error 130 and asserted that code on every non-accept, so
the accept signal is checked on all 2.4 billion runs rather than assumed.

Accepted names: `<`, `>`, `word`, `alnum`, `alpha`, `ascii`, `blank`, `cntrl`,
`digit`, `graph`, `lower`, `print`, `punct`, `space`, `upper`, `xdigit` —
exactly pcrec's 16, no more, no fewer. Cross-checked against libpcre2's own
compiled-in string table via `strings`, which holds the same 14 (with `<`/`>`
implemented separately as word-boundary cases, matching what FIX-2 says about
them). Stated limit rather than hidden: length 6 was swept lowercase-only and
7+ not at all, with the string-table cross-check carrying that confidence.

## C4 — the harness and the record

**C4-F1 — an empty expected-substring silently downgrades "rejected for the
right reason" to "rejected at all".** CONFIRMED, fixed.

`reject()`, `row_reject()` and `pinned()` check the diagnostic with
`case "$out" in *"$want"*`. `*""*` matches every string, so a blanked
expectation passes vacuously, printing `PASS: reject 'X' -> ` with nothing after
the arrow — which nothing greps for. Reproduced directly: `reject '\d' ''`
passes. FIX-2 added ~120 calls using this mechanism. The critic also confirmed
the adjacent non-finding: a genuinely *missing* argument is loud, because
`set -u` kills the script. It is the empty string that is quiet.

*Fixed:* all three helpers refuse an empty expectation. `pinned()` keeps `-` as
the explicit "verdict only" spelling, so the quiet case and the deliberate case
are now different spellings.

**C4-F2 — the MANIFEST's uniqueness assumption was false, and the "restore the
row, don't edit the count" guarantee with it.** CONFIRMED, fixed — and worse
than reported.

`must_have '[a[.b\].]'` calls itself "the ONLY row where K4's escape rule is
load-bearing". The row was written twice, verbatim. Because `seen` is a flat log
of patterns that passed any check, deleting one copy leaves the other, so the
manifest cannot distinguish "the check exists" from "a stale duplicate mentions
the string". The critic deleted the real row, bumped the exact count 201 → 200 —
the precise move the file's own failure message forbids — and the suite went
green.

*Fixed* by removing the duplicate and, more importantly, by adding a duplicate
detector: no pattern may be asserted twice. A pattern cannot legitimately appear
twice — it is either accepted or rejected — and a duplicate both gives the
manifest a spare and inflates the exact counts.

**The detector immediately found two more duplicates the critic's inventory had
missed**, `[:]` and `[:a]`, each added a second time by FIX-2. The critic's
inventory grepped lines beginning with `reject`/`accept` and reported
`[a[.b\].]` as the only duplicate in the file; it was one of three. Counts
corrected to 200 / 57 accordingly — a count edit that is legitimate exactly
because the removed rows were duplicates rather than coverage, and because the
detector now prevents a recurrence.

Consolidating those two also surfaced a stale comment: the surviving home for
`[:]`/`[:a]` still said `[::]` and `[:a:]` are "wrongly accepted (K3)". K3 is
what FIX-2 fixed, and both are pinned as rejections eleven lines below.

**C4-F3 — three of four counts in `tests/reject/CLAUDE.md` were stale, in the
commit whose headline claim they contradict.** CONFIRMED, fixed.

FIX-2's diff to that file changed "180 rows" → "201 rows" and left the rest of
the same sentence: "66 more reached by iterating" (67), "45 accept-controls"
(59), "and 5 known-wrong pins" — when the commit's whole point is that there are
now zero. A reader trusting the doc believes five known-wrong defects remain.
`tests/CLAUDE.md` carried the same sentence with the even older first figure,
180.

*Fixed* in both homes, with the correction that matters more than the numbers:
the harness prints all four in its own summary block, so they are to be read
from a run. MECH-1 (generate the figures rather than copy them) is the standing
answer and this is its fourth instance.

**C4's positive controls, all held:** message-text sabotage caught (4 failures +
MANIFEST), offset-only sabotage caught (rule 2 disabled → 3 failures +
MANIFEST), every headline count reproduced from a clean build, K3/K4 repros
confirmed no longer reproducing, K2 confirmed still open,
`docs/pcre2_compliance.md`'s new REJECTED line confirmed backed by real tests.

## The second wave, after the first three findings were already fixed

The panel did not stop when its first findings landed. C1 and C3 kept working
and produced five more, one of which is a **live bug in shipped code** rather
than in an instrument. This is the third consecutive panel whose best material
arrived after the point a less patient checkpoint would have closed.

**C3-F4 — `[[:<:]]` and `[[:>:]]` are position-restricted and pcrec did not
model it. CONFIRMED DEFECT, fixed.**

libpcre2 accepts `<` and `>` ONLY as a class's entire content. Measured across
13 patterns: `[[:<:]]` compiles; `[x[:<:]]`, `[a[:<:]]`, `[[:<:]a]`, `[^[:<:]]`
(a bare `^` is enough), `[a-z[:<:]]`, `[[:alpha:][:<:]]` are all error 130. Any
ordinary name works in every position — `[x[:alpha:]]` compiles.

pcrec answered "requires module 'classes'" for all of them. **That is the exact
over-promise FIX-2 set out to remove, surviving for the two names FIX-2 itself
discovered** — the fix was real for a bogus name and not for a real name in a
position PCRE2 refuses.

Why both differentials missed it is the finding within the finding.
`check_posix_names` varies the NAME across ~12,000 candidates and builds every
one as `[[:NAME:]]` — position fixed. `check_class_brackets` varies POSITION
across shapes and trailers, and its bodies never include `<` or `>` — name
fixed. Each sweep is large and correct on its own axis, and **the defect lived
in the cell of the cross-product neither generates.**

*Fixed:* `pcrec_registry_posix_whole_class_only()`, and the doorway now takes
`at_content_start` (false after any member, false when `^` negated the class)
and requires the class's `]` immediately after the construct. A new
`check_posix_positions` differential crosses the two axes — every name pcrec
claims, five positions, against libpcre2 — and asserts that exactly two names
are position-restricted. Reverting the rule fails 8 probes.

One case is deliberately left as it is: `[[:alpha:][:<:]]` still answers
"requires module 'classes'", because pcrec stops at the FIRST unimplemented
construct and `[:alpha:]` genuinely is one. The promise is honest — module
`classes` is what is needed to get far enough to reject the second construct —
and it matches D26's offset convention of blaming the construct actually
recognised.

**C1-F2 — `check_posix_names` had no provenance requirement, and its liveness
was satisfied by six non-class byte probes. CONFIRMED, fixed.**

R8/C1-F4 one doorway across. The check counts patterns libpcre2 ACCEPTED and
calls that "real names", but `[[:]:]]` compiles because the `]` ends the class
before any name begins. A critic filtered PCRE2's class names out of the pool
and deleted `graph` from pcrec's table: the function printed "6 real names" and
three PASS lines, all six of them non-class byte probes, with a deleted name
under test, and the reject suite did not see it either — 12 of the 16 names have
no hand-written row. The 51-failure empty-pool sabotage that DOES catch this
lives in `check_verb_names` and is about a different name space, so this check's
correctness was **parasitic on an assertion elsewhere.**

*Fixed:* every name pcrec claims must appear in the pool from a source that is
not a mutation of pcrec's own table, the accepted-name count is split by
provenance and printed, and the external contribution has a floor. The critic's
sabotage now yields 10 failures.

**C1-F3 — the delimiter space was hand-listed in the one instrument with an
external oracle. CONFIRMED, fixed.**

`CLS_DELIMS = ":.="`, taken from pcrec's own three rows, in the file whose
header says "GENERATE the space, do not list it". The 255-byte sweeps in
`registry_check.c` do generate the space but compare the parser against pcrec's
registry — a control sharing a source with what it controls — and every byte
without a `RD_FIXED` row falls through both `if` chains with no assertion
evaluated, while the line prints "all 255 bytes agree". A critic added
`if (c2 == '!') ctx_fail(...)` — a genuine tier-2 over-rejection, since libpcre2
compiles `[!alpha!]` — and **every suite in the repository stayed green.**

*Fixed:* a delimiter byte sweep against libpcre2, 255 bytes x 5 shapes. Its
liveness assertion is the interesting part: rather than reading the table to ask
"do exactly three bytes route to a module" (circular, and wrong — `[[.a.]]` is a
fixed-text rejection, not a module), it asks a question only the parser can
answer. Every byte gets a verdict vector; bytes with no construct behind them
share one; the set that departs from it IS the live delimiter set, derived from
behaviour. Expected `:` `.` `=` and `\`, the last being the class escape and
different for reasons that have nothing to do with this doorway — kept in the
sweep rather than special-cased out, because a sweep that excludes its
inconvenient bytes is how a 255-byte check becomes a 1-byte check. The `!`
sabotage now fails 6.

**C1-F4 — the graduated `accept` rows assert that something was emitted, never
WHAT. CONFIRMED, fixed.**

The most consequential of the second wave. K3's over-acceptance half was a
SEMANTIC bug — "a matcher for the character set {: a l p h}". Its over-rejection
half was fixed by making fourteen patterns compile, pinned as `accept` rows that
check exit 0 and a non-empty output file. Nothing compiled the emitted matcher
and ran it; the `.rxt` corpus contained none of these patterns; and
`check_class_brackets` compares verdicts with no subject at all.

The critic changed one line in parse.c's class member loop so that `[a[:b]`
SWALLOWS the `:` — dropping it from the member set — and measured behaviourally:
`:` no longer matches, everything else unchanged. **Every suite in the
repository passed, and the differential fuzzer reported zero divergences.** All
the verdicts were still right; the set was wrong.

*Fixed:* `tests/base/class_brackets.rxt`, 136 oracle-verified cases over all
fourteen patterns, generated by enumerating subjects to length 6 and taking
python `re`'s answer. pcrec agrees on all 136. The sabotage now fails 4.

**C1-F6 — a liveness assertion that existed only in the comment.** CONFIRMED,
fixed. `check_class_brackets`'s comment says "both buckets must be non-empty:
some pattern PCRE2 refuses, and some it accepts and pcrec defers", and only the
second was evaluated — `agree` merges both directions. Healthy today (746 of
1680), latent rather than live. One counter and one assertion.

**C1-F7 — the registry directory had no guard against its own checks being
deleted. CONFIRMED, fixed.**

`tests/reject/` has carried both a coverage count and a manifest since R7.
`tests/registry/` — the directory now holding the expensive external checks —
had neither. The critic deleted both new differentials from `main()` and the 4a
sweep: green, `make test` green, the only trace being 129 → 128 and 81 → 76 in
output nothing compared. *Fixed* with the same two layers, for the same stated
reason: a count makes a deletion visible in the diff, a manifest makes it fail.
The manifest names eight checks by the finding each one closes.

**C1-F5** (no well-formedness check for `RF_CLASS_NAMED`; `posix_names()`
shipped "for tests" with zero callers) was closed by the C3-F1 pairing assertion
and by the new provenance and position checks, which are its first callers.

## The third wave — and two of these were still green after the second

**C2-F3 — turning rule 2 off at doorway 4a for `.` and `=` only gives 1,416
over-rejections and the entire repository stays green.** CONFIRMED, fixed.

The five-byte reduction is **`[.[.]`**, which libpcre2 compiles as a class of
`.` and `[`. The mutation is one clause. It passed `make test`, `make strict`,
the reject table, the 1680-pattern differential printing numbers IDENTICAL to
the pristine build — **and it still passed after C1-F1's nested-opener floor
had been added**, because every nested opener the sweep generated was a 4b one.
The shape written for rule 2 covers `[[.a[.b.].]]`; nothing covered `[.[.]`.
*Fixed* with two more shapes at the class's own bracket. The sabotage now fails
12, the first being C2's exact reduction.

That is the C1-F1 lesson recurring inside its own remedy for the second time:
the floor asked "is a nested opener generated for every delimiter" and the
honest question was "for every delimiter AND every position".

**C1-F8 — the differential could not see a module over-promise at all.**
CONFIRMED, fixed. `check_class_brackets` classified `pc2 != 0 && rejected` as
agreement without ever reading `cmsg` — 746 of the patterns, the entire
libpcre2-refuses half. But that is exactly where the property FIX-2 exists to
establish lives: promising module `classes` for `[:alpha:]` is wrong *because*
libpcre2 rejects it. `check_posix_names` tests it only for the 4b form, so the
class's own bracket had no external check of its own over-promise — the doorway
4a half of R8/C4-7. Reverting the `open_msg` branch took the count from 4 to 11
with the verdict unchanged.

*Fixed*, and the interesting part is separating a real over-promise from an
honest one. Four baseline cases name a module for a pattern libpcre2 refuses:
`[[:alpha:]`, `[[:alpha:]x`, `[[:alpha:]$` — all unterminated classes, where
pcrec reports the leftmost construct it cannot handle and libpcre2 is objecting
to the missing `]`. Rather than a hand-listed exemption, the check appends a `]`
and asks libpcre2 again: if it compiles then, the objection was termination and
the construct pcrec named is real. `[:alpha:]]` does not compile, so the 4a
over-promise is still caught. Baseline 0 wrong, 4 unterminated; the sabotage
fails 3.

**C4V-F3 — I made the counts stale again, inside the paragraph warning about
stale counts.** CONFIRMED, fixed. The C4-F3 fix wrote 201/67/59 into two
CLAUDE.md files; removing three duplicate rows in the same review made the real
numbers 200/67/57, and the warning paragraph carried the wrong ones. Two
authors, two commits, the same failure, the second time inside the warning
itself. This is the fourth argument for MECH-1 and the most direct one: the
figures cannot be maintained by hand, and this review proves it twice over
rather than asserting it.

**C4V-F4 — the blank guard was not enough either, and a length floor cannot
fix it.** CONFIRMED, fixed.

Given the blank-only guard, the critic asked what else defeats it and measured
rather than guessed: it ran the whole 200-row suite against the real binary,
collected every diagnostic, and tested candidate expectations against that
corpus. `:`, `pcrec`, `pattern offset`, `(`, `)` and the single letters
a e s n r t o each match **200/200**. None is blank.

The cause is structural: every diagnostic has the identical envelope
`pcrec: <message> (pattern offset N)`, so anything inside the constant part
matches everything. And no length floor separates the cases — `:` is one
character, `(pattern offset 4)` is eighteen, and 31 rows legitimately pin an
offset with exactly that suffix.

*Fixed* with the rule the measurement points at: reject a `want` that is a
substring of the ENVELOPE. `(pattern offset 4)` is not one — the digit is real
content — so the offset-pinning rows are untouched, and all 8 measured literals
are refused with zero false positives across the 200 real rows. The critic also
noted the alternative it verified (strip the envelope before comparing, leaving
94 well-discriminated messages); the substring rule was chosen because it does
not disturb the rows that deliberately assert an offset.

**And extending a check disarmed it — mine again.** Adding the 4a shapes for
C2-F3 meant the per-delimiter nested-opener floor could no longer detect the
loss of the *4b* shape: with 4a openers present the counts read 154/112/112 and
the floor passed the very sabotage it was written for. The guard that caught
C1-F1 stopped being able to catch C1-F1, as a side effect of fixing C2-F3.
Caught by re-running the earlier positive control after the later change rather
than assuming it still held. The floor now counts six buckets — every delimiter
in BOTH positions — and each shape's removal fires independently.

## The fix to C3-F4, attacked in turn

The critic who found C3-F4 was given the fix to break, and produced both a
confirmation and a finding.

**The rule generalises.** 68 patterns across every axis — nested classes,
ranges, escapes, `\]`, end-of-pattern, quantifiers, groups, alternation, two
restricted names in one pattern, truncated forms, extra trailing `]`, `[^]`/`[]`
forms. 66/68 agree with libpcre2; the two that do not are exactly the
`[[:alpha:][:<:]]` case left deliberately. Under ASan+UBSan with
`-fno-sanitize-recover=all`, 18 truncated patterns plus the full differential:
zero reports. `[[:<:]` hits `close_at + 2 == patlen` exactly and the bound
correctly refuses the read.

**And the liveness assertion I added with it did not check what its name said.**
`restricted != 2` is computed entirely from libpcre2's verdict and never reads
pcrec's answer, so it **stays PASS under a full revert of the position rule** —
demonstrated in a run that failed 8 other checks. It is a real check of the
probe pool's non-degeneracy; it is not a check of pcrec, and its comment implied
it was. `wrong == 0` is what actually caught the regression.

*Fixed* by making the claim the name suggests: a second counter asks how many
names PCREC itself answers differently by position — deferring in one place,
refusing outright in another — and requires it to equal libpcre2's count. The
full revert now fails that counter 0-against-2 directly, while the pool-liveness
line stays green and says plainly that it is about libpcre2.

The critic also tried three narrower sabotages of the rule (dropping `!neg`, an
off-by-one on the `+2`, swapping the `[` check for the `]` check) and each was
independently caught by one of the five shipped shapes.

**Axis 5, the case left deliberately.** `[[:alpha:][:<:]]` still answers
"requires module 'classes'". Both readings were argued: leftmost-construct-and-
stop is precedented project-wide and pinned on purpose (`\d{3,1}`, `(*FAIL)*`),
and asking this one fix to look past its own first failure would be a one-off
exception to a single-pass architecture. Against that, pcrec has already
computed that `[:<:]` there is unconditionally hopeless and discards it. Recorded
as a named scope limit rather than closed.

## What the panel attacked and could not break

Recorded because a negative result with evidence stops the ground being
re-covered, and three of these are large:

- **K4's three scan rules**: 1,239,480 generated patterns, zero verdict
  divergences (C2).
- **The 16-name POSIX table**: ~2.4 billion probes, independently generated,
  exactly right — no 17th name, none missing (C3-F2).
- **`^` negation**: all 32 name x negation combinations plus 5 edge cases,
  pcrec agrees with libpcre2 throughout (C3-F3).
- **The position-before-name ordering claim**: holds for 16 real names and 5
  bogus candidates (C3-F5).
- **K3's behavioural fix**: `[:alpha:]` correctly rejected, and the three
  previously over-rejected patterns compile AND their emitted matchers agree
  with libpcre2 byte-for-byte over all 255 single-byte subjects (C3-F6).
- **The 201/59 → 200/57 count change**: independently confirmed honest, with no
  coverage removed beyond the three duplicates (C4V).
- **Glob injection into the reject harness**: does not exist. A quoted `"$want"`
  in a `case` pattern is literal, so `*`, `?` and `[a-z]` are safe — a
  hypothesis of mine that a critic refuted with measurements (C4V-F2).

## And the panel found two defects in the remedies

Given a second pass over the fixes themselves, C4 broke two of them:

- **C4V-F1**: the duplicate detector false-positives on a legitimate row whose
  pattern contains a newline, because `seen` is newline-joined and `reject()`
  had no display label — the hazard `accept()` was given a parameter for when it
  was written. Fails safe (spurious red), but a maintainer who hits it has every
  incentive to work around the detector, which reopens C4-F2. *Fixed:* a label
  parameter, and a refusal to log a newline at all, because an optional guard
  that must be remembered is the same shape as the bug.
- **C4V-F2**: `[ -z "$want" ]` is defeated by a single space, since every
  diagnostic pcrec prints is an English sentence. *Fixed* to reject all-blank.
  The honest limit is recorded in the code: no floor distinguishes a lazy
  expectation like `:` from a legitimately short one, so the guard stops at
  "asserts literally nothing".

## Reflection

**The fix was right; the instrument was not.** Both critics who attacked the
rule confirmed it, at 1.24 million patterns and 2.4 billion name probes
respectively. Both critics who attacked the checks found defects. That split is
worth noticing on a change whose commit message is largely about how carefully
its instrument was built — three of the four findings are in the checks FIX-2
added, and the fourth is in the docs describing them.

**A shape that names a construct is not a pattern that contains it.** C1-F1 is
the sharpest instance this project has produced. The differential had a shape
whose comment said "a NESTED opener, which wins", the sweep printed 1680
patterns, and the construct appeared zero times for two of three delimiters. The
check named the thing; nothing measured that it was generated. That is the
"GENERATE the input space, never list it" lesson at the next level down — the
space *was* generated, and the generator was broken in a way only a per-construct
count could see.

**I reproduced the panel's own finding while fixing it.** The liveness floor
added for C1-F1 counted `[x[=a=]]` as a nested opener and passed the sabotage.
It was a control measuring something adjacent to what it named, written into the
fix for a finding about exactly that, and the only reason it did not ship is
that the positive control was run before the green was believed. This is now the
fourth consecutive panel where a control shared a source or a definition with
what it controls, and the first where the author did it inside the remedy.

**Two findings were held safe only by an implementation detail of a different
function.** C3-F1's underflow is invisible because `posix_known` length-checks
before it byte-compares; C2-F1's ordering is safe because no delimiter is `]`.
Neither fact was written down anywhere, and neither is the responsibility of the
code that depends on it. Both are now assertions in `registry_check.c`. The
generalisable form: **when a dangerous operation is safe because of something
true elsewhere, the assertion belongs where the fact lives, not where the
danger is.**

**A critic's inventory can narrow the same way a check does.** C4 reported one
duplicated row after a full-file inventory; there were three. The inventory
grepped a line prefix. The detector that replaced it reads the harness's own
runtime log of what was asserted — the difference between reading the source and
measuring the run, which is the same distinction three of these findings turn
on.

**Two large sweeps can each be honest and still leave a hole between them.**
C3-F4 is the finding this review would be poorer without, and it is not a
careless sweep — it is two careful ones. One varies the name across 12,000
candidates at a fixed position; the other varies position across 1,680 patterns
with a fixed set of bodies. Both are real. The bug lived in the cell of the
cross-product neither generates, and no amount of making either sweep *bigger*
would have found it. The question that finds this class is not "is my sweep
large" but **"what are my axes, and does anything vary two of them together?"**

**Semantics are a field too.** C1-F4 is the third instance of the project's
"which suite reads this FIELD of the output" lesson, and the field this time was
the emitted character set. Every verdict was right, every suite was green, the
fuzzer found nothing, and `[a[:b]` silently stopped matching `:`. FIX-2's stated
achievement was removing a class of silent wrong matcher; the instrument it
shipped proved the verdict changed and never asked what was emitted. The
patterns whose member sets are unusual are exactly the ones a fix at that
doorway is likeliest to break, and they were the least covered patterns in the
repository.

**Ask the question only the other side can answer.** Two of the guards written
here started as "does the table say three" and became "how many bytes behave
differently from an ordinary member". The first reads the file under test; the
second reads the parser's behaviour. They pass identically today and only the
second can see a construct the table does not know about — which is the entire
category `registry_check.c` has warned about since R4 and could not close.

**And the process step this panel exists to be was nearly skipped twice.** FIX-2
shipped without it because a session reset; this session began by re-deriving
whether it was owed. It was, and it found UB in a differential, a latent
underflow, a hollow manifest, and four stale figures in a change that was green,
committed, and described as carefully instrumented.
